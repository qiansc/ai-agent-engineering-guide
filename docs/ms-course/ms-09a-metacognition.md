# Agent 如何检查自己的方法：反思、反馈与计划调整

旅行助手第一次推荐了最便宜的酒店。用户说“太吵、评分也低”，助手下次若只是换一家更贵的酒店，可能仍没抓住问题；它应该检查自己用的选择规则是否只看价格，随后把安静程度和质量纳入候选筛选。这就是“元认知”可以落地的部分：系统记录决策依据，发现结果不符合目标时调整策略，再验证改动是否有效。

## 不把“自我意识”当成工程功能

借用心理学的“关于思考的思考”，用“自我意识”“反思自己的推理”解释 Agent 行为。工程上可把它落实为四个可观察步骤：保留先前选择与理由；从工具结果或用户反馈里得到错误信号；诊断是数据错、目标变了还是策略错；改变下一轮的检索、排序或行动规则。模型说“我反思了”不等于策略真的变了，更不代表它训练了新参数。

这样做可能改善透明度、推理适应性、错误修正和资源使用。检验时分别看：运行记录能否解释为何选择；相似错误是否减少；调整是否保持硬约束；额外反思轮数是否值得成本。若反思只是多花一次模型调用而结果没变，应删掉这一步或换成明确的规则检查。

一个 Agent 的角色描述、可用工具和技能知识共同决定它能做什么。以旅行服务说明：先收集日期、预算、兴趣与特殊需求，再查航班、酒店、景点和餐馆；生成行程后征求反馈，调整建议。用户说“不喜欢拥挤景点”时，系统可以把它作为本次行程的排除条件，重新查相近活动。是否将偏好长期保存，要另经用户同意和数据管理设计。

## 在计划里保留观察与决策

旅游任务可以分成九步：收集偏好、检索信息、生成推荐、展示行程、收集反馈、调整、最终确认、预订、持续支持。每一步都可以问“下一步凭什么做”：推荐使用哪些事实；反馈改变了哪个约束；最终确认覆盖哪些具体项目；预订是否取得真实订单号。若用户改变日期，就从受影响的检索与价格开始重做，不必重问所有兴趣；若已经正式预订，则要走改签或取消流程，不能简单覆盖计划。

| 信号 | 可能的问题 | 下一步 |
| --- | --- | --- |
| 用户说“太拥挤” | 排序只按知名度，忽略拥挤度 | 把拥挤度加为过滤或排序条件，重新查候选 |
| 推荐酒店已满房 | 可用性数据过时 | 重新查实时库存，更新候选并标记旧结果失效 |
| 连续三次查询无结果 | 查询过窄或数据源不合适 | 放宽非硬约束、换数据源或询问用户，不无限重试 |
| 行程总价超预算 | 子任务单独满足条件，汇总时超限 | 重新权衡候选，但保留用户硬约束 |

示意代码里的 `Travel_Agent` 维护 `user_preferences` 与 `experience_data`，调用 `search_flights`、`search_hotels`、`search_attractions`，再用 `adjust_preferences` 根据喜欢/不喜欢更新偏好。这些函数没有具体实现，适合帮助理解状态变化，不能视为完整旅行预订系统。真正做实验时至少要记录偏好更新前后、候选集、评分和最终选择，否则无法判断“反思”是否有效。

## 酒店选择：把反思写成能测试的策略

用三家酒店做演示：Budget Inn 价格 80、质量 6；Comfort Suites 价格 120、质量 8；Luxury Stay 价格 200、质量 9。第一次按最低价格选 Budget Inn。规则认为价格小于 100 或质量小于 7 是差结果，于是切换到“最高质量”，第二次选 Luxury Stay。这个过程展示了策略切换，但若用户预算上限是 150，盲目改成“最高质量”会违反硬约束。更好的版本先过滤不可接受的候选，再在预算内按质量与价格权衡：

```python
hotels = [
    {"name": "Budget Inn", "price": 80, "quality": 6},
    {"name": "Comfort Suites", "price": 120, "quality": 8},
    {"name": "Luxury Stay", "price": 200, "quality": 9},
]

def recommend(hotels, max_price: int, min_quality: int):
    eligible = [h for h in hotels
                if h["price"] <= max_price and h["quality"] >= min_quality]
    if not eligible:
        return None
    return max(eligible, key=lambda h: (h["quality"], -h["price"]))

assert recommend(hotels, max_price=150, min_quality=7)["name"] == "Comfort Suites"
```

这里的阈值是教学例子，不代表真实酒店评分体系。真正的用户反馈可能是“房间靠近地铁但晚上吵”，这应更新安静程度要求，而不只是质量分。反思要指向导致错误的决策条件，且与原目标一起验证；单纯从“最便宜”跳到“最贵”只是另一种偏差。

## 资源管理与停止条件

每次自查、重新查询和改计划都要花时间与模型调用。给任务设置预算：最多重查几次、最多读多少文档、何时因证据不足请用户选择。不同失败需要不同动作：工具暂时超时可有限退避；用户偏好冲突要提问；预订状态不明要查询外部订单，不能重复下单。资源管理也是元认知目标，具体实现就是让 Agent 能知道自己已尝试什么、剩余预算多少，以及继续尝试的收益是否值得。

## 练习：做一次真正改变方法的复盘

先用“只按价格”选酒店，记录所选酒店及规则。给系统“太吵、预算 150 以内、质量至少 7”的反馈，要求它说明哪条旧规则错了，生成新的候选筛选条件，再运行同一批酒店。加入一家价格 110、质量 8 但标记“临街吵闹”的酒店，检查系统是否仍会选错。最后输出变化记录：旧策略、新策略、淘汰原因、最终结果。若系统只在最终回答里说“已吸取教训”，而下一次仍按旧规则推荐，测试应判失败。

## 面试会怎么问

小红书 Agent 面经问 Planner/Executor/Critic，美团 Agent 面经问长流程保障与异常测试。被问“怎么让 Agent 自我纠错”时，别只答“加一个反思 Agent”。用具体坏例说明：观察到什么错误、用什么外部信号判定、调整了哪条策略、怎样不违反预算/权限硬约束、如何测改动后是否更好。若没有可靠外部反馈，自评只能是候选意见，不能当作最终验证。
