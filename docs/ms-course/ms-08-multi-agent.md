# 多 Agent 协作：什么时候分工，交接时交什么

一个旅行助手能同时查机票、酒店和租车，并不自动需要三个 Agent。单个 Agent 配三个工具，往往更容易测试。只有当工作可以独立调查、角色需要不同工具或权限，或任务规模让单个上下文难以承担时，分工才有价值。多 Agent 设计的难点不是创建几个模型实例，而是让它们共享必要事实、保持约束一致，并能在部分失败时继续或停下。

## 先判断分工是否值得

适合分工的场景有三类：大工作负载可拆成并行部分；复杂任务有不同阶段与职责；专业知识或工具权限明显不同。例如大量资料的研究任务可以让多个角色独立搜不同来源，再由一个角色综合；涉及退款的工作流可让欺诈、支付、合规角色分别处理。这些是候选条件，不是“代理越多越快”的保证。并行会增加模型调用、状态传递和结果合并成本；一个角色失败时，其他角色也未必能安全替代。

比较单 Agent 与多 Agent，可看四件事：任务是否真的能拆成边界清楚的输入输出；分工是否减少上下文冲突；权限是否应隔离；评测是否显示收益大于协调成本。判断时还要注意：一个支持机器人只查单一知识库、用少量工具时通常保留单 Agent；每小时大量相同分类请求是吞吐扩容问题，不必为此引入多 Agent；退款流程中独立的欺诈、支付和合规角色才可能需要分工。

## 协作系统的六个构件

以旅行预订为例，逐项检查：

1. **通信**：航班角色把抵达时间交给酒店角色时，必须说明时区、日期和价格有效期；只转发一段自然语言摘要可能丢约束。
2. **协调**：酒店位置、租车取车点与机场之间有依赖；协调者要决定哪些查询并行、哪些动作等待。
3. **角色架构**：每个角色有自己的指令、工具和决策范围。航班 Agent 无权修改客户资料，酒店 Agent 不应替支付服务扣款。
4. **可视性**：记录角色之间的消息、任务状态、工具调用、耗时和结果。最终答案正确，也可能掩盖中途越权或重复预订。
5. **模式选择**：集中式由一个协调者分配，分散式角色直接通信，混合式兼有；选择取决于可审计性和交接复杂度。
6. **人类参与**：用户未认可行程、航班变动或价格超预算时，让人确认或接管。

一个实用的交接对象可包含 `task_id`、目标、必要约束、已核实事实、来源、当前状态、截止时间、允许工具和下一位负责角色。交接是状态变更，不只是把一句“你接着做”发给另一个模型。角色之间若有共享记忆，还要控制能读到哪些用户数据。

## 三种常见交互模式

**群聊**适合多个角色围绕同一问题交换候选和反驳，例如研究、方案评审。可以由中央服务器转发，也可以点对点通信。要设置主持或停止规则，否则角色容易互相重复、轮次失控。观察时记录谁提出了哪条事实、谁否定它、最终采用哪个来源。

**工作交接（handoff）**适合阶段性任务。售前 Agent 收集需求后交给预订 Agent；支付失败时交给人工支持。交接对象应包含已完成动作和不能重复执行的状态。不同角色的权限在交接点重新检查，不能因为上一个角色批准了某事，下一个就拥有永久通行证。

**协作推荐**让不同视角评价候选，例如让行业、技术面和基本面角色评估股票。各角色可以提出不同证据与风险，最终汇总者需要解释如何权衡；“三个 Agent 都同意”不等于结论可靠。对金融等高风险领域，系统不应把角色投票当成专业审批。

| 模式 | 信息流 | 适合的问题 | 主要风险 |
| --- | --- | --- | --- |
| 群聊 | 多角色围绕共享讨论 | 方案研究与审查 | 轮次膨胀、责任不明 |
| Handoff | 当前负责人移交下一角色 | 明确阶段与权限边界 | 状态丢失、重复动作 |
| 协作推荐 | 多视角独立评估后综合 | 候选方案比较 | 表面一致掩盖共同偏差 |

## 把旅行案例做成可观察的系统

仪表盘可以显示每个角色状态、用户偏好与约束、航班/酒店/租车推荐、交互记录。除了最终耗时和吞吐量，还可以记录子任务成功率、交接失败率、重复调用、预算超限和人工接管率。例如酒店角色建议的入住日期早于航班抵达，仪表盘应能追溯是航班结果没传到、传错时区，还是酒店角色忽略了约束。

容错不是“一个 Agent 坏了，其他 Agent 继续”。若负责航班的角色超时，酒店搜索可以继续收集候选，但正式预订应停在等待航班确认的状态。每个子任务的输入、结果、错误与外部副作用都要独立记录，协调者据此决定重试、改派、补偿或请求用户。

## 退款流程与客户支持练习

退款例子列出客户、卖家、支付、问题解决、合规等专门角色，也列出运输、反馈、升级、通知、分析、审计、报告、知识、安全、质量等跨业务候选。这个长名单用于练习“职责识别”，不代表每个职责都需要独立 LLM Agent。支付最好由确定性支付服务执行；审计可由日志与规则系统完成；模型角色只在需要处理模糊输入、解释政策或研究异常时介入。

尝试设计一个客户支持流程：客户提出退款问题，接待角色分类并查订单，政策角色提供对应条款，支付服务只在用户确认且条件满足后退款，升级角色处理例外，通知服务发送状态。写清每个角色的输入输出与权限，再问能否合并。职责清单还可列出反馈、分析、审计、报告、知识、安全、质量、合规、培训等角色；把它们当作职责清单，按实际流量、风险和团队能力选择实现形式。

做两个自测：其一，单知识库 FAQ、复杂退款、海量简单分类三者中，复杂退款更可能需要独立角色与协调；其二，若一套指令和工具就能完成任务，应优先选单 Agent。能使用多个工具本身不是拆 Agent 的理由。

## 面试会怎么问

小红书 Agent 面经问多 Agent 并发，美团 8 月面经问状态汇总与路由，百度实习面经问多 Agent。回答“为什么拆”时，给出原单 Agent 的具体瓶颈，以及拆分后每个角色的独立输入输出、权限和可并行性；回答“怎么协调”时，画任务状态、交接对象、失败停止点与 trace。不要只列 Planner/Executor/Critic 三个名称，也不要把并发等同于吞吐提升。
