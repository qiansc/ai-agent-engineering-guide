# 上下文工程：让 Agent 下一步只看到真正需要的信息

Agent 处理的任务越长，能看的东西越多：系统指令、用户对话、工具说明、检索片段、运行笔记和过去偏好都会进入模型输入。上下文窗口有上限，更重要的是无关、过时或相互冲突的内容会让模型做错决定。上下文工程就是围绕“下一步行动需要什么事实”持续选择、验证、压缩和隔离信息。

## 从提示词扩展到动态信息管理

提示工程主要写清角色、目标、行为规则和少量示例。上下文工程把这些指令也算作一部分，但还要管理不断变化的数据。上下文包含五类：指令；从数据库、RAG 或长期记忆取得的知识；工具定义和工具结果；持续增长的对话历史；用户偏好。每类都有来源和生命周期：系统指令较稳定，库存随时变化，工具结果只在某次任务中有效，用户偏好可能被修改。

例如“帮我订巴黎行程”，应用可以在已授权的前提下查日历空闲日期、读取用户明确保存的航空公司偏好、选择航班与酒店工具，再问是否按这些条件搜索。若未经授权就读取日历，或把去年的预算当作本次硬限制，所谓“上下文感知”会变成侵犯或误导。上下文要有**获取条件、使用范围、更新时间和优先级**。

## 先画信息地图，再搭流水线

先定义完成结果：“订巴黎行程”到底是给出候选还是已付款的订单？接着列出每一步需要的事实及其位置：日期在用户请求或日历，航班可用性在实时接口，退改规则在政策库，批准在当前操作记录。最后决定如何取得它们：预先放入少量常驻指令、按需 RAG、通过 MCP/普通工具读取，或向用户询问。

一张简单的上下文清单可以在设计时写成：

| 当前步骤 | 必需信息 | 来源 | 不应带入 |
| --- | --- | --- | --- |
| 查航班 | 日期、人数、出发/目的地、预算范围 | 当前请求、经授权日历 | 两年前无关旅游聊天 |
| 比较候选 | 价格、货币、时区、可退条件、获取时间 | 航班工具、政策资料 | 未核实的模型猜测 |
| 提交订单 | 具体航班、乘客、总价、用户批准、库存版本 | 已校验状态与实时接口 | 对另一条航班的旧批准 |

这张表比“把所有历史丢给模型”更能指导实现。每次模型调用都可以用它核对：缺了什么、混入了什么、哪些值已过期。

## 六种具体策略

**便签（scratchpad）**保存本次任务的中间结果，例如已比较的航班 ID 和未解决的问题；它可以留在窗口外的文件或运行状态里，需要时只加载摘要。**长期记忆**跨会话保存用户同意存储的偏好或反馈，不能和临时便签混用。**压缩**在历史过长时保留目标、约束、已完成动作、未完成问题和来源，删除重复聊天；压缩后应能回到原始记录核对关键事实。

**多 Agent 隔离**让不同子任务各有较小上下文，交接只传必要结果；不要把一个用户的敏感内容无差别复制给每个角色。**沙箱**把大文件或代码计算留在受限执行环境，只把必要结果带回模型。**运行时状态对象**把子任务结果、工具状态、计划版本结构化保存，避免模型靠长对话记住所有字段。这六种办法可组合：主 Agent 持有目标与状态摘要，检索 Agent 在隔离上下文里读大量文档，返回有来源的少量片段。

生产排查时也不必记录原始敏感上下文。日志可以保留候选与选中块数、文档/记忆 ID、摘要 ID、压缩前后 token 估计、隔离边界与策略标签。这样能回答“模型为什么没看到关键材料”，同时减少把私人文本复制进日志的风险。工具选择日志还应区分“可发现”“有权使用”“实际提供给模型”三个集合。

## 四种失败，四条修复路径

| 失败类型 | 旅行案例 | 先检查 | 可采取的修复 |
| --- | --- | --- | --- |
| 中毒 | 模型编造不存在的直飞航班，随后反复引用 | 该航班来自模型还是航班 API？ | 进入上下文前核验，隔离错误内容，必要时新建上下文 |
| 分心 | 久远背包旅行聊天让当前查廉价机票跑偏 | 当前输入是否塞入过多无关历史？ | 摘要本次目标与硬约束，卸载旧内容 |
| 混淆 | 工具太多，询问巴黎市内交通却调用订机票 | 工具描述是否重叠，候选集是否过大？ | 按任务与权限选择小工具集，改清描述 |
| 冲突 | 先说经济舱，后改商务舱 | 哪条偏好更新、更具体？ | 标注后者覆盖前者，保留变更记录但只给当前值 |

动态检索工具描述是一种做法，并给出“少于 30 个工具”作为经验提示。不要把数字当通用阈值；模型、工具描述与任务不同，实际应测工具选择准确率和误调用。筛选工具时也不能仅按语义相似度：模型再想用付款工具，没有用户授权仍不应出现在可调用集合。

压缩和修剪也可能丢信息。比如把“预算约 5000，但宁可多花钱换直飞”压成“预算 5000”，会改变选择；把“用户先选经济舱，后改商务舱”压成两条并列偏好，又制造冲突。给摘要设计事实保护项：目标、时间、货币单位、硬约束、用户最新决定、已产生副作用、来源与不确定性。压缩后用具体任务回放检查是否仍做出相同合理决策。

## 练习：调试下一次模型调用

构造十轮旅行对话，其中混入一次旧预算、一条模型编造的直飞航班、两个冲突舱位指令和三个无关目的地。先让 Agent 在完整历史上选择航班，再设计上下文流水线：验证外部事实、记录舱位覆盖、将无关历史卸载、只放必要工具定义。比较两次调用的工具选择、引用和最终方案。记录 ID、计数和摘要版本，不必把原始个人数据写进调试日志。最后让用户再改日期，检查更新是否只影响相关步骤。

## 面试会怎么问

百度 MEG 面经问 Prompt → Context → Harness 与 Claude Code 压缩，小红书面经问长短期记忆，字节 9 月面经问滑动窗口与摘要。回答“上下文太长怎么办”时，不要只说截断旧消息。先分类哪些是不可丢的目标、约束与副作用，哪些可按需检索；压缩时保存来源与最新状态，隔离子任务；最后说明如何通过运行轨迹与回放测试发现压缩导致的误调用。
