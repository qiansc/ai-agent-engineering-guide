# 证明“批准的就是执行的”：审批收据与生产审计

一张 Agent 工具收据能证明某密钥签过一次 `issue_refund` 记录，却不能证明客户或审批人同意了这笔退款。高风险动作需要两段可核对的事实：人先批准**具体动作**，服务后来执行**同一动作**。如果批准的是 50 元给订单 A，Agent 不能把金额改成 500 元、订单改成 B 后继续使用旧批准。

## 把完整动作规范化并绑定摘要

先定义稳定的操作对象：动作名、租户与资源 ID、收款对象、金额及货币、原因、过期时间、策略版本和幂等键。把对象按约定规范化，计算 `operation_digest`。审批人看到同一对象的可读摘要并确认后，审批服务生成类型为 `human.approval.v1` 的签名收据；执行器发出工具调用收据时记录相同 `operation_digest`，再用 `parent_approval_ref` 指向批准收据的哈希。验证时，两张收据分别检查签名，并比较两个操作摘要是否相等。

```json
{
  "action": "issue_credit",
  "tenant_id": "tenant_42",
  "invoice_id": "inv_9",
  "amount_minor": 5000,
  "currency": "USD",
  "recipient_id": "customer_7",
  "idempotency_key": "credit-inv_9-v1"
}
```

金额用最小货币单位避免“50.00”与“5000 分”的歧义。可读确认界面应显示对象、币种、实际金额、收款人和将发生的副作用；UI 显示的内容也要从同一个结构化对象产生，而不是另写一段可能与签名字段不一致的说明。

| 审批收据提供 | 执行收据提供 | 必须核对的关联 |
| --- | --- | --- |
| 签名人、操作摘要、策略版本、截止时间 | Agent、工具结果摘要、外部交易 ID | 执行收据的 `parent_approval_ref` 指向审批收据，且两者的 `operation_digest` 相同 |

这段关系的重点是前后摘要一致；执行发生后还需从真实支付/订单系统取得结果，签名不能替代外部业务回执。

## 有效签名不等于有效权威

审批人与 Agent 应使用**不同的密钥注册表**。验证者从独立配置中取预期审批人公钥、Agent 服务公钥，检查每个密钥在签署与执行时是否被授权、是否撤销。不能让收据自己携带任意 `public_key`，验证成功就宣布“公司已批准”。执行前还要核对审批是否过期、策略版本是否仍有效、操作是否已经消费过；重放旧批准不应触发第二次退款。

一组好的拒绝测试包括：篡改任何收据字段；页面误导 Agent 更换目标；同一批准重复提交；冒充审批人或 Agent 的不同密钥；坏 JSON/Base64；批准过期；策略版本变更；注册表撤销审批密钥；以及**摘要替换**——两张签名都有效，但 Agent 执行收据引用了另一笔真实批准。不同原因应产生不同错误，方便审计和恢复。审批之后若真实业务对象版本改变，也需要重新检查条件，必要时重新请人确认。

## 把收据落到生产环境

私钥放 Key Vault、KMS 或硬件安全模块，应用只拿受限的签名能力，不能把私钥写进代码或容器环境。发布受控公钥与 key ID，保留轮换和撤销记录；若采用 JWK Set，要保护发布地址和历史版本。收据应进入追加式或不可变存储，并定期把最新链头哈希锚定到独立时间戳/透明日志或另一管理域，以便发现尾部删除与重写。明确存储保留期和访问权限：收据只放摘要仍可能暴露业务关系，审计者不应自动得到完整参数。

容量也要估算。若一张收据约 500 字节、每天一万次调用，一年原始体量约 1.8 GB；签名、索引、副本和关联业务内容会增加实际存储。不要以这组示例数字当作所有系统的精确预算。运行手册应写出收据没覆盖的事：输入验证、政策执行、限流、业务结果确认、人类身份与权限。

在 Python 中可用 PyNaCl 处理 Ed25519，用 `jcs` 规范 JSON；若采用成熟收据库，仍要检查其字节规范、密钥管理和交叉验证测试向量。选择库比自己抄几十行密码学代码更有维护优势，但不能因依赖名称带“治理”就省掉拒绝测试。相关生态材料包括微软 Agent Governance Toolkit 的离线验证教程、跨实现测试向量，以及 `protect-mcp`、`@veritasacta/verify` 和 `nobulex` 等实现；它们的兼容性、维护状态和适用范围要在实际选型时核对。

## 再往前走的几种模式

**选择性披露**可给字段做 Merkle 承诺，向不同审计者只展示必要字段并提供包含证明；它比“把一个哈希放进收据”复杂，需要规定字段规范化、叶子顺序与随机盐。**撤销**在密钥泄露时标记受影响时期的签名不再可信，通常与短期密钥和公开撤销记录组合。**执行前/执行后分签**分别封存授权决定与观察到的结果，适合审批者和执行者是不同主体的流程。

**负载组合**允许把模型候选、证据、风险判断和策略检查结果放在外部结构化负载里，收据只封存其摘要；这保持收据小，但验证者要有权限取得原负载。**跨实现测试向量**让 Python、TypeScript、Rust 等实现确认规范化字节与签名一致。**后量子迁移**需要算法版本与双轨过渡设计；Ed25519 目前广泛使用，但不是后量子签名。相关草案仍在发展，生产迁移要跟随正式规范与组织风险评估，不能仅把 `signature.alg` 改成新字符串。

## 练习：让错误批准一定被拒绝

为一笔超过 50 美元的订阅 credit 生成规范操作与摘要，让审批人签批准收据，再让 Agent 执行并签结果收据。先验证正常链。随后逐次修改金额、发票 ID、收款人、策略版本和过期时间，确认即使重新给执行收据签名，摘要或权威检查仍拒绝。再重复提交原操作，确认幂等键只产生一次真实 credit。最后模拟审批密钥撤销和链尾删除，检查注册表与外部锚点能否发现问题。

## 面试会怎么问

Raytheon 系统面试复盘涉及 Agent 安全治理；要务科技面经问签名、幂等与补偿。回答“人工确认怎样防止 Agent 偷换参数”时，给出规范操作对象、摘要、审批与执行双收据、可信公钥注册表、有效期和幂等校验，再强调真实执行状态还需查询业务系统。若被问“签名过了就安全了吗”，指出签名只能保证所签数据未改，无法证明输入真实、策略正确或用户身份已验证。
