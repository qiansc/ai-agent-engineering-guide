# 从 Notebook 到生产服务：部署、扩展与治理 Agent

本地 Notebook 里由开发者 `az login`，手工看每次模型回复，任务失败就重跑。这是学习机制的好环境，却不足以支持真实用户。生产 Agent 仍是“理解目标—调用工具—处理结果”的循环，但周围要加上身份、持久状态、并发控制、版本、评测、观测和恢复。Microsoft Foundry 可以承载这条迁移路径。

## 原型与生产究竟差在哪

| 关注点 | Notebook 原型 | 生产服务需要回答的问题 |
| --- | --- | --- |
| 托管 | 开发者机器和临时进程 | 谁发布版本，失败怎样回滚？ |
| 身份 | 开发者的 `az login` | 用户与服务各拥有什么权限？ |
| 状态 | Python 内存、重启丢失 | 线程、审批、工具结果如何持久恢复？ |
| 故障 | 看堆栈后手工重跑 | 哪些可重试，哪些要补偿或进死信队列？ |
| 成本 | 少量实验调用 | 每任务成本、限额、模型路由与缓存如何控制？ |
| 质量 | 开发者挑几个问题看 | 新版本须通过哪些离线测试，线上怎样监控？ |
| 信任 | 开发者在场监督 | 风险分级、人工审批和审计落在哪里？ |

“模型约占 20%，周围运维约占 80%”强调生产工作主要在模型之外；这是形象说法，不是对所有项目测得的通用比例。真正的设计应按自己的工具副作用、用户规模和风险列检查项。

## 三种部署模式可以组合

**客户端托管**把 Agent 循环放在自己的服务进程中，直接连模型与工具。你能控制中间件、状态和路由，也必须自己承担扩容与可靠性。**Foundry 托管 Agent**把 Agent 注册为平台资源，由服务管理运行、线程和部分安全/观测能力，应用变成较薄的客户端；它省去部分基础设施，却限制了底层控制。**Agent Workflow**把多个 Agent 与确定性步骤编为有条件、审批和检查点的图，适合多角色长流程，但要监控每个节点与交接。

选择时不要只问“哪个更高级”。已有后端需要精细控制一个工具循环，可以客户端托管；需要统一云端资源管理、身份和会话，可评估托管服务；退款审批、跨角色协作或可暂停任务，使用工作流。一个系统也可让客户端服务接收用户请求、调用托管 Agent，再用自己业务服务执行写操作。

## 生命周期：评测在发布之前

从创建 Agent，到版本化、离线评测、部署、线上观察、收集失败案例、改进，再到旧版本退役，是持续循环。每个版本应包括模型和部署名、指令、工具 Schema、检索索引、记忆策略、评测集与权限配置；只给模型名字打版本号是不够的。离线测试门设置最低任务成功、安全和副作用正确标准；未过门的版本不得晋级。上线后把新失败脱敏、标注并加入离线集。

生产发布还要能回滚。若新版工具把金额单位从元换成分，回滚模型却不回滚工具合同，问题仍存在。模型、工具、数据库与索引的兼容性要一起检查。退役旧 Agent 前确认没有尚未结束的长任务和等待中的批准。

## 扩展四件事

**请求进程尽量无状态**：用户线程、任务状态、审批和工具结果放外部持久存储，使任一服务实例能接续任务；用户身份与状态必须一起校验。**模型路由**：简单分类或常见 FAQ 可用较小模型，复杂推理再用强模型；路由质量也需评测，不能只看平均成本。**缓存**：公开、稳定、权限无差别的问答可缓存；订单、个人账单或按租户过滤的 RAG 答案绝不能只用问题文本作键。缓存至少考虑租户、身份/权限范围、知识版本与失效条件。**并发与背压**：面对模型速率限制，限制并发，按错误类别退避重试，长任务可入队，明确告诉用户“已接收”与“已完成”的区别。

这些策略会相互影响。缓存命中减少模型成本，但旧政策若未失效会降低正确性；路由小模型降低费用，但如果复杂请求被错分，就会增加重复调用与人工接管。以“每个成功且合规的任务成本”作为综合指标，比只比较单次 token 价格更有意义。

## 生产可观测与企业边界

MAF 的 OpenTelemetry span 可把模型、工具和编排步骤串起来，外加 `routed.model`、客户等级等不泄露隐私的维度，观察 p50/p95 延迟、错误率和成本异常。某个客户投诉应能追溯到具体版本、检索来源和工具状态，同时避免在 Trace 中记录原始个人资料或秘密。

Foundry 的 RBAC、内容安全和审计能力有价值，但工具端仍需最小权限。第 16 课强调托管身份，而不是沿用开发者 `az login`；知识库身份可只读，工单 API 限定可修改字段。退款、删除账号和法律提交等高风险动作需人工审批，并把批准绑定具体对象和参数。MCP server 要作为外部依赖：固定版本、限制身份与速率、验证输出、及时更新，不能因使用标准协议就当成可信内部代码。

## 练习：给现有 Notebook 做生产差距检查

选一份已跑通的工具调用 Notebook。逐项写出托管地点、认证身份、状态存储、可重试错误、不可重复的写动作、离线测试、线上 Trace、成本预算和人工审批。然后选一种部署模式，说明它替你解决了哪些问题，哪些仍在业务服务。模拟进程在工具执行后、模型收到结果前崩溃，检查恢复时能否查询外部状态，而不是重新执行动作。

## 面试会怎么问

美团 9 月面经问长流程保障、交易稳定性与异常测试，影石创新面经问工具超时和恢复，要务科技面经问幂等与补偿。回答“Agent 如何上生产”时，按身份、状态、故障、质量、成本、观测和人工批准展开，并给一条超时后如何确认副作用状态的具体路径。只说“部署到云上，加 Redis”无法回答恢复与业务正确性。
