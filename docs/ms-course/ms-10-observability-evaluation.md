# 生产中的 Agent：用轨迹、评测和成本数据改进它

Agent 在演示时答对几道题，进入生产后却可能因为新用户问法、工具限流或知识库更新而失败。想知道错在哪里，需要能看到一次任务中的模型调用、工具调用、分支与结果；想知道修改有没有变好，需要固定测试集和线上反馈。可观测性回答“发生了什么”，评测回答“表现是否达到目标”。

## 一次任务展开成 Trace 与 Span

一条 **Trace** 对应用户的一次完整任务，例如“审核这张费用报销单”。其中每次模型请求、数据检索、工具执行或人工审批可以是一个 **Span**。记录父子关系后，团队能判断 20 秒延迟是模型推理、搜索还是外部 API，错误是模型选错工具、工具返回坏数据，还是最后总结遗漏了证据。Langfuse、Microsoft Foundry 和 OpenTelemetry 等工具采用类似概念。

Span 不应只记耗时。可记录任务 ID、步骤类型、模型和工具版本、调用次数、状态、错误码、输入输出的安全摘要、引用 ID、token 与费用。涉及用户 ID、原始对话和个人资料时要按权限脱敏与控制保留时间。

MAF 可通过 OpenTelemetry 建立一次任务的根 Span，再把内部模型与工具调用挂在它下面。下面保留最小埋点形状，`pass` 要替换为实际的 Agent 调用；`get_meter()` 则用于计数、耗时等指标，不会因为取得对象就自动生成有意义的数据：

```python
from agent_framework.observability import get_tracer, get_meter

tracer = get_tracer()
meter = get_meter()

with tracer.start_as_current_span("agent_run"):
    # await agent.run(...)  # 把真正的一次任务放在此处
    pass
```

若框架自动 Span 不含业务状态，可在应用边界手动补 Span 或属性。Langfuse 一类工具提供 `start_span(name="my-span")` 与 `span.end()`；异常路径也要结束 Span，不能只在成功分支调用 `end()`。调试时先验证导出器是否收到数据、Span 父子关系是否正确、失败调用是否带错误码，再讨论仪表盘好不好看。

## 要看哪些指标

| 指标 | 能回答的问题 | 不能单独说明什么 |
| --- | --- | --- |
| 任务与各步骤延迟 | 用户等在哪里，是否有慢工具 | 速度快不代表答案好 |
| 每任务 token/API 成本 | 哪个模型调用或循环过贵 | 成本低不代表值得上线 |
| 请求与工具错误率 | 哪些外部依赖或参数失败 | API 成功不代表业务成功 |
| 任务成功率/准确率 | 目标是否真正达成 | 需先定义可核查的成功条件 |
| 显式反馈 | 点赞、差评、评论中的坏例 | 反馈用户可能不代表所有人 |
| 隐式反馈 | 重问、立即改写、点击重试 | 行为也可能由其他原因造成 |
| 自动评估 | 批量检查相关性、安全或格式 | LLM 评分本身可能有偏差 |

可用 RAGAS 等工具评估检索生成，LLM Guard 等工具检查有害内容或提示注入。接入任何评测器前，先明确它评价的是哪一层：证据召回、引用正确、答案事实、工具路径、安全，还是用户满意度。模型打分可辅助筛选坏例，高风险任务仍需人工标注与外部事实验证。

## 离线评测：上线前能重复跑

离线数据集收集已知输入和期望行为。例如数学题集有确定答案；费用报销 Agent 则需要正常、重复报销、缺凭证、越权、金额冲突等案例。每个用例不仅写期望文本，还写允许/禁止的工具动作、是否需要人工审批，以及数据库最终状态。把小型 smoke tests 放在 CI 快速拦截主要路径退化，再用较大数据集比较模型或提示版本。

离线集会老化。模型若在固定一百题上很好，仍可能无法处理生产中新出现的政策或提问方式。应持续把线上失败纳入离线集，但不能把包含用户敏感数据的 Trace 直接复制进公开测试仓库；先脱敏、标注与审查。避免在同一测试集上无限调参后宣称泛化提升，留出独立验证集。

## 在线评测：发现测试集没有的事

线上监控观察真实成功、用户反馈、异常峰值与行为漂移。影子测试可让新版本接收相同输入但不对用户产生副作用；A/B 测试则比较不同版本的真实体验。若做付款、发邮件等动作，影子版本必须关闭写工具或指向安全隔离环境，不能为对照实验复制副作用。线上标签常不完整，用户没有投诉并不证明正确；需结合业务最终结果、人工抽查与趋势分析。

有效循环是：离线基线 → 小范围上线 → 观察 Trace 和业务指标 → 归类新坏例 → 纳入离线测试 → 修改并重测。更换模型、工具 Schema、检索索引或提示时，最好记录版本和变更时间，才知道退化从哪次发布开始。

## 四类常见问题怎么查

常见问题有任务表现不一致、Agent 陷入循环、工具调用差、多 Agent 不稳定。排查时先看轨迹，不要先修改 Prompt。不一致可能因输入缺字段、检索索引不同或工具结果时效不同；循环要看终止条件、重复调用和预算；工具问题先在 Agent 外单独测接口，再检查名称、描述与参数；多 Agent 问题要看路由与交接，明确每个角色职责和权限。分层排查比“再加一个模型反思”更可控。

## 控制成本而不盲目降质

控制成本可从三处入手：对简单任务使用小模型，把请求按复杂度路由到不同模型或函数，以及缓存重复请求。每项都要通过评测。分类/参数提取可先试小模型，复杂推理保留更强模型；路由器自身会增加错误和开销，需测误分流率；缓存常见问答要考虑用户权限、知识版本与时效，不能把上一位用户的私有答案给另一位用户。成本可用“每个成功任务花费”而非只看单次模型价格。

`10-expense_claim-demo.ipynb` 用费用报销场景演示监控与评估。阅读时可用这份检查表逐个标记：Trace 有没有覆盖完整任务；工具失败在哪个 Span；是否有成功/失败标签；一次坏例能否重放；模型改动后是否有成本和质量对照。

## 面试会怎么问

百度 Agent 实习面经问 trace，美团 AI Agent 面经问异常测试，Raytheon 复盘谈轨迹评测。回答“如何评测 Agent”时，先定义任务成功与副作用正确性，再讲离线用例如何覆盖坏例、线上如何监控和采样，最后用 Trace 定位某一次失败。若只能报“模型回答准确率”，面试官会继续追问工具选错、超时、循环和成本。
