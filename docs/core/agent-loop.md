# Agent Loop：决策、执行、观察与终止

Agent Loop 是一段由宿主程序控制的循环：把目标和当前状态交给模型，接收最终答案或动作请求，校验并执行动作，再把观察结果写回状态。模型能建议下一步，但不能自行宣布外部动作已经成功。理解这段循环后，框架中的 node、step、handoff 和 checkpoint 才有明确含义。

```text
while budget.remaining():
    decision = model(goal, visible_state, available_tools)
    if decision.kind == "final":
        if verify(decision.answer, state):
            return decision.answer
        state.append_error("final answer failed verification")
        continue
    step_id = state.next_step_id()
    call = validate(decision.tool_call, identity, policy)
    operation = state.bind_operation(call, retry_of=decision.retry_of)
    if operation.status == "completed":
        state.append(step_id, operation.id, operation.result)
        continue
    if operation.status == "uncertain":
        outcome = reconcile_external_result(operation)
        if outcome == "unknown":
            return escalate("execution status unknown", checkpoint=state.snapshot())
        if outcome == "completed":
            state.append(step_id, operation.id, outcome.result)
            continue
    result = execute(call, timeout=30,
                     idempotency_key=operation.idempotency_key)
    state.append(step_id, operation.id, normalize(result))
return escalate("budget exhausted", checkpoint=state.snapshot())
```

这段伪代码中的每个动词都需要具体合同。`validate` 要检查工具是否在当前任务中可用、参数是否符合 schema、资源是否属于当前用户；`execute` 要处理超时、取消与部分成功；`normalize` 要把巨大的工具输出缩成可供下一步判断的状态，同时保存原始产物引用；`verify` 要用任务验收条件检查答案。实际实现还应捕获模型响应格式错误与校验异常，把它们记录成可诊断的状态，而非让进程直接退出。

`step_id` 标识当前循环轮次，不能直接当写操作的幂等键。`bind_operation` 为首次接受的业务动作分配持久 `operation_id` 和幂等键；模型再次提出“重试”时，宿主必须核对它是否指向同一动作、同一对象和同一参数，再复用原键。若上次超时且执行状态未知，先向外部系统核对；无法确认时暂停并升级，不能凭一个新的轮次 ID 重新写入。确实要执行第二次同类业务动作，必须显式创建新的 operation，并重新经过相应审批。

## 一轮动作怎样流动

以“解释一张账单为何比上月高”为例，模型先请求 `get_invoice(invoice_id)`。宿主校验用户身份与账单归属后读取金额和条目，并将结果作为工具消息送回模型。模型发现新增了订阅项目，再请求 `get_subscription_change(account_id)`。如果变更记录能解释差额，模型生成带证据的结论；若账单工具超时，状态中必须保存失败码，模型才能选择重试、改查历史记录或向人说明暂时无法判断。

消息层也有边界。用户界面显示的是轮次，模型实际接收的是经特定消息模板序列化后的角色、内容、工具调用和工具结果。模型预测一个动作不等于工具已经执行；宿主必须在完整动作形成后停止生成、解析结构化参数、执行工具，再把真实观察送回。若允许模型继续“编造工具返回”，它会在没有访问系统的情况下写出似乎可信的账单原因。现代原生工具调用可减少手写动作解析，但权限与执行检查仍由宿主负责。

一次模型响应也可能包含多个工具请求。宿主需要判断它们是否独立：两个只读搜索可并行，创建草稿与提交草稿有依赖，不能同时发出。每个请求都应分配 step ID、记录参数校验结果和执行状态；若其中一个失败，下一轮模型应看到明确的部分结果。把多个请求揉成一条“工具完成”消息，会掩盖失败位置，也让恢复时无法知道哪一步需要补做。

将账单案例展开成一条可检查的轨迹，更容易看出“模型判断”和“环境事实”的区别：

| 步骤 | 模型请求或结论 | 宿主实际检查 | 写入状态的观察 |
| --- | --- | --- | --- |
| 1 | 查询两期账单 | 当前用户能否读这两张账单 | 账单 ID、版本、条目和差额 |
| 2 | 猜测新增订阅造成差额 | 此时只是待验证假设 | 假设及所需证据，不写入事实 |
| 3 | 查询订阅变更 | 账户归属、查询时段和工具预算 | 变更生效时间、套餐价格与来源 |
| 4 | 生成差额解释 | 数额能否对齐、引用是否对应 | 通过验收的答案或缺口 |

假设第二步发现差额为 39 元，而订阅升级只解释 29 元，第四步便不能输出“完全由升级造成”。系统可以查询税费或折扣变化；预算不足时应指出尚有 10 元差额未解释。这里的关键不是模型是否会算减法，而是验收条件把“所有差额都有证据”写成了可检查规则。若只要求“给用户一个解释”，模型可能在证据尚不完整时提前收尾。

## ReAct、计划执行与显式 Workflow

ReAct 适合下一步依赖最新观察的环境，如网页导航和故障排查。模型每走一步都读取反馈，灵活但模型调用多、路径不易复现。Plan-and-Execute 先把目标拆成结构化步骤，适合依赖关系清楚且需要显示进度的长任务；执行时仍应根据新证据局部重规划。显式 Workflow 由代码定义节点与分支，适合业务规则稳定、审计要求高的任务。一个系统可以混合三者：固定审批流程中，Agent 只负责开放式调查；调查内部采用粗计划和逐步观察。

计划对象至少包含步骤 ID、目的、依赖、负责人、前置条件、验收标准与状态。只写“先查资料，再总结”无法恢复，也无法知道哪一步可并行。下面的状态片段可以用于练习：

```json
{
  "step_id": "find_policy",
  "depends_on": ["verify_account"],
  "status": "pending",
  "success_check": "返回当前生效的政策 ID 与版本",
  "on_failure": "停止自动回复并请求人工核对"
}
```

计划生成后，运行时还要检查它是否可执行：每个依赖 ID 是否存在，是否形成环，步骤所需工具是否获授权，是否有不可逆动作先于审批。计划可以由模型提出，但这些检查应由程序完成。执行中新增证据只需要改变尚未执行的步骤。例如发现订单属于企业合同，原计划中的普通退款政策检索应被标记为失效，换成企业合同检索；已经完成的身份核验无需重做。对用户展示的进度可直接来自状态对象，避免模型凭记忆估计“已完成 80%”。

何时使用哪一种编排，可以用“自由度来自哪里”来判断。若所有节点和转移条件都已知，固定 Workflow 更容易测试。若节点固定但数据需要模型解释，可在节点内部使用模型。若连下一步该查哪个来源也依赖新观察，再交给 Agent Loop。开放式决策只放在真正不确定的局部，有助于压低成本，也让高风险业务保持可审计路径。

## 终止和重规划由什么触发

成功条件最好是可观察的产物检查：报告存在且每个关键结论有引用，补丁通过相关测试，草稿已经创建但未发送。失败条件包括权限拒绝、依赖不可用、相同错误超过阈值。预算包括步数、总时间、token、费用和工具调用数；耗尽时保存现场并说明未完成部分。风险升高或不确定性过大时，应转人工，而不是让模型继续猜。

重规划也需要明确触发条件。工具返回新事实使原步骤无效、用户更改目标、关键依赖失败、连续几步没有进展，都可能触发重规划。不要每一步都把全部任务重新规划，否则早已完成的动作可能被重复执行。系统应保留已验证事实和已执行副作用，只调整未完成步骤；计划版本与修改原因写进 trace。

## 三类常见循环故障

**路径震荡**表现为反复在两个搜索词、两个工具之间切换。状态应记录动作指纹和已尝试原因；相同调用多次无新增证据时熔断。**假完成**表现为模型给出流畅答案，但没有工具证据或产物未落地；最终验收必须独立于模型声明。**无限反思**表现为每轮都新增自我检查，却没有可验证的动作；反思应限定次数，并要求指出一个具体可检测的缺陷。

工具错误也可能诱发循环。`RATE_LIMITED` 通常等待后重试，`PERMISSION_DENIED` 应停止并提示权限问题，`NOT_FOUND` 可换查询，`PARTIAL_SUCCESS` 要先查询已完成集合。若只把所有错误写成“失败，请重试”，模型缺少区分路径的依据。对有副作用的工具，是否重试必须由运行时根据幂等键和实际执行状态决定。

循环中的状态也应按“已验证事实、待验证假设、已执行动作、未完成步骤”分开。账单明细由数据库返回，是已验证事实；“金额变化可能与订阅升级有关”只是待验证假设。若把假设写入事实摘要，后续模型会把它当作前提，形成自我强化的错误。任务暂停或上下文压缩时，这种区分尤为重要。恢复后先确认外部副作用，再继续思考下一步，而不是从旧对话最后一句直接续写。

## 运行时如何处理失败与续跑

每次循环最好有 `run_id`、`step_id` 和单调递增的状态版本。开始执行工具前先记录“准备调用”，执行成功后记录实际产物 ID；超时时记录“不确定是否成功”。进程重启后，不能直接重放最后一个动作，应先用幂等键或业务查询确认外部状态。确认未执行才重试，确认已执行则把结果补入状态。无法确认时转人工或进入补偿流程。对于只读查询，重新执行一般较容易；对于发消息、付款或发布，必须明确业务副作用和去重规则。

取消也有阶段差异。模型尚未发起工具时可以立即停；工具正在运行时需要传递取消信号，但外部系统未必能中止；工具已经完成后，“取消任务”不等于撤销业务动作。用户界面应区分任务已取消与某个副作用需要补偿。长任务中的审批暂停应持久化等待对象和期限，唤醒后重新核对用户身份、参数与资源状态，而不是沿用暂停前的假设。

排错时先看哪一层没有提供正确信号：模型是否选错动作，工具是否给了含糊错误，状态是否漏记结果，最终验收是否过松。相同错误反复出现不一定是模型能力不足，也可能是工具返回 `500` 而隐藏了“订单不存在”。修复工具合同之后重放同一轨迹，观察循环是否自然停止，比继续叠加“请仔细思考”的提示更有诊断价值。

可以把一次运行划分为 `ready`、`deciding`、`validating`、`executing`、`observing`、`verifying`、`waiting_for_human` 和终态。每次转移有触发事件和版本号。`deciding` 收到工具请求后进入 `validating`；参数非法则记录校验错误并返回下一轮，但连续非法达到阈值进入失败终态；执行器返回“可能已执行”的超时则进入待确认状态，不允许直接再次执行。用户审批到来时从 `waiting_for_human` 恢复，先重新核对权限与参数，再继续。这样任何阶段崩溃后都知道该检查什么。

聊天日志仍有价值，它帮助解释模型看到什么；但任务数据库才是运行控制的依据。若模型说“我已经发送”，而状态里没有工具成功事件，运行时不能展示“已发送”。反过来，若工具已发送成功但模型回答超时，恢复时应补发状态通知，而不是重新发送消息。把每次模型输出、校验、工具执行和终止检查作为不同事件记录，能够支持回放、审计和故障归因。

评估循环效率时，除了最终成功率，还要看平均步骤、重复动作、无进展轮数、每次工具失败后的恢复率以及人工接管率。一个模型可能以较高成本完成任务，另一个模型虽然少走几步却经常提前宣称完成。应在相同题集和工具响应下比较，并单独报告越权尝试与副作用错误。上线后若重复调用率突然升高，先检查工具结果是否被正确回填、压缩是否丢失已尝试动作，再考虑模型版本变化。

## 练习：实现 50～150 行的最小循环

实现 `search_policy` 和 `read_policy` 两个只读工具。让输入“某订单适用哪版退款政策”触发最多六步；最终答案必须包含政策 ID、版本和引用。构造一个过期版本、一次空搜索、一次超时、一次重复调用。记录每轮模型决策、校验结果和状态变化，并回答：模型什么时候认为已完成，宿主凭什么允许完成，预算耗尽后如何交接？跑通后再接入框架，比较框架帮你处理了哪些合同，哪些仍需自己负责。

验收时还可以把一条完整轨迹逐步重放：固定每次工具结果，让模型只面对相同观察，检查不同模型版本是否仍能在预算内完成。重放能揭示“答案碰巧正确、路径却危险”的情况，例如重复查询敏感资源或在权限拒绝后改用另一工具尝试绕过。最终结果与动作轨迹应分别评测；前者衡量完成任务，后者衡量完成方式是否可接受。

可以把通过条件写进自动测试：正常样例最多四次模型调用；旧政策不会被引用；权限拒绝后不再尝试同一资源；差额对不齐时不宣称完成；预算耗尽时返回未解决差额与已查来源。再更换模型或改写工具描述，只要任一断言退化就定位到对应步骤。测试不要求每次自然语言完全一致，但必须守住事实、动作和终止边界。

## 面试会怎么问

近期的百度 Coding Agent 复盘问到了 ReAct；小红书 Agent 开发复盘继续追问 Planner、Executor、Critic 怎样协作。准备这类题时，先画出一次真实执行轨迹，再解释编排方式的取舍。

**问：ReAct 循环里，模型说“任务完成”就可以结束吗？** 答：不能只看模型的结束语。宿主先检查任务定义的成功条件，例如补丁是否通过测试、答案是否有足够证据、写操作是否真的返回产物 ID。若验证失败，把具体失败作为下一轮观察；若步数、时长或费用预算已耗尽，保存检查点并报告尚未完成的部分。这样回答同时交代了模型决策、宿主执行和最终验收三种不同责任。

**问：什么时候把 ReAct 换成 Planner / Executor / Critic？** 答：先看任务依赖是否清晰。若步骤固定且需要审计，可以把依赖与验收写成工作流；若下一步必须根据工具观察来决定，保留局部 ReAct。Critic 不能只是再让模型“想一遍”，要检查具体结果，例如引用是否支持结论或工具动作是否越权。最后用同一组任务比较成功率、路径错误、调用次数和恢复难度，不能只说多一个角色会更可靠。

这两组问题来自候选人个人复盘，原帖见下方来源；它们适合练习回答结构，不代表公司统一题库。
