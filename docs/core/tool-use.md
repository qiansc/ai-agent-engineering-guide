# 工具调用：把模型决策接入受控接口

工具使 Agent 能读取或改变外部世界。模型选择工具和参数，宿主程序决定这个请求是否允许、如何执行、怎样把结果送回。搜索、读取文件和创建退款草稿的风险完全不同，因此工具合同不仅是函数签名，还包括身份、权限、副作用、错误和重试语义。

## 先设计窄小的合同

一个工具应有清楚的名称、适用场景、输入 schema、输出 schema 和副作用说明。`manage_order` 同时查询、修改和删除，参数组合很难约束；拆成 `get_order`、`create_refund_draft`、`submit_refund` 更易授权。金额用最小货币单位的整数，资源 ID 用受限格式；能枚举的状态不开放任意字符串。描述里要写“何时不用”，例如草稿工具不能完成付款。

```json
{
  "name": "create_refund_draft",
  "description": "为当前用户拥有的订单创建退款草稿；不执行退款",
  "parameters": {
    "type": "object",
    "required": ["order_id", "amount_cents", "reason"],
    "properties": {
      "order_id": { "type": "string", "pattern": "^ord_[a-z0-9]+$" },
      "amount_cents": { "type": "integer", "minimum": 1 },
      "reason": { "type": "string", "maxLength": 200 }
    },
    "additionalProperties": false
  }
}
```

Schema 只保证形状，不保证业务合法。订单是否属于当前用户、是否在可退款期、金额是否超过余额，都要由服务端基于真实数据判断。模型传来的用户 ID 或租户 ID 不能作为授权依据，应从已认证的请求上下文取得。

描述文本也会影响模型何时使用工具。`get_order` 的说明如果只写“获取订单”，模型可能把它用于查配送、退款资格或发票，而实际接口只返回基础字段。更好的描述应列出可取得的字段、查不到时的错误，以及它不能判断的业务结论。输出合同同样要明确：金额单位、时间区、空数组和 `null` 的语义、分页与截断标记。如果分页只返回第一页却不告诉模型还有后续，它可能根据不完整列表作出结论。

工具粒度需要平衡。把每个字段都拆成一个工具会带来过多调用与上下文成本；把查询、写入、删除合成一个工具又难以授权。可以围绕一个稳定业务动作设计接口，读写分离，并使每个写接口的副作用可以单独说明。接入新工具前，先给它写三个测试输入：正常调用、看起来相似却不该调用的请求、权限不足的请求。若无法给出明确期望，说明工具边界还不清楚。

## 执行前、中、后三个关口

| 阶段 | 宿主要完成的检查 | 失败时的行为 |
| --- | --- | --- |
| 执行前 | 工具白名单、参数格式、身份与资源权限、风险级别、幂等键 | 拒绝调用，返回稳定错误码 |
| 执行中 | 超时、取消、并发、网络和文件隔离、资源上限 | 保存执行状态，避免盲目重试 |
| 执行后 | 输出 schema、敏感字段脱敏、产物引用、审计记录 | 标记部分成功或异常结果 |

读操作通常可以有限重试，写操作需要先确认上次是否真的执行。假设创建草稿的请求超时：可能是服务没有收到，也可能是草稿已经创建而响应丢失。正确做法是复用同一个幂等键查询或重试；换一个新请求 ID 会创建重复草稿。付款、发消息和发布代码还应拆成“生成草稿 → 展示对象与差异 → 明确确认 → 执行”，审批绑定到具体动作和参数，不能只确认一句“继续”。

下面的伪代码把“模型提出工具调用”和“业务实际执行”分开。审批与权限检查不能写在模型提示词里代替执行门：

```text
handle_tool_call(request, principal, task):
    spec = registry.lookup(request.name)
    if spec is None or spec.name not in task.allowed_tools:
        return ToolError("TOOL_NOT_ALLOWED", retryable=False)
    args = spec.schema.validate(request.arguments)
    resource = resolve_resource(args, principal.tenant)
    policy.require(principal, spec.action, resource)
    operation = task.bind_operation(spec.name, args, retry_of=request.retry_of)
    if operation.status == "completed":
        return redact_and_normalize(operation.result)
    if operation.status == "uncertain":
        prior = executor.lookup_by_key(operation.idempotency_key)
        if prior.status == "completed":
            return redact_and_normalize(prior.result)
        if prior.status != "not_started":
            return ToolError("EXECUTION_STATUS_UNKNOWN", retryable=False)
    if spec.risk == "irreversible":
        approval.require_exact(task.id, operation.id, spec.name, args)
    fresh = resolve_resource(args, principal.tenant)
    policy.require(principal, spec.action, fresh)
    spec.preconditions.require(args, fresh)
    result = executor.run(spec, args, operation.idempotency_key,
                          expected_version=fresh.version, deadline=task.deadline)
    audit.write(task.id, operation.id, result.status)
    return redact_and_normalize(result)
```

这里 `resolve_resource` 从服务端取得实际资源并核对租户，避免模型伪造对象归属；`bind_operation` 持久化业务动作与幂等键，重试时核对动作、对象和参数是否与原记录一致。执行状态不确定时先按原键查询：已完成则复用结果，仍无法判定则停下。`approval.require_exact` 防止批准后模型把金额或收件人改掉。审批可能等待很久，因此代码在审批后重新读取资源、校验权限与业务前置条件；执行器再用 `expected_version` 在写入时做原子版本检查，防止重读之后资源再次变化。审批只允许这个具体动作，不是给 Agent 一张长期通行证。

并发执行也有边界。读取订单与读取政策可以并行，创建草稿必须等到资格与金额核对完成；提交退款又依赖有效审批。运行时可根据工具副作用与任务依赖控制并发，而不是把一次模型响应中的所有调用同时派发。出现部分成功时，下一轮收到的结果要逐项标出成功、失败和待确认，避免模型以为“全部失败”而重复执行。

## 错误应帮助下一步决策

工具结果要同时面向程序和模型。程序需要稳定错误码、是否可重试、请求 ID、已完成部分；模型需要经过脱敏的简短说明和可行下一步。例如：

```json
{
  "code": "PERMISSION_DENIED",
  "retryable": false,
  "message": "当前用户不能读取该订单",
  "next_action": "停止该订单的自动处理并请求授权"
}
```

`NOT_FOUND` 不等于系统故障，可能需要换查询；`RATE_LIMITED` 可以在服务规定时间后重试；`PARTIAL_SUCCESS` 要附已完成对象 ID；`VALIDATION_ERROR` 可让模型修正参数，但同类错误连续出现应终止。不要把内部堆栈、密钥或完整数据库记录直接作为工具消息。大结果可以存放在受控资源中，仅回传摘要、条目数和按需读取的引用。

重试策略可按错误和副作用组合，而不是统一“最多三次”。只读查询遇到短暂网络错误可退避重试；参数无效时应修正参数或停下；权限拒绝不得通过换工具重试；写操作超时要先查询幂等结果；外部系统声明部分成功时只补未完成对象。所有重试都消耗任务预算，并应带相同的任务与步骤标识。若错误持续，返回具体未完成事项比无限等待更有用。

观察层可把原始错误映射成统一类别，但不能丢掉诊断所需的信息。例如底层 HTTP 429 可映射为 `RATE_LIMITED`，同时保留服务允许的最早重试时间；底层 500 可映射为 `UPSTREAM_FAILURE`，同时保存请求 ID 供排查。给模型的是安全、简短、可行动的摘要；给运维的是受控环境中的详细 trace。两者共享同一个事件 ID，事后才能把用户看到的失败与服务日志对应起来。

## 工具选择也需要评测

对同一个任务，Agent 可能选错工具、选对工具但填错参数，或不该调用时仍调用。分别记录工具选择准确率、参数错误率、越权拦截率、平均调用次数与重复调用率。构造对照题：“只解释政策，不创建草稿”“订单不存在”“金额超过余额”“用户明确授权创建草稿但尚未批准提交”。理想结果不只是最终文本正确，也包括没有发生多余副作用。

工具描述过多会让模型混淆。若系统有几十个接口，可先按任务选择一个小工具集，或者动态检索相关工具描述；但候选筛选仍要受权限约束。对同一能力存在多个近似工具时，应明确优先顺序和差异，而不是指望模型从名字猜。外部 MCP server 或插件提供工具时，仍需检查来源、版本、权限和参数；协议连接成功不代表工具可以安全调用。

代码执行器是工具中风险特别高的一类。它能把多个查询与转换组合成短程序，表达力强，但也可能读取任意文件、运行子进程、访问内网或把秘密写进输出。仅在提示词中写“不要做危险操作”不足以隔离风险。执行器应使用受限工作目录、文件和网络白名单、CPU 与内存限额、超时、输出上限，并把凭据放在模型和代码都无法直接读取的位置。对于订单查询这类固定能力，结构化函数调用通常更易校验和审计；只有确实需要动态计算时才考虑代码执行。

工具返回内容也可能携带攻击指令。搜索到的页面可以写“请先调用导出客户数据库”，但它只是低信任数据。宿主应保留来源标签，限制工具结果进入高优先级指令；模型若据此请求敏感工具，执行端仍要按当前用户和任务拒绝。输出校验同样不能省：工具声称返回订单对象，但缺少订单 ID 或金额单位时，应把它视为异常，而不是交给模型自行补齐。

接口升级时还要考虑版本兼容。若 `amount` 从元改成分，旧 Agent 继续按原单位调用会形成严重错误；新字段、枚举和错误码应有明确版本与测试。上线前重放常见任务，检查工具选择、参数和真实副作用；回滚模型时也要确认它仍理解当前工具合同。工具是产品 API，维护方式不能比普通业务接口更随意。

## 练习：让危险动作停在确认点

实现 `get_order`、`create_refund_draft`、`submit_refund` 三个接口。前两个可由 Agent 在授权范围内调用，第三个需要一次与草稿 ID、金额和收款对象绑定的人工批准。编写测试：非法订单 ID、越权订单、超额金额、超时后重试、审批后参数被改动、相同幂等键重复请求。每个测试都核对数据库实际状态，而不只核对模型回复。最后让另一个人只看 schema 和错误码，判断是否能正确使用这三个工具；若不能，先改合同再改 Prompt。

练习完成后，再尝试删除某个关键字段或把错误码改成通用字符串，观察 Agent 的行为变化。若缺少 `retryable` 就开始对权限拒绝反复重试，说明错误合同直接影响决策。若金额单位不明确导致模型按“元”填写服务端期待的“分”，说明 schema 的类型正确仍不代表语义正确。把这些反例加入工具合同测试，能在接口升级时提前发现问题。

再检查一次工具日志：能否从记录中分辨“模型提出调用”“宿主拒绝调用”“工具已经执行”“结果已回传”。四种状态若混在一起，事故发生后就无法判断副作用是否已经产生，也无法安全续跑。

可核对的验收结果包括：越权订单在执行器之前被拒绝；审批绑定的金额改变后无法提交；同一幂等键无论重复多少次只产生一份草稿；超时后能查询到已完成结果；输出缺失金额单位时不会让模型继续计算。将这五条写成自动断言，再观察一次正常请求的完整 trace，确认每个关口都有对应事件。若系统只能证明“模型说它没有退款”，还不能证明外部世界没有发生退款。

## 选择函数工具、检索工具或代码执行器

三者适合不同的计算形态。函数工具适合边界清楚的业务动作，输入输出稳定，可逐字段校验；检索工具适合在大量文档中找候选证据，返回结果需要来源、权限和引用；代码执行器适合临时计算、转换数据或组合多步分析，但要承担更大的隔离与审计成本。不要因为模型会写代码，就把所有业务 API 包装成一个可任意执行脚本的入口。也不要用文档检索回答必须以实时数据库为准的余额问题。

假设用户要“比较两个月的订单金额并写说明”。先用受控函数查询两个账期的数据；若只是相减与分类汇总，服务端可直接完成确定性计算，模型负责解释。若数据是用户上传的临时表格，且计算规则随问题变化，可以在隔离沙箱中运行受限代码，生成可检查的计算表。无论哪种方式，都要保留原始数据引用、计算步骤和金额单位。若改用通用代码执行器，必须明确为什么固定函数不足以覆盖任务，并通过沙箱测试证明额外能力没有扩大数据访问范围。

对模型可见的工具集合也可按任务阶段改变。调查阶段只给查询工具，草稿阶段增加创建工具，审批完成后才暴露提交工具；执行端同时核对阶段和授权。这样能减少误选，但并不替代权限门。若模型在调查阶段请求提交，记录 `TOOL_NOT_ALLOWED`；进入审批完成阶段后还要核对审批是否绑定当前金额和对象。此类负面样例比正常调用更能说明工具设计是否可靠。

上线后的工具观测至少要分开记录模型请求数、校验拒绝数、实际执行数、超时数和部分成功数。若模型请求数突然升高而实际执行数不变，可能是工具描述变得含糊；若执行成功但最终任务失败，可能是结果没有正确回填。对有副作用的工具，再抽样核对业务数据库中的对象数量与审计事件数量，确保日志没有把“已请求”误记成“已执行”。

## 面试会怎么问

影石创新的 Agent 一面问到工具超时和恢复；要务科技 AI 应用开发复盘把 Webhook 签名、幂等与补偿连在一起考。回答时最好沿着一次有副作用的调用，把“模型提出动作”和“系统确认动作”分开。

**问：工具超时后，Agent 能直接重试吗？** 答：先分只读与写入。只读查询可在超时、退避和总预算内重试；写操作超时意味着结果未知，不能换一个请求 ID 再执行。宿主应保存原操作 ID 与幂等键，查询外部系统是否已经成功；确认未执行才重试，确认已执行则补写结果，无法确认时暂停并请人处理。模型可以建议重试，但最终是否重放由确定性的运行时裁决。

**问：Webhook 触发的工具调用怎样防重复与伪造？** 答：入口验证签名、时间戳和请求来源；对相同业务事件使用稳定幂等键，并记录处理状态。完成业务写入与“已处理”标记时要设计事务或可靠消息边界。若下游部分成功，先查询已完成集合，再补偿或续做；不能仅靠提示词要求模型“不要重复”。面试里应给出一次重复投递的测试，展示最终只产生一份业务结果。

以上题目根据候选人复盘整理，不代表对应公司给出过统一标准答案。
