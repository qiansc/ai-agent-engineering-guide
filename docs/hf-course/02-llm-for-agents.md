# Agent 使用的大语言模型：Token、预测与上下文

Agent 的模型会阅读用户消息、工具描述和执行结果，再决定下一步。理解模型如何读取这些文字，能帮你解释为什么工具说明要写清楚、为什么长对话需要管理上下文，以及为什么模型的回答不能直接当成外部事实。

## Transformer 模型承担了不同工作

大语言模型从大量文本中学习模式。这里介绍 Transformer 的三种常见结构：编码器把输入变成适合分类或检索的表示，例如 BERT；解码器逐 token 生成文本，常用于对话和代码生成，例如 Llama；编码器—解码器先处理输入再生成输出，常用于翻译和摘要，例如 T5、BART。构建对话式 Agent 时，最常见的是使用具备指令遵循能力的生成模型；构建检索工具时，编码模型也可能参与计算文本表示。

| 结构 | 主要输出 | 在 Agent 系统中的位置 |
| --- | --- | --- |
| 编码器 | 输入的向量表示或任务预测 | 文档检索、文本分类 |
| 解码器 | 按顺序生成的新 token | 对话、计划、工具调用意图 |
| 编码器—解码器 | 条件生成的序列 | 翻译、摘要等专项任务 |

一个模型「参数多」不自动等于「会使用工具」。模型还需要相应的指令训练、正确的消息模板、清晰的工具描述，以及外部执行器把调用真正落地。

## Token 是模型阅读文字的单位

模型并不直接以整篇文字或完整单词为基本单位。分词器会把输入切成 token，常见情形是把词拆成可复用的子词片段。例如英语中的 `interest` 与 `ing` 可组合为 `interesting`。不同模型使用不同词表和分词规则；同一句话在两个模型中的 token 数也可能不同。

一段 Agent 输入里通常同时有用户问题、系统指令、工具定义、历史消息和工具返回。它们都占用上下文窗口。因此「把所有历史原样塞进去」会遇到长度和费用限制。检查上下文时不要只数用户输入，工具返回的长网页、日志和代码也常是主要部分。

可以使用 [Tokenizer Playground](https://agents-course-the-tokenizer-playground.static.hf.space/)；你可以把自己的工具定义和一段真实工具返回粘进去，观察切分结果。练习的重点不是记住某句子占多少 token，而是意识到格式标记、重复工具说明和长输出都会消耗预算。

## 下一个 token 预测怎样变成完整回答

生成式模型读取已有 token，给词表中的候选下一个 token 计算分数，再按解码策略选出一个。新 token 加入序列后，模型再次预测。这个自回归过程持续到结束标记或其他停止条件。这里用「The capital of France is ...」说明上下文中的 `capital` 与 `France` 对候选结果的重要性。

最简单的解码方式每次选最高分 token。束搜索会维护多个候选序列再比较整体分数；采样则可以引入不同程度的随机性。策略会影响输出的稳定性与多样性，但不能替代事实校验。你可以用这里的 [解码可视化工具](https://agents-course-decoding-visualizer.hf.space) 和 [Beam Search 工具](https://agents-course-beam-search-visualizer.hf.space) 观察不同选择路径。

Transformer 中的注意力机制帮助模型在处理当前位置时利用输入序列的其他位置。上下文长度表示单次处理的 token 上限；它不是「模型能永久记住多少事情」。一次调用中没放进输入的旧消息，模型通常无从读取。上下文越长，也不保证每条信息都被正确使用，所以 Agent 需要显式保留关键事实和工具结果。

## 特殊 token 与结束条件

不同模型通过特殊 token 标记消息或序列边界，例如 SmolLM2 的 `<|im_end|>`、Llama 3 对话格式里的 `<|eot_id|>`。它们不是用户日常文本的一部分，而是模型训练和输入格式的组成。不要把某个模型的标记直接复制到另一模型；也不要把「消息结束」「助手本轮结束」「整段文本结束」一概当作同一事件。实际集成时查所用模型的 tokenizer 配置与聊天模板，比背一张通用标记表可靠。

这件事与工具执行直接相关：当模型生成一个动作请求，运行时需要知道动作在哪里结束，然后停止生成、解析调用、执行工具，再把真实结果作为下一条消息。若继续让模型输出「观察」，那一段可能只是它自己写出的假结果。

## 预训练、指令训练与提示

预训练让模型学到语言和代码中的统计规律。指令微调、偏好训练或专门的工具调用训练，可以让模型更适合遵循指令与消息格式。提示则是在使用模型时提供目标、上下文、规则和示例。它能引导模型，却不能凭空赋予模型没有连接的外部数据，也不能保证所有指令都被严格遵守。

这里主要通过 Hugging Face 托管推理接口使用模型，也提到具备硬件条件时可在本地运行。选择方式会影响延迟、数据流向、模型可用性和费用；选择之前应核对当前服务的模型支持与权限。后面「手写最小 Agent」一课会用 `InferenceClient` 显示消息格式与生成停止的关系。

## 动手检查一条 Agent 输入

取一条真实或模拟请求，写成五段：系统指令、工具描述、历史消息、最新用户问题、最近一次工具返回。给每段标记目的。然后故意删除最近的工具返回，判断模型还能否有依据地回答。这个练习能看出模型生成能力与可验证事实之间的分界。

## 面试会怎么问

**问题：上下文为什么会膨胀，压缩时先保留什么？** 小红书与字节的 Agent 面经都追问过上下文压缩。先指出占用来源：多轮消息、工具 schema、网页或日志等观察结果。压缩时优先保留当前目标、已执行动作及其结果、关键证据、未解决问题和不可重复的副作用状态；冗长的原始输出可保留引用或摘要。最后说明如何验证压缩没有把「待验证猜测」误写成事实，也没有丢掉已执行动作，避免恢复后重复调用。
