# GAIA 实战：搭建、提交并复盘一个可评估的 Agent

前一篇弄清了 GAIA 测什么，这一篇把它落到一个练习项目：领取题目与附件，让 Agent 独立作答，按指定接口提交，再通过失败样本改进。这个项目对编程、工具调用与错误处理的要求高于前面的单工具练习。课程材料里曾把某个分数门槛与证书绑定；那是当时活动规则，不能视为现在仍然有效。学习目标是把评测流程跑通、读懂结果。

## 先确认评测接口和范围

课程配套的练习使用从 GAIA 验证集一级题目中筛选出的 20 道题。示例 API 设计有四类路由：

| 路由 | 用途 | 实作时要注意 |
| --- | --- | --- |
| `GET /questions` | 取完整题目列表 | 保留 `task_id` 与题目文本的对应关系 |
| `GET /random-question` | 随机取一道题 | 便于单题调试，不适合直接代表整体成绩 |
| `GET /files/{task_id}` | 取指定题目的附件 | 按文件类型处理，记录下载/解析失败 |
| `POST /submit` | 提交答案并计算分数 | 按接口要求传用户名、代码链接与答案列表 |

接口地址、认证方式与字段约束可能变化，实际运行前以页尾的实时 API 文档为准。不要盲目把旧版本代码复制后批量提交。

## 一个稳妥的运行流程

先用随机题走通“取题—读附件—回答—本地检查”闭环。拿到题目后保存 `task_id`，识别是否有文件；遇到 PDF、图片、音频等附件时，先检查能否正确读取，不要让模型在没看到附件内容时猜答案。让 Agent 明确记录使用了什么工具、从哪里得到关键事实，并单独生成一个给评分器的简洁答案字段。

因为评分按完全匹配，最终提交应只保留答案本身，不要包含 `FINAL ANSWER:`、思考过程、寒暄和多余标点。完全匹配也会放大格式问题，例如日期形式、大小写、复数或分隔符；可在提交前编写小型规范化/校验器，但不要用规范化规则去猜测题目事实。

再跑完整题集，并保存每题的 `task_id`、问题、附件类型、工具调用、原始回答、提交答案和错误状态。工具失败时把该题标为失败或重试，不要悄悄填空。这样拿到分数后才能逐题定位原因。

## 提交数据与公开代码

示例提交包含三个核心部分：用于识别提交人的 Hugging Face 用户名；指向公开 Space 代码树的 `agent_code`；以及按题目 ID 排列的 `answers`，每项形如：

```json
{
  "task_id": "example-task-id",
  "submitted_answer": "concise answer only"
}
```

可复制基础 Space 模板作为起点，然后替换模型、工具、提示词、附件解析与错误处理。不要把私有 Token 写进公开代码或提交载荷；凭据用平台 Secret 管理。公开代码链接的目的，是让他人理解你的实现并核对结果，不是展示一段无法运行的脚本。

## 从错误中选下一轮改进

先挑几个错题重放轨迹。如果答案事实正确却格式不对，优先修最终答案提取；如果搜索结果偏题，改检索查询、来源过滤和交叉核对；如果附件读取失败，修解析器与降级路径；如果 Agent 漏步骤，改任务拆解和中间检查点。一次只改一类原因，再复跑相同题集并记录变化，避免把偶然波动误判为改进。

排行榜是学习交流渠道，不是单独的能力证明。课程原稿提到过 30% 的活动门槛、排行榜和证书页面；这些属于外部活动状态。2026 年使用时应重新核对页面是否仍开放、规则是否更新、是否仍有证书资格，不能凭旧材料承诺读者“达到分数就能领证”。

## 做完后继续学什么

如果评测暴露的是“工具太多、接线难”，可以继续学习 MCP 这类 Agent 与工具/数据源的接口协议；如果问题是多 Agent 协作与交接，可再看 A2A。二者解决的连接方向不同：前者主要连接应用与外部能力，后者主要讨论 Agent 间互操作。协议不能替代任务评测、安全边界或可靠的业务数据。先做一个可复现的单 Agent 基线，再判断是否真的需要跨服务或多 Agent 架构。

## 面试会怎么问

**问：只有最终分数，怎样定位 Agent 的问题？** 答：保留逐题轨迹，包括检索、附件解析、工具参数/结果、原始回答与提交答案，按检索、理解、规划、执行、格式五类归因。随后每次只改变一项策略，在固定题集上复测。

**问：为什么公开排行榜高分不能直接证明方案可上线？** 答：题集范围、数据污染、人工介入、重复尝试和答案格式都会影响分数；上线还要测成本、延迟、鲁棒性、安全、隐私与真实业务数据。排行榜是一个受限实验，不是完整生产验收。
