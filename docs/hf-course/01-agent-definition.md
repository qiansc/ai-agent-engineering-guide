# AI Agent 到底是什么：从目标、模型到行动

如果一个程序只把问题交给大语言模型，再把文字回答显示出来，它已经有了很实用的语言能力。要完成「查今天纽约的天气，再给我出门建议」这样的任务，程序还需要让模型选择天气工具、执行调用、接收真实结果，最后依据结果回答。这样的系统就开始具备 Agent 的能力。

一个便于工作的定义是：**Agent 使用 AI 模型，根据用户目标决定下一步，并通过被授权的工具与环境交互，直到任务结束或需要交还给人。** 模型负责理解与决策；工具和运行程序负责真正读取、计算或修改外部世界。模型说「已经发送邮件」不等于邮件真的发出，这一点在后面的课程会反复用到。

## 跟 Alfred 一起走完一次任务

这套练习用管家 Alfred 解释这个过程。用户说「我想来杯咖啡」。Alfred 先理解目标，再规划去厨房、使用咖啡机、煮咖啡、端回来的步骤。规划本身还没有产生咖啡；必须调用现实中的能力，并观察结果。如果咖啡机缺水，原计划需要调整，而不是直接告诉用户「咖啡已经做好」。

把这个比喻换成软件系统，就会得到下面的对应关系：

| Alfred 的任务 | 软件 Agent 中的对应部分 | 要检查什么 |
| --- | --- | --- |
| 听懂「来杯咖啡」 | 模型读取用户目标 | 目标、约束是否明确 |
| 决定先去厨房 | 模型决定下一步 | 这一步是否必要、是否获准 |
| 使用咖啡机 | 程序执行工具调用 | 参数、权限与实际结果 |
| 看到咖啡煮好 | 工具结果作为观察回到模型 | 是成功、失败还是状态未知 |
| 把咖啡送达 | 最终产物与用户确认 | 是否真的完成目标 |

这个类比最有帮助的地方，是把「会说」和「会做」分开。模型通常输出文本或结构化消息；真正做事的是宿主程序连接的工具。Agent 能做什么，取决于其可用工具及其权限，而不是取决于模型是否愿意声称自己做到了。

## “大脑”与“身体”各管什么

这里把 AI 模型称作「大脑」，把能力与工具称作「身体」。这个说法适合入门，但设计系统时还要再加上第三部分：**运行时**。运行时负责把模型提出的动作解析、校验、执行，再把结果送回模型。没有这层约束，模型可能生成一个看似正确的工具调用，却没有系统替它执行。

大脑通常是大语言模型（LLM），也可以是能处理图像的视觉语言模型（VLM）。它读取用户消息、已有观察和可用工具描述，决定回答还是行动。工具可能是 `get_weather(city)`、网络搜索、数据库查询、生成图像，也可能是发送消息等有副作用的操作。运行时要区分这些风险：查天气是只读，发邮件会影响别人，不能使用同一套随意重试的规则。

下面的例子刻意把模型与执行器分开：

```python
def send_message_to(recipient: str, message: str) -> str:
    """发送邮件并返回外部系统的消息 ID。"""
    ...

# 模型可以提出这样的调用意图：
proposal = {
    "tool": "send_message_to",
    "arguments": {
        "recipient": "Manager",
        "message": "Can we postpone today's meeting?",
    },
}

# 程序还必须检查身份、收件人、内容和是否需要确认，
# 然后才可能真正执行 send_message_to(...)
```

示例中的 `send_message_to("Manager", "Can we postpone today's meeting?")` 展示了工具调用的形状；它不意味着所有邮件 Agent 都应自动发送。尤其在代表用户对外沟通时，应明确什么时候只是起草，什么时候得到确认后发送。

## Agent 能力有层次，不必每个任务都做成多步循环

Agent 能力可以按模型对程序流程的影响程度来观察：

| 模型能决定什么 | 程序形态 | 典型任务 |
| --- | --- | --- |
| 只生成待处理的内容 | 程序固定调用模型 | 生成一段摘要后由固定规则保存 |
| 选择一个分支 | 路由 | 判断一封邮件进入销售或客服队列 |
| 选择函数及参数 | 工具调用 | 选择要查询的城市和天气工具 |
| 选择下一步并决定是否继续 | 多步 Agent | 搜索、读取、核对并继续查找 |
| 触发另一个 Agent 流程 | 多 Agent | 研究 Agent 把任务交给代码 Agent |

层次越高，灵活性通常越大，检查与调试的难度也会提高。若任务只有明确的一次数据库查询，固定程序或单次工具调用更容易验证。只有下一步确实依赖上一轮的观察时，多步循环才真正有用。

## 三个应用场景，关注能力边界

个人助理可以设置提醒、查询日程、发送消息；这些动作涉及用户身份和权限。客服 Agent 可以回答知识库问题、查询订单、创建工单，甚至在允许的业务流程里办理交易；读订单和改订单必须分别授权。游戏 NPC 可以根据玩家状态生成对话或行为；与固定行为树相比，模型能处理更开放的输入，但仍受游戏规则与可执行动作限制。

对于这三类场景，评估 Agent 不能只问「回答是否流畅」。还要问：它取得的信息是否真实？操作是否真的执行？用户有没有给这项操作授权？出错时能否说明没有完成？这些检查就是后续工具、观察和循环这里的起点。

## 做一个小练习

选一个自己熟悉的任务，比如「查某订单适用的退款政策」。分别写出用户目标、模型需要判断的事、可用工具、工具可能返回的失败、最终答案的验收条件。然后把其中一个工具拿掉，判断任务还能否完成。这样比只记住「Agent = LLM + Tools」更容易发现系统设计中的空缺。

## 面试会怎么问

**问题：什么时候需要 Agent，而不是直接调用一次 LLM？** 小红书的 Agent 开发面经把「为什么用 Agent」作为项目追问。回答时先描述任务中哪一步无法预先写死：例如用户问的资料来源不固定，需要先检索、阅读结果，再决定下一次检索；或者工具返回错误后需要换路径。接着说明工具集合、每一步的权限与结束条件。若流程完全固定、只需模型生成文字或分类，承认普通工作流更简单，也更容易测试。这样回答比把所有接了 LLM 的程序都叫 Agent 更有说服力。
