# 用 LoRA 微调函数调用模型：从数据到验收

当现成模型经常选错工具、参数不合格式或不能在工具结果后继续回答时，可以考虑针对函数调用做监督微调。微调不是第一步：先检查工具描述、聊天模板、推理 API 和验证器是否正确，再看是否真的存在稳定、可复现的模型能力缺口。训练数据的质量通常比“多训几轮”更重要。

## 选择什么模型作为起点

预训练基础模型主要学习词元预测；指令微调模型进一步学习对话和遵循任务要求；偏好对齐则调整回答风格与行为边界。这些阶段不是每个模型都严格按同一顺序发布，但足以解释为何函数调用实验通常从指令模型起步。

例如 `google/gemma-2-2b` 是基础模型，`google/gemma-2-2b-it` 是指令版本。若训练目标是多轮对话里的工具调用，后者已有对话与指令能力，所需新增能力更集中。开始前检查模型许可、访问权限、硬件显存、tokenizer/chat template 以及推理端是否支持你选定的工具格式。

## 训练样本要教会什么

至少覆盖三种回合：有工具可用时选择正确函数与参数；不需要工具时直接回答；工具返回正常、空结果或错误后正确继续。对同一工具要有不同参数、不同用户措辞以及容易混淆的负例。若数据只包含“用户问天气→调用天气”，模型可能学会一见问题就调用，而不会判断何时无需调用。

样本应保留消息边界，包含用户消息、可用工具定义、助手的工具调用、工具观察和最终回答。先确定训练所用模型的聊天模板，再将结构化消息序列化；不要随意把 `[TOOL_CALLS]` 等别家模板 token 塞进当前模型，或只对答案文本训练却要求推理时生成结构化调用。

划分训练/验证集时按任务族或问题模板做隔离，避免同一道题只换一个 ID 就同时出现在两边。验收既要看最终回答，也要看工具选择准确率、参数 schema 合法率、无工具题的误调用率和工具失败后的行为。

## LoRA 如何降低训练成本

全量微调会更新大量基础权重。LoRA 冻结原模型，在部分线性层加入低秩的可训练矩阵，只训练这些适配器。可训练参数少，通常降低显存与存储需求，也便于为不同任务保存多个适配器。它不是“训练免费”：长序列、batch、优化器状态和模型激活依旧占资源；推理时适配器也必须正确加载或合并。

动手时可以沿着这条流程核对：加载指令模型与 tokenizer；设置与推理一致的聊天模板；把工具调用轨迹转成训练数据；配置 LoRA 的目标模块、秩和缩放参数；用监督微调训练器运行；保存适配器；在保留测试集上与未微调基线比较；再做一次真实工具执行的端到端测试。具体训练参数依模型和硬件而定，不宜照抄过时笔记本当成通用配置。

## 为什么“loss 降了”还不够

训练 loss 低，只说明模型更会复现训练分布；它可能仍会编造工具结果、输出非法参数或在陌生工具上退化。用如下样本验收更有说服力：工具描述相似但只能选一个；用户信息不足时应先澄清；工具返回 404/超时后不得当作成功；用户请求执行有副作用的操作时必须满足权限与确认。记录基线与微调模型在同一组样本上的差异，并保留失败轨迹。

配套训练 Notebook 在页尾给出。本文把训练原理与检查点讲全，但没有复刻 Notebook 的每一格代码；运行实际训练时应阅读该 Notebook、核对当时依赖版本和模型许可。训练涉及计算资源与平台凭据，先小样本试跑，再扩大数据量。

## 面试会怎么问

**问：为什么微调函数调用模型要从 instruct 模型而非基础模型起步？** 答：指令模型已有对话和任务跟随能力，训练可以聚焦于工具选择、参数格式与观察后的续写；基础模型还需同时学会基础聊天行为，数据和成本通常更高。

**问：LoRA 解决了什么，没有解决什么？** 答：它减少可训练权重与适配器存储成本；不保证数据正确、工具调用安全或泛化。仍要做数据隔离、基线比较、schema 验证与端到端评测。
