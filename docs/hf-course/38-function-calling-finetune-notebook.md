# 从数据到适配器：逐步做一次 Function Calling 微调

上一课解释了为什么从指令模型起步、LoRA 节省了什么，以及为什么训练 loss 不是工具调用能力的证明。这一课把这些概念落到一条具体的实验链上：整理多轮工具轨迹，确定聊天格式，扩充 tokenizer，加载基础模型，配置 LoRA 与 SFT，最后重新加载适配器检查输出。你不必先有 GPU 才能理解流程；每一步都可以先检查输入和预期形状，再决定是否投入训练资源。

本实验以 `google/gemma-2-2b-it` 为基础模型，以带有工具调用和 `<think>` 片段的对话数据做监督微调。模型、数据和依赖只是这一轮实验的选择，不是 Function Calling 的通用标准。如果你换模型，最先要重新核对的是许可、访问权限、聊天模板、特殊 token 与训练资源。

## 开始前：先确认四个边界

第一，模型需要获得访问许可。模型仓库若要求接受协议，即使代码正确，未获授权的下载仍会失败。数据集也要确认使用条款和用途。第二，训练要有足够的 GPU 显存；打开 Notebook 并不等于免费完成训练。第三，Notebook 使用的是它写作时的库接口，安装命令没有为所有依赖锁定版本；今天运行时应记录 `transformers`、`trl`、`peft`、`datasets` 和 `torch` 的版本，遇到参数名变化按当前文档调整。第四，发布模型是可选步骤，需要有写入权限的 Hugging Face 凭据；不发布也可以在本地验证。

把训练当作一次可复现实验：记录基础模型 revision、数据集 revision、随机种子、训练/验证样本 ID、聊天模板、tokenizer 词表大小和超参数。只留下最终 adapter 文件，很难解释之后为什么表现变化。

## 先看数据：模型到底要学会哪一段行为

数据不是一个孤立的“问题—答案”表。一个有教学价值的工具调用样本，至少能让模型看到：用户提出任务、可用工具是什么、助手选择哪一个工具并填写参数、工具返回了什么，以及助手如何根据返回继续回答。有些样本还包含多次工具调用或中间思考片段。实验数据使用 `Jofthomas/hermes-function-calling-thinking-V1`；它基于 Hermes Function Calling 数据，并增加了 `<think>` 内容。

下面是**讲解用的简化例子**，不是训练数据里的原样本：

```text
用户：查一下北京明天的天气，并告诉我是否需要雨伞。
可用工具：get_weather(city, date)
助手工具调用：get_weather(city="北京", date="明天")
工具结果：降雨概率 70%，最高温 25°C。
助手最终回答：建议带伞；预报给出的降雨概率是 70%。
```

只训练“工具调用”而没有“工具结果后的回答”，模型可能学会发请求，却不会正确使用观察。只训练成功样本，遇到空结果、超时或参数缺失时也可能编造结果。`<think>` 出现在数据里不代表它就是可信的执行记录，更不能把它当作用户必须看到的解释；评测仍应以结构化调用、实际工具结果和最终回答为准。

原实验加载约 3,570 条样本，先随机划分出约 3,213 条训练与 357 条测试；为演示计算流程，又只取前 100 条训练和前 10 条测试。这两组数字不要混淆：Notebook 的短跑只证明管线能够跑通，不能证明模型在未见工具和复杂任务上泛化。随机拆分还可能把同一任务模板的近似题分到两边；做正式实验时应按任务族、工具 schema 或数据来源隔离，并保留一个完全不用于调参的最终测试集。

## 对话模板是协议，不是装饰

Gemma 指令模型原有的聊天模板能处理普通 user/assistant 对话，却不是为这批工具轨迹的全部结构量身做的。训练前需要定义消息怎样串成模型实际看到的 token 序列：工具定义放在哪里、工具调用怎样开始和结束、工具结果怎样回填、轮次边界怎样标记。Notebook 修改了 `chat_template`，并在预处理时把 system 消息合并进第一条 user 消息，再调用 `apply_chat_template` 生成文本。

这一步为什么关键？假设训练时工具声明用 `<tools>…</tools>`，而推理时仅把一段 JSON 直接放在普通用户消息尾部，即使语义相近，模型看到的格式也不同。它可能输出错误标签、漏掉调用边界或直接作答。反过来，若推理环境只接受标准 API 的结构化 tool call，而你训练的是文本形式 `<tool_call>`，还需要一个可靠的解析器与转换层，不能以“模型写出了看似正确的 JSON”当作工具已经执行。

检查一条序列化结果时，至少逐项读出：系统约束、用户任务、工具定义、助手发出的调用、工具返回、最后答案。查看边界是否粘连，是否出现重复角色，是否把工具结果误标成助手自己说的话。可以用一条短样本先执行 `tokenizer.apply_chat_template(..., tokenize=False)`，肉眼确认后再批量处理。Notebook 所用的消息标记包括 `<tools>`、`<think>`、`<tool_call>`、`<tool_response>`；这些属于本实验的文本协议，不是所有模型共通的官方工具调用语法。

## 为什么还要改 tokenizer 和模型词表

把新标签写进模板，不等于 tokenizer 会把每个标签识别为单独的特殊 token。实验将工具相关标记加入 tokenizer 的额外特殊 token 列表，随后让基础模型的输入 embedding 大小匹配新词表。两步缺一不可：若 tokenizer 新增了 token ID，模型 embedding 却仍只有旧行数，遇到新 ID 可能越界；若推理时用了原版 tokenizer，则训练时学到的新标签边界也不一致。

可按这个顺序自检：

1. 记录添加前后的 `len(tokenizer)`，确认新增的标记数量符合预期。
2. 对一条样本编码再解码，检查标签没有被吞掉、错写或与相邻文字粘在一起。
3. 加载基础模型后执行 embedding resize，并确认输入 embedding 行数与 tokenizer 长度相同。
4. 保存 adapter 时一起保存与它配套的 tokenizer 和聊天模板；重新加载做推理时再次核对长度。

LoRA 通常只训练指定模块，并不会自动替你解决新 token 对应 embedding 的训练与保存问题。这个实验把 `embed_tokens`、`lm_head` 也列入目标模块，范围比仅在注意力投影层加 LoRA 更大。它会影响显存、适配器大小和兼容性，所以要以真实的“可训练参数数目”和保存文件内容核对，而不是见到 LoRA 字样就假设所有实验成本一样。

## LoRA 配置：知道每个数字在改变什么

实验的 LoRA 秩 `r=16`、缩放 `lora_alpha=64`、dropout `0.05`，任务类型为 `CAUSAL_LM`。目标模块覆盖注意力投影（如 `q_proj`、`k_proj`、`v_proj`、`o_proj`）、前馈网络投影（如 `gate_proj`、`up_proj`、`down_proj`），以及刚才提到的词嵌入和输出头。秩越大通常可训练参数越多，但不是越大越好；缩放影响适配器贡献，dropout 是训练时的正则化。目标模块名依模型架构而异，换模型前要打印模块结构核对，不能盲拷配置。

这些值是一个起点，不是调参结论。若 100 条短跑的训练 loss 下降但工具调用没有改善，先检查标签、模板和数据，再考虑调大秩。若显存不足，则先看序列长度、batch、目标模块和精度设置。把一组未经评测的超参数搬到另一个模型，不会自动得到相同能力。

## SFT 训练：一轮短跑能告诉我们什么

实验使用监督微调训练器。示例设置为每设备 batch 1、梯度累积 4、学习率 `1e-4`、一个 epoch、warmup 比例 `0.1`、cosine 调度、最大序列长度 1,500；同时开启 gradient checkpointing、packing 与 bfloat16，并按 epoch 做一次评估。这些配置放在一起读才有意义：batch 1 加累积 4，使一次参数更新汇集多个小批次；checkpointing 以额外计算换较低激活显存；packing 尽量把短样本拼进固定长度，减少空白，但也要求你核对样本边界不会错误互相污染；bfloat16 需要硬件支持。

训练器接收基础模型、训练/测试数据、tokenizer 和 LoRA 配置，完成训练后保存 adapter。Notebook 展示的那次短跑日志中，训练 loss 约 1.24，验证 loss 也约 1.24。这个数字只说明当前监督目标下的预测损失，不能推导出“工具选择准确率达到某值”。验证集只有 10 条演示样本，波动尤其大。若改了 tokenizer 或模板，旧 loss 也不能直接与新实验比较。

运行时建议分三关。先做**无训练预检**：取一条样本，确认序列化、token 数和 embedding 尺寸。再做**极小样本过拟合试验**：让模型在几条训练样本上明显降低 loss，检验梯度和标签是否真正生效。最后才跑正式训练与独立评测。训练前还应保存基础模型在同一测试集上的输出，免得训练后没有比较对象。

## 保存、加载和试问：避免“训练成功，推理读错”

实验演示把 adapter 和 tokenizer 发布到模型仓库，然后从 adapter 配置中找到基础模型，再用 PEFT 将适配器挂回基础模型。发布前先检查仓库可见范围，特别是训练数据和模型输出是否可能泄露私人信息；令牌应来自安全凭据存储或环境变量，不能写进 Notebook 单元格、截图或提交记录。仅做本地实验时，可直接保存到受控目录而不发布。

重新加载时要把三件东西配齐：**相同的基础模型、训练后的 adapter、与之匹配的 tokenizer/聊天模板**。实验的 tokenizer 增加了标记，因此加载基础模型后仍需核对 embedding 大小。若 adapter 权重、模型 revision 或 tokenizer 任何一项错位，模型可能能启动，却持续生成错误的边界标记，这比显式报错更难发现。

Notebook 最后用一条测试提示调用 `generate`，限制最多生成 300 个新 token，并设定采样参数观察输出。这是烟雾测试：能看到模型产生符合协议的文本，但不证明“函数调用系统可用”。完整验收应把生成内容交给解析器，检查工具名存在、参数可通过 schema 校验、没有越权操作，再把模拟或真实工具结果回填，检查最终答案是否引用了观察而非自行编造。生成时使用采样会引入随机性；做模型对比应固定提示、随机种子和解码设置，并报告多条样本的统计结果。

## 动手练习：把短跑变成可信的小实验

挑三类各 10 道未进入训练的题：必须调用工具、不应调用工具、工具返回错误或空值。对基础模型和适配器模型使用完全相同的模板和工具声明，记录调用是否出现、工具名是否正确、参数是否能解析及通过 schema、回填后回答是否忠实。若模型输出 `<tool_call>` 却包含不存在的函数，要记为错误，而不是因为它“看起来懂任务”就算通过。

随后故意改掉一个条件做排错：把推理模板中的 `<tool_response>` 写错，或改用未扩充的 tokenizer。观察生成如何变化，再恢复正确设置。这个实验比只盯训练 loss 更能帮你理解 Function Calling 的核心：训练学到的是一整套消息协议和行为模式；推理环境必须以相同协议给模型输入，并由运行时负责解析、执行与验证。

## 面试会怎么问

**问：为什么已经有工具调用数据，还要改 chat template 和 tokenizer？** 答：模型最终只看到 token 序列，不直接理解 Python 字典或 Notebook 表格。模板确定角色、工具定义、调用和观察的顺序；特殊 token 提供稳定边界。训练和推理的序列化协议一旦不一致，就可能出现合法语义却非法格式的输出。

**问：Notebook 的训练 loss 降了，能证明模型会 Function Calling 吗？** 答：不能。这里的 100/10 演示子集和单条生成只证明管线跑通。还要在隔离的多任务测试集上比较工具选择、参数合法率、不该调用时的误调用、工具错误后的续写，并做实际执行链的验证。

**问：LoRA adapter 迁移到推理服务时最容易漏什么？** 答：配套基础模型 revision、扩充后的 tokenizer 与聊天模板、embedding 尺寸，以及文本 `<tool_call>` 到运行时结构化请求的解析层。只挂载 adapter 权重而忘了这些协议，会出现“能生成但不能调用”的故障。
