# 把对战 Agent 放进竞技场，并用对战记录改进它

本地能返回一个合法招式后，才进入联机对战。对战 Space 和直播服务是外部在线活动，地址、开放时间和界面可能变化；先确认它们仍可访问，再投入部署。即使服务下线，前一篇的本地合法性测试与多场离线评估仍可继续做。

原练习还提供一条**不写 Agent 也能体验**的路线：打开直播和它使用的 Pokémon Showdown Space，先在对战页面选好自己的用户名，再从直播画面确认当前在线 Agent 的用户名，在 Showdown 中搜索该名字并发出邀请。直播当时提示一次只有一个 Agent 在线，因此找不到对手不一定是你的操作有误。直播、用户名和入口都可能改变；这里说明的是对战流程，不保证活动现在持续开放。

## 部署与邀请流程

在活动 Space 中复制一个自己的版本，检查项目结构和依赖，把 `TemplateAgent` 的真实实现放进项目指定的 Agent 文件，再在 `app.py` 注册类名和下拉菜单选项。原说明一处写 `agent.py`，示例仓库使用 `agents.py`；应以复制后的实际项目结构为准，别同时创建两个相互矛盾的入口文件。

运行前把模型 API 凭据配置为 Space Secret，确认启动日志无导入错误，再在下拉菜单选中你的 Agent。输入你在 Pokémon Showdown 页面使用的用户名，发送战斗邀请，在对战页接受。若邀请不出现，依次检查服务在线、用户名一致、Agent 进程已启动、网络连接和是否已有一场战斗占用它。直播演示可能一次只开放一个 Agent，不宜假设随时都能匹配。

复制 Space 后按页面实际文件结构放置实现，再在 `app.py` 的选择列表中注册；不要只把类贴进文件却忘了入口注册。选中自己的 Agent 后，输入**与 Showdown 页面完全一致**的用户名，点击发送邀请，然后切到对战页面接受。收到邀请后先核对对手是否是自己刚启动的 Agent，再开始比赛；这能排除把用户名输错或选错下拉项造成的假故障。

## 一场比赛里记哪些数据

每回合至少保存：回合号、摘要状态、可用招式/切换、模型返回的函数名与参数、验证结果、最终执行的动作、回退原因、决策耗时与调用成本。完整提示词可能含私密凭据或用户数据，公开日志前要脱敏。

输掉一场并不能说明策略失败：属性克制、队伍组成、随机命中与对手水平都会影响结果。把相同配置与多个对手重复对战，比较基线策略和新策略的胜率、非法动作率与平均回合时延。如果胜率略升但每回合花几十秒、频繁回退，实际体验仍可能很差。

## 一个小型复盘模板

选三段代表性轨迹：一段正确选择关键招式，一段错误切换，一段模型输出无效被随机回退。对每段问：输入状态里是否缺了重要信息？模型是否读错属性？工具 schema 是否含糊？名字解析是否错误？超时是偶发还是稳定？只修能被轨迹支持的问题，再重复相同对战集。这样改进的是可解释的决策链，而不是凭一场输赢反复改提示词。

## 面试会怎么问

**问：线上对战 Agent 偶尔选出非法动作，如何定位？** 答：把模型输出、当回合合法动作集合与归一化/校验结果一起记录。区分模型选择错误、响应解析错误和 API/状态同步错误；回退保证比赛继续，但回退率必须进入指标。
