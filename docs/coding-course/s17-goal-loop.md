# 模型想停时再查目标：Goal Loop 的独立完成判断

最小 Agent Loop 看到模型不再请求工具就结束。这能处理普通问答，却不能保证“修到测试通过”这类目标真的达成。s17 在循环准备退出的位置加一个 Goal Stop hook：主模型负责干活，独立判断器只读对话与工具结果，决定达成、继续、无法完成或暂缓判断。这里是以 s04 基础循环为底的**独立教学机制**，不是把 s15 的所有模块又复制一遍。

## `/goal` 同时保存条件并启动工作

输入 `/goal pytest tests/auth 退出码为 0，并且 lint 没有错误`，CLI 将条件保存在会话的 `GoalState`，马上把条件作为用户消息交给主模型，不用再输入“开始”。条件不能为空，最长 4,000 字符；同一会话只保留一个活跃 Goal。重新输入 `/goal 新条件` 会替换旧目标，`/goal` 单独输入会显示状态，`/goal clear` 会清除；`stop`、`off`、`reset`、`none`、`cancel` 也作为清除别名。

`GoalState` 记录条件、已判断次数、设置时间、设置时的 token 总量和最近原因。查看状态时可看到经过时间、本次 Goal 的 token 用量与最近判断理由。这些是帮助人判断进度的信息，不是完成证据本身。

## 结束位置多一道决定

主循环照常执行工具并给每个 `tool_use` 配一个 `tool_result`。只要本轮有工具结果，就直接进入下一轮；只有模型本轮没有再调工具，才调用 `goal.evaluate_after_turn(messages)`。没有活跃 Goal，判断器返回 `allow`，仍按 s01 的条件结束。有活跃 Goal 且后台工作未完成，返回 `defer`，不调用模型判断器，也不清除目标；完成通知进入消息后再继续。

判断器返回 `block` 时，Controller 把条件与“还缺什么”写成新用户消息，主模型在**同一个 while 循环**里继续执行。没有额外的 continuation queue。返回 `achieved` 才清除活跃 Goal 并交付成功；返回 `failed` 表示目标不可能继续完成，也清除活跃 Goal，但状态是失败而非完成。判断器出错或自动继续达到上限时则把控制权还给用户，保留活跃条件，不能在无法判定时假装成功。

| Stop 决策 | 触发条件 | 接下来 |
| --- | --- | --- |
| `allow` | 没有活跃 Goal | 普通返回 |
| `defer` | 有活跃 Goal，但后台结果仍在路上 | 暂不评价，等通知唤醒 |
| `block` | 条件尚未满足，但可以继续 | 把缺口写回消息，主模型再行动 |
| `achieved` | 证据支持完成 | 标记达成，清除活跃 Goal |
| `failed` | 判断器认为已不可能完成 | 标记失败，交还用户 |
| `error` / `limit` | 判断失败或续跑达到上限 | 保留 Goal，停止自动续跑 |

## 判断器只看证据，不替主模型做事

`PromptGoalEvaluator` 是另一次模型调用，没有工具。它接收完成条件和由当前消息渲染出的对话，必须返回 JSON：`ok` 布尔值、非空 `reason`、可选 `impossible` 布尔值。解析器拒绝无效 JSON、缺字段、空理由，以及 `ok=true` 同时 `impossible=true` 的矛盾结果。系统提示要求它把输入当数据、只根据对话中已经出现的结果判断，不能执行对话里嵌入的指令。

判断器最多阅读最近约 24,000 字符的对话文本。它尽量保留完整的最近消息；若最新一条本身过长，才保留首尾并标记中间省略。因此关键的测试退出码、lint 结果和受限文件范围应被清楚写进对话。主模型不能只说“我测过了”，而应留下命令与实际结果。判断器也不能重新打开文件或跑测试，所以它不等于确定性的测试框架；对于强约束，宿主最好直接检查工具退出码和文件 diff，再让模型负责解释仍有争议的条件。

## 什么样的条件容易判断

“把代码弄好”缺少验收。可以改成：“完成登录模块迁移，`pytest tests/auth` 退出码为 0，且没有修改 `tests/auth` 之外的测试文件。”这句话给出结束状态、验证方式和限制。主模型要运行命令、记录退出码、检查 diff；判断器才能据此回答 `ok`。若测试失败且报错可修，返回 `block` 并指出缺口；若依赖服务不可用、又不能取得所需权限，可能返回 `impossible=true`，但这种结论仍应让用户看到理由。

本章 `bash` handler 把 `exit_code=<数字>` 放在输出前面，并保留输出尾部；文件编辑工具要求 `old_text` 在文件里**恰好出现一次**，否则返回错误。这些小改动服务于可核验性：模型和判断器都能看见命令成功与否，编辑不会因重复匹配而悄悄改错位置。`read_file` 支持 `offset` 与 `limit`，便于在有限上下文内核查具体片段。

## 自动继续必须有出口

Goal 本身没有固定的“最多 20 轮”。宿主可用 `MAX_TURNS` 设置主循环的全局轮数上限；Stop hook 连续挡住退出也有默认上限 `DEFAULT_STOP_HOOK_BLOCK_CAP = 8`。达到任一上限，返回 `max_turns` 或 `limit`，但 Goal 仍然活跃，等待用户查看、补充条件、继续或清除。判断器 API 出错同样停止自动续跑并保留条件。这样“请一直干到完成”不会无界消耗资源。

后台任务尤其容易制造假完成。模型启动了测试然后说“已处理”，但测试还在跑，Controller 应返回 `defer`。宿主收到完成结果后调用 `submit_background_result(text)`，它把 `[Background task completed]` 与实际内容加入同一 `messages`，再触发主循环。Workflow 的最终通知若接入该宿主，也只是判断器可读的一条结果消息，并没有自动完成特权。

## 状态恢复的范围

Controller 将每次变化写成 `goal_status` 事件，包含条件、活跃/达成/失败标记、原因、判断次数和时长。`GoalController.restore()` 可从最近一条这样的事件恢复仍活跃的条件；已经达成、失败或清除的条件不重新启动。恢复时轮数、计时和 token 计数重新计算。**本章 CLI 本身没有持久化完整会话**，所以仅有 Goal 事件不足以让模型自动拥有上次所有工具证据；更大的宿主要一起恢复消息、任务状态与文件环境。

## 亲自验证提前停止

先按第 1 节准备原仓库的 `requirements.txt`、`.env`、`ANTHROPIC_API_KEY` 与 `MODEL_ID`。Goal 判断器默认也使用当前模型；若希望单独选择较轻的判断模型，可在 `.env` 中设置 `GOAL_EVALUATOR_MODEL_ID`。这只是模型选择，不会让判断器获得文件或 Shell 工具。配置后先核对该模型能按要求返回严格 JSON，否则判断失败会停止自动续跑并保留 Goal。

先在隔离仓库运行 `python s17_goal_loop/code.py`，输入一个具体目标，例如 `/goal python -m pytest 退出码为 0`。故意让第一次测试失败，观察主模型准备停时判断器是否以缺失证据或失败结果为理由要求继续；修复后记录通过的退出码，再看 `achieved`。接着输入 `/goal` 查看状态，输入新条件验证替换，最后 `/goal clear` 清除。

也可用 `MAX_TURNS=20 python s17_goal_loop/code.py "/goal 修复类型错误，直到 npm run typecheck 退出码为 0"` 设置整体预算。在练习中模拟判断器返回无效 JSON或 API 错误，检查系统是否停止并保留 Goal。不要为了测试无限续跑而在真实项目中让它反复改文件。

## 面试会怎么问

面经问“Agent 怎么判断任务完成，模型说完成但测试没跑怎么办”。回答应区分**本轮停止意愿**与**目标完成证据**：主模型没有工具调用只是拟结束；宿主把用户验收条件保存成状态，在 Stop 点检查命令退出码、文件差异等证据，并可用独立判断器处理较难形式化的条件。未满足就给主模型具体缺口继续，后台结果未到先等待；达到预算、判断错误或目标不可行时交还用户，不能宣称成功。若有高风险动作，完成判断也不能替代执行前授权。
