# 到点再开始：Cron 调度、待交付标记与 Agent 空闲窗口

s11 管的是命令**开始后**如何不阻塞；s12 管的是任务**何时开始**。用户说“每天九点检查一次”后，Harness 必须保存时间表达式，持续观察本地时间，到点将 prompt 放进队列，再在 Agent 空闲时启动一轮工作。它不是把 shell 命令直接交给系统 crontab，而是在 Agent 进程内调度下一次对话。

## 一个 CronJob 记录什么

`CronJob` 存 `id`、五段式 `cron`、到点送给模型的 `prompt`、是否周期重复的 `recurring`、是否落盘的 `durable`，以及 `pending_delivery`、`last_fired`。后两个字段解决两种重复：已经到点但尚未送达时不要重复入队；同一分钟内调度线程每秒检查，也不能连续触发几十次。

表达式按“分钟、小时、日、月、星期”排列，支持 `*`、`*/N`、单值 `N`、范围 `N-M` 与逗号列表。例如 `0 9 * * *` 表示本地时间每天 09:00，`*/5 * * * *` 表示每五分钟。`validate_cron()` 在保存前检查字段数、语法与各字段范围。输入表达式有效，不代表时区或停机补偿自动满足用户预期；本章使用进程所在机器的本地时间。

## 从到期到模型接收

调度线程每秒调用 `poll_due_jobs(moment)`。匹配且本分钟未触发的任务，先设置 `pending_delivery` 和 `last_fired`，保存持久记录成功后才加入内存队列；持久化失败会恢复旧状态，避免出现“队列收到了、磁盘却没有”的半成品。

队列处理线程每 0.2 秒查看是否有待交付任务，并尝试非阻塞取得 `agent_lock`。主 Agent 正在处理用户消息时，它不会同时改同一份 `history`。拿到锁后，`consume_cron_queue()` 取出任务，追加 `[Scheduled] {prompt}` 用户消息，再进入 Agent Loop。模型请求失败时，这些消息从当前会话撤回、任务重新入队；模型成功接收后，一次性任务删除，周期任务清除 `pending_delivery`，等下一次时间匹配。

| 阶段 | 持久或运行时状态 |
| --- | --- |
| 注册 | `schedule_cron` 创建 CronJob；`durable=True` 写 `.scheduled_tasks.json` |
| 到期 | 写 `pending_delivery=true` 与 `last_fired`，再入内存队列 |
| Agent 忙 | 队列保留，等待取得 `agent_lock` |
| 模型调用失败 | 恢复队列，保持待交付状态 |
| 模型成功接收 | 周期任务清待交付标记；一次性任务删除 |

这种设计提供**至少一次交付**：如果模型实际接收 prompt 后，进程在写回确认状态前退出，重启可能再交付一次。定时任务若会发信、下单或部署，下游动作必须有幂等键或明确审批，不能把调度器的“会重试”误当成“只执行一次”。

## 持久化与停机边界

`durable=True` 的任务写入 `.scheduled_tasks.json`，采用临时文件加 `os.replace()` 更新；启动时重新加载，损坏文件会报错。`durable=False` 只在内存中，重启就消失。即使任务定义持久，调度线程也只随 CLI 进程运行：停机期间错过的时点**不会补跑**。如果用户真正要求“电脑和 Agent 都关了仍在九点执行”，需要外部调度器唤醒服务。

队列处理线程中的定时回合没有前台用户可以读 `input()`。实现代码遇到需要交互审批的动作会拒绝，而非让后台线程卡在终端。这也是定时任务适合先安排只读检查、生成报告，不适合未经预授权直接执行高风险操作的原因。本章没有把 s11 的后台命令叠进来：定时 prompt 与异步 shell 是两种独立机制，到 s15 才合在同一个宿主。

## 亲自跑一分钟级实验

运行 `python s12_cron_scheduler/code.py`。先让模型创建“每两分钟运行 `date`，重启后仍保留”的任务；用 `list_crons` 核对表达式与 `durable`，检查 `.scheduled_tasks.json`。保持程序运行至触发时间，观察 `[Scheduled]` 如何进入新一轮 Agent Loop。然后用 `cancel_cron` 取消，再确认下一次不再触发。若要测试一次性提醒，将 `recurring=false`，触发后检查它被移除。

可再测试错误表达式、停机后重启、用户正在与 Agent 对话时到期三种边界。停机测试应预期“恢复定义但不补跑错过的时间”；并发测试应预期等 Agent 空闲，而不是抢同一个消息列表。必要时把时间限制写进测试，避免无限等待定时触发。

## 面试会怎么问

“每天定时让 Agent 检查状态，怎么避免重复执行或与用户当前对话冲突？”可以按本章解释：定义任务与本地时间匹配，`last_fired` 防同一分钟重复入队，`pending_delivery` 表示到期未交付，队列在持有会话锁时注入 prompt。确认写回有崩溃窗口，因此实际交付至少一次，高风险下游用幂等和审批。若问“服务关了还会跑吗”，直接回答本地线程不会；需要系统级调度或持久队列，不夸大 `durable` 字段的作用。
