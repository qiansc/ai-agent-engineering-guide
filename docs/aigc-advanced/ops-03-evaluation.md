# Agent 评测：指标、公开基准与企业任务集

Agent 评测要回答三件事：任务有没有完成，过程是否安全合理，成本与稳定性是否能承受。不同场景需要不同环境，不能拿单一公开榜单替代企业自己的工作流测试。

## 从结果到过程建立指标

| 维度 | 可测指标 | 要追问的问题 |
| --- | --- | --- |
| 任务成功 | success rate、completion、pass@1/pass@k | 失败集中在哪类任务？ |
| 过程质量 | 工具选择/参数准确率、重复调用率、路径合理性 | 成功任务是否绕路或循环？ |
| 安全合规 | 越权率、注入成功率、泄漏率、误拒/误放率 | 高风险动作前是否审批？ |
| 可靠性 | 多次运行稳定性、恢复率、断线恢复率 | 同一任务能否稳定完成？ |
| 成本性能 | token、工具调用、耗时、费用、缓存命中 | 单个成功任务要花多少？ |
| 人机协作 | 审批、接管、review 通过率 | 人审负担是否可接受？ |

只报告“80% 任务成功”远远不够：剩余 20% 的失败是什么，成功路径有没有违规，失败后是否能恢复，人工有没有被大量无意义审批打断，都决定能否上线。

## 公开 Benchmark 分别测什么

| 任务环境 | 常用基准 | 它帮助发现什么 |
| --- | --- | --- |
| 真实仓库 issue 修复 | SWE-bench、Verified、Pro | 读代码、改代码、跑测试的能力 |
| 网页操作 | WebArena | 浏览器理解与多步交互 |
| 桌面 GUI | OSWorld | 跨应用操作和文件管理 |
| 通用助理 | GAIA | 搜索、文件、工具结合的任务 |
| 客服工具与规则 | τ-bench | 用户、工具和政策的多轮交互 |
| 多环境综合 | AgentBench | 跨场景规划与工具使用 |

SWE-bench 来自真实 GitHub issue，Verified 是经过人工筛选的更可靠子集，Pro 提高难度并减少一些常见污染与饱和问题。即便在这类基准表现优秀，也不能推断 Agent 会遵守你公司的私有仓库规范、审批制度、PR review 质量或生产发布流程。WebArena 不等于真实支付站点的安全验收，GAIA 也不覆盖企业 IAM。

## 企业任务集怎样构建

从历史工单、真实客服对话、已关闭 issue、CI 失败、安全事故、业务流程和红队样本中选任务。每条样本保存输入、初始环境、允许动作、期望结果、风险标签与判分方式，并去除不应进入评测环境的敏感数据。

任务集可分五层：每次发布必跑的 smoke、历史失败组成的 regression、权限/注入/隐私构成的 safety、核心业务流程构成的 business，以及长任务与工具异常构成的 stress。样本不宜只有“标准答案”，还应说明哪些过程绝对不可接受。

## Eval Harness 的最小闭环

一套内部评测框架需要任务数据集、可复现的工具/网页/API 模拟环境、固定版本的 Agent Runner、记录完整调用链的 Trace Collector、规则与人工结合的 Evaluator、结果报告，以及与 CI/CD 联动的回归门禁。运行时固定模型、Prompt、Tool、权限策略版本；否则两次得分变化无法归因。

报告至少给出成功/失败、失败阶段、工具和参数错误、权限违规、人工介入、成本耗时及 trace 链接。对不能用程序准确判断的开放式输出，可用模型评审配合人工抽样；确定性的越权问题则优先用规则判断。目标不是给 Agent 一个漂亮总分，而是知道哪项改动让哪类任务变好或变坏。

## 面试会怎么问

**公开基准怎样选？** 先匹配场景：代码看 SWE-bench，网页看 WebArena，桌面看 OSWorld，通用助手看 GAIA，客服工具流程看 τ-bench；随后说明私有权限和流程必须自建任务集。

**企业 Eval Harness 有哪些模块？** 从任务样本、环境模拟、固定版本运行、trace、判分、报告、发布门禁按一次任务走完。

**成功率之外看什么？** 安全、轨迹、稳定性、成本和人工负担都要列出，并用“成功却违规读取”解释为什么。
