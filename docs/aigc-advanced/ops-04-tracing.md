# 用 Trace 找到 Agent 失败的真正环节

Agent 失败可能发生在理解需求、检索上下文、规划、工具调用、读取反馈或最后交付中的任意一步。没有可还原的运行轨迹，就只能看最终答案猜原因，也无法把线上错误转成回归样本。

## 每次运行应记录什么

把一次任务串到同一条 trace 上：`session_id`、`task_id`、用户和租户标识、Agent/Prompt/Tool/Policy 版本、模型参数与 token、每次工具名和参数、返回或错误、耗时、审批与 guardrail 结果、Memory 读写、RAG 检索、子 Agent 交接、后台状态、最终输出和用户反馈。

记录要有数据边界。Secret 不能写入日志，敏感字段应脱敏；不同租户 trace 隔离并设置访问和保留策略。审计需要留下“做了什么和谁批准”，不等于允许把完整私密正文无期限复制到每个观测系统。

## 沿调用链定位失败

| 失败位置 | Trace 中常见线索 | 下一步检查 |
| --- | --- | --- |
| 需求理解 | 计划与用户目标不符 | 用户约束是否进入当前上下文 |
| 上下文 | 没召回关键文档或文件 | 检索、权限过滤、索引新鲜度 |
| 规划 | 漏步骤、顺序错误、缺验证 | 任务拆分与停止条件 |
| 工具选择/参数 | 选错工具、重复调用、参数越界 | Schema、路由、策略 |
| 工具执行 | 超时、权限不足、环境错误 | 重试、凭证、模拟环境 |
| 观察解释 | 工具结果正确但模型误读 | 结果格式和上下文组装 |
| 安全策略 | 误放行或误拒 | 规则与审批记录 |
| 状态/交付 | 错误记忆、断线恢复失败、最终格式错 | 持久化、版本、交付检查 |

分析时先找到第一个偏离预期的节点，再看它如何传播。最终文案错误可能源于检索缺失，也可能是工具返回正确但模型误读；只改最终 Prompt 未必有效。给失败打标签，并保留能重放问题的初始环境和工具 mock。

## 线上监控与告警

业务侧看任务完成、自动化、人工接管、满意度；质量侧看工具成功、参数错误、review 通过和回归；安全侧看权限拒绝、注入拦截、隐私事件；性能侧看 P95/P99 延迟、token、调用次数与单任务成本；系统侧看模型错误、工具超时、队列积压和断线恢复。

任务成功率突降、某工具错误率升高、单任务成本突然暴涨、注入拦截激增或人工接管率异常，都是需要按版本、租户、场景下钻的信号。报警阈值应由真实基线决定，不能从教学示例照抄。

## LLM-as-Judge 与失败回流

开放式回答是否完整、总结是否忠于证据、轨迹是否合理，可交给带明确 rubric 的模型辅助判断。输入应包含证据和 trace，不只给最终答案；要抽样与人工对照，观察一致率并防止候选答案的注入内容影响 Judge。越权、金额、工具白名单这类可确定判断应优先用规则；高风险结论不能只交给 Judge。

失败回流的闭环是：线上 trace 捕获→自动分类→人工抽样复核→高价值样本进入评测集→定位 Prompt、工具、策略、RAG、Memory 或工作流的具体问题→回归验证→灰度上线→监控同类失败。保留原始输入、环境状态、工具 mock、期望行为、风险标签和判分标准，才能稳定复现。许多失败不是模型参数问题，直接拿去微调通常找不到根因。

对于外部模型调用结果难以稳定复现的任务，可在受控环境录制请求、响应与工具交互，离线重放同一条轨迹，再比较不同版本的行为。重放能帮助定位回归，但不能自动证明新版本在真实生产环境也会成功；真实权限、网页变化和业务系统状态仍需单独验证。

## 面试会怎么问

**Trace 应记录哪些字段？** 按身份/版本、模型、工具、权限、状态、输出五类讲，再说明脱敏和租户隔离。

**如何用 Trace 定位失败？** 从首个偏离预期的节点切入，区分没检索到与检索到却误读，并把失败标记转为回归样本。

**LLM-as-Judge 能替代人工吗？** 能辅助开放式评分，但要 rubric、证据、抽样校准；确定性权限判断和高风险合规不能完全依赖它。
