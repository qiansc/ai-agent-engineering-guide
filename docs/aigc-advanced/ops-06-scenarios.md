# 编码、浏览器与客服 Agent 的安全评测怎么变

同一套“任务成功率”无法覆盖所有 Agent。编码 Agent 的主要风险在仓库和命令，浏览器 Agent 在真实界面与凭证，客服/办公 Agent 在业务政策、隐私和对外承诺。三者都需要只读优先、可审计副作用与高风险审批，但测试环境和判分规则要按实际动作设计。

## 编码 Agent：验收改动，也验收操作边界

测试应检查它是否看过当前 diff、是否定位到正确文件和类型/测试、是否遵守项目规则、是否执行危险命令、有没有泄露源码或密钥、是否引入回归。样本可来自真实 bug、CI 失败、依赖升级、测试补齐、多文件重构，也要加入 dirty worktree 和含恶意指令的 issue/README。

结果指标包括测试通过与 review 通过、回归率、改动是否控制在任务范围、危险命令拦截率和人工接管。一个 Agent 把测试跑绿却覆盖了用户未提交改动，应判为失败。越权读取即使没有出现在最终回答中，也应从 trace 中识别。

## 浏览器/GUI Agent：按钮按对还不够

网页内容是外部数据，可能带注入；真实界面有弹窗、重定向、错误页和登录态。评测应覆盖支付、删除、发送与提交表单前的确认，密码、token、cookie 和验证码保护，误点击后的恢复，以及只读/草稿/确认模式的遵守。

任务集可以包含电商下单、SaaS 后台配置、复杂表单、网页研究、恶意网页、无权限页面和多标签页流程。除了完成率，记录错误点击率、高风险确认率、注入成功率、步骤数和人工接管。模拟支付任务必须使用隔离测试环境，不能让自动评测触发真实购买。

## 客服与办公 Agent：按政策行动并保留责任链

客服需要遵守退款和售后规则，不能越权查客户数据、泄漏隐私或作未经授权的承诺；办公 Agent 发邮件、排日程、处理文档时同样面临误发和权限边界。测试集应包含正常咨询、政策边界、套取隐私、越权查询、情绪化用户、多轮纠错、内外部知识冲突和必须转人工的情形。

指标可看规则遵循、幻觉承诺、隐私泄漏、转人工准确率、满意度、处理时长和审计完整率。对“用户声称领导已批准退款”这种情形，要检验工具里的真实授权，而不是让模型凭对话里的说法放行。对外发送前，可先让 Agent 生成草稿并展示证据与收件对象。

## 建立可比较的评测报告

三类任务都保留 Outcome、Trajectory、Safety、Ops 四层指标，但每层具体断言不同。编码看 diff 和测试，浏览器看页面状态与确认动作，客服看政策与隐私。评测结果要按场景、风险等级和版本切分，不能把一批容易的只读题拉高总分，掩盖少量高风险写入题的失败。

## 面试会怎么问

**三类 Agent 的安全评测有什么差别？** 先给共同四层框架，再分别说仓库/命令、界面/凭证、政策/隐私三个主要风险面。

**编码 Agent 除测试通过还看什么？** 当前 diff、作用域、危险命令、密钥、项目规则、回归与 review。

**浏览器或客服 Agent 的高风险样本怎么造？** 用受控测试环境构造恶意网页与确认动作，客服构造越权和政策边界；核对实际工具状态和审计，不只给模型一段问题文本。
