# 记忆的类型，以及怎样与 RAG 配合

说“给 Agent 加记忆”之前，先明确它要记住什么。当前对话、进行中的任务、用户的稳定偏好和外部产品文档，生命周期不同，不能都放进一个向量库。一个实用的分法是同时看保存时长、业务用途和数据结构。

## 按时长区分：对话、工作、情景与长期记忆

| 类型 | 应保存的内容 | 典型生命周期 | 例子 |
| --- | --- | --- | --- |
| 短期记忆 | 最近消息与工具观察 | 当前会话或窗口 | “本轮预算 5000 元” |
| 工作记忆 | 目标、计划、步骤状态和中间结果 | 当前任务 | “机票已选，酒店未订” |
| 情景记忆 | 一次任务的事件轨迹与结果 | 可跨会话按事件检索 | “上次日本七日游最终选东京和京都” |
| 长期记忆 | 稳定偏好、事实、经验或关系 | 跨会话，直到更新或遗忘 | “用户偏好靠窗座位” |

工作记忆在任务结束时可以压缩为一次情景记录；其中反复可用且经确认的事实，才适合进入长期记忆。别把每个临时预算都永久保留，也不要在任务尚未完成时只存一句“旅行规划进行中”。

按用途，还可以拆成个人记忆、任务经验、工具经验、项目规则和安全约束。个人记忆按用户隔离；任务经验可在同项目或相同任务类型中复用；工具经验记录某工具参数模式、超时或失败表现，通常不应写进用户画像。项目规则最好带仓库或目录作用域；用户撤回与禁止保存的约束需要独立治理。

数据结构随用途选择：最近对话可用消息列表，当前任务用结构化状态，稳定偏好用键值或关系表，语义经验用向量索引，实体关系复杂时才考虑图，原始事件用日志保存以便审计和回放。

## Memory 与 RAG 的不同任务

Memory 保存交互中产生、会影响后续行为的偏好、状态与经验。RAG 根据当前问题检索外部知识，例如企业制度、API 手册和产品文档。二者可能都使用向量搜索，但不能因为实现相似就混同数据边界。

| 问题 | 适合放在哪里 | 理由 |
| --- | --- | --- |
| “我不吃香菜” | 用户记忆 | 属于用户明确偏好，需支持查看和删除 |
| 报销制度的最新版本 | RAG 知识库 | 属于机构文档，要按文档版本和权限管理 |
| 本次工单已经查到订单状态 | 任务工作记忆 | 当前流程状态，任务结束后归档 |
| 上次部署失败因 staging 缺少环境变量 | 项目任务经验 | 经过验证后可复用，不应污染个人画像 |

Memory 通常更频繁地随互动增量更新；知识库文档多按发布版本或批量索引更新。但这只是典型情况，不能拿更新频率当唯一分类规则。真正重要的是来源、所有者、作用域、生命周期与写入权限。

## 一次请求如何组合二者

以企业客服处理售后为例：先读取这位客户当前工单状态与允许使用的历史偏好，再根据问题检索现行政策和产品说明。上下文组装时，明确标记“用户当前要求”“历史记忆”“检索文档”“工具实时结果”，并附权限与更新时间。模型提出回复或动作后，校验政策与权限；任务结束才判断哪些新信息值得写回记忆。

一条检索到的网页指令不能升级为系统规则，RAG 文档也不能自动变成客户的个人偏好。旧记忆与当前用户陈述冲突时，应优先处理冲突，而非把两者平铺给模型。

## 面试会怎么问

**短期、工作、长期和情景记忆怎么区分？** 用同一个旅行任务贯穿四类，再说明“工作状态完成后如何归档和提炼”，能展示生命周期理解。

**个人、任务、工具记忆分别解决什么？** 除用途外，说清作用域：用户隐私不进共享经验库，工具故障不写进个人画像。

**Memory 与 RAG 有什么区别、如何结合？** 从数据来源和治理责任切入，用“记住用户偏好 + 检索当前制度”的流程回答；两者都可向量化，但身份和权限不能混。
