# 上下文窗口满了，怎样保住任务线索

长任务的窗口常被浏览器页面、仓库文件、工具输出、测试日志和多轮推理填满。处理溢出时，目标不是让模型看到最多文字，而是保住它下一步决策和任务恢复所需的事实。若只把旧消息全部丢掉，Agent 会忘记用户目标；若一律做模糊摘要，又可能漏掉错误堆栈、文件路径或审批状态。

## 三种压缩方式怎么选

| 方法 | 做法 | 适用 | 主要代价 |
| --- | --- | --- | --- |
| 滑动窗口 | 只保留最近若干轮 | 简短连续对话 | 早期约束可能丢失 |
| 摘要压缩 | 把较早历史整理为任务摘要 | 长任务、咨询与编码 | 摘要生成有成本，也可能漏关键细节 |
| 语义压缩 | 选择高相关片段并去冗余 | 文档分析、研究 | 可能破坏时序，规则更复杂 |

选择性保留针对“哪些消息留下”；内容裁剪针对“一条很长的消息保留哪部分”。测试日志可以保留失败堆栈及上下文，浏览器 DOM 保留目标节点和必要邻近内容，代码只读相关函数、类型、调用方和测试。但裁剪要有可观测规则：如果提炼后的片段不足以回答问题，应能回到原始材料继续读。

一份能恢复工作的摘要应包括用户目标、当前约束、已完成步骤、关键决策、改动文件、工具结果、失败尝试、未解决问题、待审批动作和下一步。只写“用户让继续完成”没有恢复价值。对高风险动作，原始证据坐标和审批对象要保留，不能仅剩自然语言概括。

## Context Engine 的三个动作

`retrieve` 找到当前相关的记忆、RAG 文档、仓库文件与历史工具结果；`assemble` 按权限、时效、可信度和 token 预算组装这一轮请求；`compact` 在接近预算时把低价值历史压缩或移出，并保存可恢复状态。三者循环进行，不是只在溢出报错后补救。

一个简化的组装顺序是：先放平台和安全规则、用户当前目标与约束，再放任务状态和关键错误，然后注入经过过滤的记忆、检索证据和工具观察。外部网页与工具返回是数据，不得借“引用了文档”覆盖更高优先级指令。长期记忆也不能覆盖用户当下的明确更改。

## 编码 Agent 的额外难题

代码库不只大，还会在任务中持续变化。相关信息可能分散在实现、类型、测试、配置、文档和用户未提交改动里。先用文件索引或 `rg` 定位，再读关键片段；写入前检查当前 diff，避免覆盖用户工作。修改后旧代码片段应标记为过期，必要时重读。失败日志优先保留错误附近，完整日志仍要可回查。

长任务压缩时应明确记录改过哪些文件、验证命令与结果、尚未处理的失败，以及下一步需要哪份新鲜上下文。子 Agent 返回结论、证据位置与未解决点即可，不必把整个探索对话倒回主 Agent。这里的核心是相关性、新鲜度和可验证性：读到一份旧文件，往往比少读一些闲杂材料更危险。

## 面试会怎么问

**上下文窗口溢出怎么办？** 不只答“摘要”，要比较窗口、摘要、语义压缩、裁剪、外部记忆和更长窗口的代价，并说明哪些事实不能压没。

**Context Engine 的 retrieve、assemble、compact 怎样协同？** 先检索、再按权限与预算组装、接近上限时结构化压缩；每轮工具反馈后可再次执行。

**编码 Agent 有什么特殊性？** 说出跨文件关联、dirty worktree、文件新鲜度、日志裁剪和测试验证。保留 diff 与失败定位，而不是永久装入全仓库。
