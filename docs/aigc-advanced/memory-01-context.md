# 记忆与上下文工程：让 Agent 连续完成任务

大模型每次推理只能处理当前请求里提供的信息。一个 Agent 要连续工作，就需要保存任务进度，在下一轮找回相关信息，并决定哪些内容真正值得放进模型窗口。保存与更新是记忆系统的职责；为当前一步选择、排序、压缩信息，则是上下文工程的职责。

例如，一个旅行助手要记住用户长期偏好的靠窗座位，也要暂存这次行程的预算和订票进度；查询实时航班政策时还要检索外部资料。把三类信息直接堆成聊天历史，既贵又容易把旧限制当成当前要求。

## Prompt 与 Context 各管什么

| 维度 | Prompt Engineering | Context Engineering |
| --- | --- | --- |
| 主要问题 | 指令怎样写得清楚、可执行 | 这一轮模型应看到哪些信息 |
| 常见对象 | 角色、规则、输出格式、示例 | 消息历史、任务状态、工具结果、记忆、检索文档、文件 |
| 变化节奏 | 可作为相对稳定的配置 | 随任务、工具反馈和用户新要求不断变化 |
| 典型失误 | 指令含糊或互相冲突 | 关键文件没读到、过期事实被注入、窗口被日志挤满 |

两者并非互斥：清楚的规则需要放进合适位置，动态检索的事实也必须带上来源和可信度。一次请求可按“固定安全规则—用户当前目标—任务状态—相关记忆—外部证据—工具观察”组织；具体排序还要遵守平台的指令优先级，不能让网页文本或工具返回改写系统规则。

## 聊天历史何时成为记忆

普通聊天历史按时间保留原始消息，能支持近几轮接话，却不保证未来能准确找到一条偏好。Agent Memory 要额外做四件事：选择值得保存的信息，标注作用域和来源，为检索建立结构，以及在事实变化时更新或删除。

假设用户上周说“以后用英文回答”，今天改成“这个项目都用中文”。系统不能仅把两句话一同塞给模型，让模型猜哪条有效。记忆记录应区分全局偏好与项目偏好，保留更新时间和用户确认信息；当前明确要求优先，必要时提示用户确认是否覆盖长期偏好。另一个例子是工具返回“某 API 可能超时”，这只是一条观察，不能直接写成“用户偏好不用此 API”。

聊天记录可以成为提取记忆的原始材料，也可以保留为审计轨迹；它本身并不等于经过治理的记忆。长期记忆至少应支持查、改、删和隔离，而不只是保存一个不断变长的摘要。

## 为什么长上下文仍不够

更大的窗口允许模型暂时读入更多材料，但每轮重放大量历史会增加 token、延迟和成本。长文中的关键证据还可能被重复日志与过期尝试淹没。窗口也无法自动解决跨会话持久化、用户删除、权限隔离、冲突更新和有效期。

较稳妥的组合是：当前任务的原始文件和关键工具结果放进窗口；跨会话稳定信息留在有权限边界的记忆层；企业手册等外部知识通过检索按需提供；历史长任务压缩为可恢复的结构化状态。每次检索要知道材料属于哪个用户、任务和项目，避免语义相近却作用域错误的信息进入模型。

设计时可从一条可验证的任务开始：记录模型漏掉了什么，再判断是指令没写清、检索没找对、记忆没保存，还是组装时被裁掉。不要把所有质量问题都归因于“模型不够长”。

## 面试会怎么问

**Prompt Engineering 与 Context Engineering 有什么区别？** 先说前者优化指令表达，后者动态选择当前可见信息，再用“长任务工具日志压缩，但保留用户约束和错误堆栈”的例子说明；补充可信度、权限和 token 预算。

**Agent Memory 与普通聊天历史有什么区别？** 从选择性写入、结构化作用域、检索、更新遗忘四点回答。原始聊天可作为来源，但不能代替可治理的长期记忆。

**为什么不直接使用长上下文模型？** 除成本和注意力外，重点讲跨会话、冲突、删除与租户隔离。回答不应把长上下文说成无用，它适合承载当前高价值原始材料。
