# Agent 为什么要评测行动过程

普通聊天产品的错误多表现为回答不准；Agent 还能读文件、发消息、修改数据和运行命令。最终答案看起来正确，过程也可能访问过无关隐私、跳过审批或产生不可逆副作用。所以评测对象必须从“答案”扩大到“模型、工具、权限、状态、流程与人工协作”。

## 风险边界从说话扩展到行动

| 维度 | 聊天应用 | Agent 应用 |
| --- | --- | --- |
| 输出 | 主要是文本 | 文本、工具调用、外部动作 |
| 典型错误 | 幻觉、不当内容 | 误发、误删、越权、泄漏、错误持久记忆 |
| 运行范围 | 多为一次会话 | 多步骤、后台任务、跨会话 |
| 攻击面 | 用户输入 | 用户、网页、邮件、文件、RAG、工具返回、插件 |
| 审计 | 可重点查看问答 | 必须还原调用、授权、状态和副作用 |

编码 Agent 可能运行危险命令；浏览器 Agent 可能在钓鱼页输入凭证；客服 Agent 可能承诺了政策不允许的退款；个人助理可能把私聊写进共享记忆。防护不能只检查最终文案，还要约束工具调用前的决策。

## 评测至少覆盖四层

1. **Outcome：**任务是否完成，最终产物是否正确。
2. **Trajectory：**工具选择、参数、顺序、重复与循环是否合理。
3. **Safety：**是否越权、泄露、误写，被注入或绕过审批。
4. **Ops：**成本、延迟、稳定性、断线恢复与人工接管是否可接受。

例如编码 Agent 修好了测试，但顺手读取了无关密钥文件；只看通过率会判成功，安全评测则必须失败。另一个 Agent 全程合规却反复调用昂贵工具、最终超时，业务上也无法交付。评测报告应同时呈现成功率、失败原因、违规率、耗时和成本，不要用单一分数遮住问题。

## AgentOps 管哪些事情

MLOps 管训练、部署、数据和模型监控；LLMOps 进一步管理模型调用、Prompt、RAG、评测与 token 成本；AgentOps 面向任务和行动，还要管理工具权限、运行轨迹、会话与任务状态、人工审批、后台运行、多 Agent 链路、Memory 读写、灰度、回滚和事故响应。这些范围可以重叠，并非三套必须独立购买的系统。

一次任务应能复现“谁提出目标—哪个 Agent/版本接受任务—用什么上下文—选了什么工具和参数—策略为什么批准—外部系统返回什么—状态怎样变化—最终交付什么”。能记录这条链，才能把一次失败转成可重放的测试。

## 面试会怎么问

**Agent 和 Chatbot 的风险有什么不同？** 从副作用和权限切入，举误发邮件或越权查询例子，说明安全从文本输出延伸到工具与状态。

**为什么不能只看最终答案？** 用“答对但读了密钥”说明 Outcome 与 Trajectory/Safety 分离，再补充成本与可恢复性。

**AgentOps 和 LLMOps 有什么区别？** 说出 AgentOps 多了任务状态、工具链、授权、人工接管和事故处置；它建立在模型运维能力之上。
