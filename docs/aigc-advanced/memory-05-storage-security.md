# 长期记忆的存储、共享与隐私边界

长期记忆同时需要精确字段查询、语义检索、权限判断、版本更新和删除审计，通常无法由单个“万能数据库”负责。选择存储前先问：这条记录属于谁、要怎样找、何时失效、谁能更改、用户要求删除时会影响哪些副本。

## 各类存储的分工

| 层 | 常放什么 | 优势 | 需要补的能力 |
| --- | --- | --- | --- |
| 关系数据库 | 画像字段、记忆元数据、权限、版本 | 事务与精确查询 | 语义召回 |
| 向量索引 | 文本记忆和任务经验嵌入 | 语义相似搜索 | 精确权限、更新删除与审计 |
| 图数据库 | 人、项目、实体关系 | 关系与路径查询 | 建模及维护成本 |
| 事件日志 | 原始消息、工具调用、变更事件 | 审计、回放 | 不宜直接承载在线相关性检索 |
| 对象存储 | 长文档、附件、完整 transcript | 容量与成本 | 需要索引和权限层 |
| 缓存 | 当前任务状态、热点记忆 | 低延迟 | 失效与持久化机制 |

一种常见组合是事件日志留原始轨迹，关系库管记忆记录和权限，向量索引帮助召回，必要时用图表达复杂关系，长文件放对象存储，热点结果进入缓存。产品可用 PostgreSQL/pgvector、Milvus、Neo4j、S3/OSS、Redis 等实现；这些是候选例子，不表示每个产品都必须部署全套。数据模型与删除策略要先定，技术选型再跟上。

## 跨 Agent 共享，先分域再复用

多 Agent 协作可复用任务经验和工具经验，但个人偏好默认不应全局共享。可以按 `tenant_id / user_id / project_id / task_type / agent_role` 分域，为搜索、添加、更新、删除、摘要和合并提供统一 API。检索必须先按授权作用域过滤，再做相似度与重排；每条共享记忆记录来源 Agent、任务、时间和置信度。只有经过验证的经验才进入团队级空间。

例如一个编码 Agent 总结“该仓库修改配置后要跑特定测试”，可经核实后放入项目经验；用户告诉私人助理“对坚果过敏”，不应被其他员工的办公 Agent 检出。把所有 Agent 直接接到同一个全局向量库会产生跨用户串线和污染，哪怕检索结果在语义上很相关。

## 污染与隐私风险如何出现

污染包括模型猜测被写成事实、过期政策继续使用、恶意网页指令被记成规则，以及 RAG 文档内容被误当成用户偏好。隐私问题包括密码和 token 被长期保存、租户间检索串线、敏感信息在共享摘要中传播，以及不透明的个性化使用让用户失去控制感。

防护要覆盖写入和读取两端：写入前进行敏感信息检测、来源标注、用户意图与作用域判断；读取前做身份、租户和资源过滤；注入模型时标明可信级别。用户应能查看、修改和删除个人记忆，高风险写入可要求确认或审批。TTL、低价值清理和污染率监测保证长期运行后质量不会持续下降。

企业系统还需要 RBAC/ABAC、记忆版本、审计日志、备份与合规删除，并让 Memory 与 RAG、Session Store、Tool Trace 各有边界。值得监控的指标包括写入准确率、检索命中率、错误记忆率、隐私违规率、检索延迟、用户删除处理时延，以及记忆对任务成功率的实际贡献。

## 面试会怎么问

**长期记忆选什么数据库？** 先说数据需求和删除权限，再说明关系库管结构与授权、向量索引管语义、日志管回放，图数据库仅在关系查询有真实需求时加入。

**跨 Agent 共享怎么防串线？** 答出用户/租户/项目分域、检索前过滤、来源和质量审核，强调“共享经验”和“共享隐私”不是一回事。

**企业 Memory 最重要的工程能力？** 除检索效果，还要说 CRUD、TTL、版本、PII、审计、备份与合规删除；用错误记忆率和跨租户泄露测试验收。
