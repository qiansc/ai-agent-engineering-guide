# 从 PoC 到生产：选对场景并安排人审

Agent 项目能在演示里跑通，不等于用户愿意长期使用，更不等于能在真实数据和权限下安全运行。产品落地应分阶段回答：能不能做、用户是否受益、能否稳定合规、能否跨团队复用。

## 六个阶段各验什么

1. **场景筛选：**找高频、低风险、可验证且工具数据可得的任务。
2. **PoC：**用有限数据和工具验证基本可行性。
3. **Pilot：**让小范围真实用户试用，收集失败和人工纠错。
4. **受控生产：**接入身份、审批、审计、评测、监控与灰度，限制自动化边界。
5. **规模化：**扩展团队、工具、知识与场景，观察成本和故障是否线性增长。
6. **平台化：**沉淀共享工具、知识、任务集、模板、Agent 与 Skill 市场。

PoC 主要验证“能不能做”，Pilot 验证“用户愿不愿用”，生产验证“长期能否稳定安全地做”，平台化验证“是否真能复用”。阶段可因业务而调整，但不能跳过真实用户和安全评测的验证。

## 四类常见产品场景

| 场景 | 价值 | 主要风险 | 首要能力 |
| --- | --- | --- | --- |
| 客服 | 统一知识回答，减轻重复处理 | 错误承诺、隐私 | 政策 RAG、工单、转人工 |
| 数据分析 | 降低取数与分析门槛 | 越权 SQL、错误结论 | 数据权限、查询验证、图表 |
| 编码 | 缩短研发重复劳动 | 改错文件、回归 | 仓库理解、diff、测试、CI |
| 办公 | 自动处理文档、邮件、日程 | 误发、权限冲突 | 草稿预览、收件确认、审批 |

落地难度取决于结果是否可判对错、工具副作用能否控制、数据授权是否清晰、用户是否能快速审查和失败成本是否可承受。早期通常适合只读问答、回复建议、代码 review 或报告草稿；不必急于自动发送、支付和部署。

## 怎样判断一个场景值不值得做

可以逐项评估频率、节省时间或新增价值、结果可验证性、错误风险与可回滚性、工具完备度、权限清晰度、人审成本、历史样本可用性。高频、低风险、已有 SOP、可从历史数据构造任务集的场景优先。低频高风险、结果高度主观、权限边界不清的场景应慎重；即使模型能写出好答案，也未必值得自动化。

低代码 Builder 很适合知识问答、客服、简单表单、内容生成、内部助手与快速 PoC，因为业务人员可以维护话术和流程。复杂状态机、深度仓库操作、核心生产写入和强定制多租户治理往往需要更明确的工程实现。低代码并不免除评测、权限和回滚。

## Human-in-the-loop 放在哪

人审不是失败后才出现的兜底。可在开始前确认目标与权限、计划生成后确认方向、高风险工具执行前审批、结果生成后 review、低置信或异常时接管。界面应说明 Agent 将做什么、用哪些数据和工具，展示 diff、草稿或预览，并允许批准、拒绝、修改、追问。

不必每一步弹窗。低风险动作可自动完成，中风险抽样复核，高风险由人确认；风险等级要结合具体资源与副作用，而不是只按工具名称。审批记录留在 trace 中，以便之后解释责任和恢复任务。

## 面试会怎么问

**PoC 到生产有哪些阶段？** 逐阶段给验收问题，并强调 Pilot 用户反馈与受控生产治理。

**怎样选 Agent 场景？** 用频率、价值、可验证性、风险、工具、权限、人审、样本八维判断；别只说“高 ROI”。

**HITL 怎样设计？** 讲决策节点、预览内容、approve/reject/edit 和风险分级；不是把所有动作都交给用户点确认。
