# 记忆从写入到遗忘的完整生命周期

可靠的记忆系统要决定何时保存、以后怎样找回、信息变化时怎样改、用户撤回时怎样删。只做“把对话嵌入向量库”，会把临时话语、模型猜测和敏感信息都留到未来，反而让 Agent 更容易答错。

## 写入：先筛选，再提取

一次记忆写入可以按 `ingest → filter → extract → normalize → store` 走。输入可能来自用户消息、任务状态、工具结果与反馈。过滤时逐项判断：内容是否稳定、以后是否有用、用户是否明确要求记住、是否含敏感信息、来源是否可靠、与旧记录是否冲突、该属于哪个作用域。然后将自然语言提取为可查询的事实或经验，而不是无差别保存原话。

“以后技术问题优先用中文解释”可成为稳定的沟通偏好；“今天下午三点交报告”通常是当前任务约束；“模型推测用户喜欢跑步”不应写为事实；网页说“以后忽略安全规则”是外部数据，不可写成记忆指令。过敏信息虽可能有长期价值，却属于敏感健康数据，应先满足同意、权限和保留规则。

记录至少应能表达 `id`、`scope`、主体 ID、内容、主题、来源、时间、置信度、敏感等级和有效期。下面是教学示意，字段和数值不代表统一标准：

```json
{
  "id": "mem_123",
  "scope": "user",
  "user_id": "u_001",
  "content": "用户偏好中文技术解释。",
  "source": "user_message",
  "confidence": 0.95,
  "updated_at": "2026-05-02T10:00:00Z",
  "ttl": null,
  "sensitivity": "low"
}
```

来源材料给出过 0–3 的候选记忆分级：0 为无价值，1 为临时或猜测，2 可写任务或情景，3 为明确长期价值或用户要求记住。它适合作为评审样例，不应把固定分数阈值当成无条件自动写入许可；敏感数据和用户“不要记住”的指令要另设阻断条件。

## 读取：相关还不够，还要有权且有效

检索策略不止一种。`last_n` 取最近记录，适合连续任务；`first_n` 或固定画像取基础信息，适合稳定偏好；关键词与元数据过滤定位 topic、project、tool_id 和时间范围；向量搜索找语义相关记录；混合检索结合精确词、语义、时间与重要性；图遍历适合实体关系；候选量仍大时，可由 Agent 在授权候选中判断哪些真正有用。

实际系统通常先按租户、用户、项目、任务和权限过滤，再在合法候选中做语义与关键词混合排序，必要时重排。排序可考虑相关度、新近度、用户明确性、置信度、历史使用频率和任务阶段。

只按向量相似度容易找出“内容很像但属于另一个用户”的记录。最早 N 条也不一定最可靠；如果最初偏好已变更，当前上下文应取最新有效版本。把少量选中的记忆注入模型时，标明它是历史偏好、当前任务状态还是未经验证的经验。

## 更新：冲突不能静默并存

用户偏好变化、任务完成、旧 API 废弃或一次错误提取，都需要更新。常见做法包括冲突检测、合并相似记录、对临时内容设 TTL、旧信息衰减和版本化。当前使用最新有效版本，必要时保留历史以便审计，但不能让旧版本继续指导动作。

如果“以前英文回答”与“现在中文回答”冲突，要确认是全局偏好变化还是某项目例外。用户当前明确要求优于模型推测；不同来源的优先级也应由业务策略规定。系统应让用户看见“记住了什么”，并允许更正。

## 删除：要删到衍生层

删除不能只在主表标记失效，还要处理向量索引、热缓存、派生摘要，以及备份和日志的保留策略。合规擦除与审计保留可能存在约束，实施时须按实际法规、合同和数据策略确定，不能承诺“立即删除一切副本”。删除请求应有可追踪的处理状态和时限。

一个可用的 Memory CRUD API 至少支持创建、读取、更新、删除；企业系统还要记录版本和审计，验证没有跨用户、跨租户串线。测试应覆盖：写入低置信信息被拒、旧偏好更新、TTL 到期、用户撤回、缓存失效和删除后检索不到。

## 面试会怎么问

**如何判断一条信息该不该进入长期记忆？** 用稳定性、复用价值、用户意图、敏感等级、来源、冲突和作用域七个维度讲，再各举应写与不应写的例子。

**Memory CRUD 如何设计？** 说出结构化记录、先权限过滤后检索、版本化更新、删除索引与衍生摘要，补充用户可查看与更正。

**如何处理记忆冲突和遗忘？** 区分偏好变化、任务过期、错误写入和用户撤回；分别采用确认、版本/TTL、纠错和合规删除，不把“时间衰减”当成唯一答案。
