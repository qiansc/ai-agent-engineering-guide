# 企业平台的成本、发布、审计与长任务

单次 LLM 调用的成本容易估算，Agent 却可能多轮推理、反复查询、等待审批，甚至后台运行数小时。平台要同时给出预算、超时、状态恢复、版本与审计，让业务方知道一次成功任务的真实成本，也让失败任务可以被接管和回滚。

## 模型路由与任务成本

模型路由可以结合任务难度、敏感等级、时延目标、预算和供应商可用性。分类与抽取可先评估小模型，复杂规划或代码修复评估更强模型，涉密数据按企业政策选择私有模型或允许的部署区域。失败时的 fallback 必须仍满足权限和数据边界，不能为了可用性把机密请求送到未经授权的服务。

平台可用上下文压缩、检索与工具缓存、最大轮数和调用次数、异步任务、租户配额控制成本。延迟方面可并行独立工具调用、流式反馈、预取、超时和熔断；可靠性依赖状态持久化、幂等键、重试退避和人工接管。指标最好是 `cost per successful task`，纳入模型、工具、失败重试和人工审批时间，而非只看 token 单价。

## 把发布能力产品化

一个版本包可能包含 Prompt、模型、Tool Schema、MCP Server、workflow、Memory/Guardrail 策略、Skill、RAG index 和权限配置。发布流水线做版本打包→smoke eval→regression eval→安全扫描→小流量灰度→指标观察→扩量或回滚。灰度可按用户、租户、团队、任务或工具权限进行。

每次任务必须知道使用了哪个版本组合。长任务运行中版本变化时，旧状态如何被新 workflow 读取需要明确兼容策略；回滚 Prompt 也不会自动撤销已经发出的邮件或工单，因此外部动作要能对账和补偿。平台提供回滚开关只是入口，业务系统的撤销能力需要单独设计。

## 可观测性与审计的不同用途

可观测性服务于运行质量：请求量、任务与工具成功率、P95/P99 延迟、token 与费用、人工接管、失败类型、guardrail 拦截和满意度。审计服务于责任追踪：谁发起、哪个 Agent 执行、使用哪个模型与 Prompt、访问了什么资源、权限如何批准、产生了什么副作用、交付了什么。

平台应支持按任务、用户、租户和版本查询 trace，对敏感字段脱敏，设置日志保留与导出权限，并提供安全告警。审计日志不能无边界地保存 secret；同时不能因过度脱敏而无法判断实际访问对象。字段设计需由安全与业务责任共同决定。

## 长任务需要状态与事件

长文档分析、仓库扫描、报表、多网页调研、批量工单和多媒体处理，都不适合把全部过程压进一次同步 HTTP 请求。平台为任务分配 ID，维护 `queued → running → waiting_approval → succeeded/failed/cancelled/timeout` 等状态，提供队列、进度事件、断点恢复、取消、后台通知、结果归档和幂等键。

状态迁移取决于任务行为：等待审批后可能回到运行；超时是否允许重试，要先查外部副作用是否已发生。用户看到的进度最好对应真实检查点，而不是模型编造的百分比。任务、事件、状态架构能让人暂停和恢复 Agent，避免“页面关了就不知道发生了什么”。

## 面试会怎么问

**平台怎样治理成本和延迟？** 从路由、预算、缓存、并行、超时、fallback 到成功任务总成本串起来，并说明敏感数据不能为 fallback 越权。

**发布灰度回滚怎样实现？** 回答联合版本、固定评测、按群灰度、任务状态兼容和外部副作用补偿。

**为何长任务要任务系统？** 说出状态机、检查点、审批、取消、幂等和通知，区分同步对话与可恢复工作流。
