# Agent 从只读试运行到自动执行

Agent 的上线不是把一个开关从关拨到开，而是逐步开放数据和动作权限。越容易产生外部副作用，越需要可验证任务、预览、审批、审计和补偿。生产交付还要把模型、Prompt、工具、工作流和策略视为一组联合版本，否则失败时不知道该回滚什么。

## 自动化程度分阶段放开

| 阶段 | Agent 可以做什么 | 人的角色 |
| --- | --- | --- |
| 只读 | 搜索、读取、解释、总结 | 审查答案，不允许写入 |
| 建议 | 生成草稿、patch、SQL、计划 | 决定是否执行 |
| 受控写入 | 在限定范围修改文件、建工单、存草稿 | 看预览或 diff，批准高风险动作 |
| 半自动 | 稳定流程的低风险步骤自动执行 | 审批高风险节点，接管异常 |
| 自动执行 | 在充分评测且可回滚的边界内完成任务 | 监控、抽查、处理事故 |

编码 Agent 可先做 review，再生成 patch，再在分支内受控写入，最后才考虑自动 PR；客服可先查知识库，再给回复建议，稳定低风险模板经过评测后再自动发送。金融、医疗、法律等高风险场景可能长期保持“建议 + 人审”，不应把全面自动执行当成产品成熟的唯一标志。

## 发布与灰度管理的是一组配置

发布对象包括模型版本、system prompt、Tool Schema、MCP Server、Skill、Memory 策略、Guardrail、workflow 图、权限配置和相关知识索引。每次运行保存这组版本的标识，便于复现和回滚。

发布前跑 smoke 与历史失败回归，再按内部用户、小租户、任务类型或流量比例灰度。新旧版本比较任务成功、安全、人工接管、延迟和成本；关键指标恶化时停止扩量并回滚。工作流中途升级可能遇到旧状态与新状态不兼容，需要状态迁移或让旧任务跑完。外部副作用不一定能通过回滚代码撤销：发出的邮件、创建的订单要有对账、撤销或补偿办法。

## 给单个任务设预算

成本治理可通过模型路由、上下文压缩、工具/RAG 缓存、步数与调用次数限制、批处理和异步执行完成；延迟治理可用并行工具、流式响应、预取、快速失败和超时；可靠性依靠幂等键、退避重试、备用模型/工具、状态持久化与人工接管。

一个任务可以明确 token、工具调用、时间、风险和人工审批预算。例如“最多 12 次工具调用、5 分钟、不允许生产写入”是一组教学示例，不是通用阈值。预算必须按实际任务风险和服务等级制定。监控最好看每个成功任务的总成本，纳入重试、工具和人工时间，而非只看模型 token 单价。

## 事故发生时怎样处置

误发消息、错误修改数据、越权访问、泄漏、危险命令、错误长期记忆和成本失控都属于 Agent 事故。处理顺序是发现异常→暂停相关 Agent/工具/版本或权限→用 trace 还原输入、上下文、授权和动作→确定受影响用户与系统→回滚配置并尽可能撤销或补偿副作用→通知相关方→复盘与补充回归样本。

审计记录至少能回答：谁发起、哪个 Agent/版本执行、调用了什么工具和参数、审批如何发生、结果是什么、是否产生外部副作用。具体日志保留与通知义务由组织政策和适用法规决定，不能以“模型不确定”免除责任。

## 面试会怎么问

**Agent 怎样分阶段上线？** 从只读到建议、受控写入、半自动和自动执行，逐级说明授权、可验证性和人审位置。

**发布、灰度、回滚如何做？** 回答联合版本、固定评测集、分群灰度、关键指标、状态兼容和外部动作补偿。

**成本与事故如何治理？** 把预算、超时、幂等与人工接管串成运行闭环；事故先止血再定位和补偿，最后回流样本。
