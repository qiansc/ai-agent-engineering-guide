# Skill 与项目记忆：按需加载工作方法

有些上下文来自任务过程，有些是团队预先写好的工作方法。Skill 把某类任务的说明、流程、模板、参考资料和脚本放在一起，Agent 需要时才加载。项目记忆文件则告诉编码 Agent 当前仓库的目录、命令、约束与常见陷阱。两者都能减少每次重新摸索，但都必须有作用域和更新责任。

## 四种能力不要混用

| 概念 | 它解决的问题 | 例子 |
| --- | --- | --- |
| Tool | 能执行什么动作 | 读文件、查数据库、运行测试 |
| Skill | 某类任务该怎样做 | 代码审查步骤、论文阅读流程 |
| Memory | 过去发生过什么、用户偏好什么 | 上次失败原因、用户表达偏好 |
| RAG | 当前问题要查哪份外部知识 | 产品说明、API 手册、制度 |

一个代码审查任务可能同时使用四者：Tool 读 diff 和跑测试，Skill 提供审查检查项，Memory 帮助回忆该项目曾出现的缺陷，RAG 查询框架 API 文档。Skill 不是工具本身；它可能引用脚本，但脚本运行仍要经过工具权限与审批。

## 为什么渐进式加载有效

如果把所有任务指南永久塞进系统提示词，窗口会被大量不相关规则占满，规则还可能互相冲突。渐进式做法是先展示能力摘要和适用条件，确认当前任务匹配后再加载主说明，需要时进一步读取参考资料或脚本。一个典型目录如下：

```text
my-skill/
├── SKILL.md
├── references/
└── scripts/
```

这种组织使专业流程可在多个 Agent 之间复用，也方便单独版本化和审核。决定是否加载时，要看任务类型与作用域；加载后仍要遵守更高优先级的用户要求和工具授权，不能因为 Skill 附带脚本就自动取得写入权限。

## 项目记忆文件怎样发挥作用

仓库级文件可记录项目简介、目录结构、构建与测试命令、代码风格、模块边界、禁用操作、安全要求和提交流程。编码 Agent 进入仓库后按目录作用域读取对应规则，再结合实际代码、配置和 CI 验证。比如文件写着“运行某测试命令”，而当前 `package.json` 或脚本已改名，就应核查差异，不盲信旧说明。

多层目录中的规则要有明确适用范围：根目录管全局，子项目文件补充本地细则；子目录规则不能被无关根目录文本随意覆盖。任务过程中还要关注用户未提交改动，不能把项目记忆当成覆盖用户当前工作的许可。规则文件可能过期，因此需有维护 owner 和更新机制。

## 把它放进长期个人助理

一个长期运行的助理可以按八层设计，逐层解释它处理的数据：

1. **事件采集：**接收用户消息、日程、任务、工具调用、反馈，以及用户明确的“记住/别记住”要求。
2. **记忆提取：**从事件中识别偏好、事实、约束、关系、任务状态和成功/失败经验，不把模型猜测自动写为事实。
3. **安全过滤：**检查 PII、敏感等级、用户同意、来源可信度与作用域，决定拒绝、脱敏或候选写入。
4. **存储：**用户画像放结构化库，语义片段建索引，复杂关系可用图，原始事件保留在受控日志中。
5. **检索：**按当前任务、权限、时间、主题与语义组合召回，避免另一个用户或已过期的偏好混入。
6. **上下文组装：**只选择当前一步需要的少量记忆，并区分它与 RAG 外部资料和用户当前指令。
7. **更新遗忘：**合并冲突、设置 TTL、处理用户删除及衍生索引擦除。
8. **可观测与控制：**让用户检查“系统记住了什么”，记录写入准确率、命中与隐私风险，并允许更正和撤回。

任务状态留在工作记忆；专业流程由 Skill 按需加载；外部事实通过 RAG 查询。这样个人助理不必把所有历史都变成永久画像。

落地时建议先选一个可衡量的场景，例如跨会话旅行规划。比较启用记忆前后的任务完成、错误偏好使用和人工纠错次数，同时验证删除后不再召回。这样才能判断系统是真的更会帮忙，还是只是存了更多数据。

## 面试会怎么问

**Skill、Tool、Memory、RAG 有何区别？** 按“动作、方法、过去、外部知识”解释，再用代码审查场景串起来；补充 Skill 的脚本仍受工具权限约束。

**项目记忆文件怎样帮助编码 Agent？** 说清减少重复探索、统一命令和边界，也强调目录作用域、过期校验和不覆盖用户改动。

**怎样设计长期个人助理记忆？** 从采集到删除说完整生命周期，重点展开用户控制权、隐私、记忆质量和当前窗口预算，不止答“向量数据库”。
