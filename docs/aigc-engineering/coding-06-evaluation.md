# 评估编码 Agent：修好了，还要看怎样修好的

一条 issue 的测试通过，只能说明某个检查通过。要判断编码 Agent 对团队是否有用，还要看它是否改对范围、是否覆盖边界情形、是否破坏用户已有改动、是否遵守权限，以及花了多少时间与费用。真实生产评测因此需要同时保存最终产物和执行轨迹。

## 从任务结果到工程质量

结果指标包括 issue 修复率、相关测试通过率、编译/lint/类型检查、人工 review 通过率和是否引入回归。工程质量要看 diff 是否过大、是否修改了无关模块、测试是否能解释需求，以及错误恢复是否可靠。成本指标有任务耗时、模型 token、工具调用次数、费用和人工接管次数。安全指标则看越权尝试、危险命令、敏感信息暴露和写操作的重复执行。

SWE-bench 让模型面对真实 GitHub issue，是重要的共同基线；但它不能代替企业自己的任务集。私有仓库规则、复杂构建、跨 PR 协作、权限审批、文档迁移、性能优化和架构设计，未必被单一基准覆盖。团队可以从历史 issue、CI 失败、重构、测试补齐和安全修复中抽取样本，冻结仓库版本与测试环境，在同一题集上比较系统变化。

## Trace 要能解释失败发生在哪

一条可分析的 trace 应记录目标、模型和提示词版本、当轮可用工具、工具请求及参数摘要、策略判断、工具输出和退出码、文件 diff、测试结果、子 Agent 任务、压缩边界、耗时与成本。对敏感文件、cookie、密钥和个人信息做脱敏，并支持用户或企业规定保留期和删除方式。遥测有收集边界，不能为了排障把完整私有仓库默认上传。

例如测试没跑就结束了，可能是模型提前宣布完成、最终验收过松，也可能是测试工具从可用列表消失。若 trace 只留最终答案，就无法区分这些原因。改错文件则可能来自搜索不足、索引过期或项目说明过时。工具失败之后持续重复同一调用，可能是错误类型不够具体或状态压缩丢掉了失败尝试。

## 常见失败与针对性处理

| 现象 | 应先检查 | 可尝试的修复 |
| --- | --- | --- |
| 改错文件 | 搜索轨迹、定义/引用、测试定位 | 缩小候选集后读实际调用链 |
| 覆盖用户改动 | 写前 Git/文件版本 | 条件编辑与冲突提示 |
| 测试没有运行 | 计划和终止条件 | 把相关测试作为验收项 |
| 编造 API | 类型定义、官方文档是否读取 | LSP 和精确文档查询 |
| 危险命令 | 工具策略和审批记录 | 参数级策略、沙箱、人工确认 |
| 长任务漂移 | 摘要、计划版本与失败记录 | 结构化任务状态和检查点 |
| 子 Agent 冲突 | 文件所有权与提交顺序 | 明确可写范围，统一整合 |
| 注入影响动作 | 外部工具结果与权限判断 | 把输出当数据，动作独立授权 |

## 企业内怎样逐步上线

可从只读代码解释、搜索和 review 开始；再允许生成 patch 供开发者应用；经过评测后，在受控分支允许写入和运行测试，所有 diff 由人审；PR 自动创建也不等于自动合并。上线能力需要 SSO/RBAC、仓库权限继承、审计、网络隔离、secret scanning、模型与数据策略、灰度和回滚。每一阶段用相同任务集和真实失败样例比较，决定是否扩大权限。

## 怎样避免评测只奖励“碰巧答对”

在同一个冻结仓库版本上重放任务时，除了最终测试，还应检查 Agent 曾经尝试的动作。一个系统也许通过了修复测试，却在中途读取了无关密钥文件；另一个系统也许用覆盖整个模块的方式碰巧通过。两者都不能与“定位准确、最小改动、遵守权限”视为同分。可以把任务断言拆成结果、路径、安全三组：目标测试是否过、是否仅修改允许文件、权限拒绝后是否停止、重复工具调用是否被控制。

线上反馈也要按失败类型沉淀，而非只存“用户不满意”。Review 拒绝可能因为代码风格、需求误解、未跑测试或越界改动；不同根因要改的模块不同。模型升级、提示词修改、工具 schema 变化和索引刷新都可能改变结果，实验记录应保留版本，才能比较回归。

## 面试会怎么问

字节 Agent 一面涉及 AI Coding 质量保障，要务科技复盘问 AI Coding 工作流。回答“怎么证明编码 Agent 有用”时，先讲任务集与成功条件，再讲 diff、回归和轨迹安全，最后说明线上反馈如何回流。不要只报 benchmark 分数或“开发速度快了”；若没有实测数据，就陈述你会如何设计实验。
