# Function Calling：模型提出调用，程序负责执行

Function Calling 把自然语言请求变成结构化的工具名与参数。例如用户说“查一下我的上周订单”，模型可输出调用 `list_orders` 的参数；宿主先确认用户身份、日期范围和权限，再真正访问订单服务。模型的输出是一项调用建议，不是 API 已执行的证明。

## 一次调用的完整路径

宿主向模型提供工具描述与 schema → 模型选择工具并生成参数 → 宿主校验 schema、权限和业务规则 → 执行函数 → 把真实结果作为工具消息送回模型 → 模型回答或提出下一步。传统 API 调用由程序逻辑显式决定目标函数与参数；Function Calling 把语义选择交给模型，但控制权仍在程序。

| 维度 | 普通程序调用 API | Function Calling |
| --- | --- | --- |
| 调用选择 | 开发者写死或按规则分支 | 模型根据请求与上下文建议 |
| 参数生成 | 程序构造 | 模型从自然语言抽取 |
| 执行 | 程序 | 仍是程序 |
| 新增风险 | 业务异常 | 误选工具、参数幻觉、越权意图 |

## Schema 怎样写才便于模型使用

工具名写清动词和对象，描述交代适用与禁用场景，参数用类型、枚举、必填项、范围及格式约束。`do_action(input: string)` 过于模糊；`search_customer_orders(customer_id, from_date, to_date, status)` 更能限制意图。返回应稳定包含状态、关键字段和可恢复的错误类型，如参数无效、权限不足、资源不存在、超时和部分成功。

不要把所有能力塞进万能 `execute_sql` 或 `run_shell`。生产场景更适合只读查询、经批准的报表或具体业务工具。Schema 也不能代替权限检查：模型生成一个合法 `customer_id`，不代表当前用户能查询那位客户。高风险写操作应有独立审批，不能靠让模型自动填 `confirm=true` 实现授权。

## 模型为什么会使用工具

模型在预训练中学到代码、JSON 与 API 语义，再经过带工具说明、正确工具选择、参数和最终回答的监督数据，以及偏好优化等训练；产品运行时提供工具列表、结构化输出和多调用控制。实际能力不是单一训练技巧带来的，取决于模型、描述质量、运行时和评测。负样本尤其重要：系统需要学会什么时候不调用工具。

完整 Agent 还要处理目标、计划、多步状态、工具失败、权限、记忆、成本与停止条件。一次 Function Calling 本身没有保证多轮循环，也不会自动记住先前副作用。工程上要分别评测工具选择准确率、参数有效率、执行成功率与安全违规率。

一个容易混淆的边界是 Structured Output：它约束模型生成的数据结构，但不一定请求执行外部动作。模型返回合法 JSON 的订单号，仍不等于订单被创建；只有宿主实际调用工具并收到成功结果，才有业务副作用。把两者混在一起，会让最终回答声称“已创建”，而系统实际上只生成了参数。

并行工具调用也需要宿主判断依赖。查询订单与读取政策可以并行；创建草稿和提交草稿不行，因为后者要用前者的产物 ID。若模型一次请求多个工具，结果应逐条回填：某一个失败时，不能把整批写成“成功”。对于网络超时的写操作，先按请求 ID 查询执行状态，再决定重试；参数格式正确不代表可以盲目重放。

## 面试会怎么问

字节 Agent 一面涉及 Function Calling 与 RAG：前者让模型请求动作或结构化查询，后者是为回答提供检索到的知识，二者可以组合。若问“Function Calling 与传统 API 的区别”，强调模型负责语义选择，宿主仍负责执行、授权和错误处理；再给一个错误参数或越权查询的处理例子。
