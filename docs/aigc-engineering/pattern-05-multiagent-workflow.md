# 多 Agent 编排与可恢复工作流

多 Agent 的好处来自任务真能分工，而不是角色名称多。研究、实现、审查和测试可以由不同会话承担，也可以由一个 Agent 顺序完成。设计时先看子任务是否独立、权限是否不同、是否能并行，随后再选组织方式。

## 常见协作方式

| 模式 | 谁决定下一步 | 适合场景 | 常见问题 |
| --- | --- | --- | --- |
| Router | 路由规则或分类器 | 意图分发、专门客服 | 选错目标 Agent |
| Supervisor | 上级 Agent | 复杂研究或工程任务 | 上级成为瓶颈 |
| Pipeline | 预设顺序 | 稳定的多阶段处理 | 前段错误传到后段 |
| Crew / Team | 固定角色协作 | 角色边界与输出合同明确 | 通信与整合成本 |
| Swarm | 动态交接 | 开放探索 | 难追踪责任和终止 |
| Debate | 多方案讨论、评审裁定 | 高价值判断 | 多个 Agent 可能共错 |
| Blackboard | 共享工作区 | 需要共同维护中间产物 | 并发写冲突 |
| Bidding | Agent 按能力竞争任务 | 动态资源分配 | 调度与评价复杂 |

工程中常用 Router、Supervisor、Pipeline 和固定 Team，因为路径较容易审计。一个软件任务可由 Planner 定目标、Researcher 查资料、Engineer 改代码、Tester 跑测试、Reviewer 检查 diff；但给每个角色都开完整仓库写权限没有必要。让每个角色拥有明确输入、输出、可用工具和停止条件，副作用文件最好有单一写入责任人。

Router 适合把“查物流”“申请售后”“修改地址”派给不同处理器，路由信心不足时回到澄清问题。Supervisor 适合分解较大的报告任务，但要限制重复派发、等待慢子任务和整合矛盾结论。Debate 只在不同观点确实可能揭示盲点时有价值；多个模型读同一错误资料可能一致地答错。Blackboard 让 Agent 共享中间产物，必须有版本、写入所有者和冲突处理，不能只共享一段不断增长的聊天记录。

Market/Bidding 让不同 Agent 声明自己能处理的任务与代价，由调度器选择执行者；只有任务类型多、能力差异大且评估标准明确时才值得引入，否则一个稳定 Router 更简单。Swarm 的动态交接同样需要共同的终止条件和审计链：从 A 交给 B 后，谁继续拥有用户响应责任、谁能进行写操作，都不能因为“自组织”而悬空。

## 什么时候单 Agent 更好

短任务、工具少、目标明确且需要快答时，一个 Agent 通常足够。多 Agent 增加上下文复制、消息传递、冲突、错误传播、调试和 token 成本。只有任务天然可拆、并行探索确实节省关键路径时间，或不同角色需要独立权限与审查时，才值得增加角色。比较方案应看同一任务集的成功率、人工接管、路径错误、延迟和成本。

## 让工作流从对话变成状态机

可恢复工作流要显式记录任务目标、节点、依赖、执行状态、工具结果摘要、待审批项和失败原因。节点可以是 planner、tool_call、evaluate、human_review、replan 和 finalize；每个节点完成后写入检查点。进程重启先读取检查点，再与外部副作用对账，不能简单重放最后一条模型输出。

对只读调用可较容易重试；写文件、发消息、创建工单与提交 PR 需要稳定幂等键、状态查询或补偿流程。人审节点应允许批准、拒绝、修改和终止，并在恢复时核对授权对象仍相同。Trace 保存模型、工具、审批、错误和成本事件；最终产物与过程都能回放。

要区分“节点重试”和“整条工作流重跑”。分析节点失败时，取数产物若仍有效且未过期，就不必重取；若数据源版本已变，取数节点也要失效并带新版本重跑。检查点应记录输入版本和输出哈希，恢复时能判断哪些结果可复用。对发布这类终端写操作，重试前先按业务 ID 对账；仅在确定未执行时复用相同幂等键继续。

例如“整理季度报告”可以按取数→分析→撰写→审核→发布建图。取数与部分背景检索可并行；审核没通过就回到撰写，而不能直接发布。若发布请求超时，先查目标系统有没有生成文档，再决定是否重试。LangGraph 等框架能帮助维护图与检查点，但业务幂等和授权边界仍需应用设计。

## 面试会怎么问

小红书面试问多 Agent 并发与 Planner/Executor/Critic，美团面试问状态汇总和路由。回答“多 Agent 比单 Agent 好在哪”时先给可并行依赖图，再说消息合同、文件所有权和结果整合；回答“如何恢复”时强调检查点、外部动作对账和待审批状态。不要把“启动多个 Agent”当作性能结论。
