# CLI、IDE 与远程会话：同一个 Agent 怎样服务不同入口

CLI 靠近 Shell、工作目录和 Git；IDE 知道光标、选区、诊断和 inline diff；远程会话能让长任务在云端继续运行。三种入口连接的可以是同一套模型与工具运行时，但它们携带的上下文、展示方式和故障处理各不相同。

## CLI 和 IDE 给 Agent 的信号

| 维度 | CLI | IDE |
| --- | --- | --- |
| 天然上下文 | `cwd`、Shell、Git、文件系统 | 打开文件、选区、光标、诊断、项目树 |
| 最顺手的反馈 | 文本流、命令输出 | inline edit、diff、问题面板 |
| 常见优势 | 适合脚本与仓库级任务 | 适合局部编辑与可视化 review |
| 典型风险 | 命令副作用更直接 | 编辑器状态与磁盘状态不同步 |

IDE Bridge 需要双向传递工作区、打开文件、光标或选区、诊断、用户引用和语言服务状态；Agent 则可能要求 IDE 打开文件、定位行号、展示 diff、请求审批、通知进度或应用编辑。桥接消息要带工作区与文档版本，防止 Agent 在用户切换项目或修改文件之后，把旧补丁应用到新内容。连接要鉴权；本地监听端口也不能假定“只有本机网页能访问”。

## 远程会话不是把 CLI 搬到服务器

远程 worker 跑工具，客户端通过事件流接收 token、工具开始、工具进度、结果、审批请求和最终答案；控制通道提交用户消息、interrupt 与权限响应。`session_id` 标识持续任务，客户端断线后凭游标或事件序号补收遗漏事件。若流式连接重建失败，可先查询任务状态，避免向同一任务重复提交用户消息。

`interrupt` 是停止继续执行的请求，不保证已经发起的外部动作被撤销。`resume` 要恢复消息摘要、待办、pending permission 和工具状态，还要重新读取文件与授权状态。会话不存在、压缩边界刚写入或后台任务暂时不可见时，客户端可以有限重试；超过窗口后应呈现明确错误，而不是悄悄创建一条新会话。

MCP 在编码 Agent 中常用来接 GitHub/GitLab、Issue/PR、数据库、文档、浏览器、云服务和内部搜索。它给工具提供统一发现与调用接口，但 MCP Server 的认证、授权、输出隔离与副作用审批仍需做好。编码场景里的 MCP 通常作为工具接入层，不能代替整个会话运行时。

## 用一次断线演练检查设计

让远程 Agent 创建一个 PR，但在工具返回前断开客户端。重连后，服务端应能回答：PR 请求是否仍在运行、是否已成功、产物 ID 是什么、是否还有待批准动作。若只能“重新试一次”，设计还缺副作用对账和事件持久化。再模拟用户在断线期间编辑文件，恢复后应先检查版本冲突。

## 让三个入口共享一致状态

同一任务先在 IDE 启动、之后从 Web 查看、最后在 CLI 继续时，服务端要保存 canonical session state，而不是由每个客户端各存一份聊天副本。IDE 选区是启动任务时的上下文快照，恢复到 CLI 后不应假装光标还停在旧位置；磁盘文件和 Git diff 则要重新读取。客户端发送消息最好带 session 与预期版本；若另一端已经推进任务，就提示冲突或加入新一轮，而不是覆盖进度。

远程权限请求也要绑定发起它的用户和设备。某人在手机上看到“允许执行脚本”，若请求已经过期或脚本参数变化，原确认不能复用。系统可显示审批历史、取消状态和工具实际结果，帮助用户区分“我批准了”与“命令已成功”。

## 面试会怎么问

字节 Agent 开发复盘问到 SSE 与 WebSocket；影石创新面试涉及工具超时与恢复。回答“远程编码 Agent 如何断线恢复”时，把 session 状态、事件序号、权限请求、工具结果对账与工作树复核说完整。讨论 SSE/WebSocket 时不要只比较协议名称，要结合服务端单向事件流、客户端控制消息和现有基础设施选择。
