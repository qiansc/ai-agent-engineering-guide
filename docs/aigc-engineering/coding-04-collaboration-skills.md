# 子 Agent、Skills、Hooks：什么时候拆任务，什么时候复用流程

一个编码任务可能既要查前端调用，又要看服务端接口和测试。此时可以分给子 Agent 并行探索；而“怎样发布库”“怎样审核安全风险”这类反复出现的专业流程，更适合写成按需加载的 Skill。Hooks 则在固定生命周期点执行程序逻辑。三者都能帮主循环，但解决的问题并不相同。

## 子 Agent 是隔离的工作会话

子 Agent 适合边界清晰且可以独立推进的工作：并行查不同模块、实现互不冲突的文件、补测试、做审查、复现错误或比较方案。每个任务应交代目标、可读范围、可写文件、成功标志和返回格式。主 Agent 负责整合结果、处理冲突并完成最终验证。

需要立刻决定主流程下一步的操作，不适合异步分派；多个子 Agent 写同一文件也容易互相覆盖。高度耦合的架构决策可先并行调查，最后由一个负责人定方案。子 Agent 的摘要应指出具体文件与观察，不应只说“检查过没问题”；主 Agent 仍要看 diff 和测试。

## Skill 与 Tool 各做什么

| 对象 | 提供的东西 | 例子 |
| --- | --- | --- |
| Tool | 一个可执行动作和输入输出合同 | `read_file`、`bash`、`search` |
| Skill | 某类任务的触发条件、步骤、参考资料与资产 | code review、发布流程、文档翻译 |
| Hook | 生命周期事件发生时执行的逻辑 | 工具前策略检查、压缩前状态保存 |

一个 Skill 可以包含说明文件、脚本、模板和示例，使用时先加载相关说明，再按流程调用工具。这样专业信息按需进入上下文，不必把所有流程塞进系统提示词。Skill 并不自动获得额外权限：其中的脚本仍受工具策略和沙箱限制。原文将 Skill 概括成“能力包”，实际实现随产品而异，面试时要说明所用产品的真实触发与加载机制。

## Hooks 放在哪些阶段

典型位置有会话开始、模型调用前、工具调用前后、上下文压缩前后、会话结束。工具前 Hook 可拦截危险参数；工具后 Hook 可记录实际退出码；压缩前 Hook 可保存未完成计划。Hook 要有失败策略：安全校验失败一般应阻断，非关键指标上报失败可以记录后继续。不能把“Hook 会检查”写成安全保证，仍要验证它是否覆盖所有执行入口，以及用户是否可能绕过。

自动格式化、lint 和测试也可以由 Hook 触发，但要避免每次微小编辑都跑完整构建。给 Hook 设置超时、幂等标识和 trace，才能分辨模型问题与自动化扩展问题。

## Plan Mode、Todo 与任务状态

长任务需要外显状态：待做、进行中、完成、阻塞，以及每一步的验收条件。只读的 Plan Mode 适合先探索和让用户确认方案；进入执行后，Todo 帮助跟踪是否做了验证和交付。状态应由实际事件更新：测试失败不能标完成，用户拒绝权限应标阻塞。原文建议“一次只应有一个核心 in_progress”，这是降低注意力分散的经验，不是所有系统的硬约束；并行子任务可以分别处于进行中，但要有明确所有者和依赖关系。

## 一个并行分工例子

要为一个跨前后端功能补测试，主 Agent 可让子 Agent A 只读调查前端入口与已有测试，让子 Agent B 只读调查服务端契约；两者分别返回文件位置、相关函数、风险和建议测试点。主 Agent 汇总后决定实现顺序。如果前后端测试文件互不冲突，才把写入分给不同 Agent，并明确各自可写路径。最终统一运行测试和审查 diff，不能把两个“各自通过”的结论直接相加当作整体通过。

Skill 的一个例子是库发布流程：它可提供变更分类、版本策略、运行命令、回滚步骤和模板。Agent 只有遇到发布任务才加载它；其中的脚本执行前仍需检查当前项目版本、用户授权与工作树状态。Hook 可以在发布命令前验证分支与权限，在发布后记录结果，但不能假设所有人都通过这一个入口执行。

## 面试会怎么问

百度 Coding Agent 复盘提到 Skill 误调用，小红书 Agent 开发复盘问多 Agent 并发与 Planner/Executor/Critic。回答时可以先解释什么工作值得拆，再讲文件所有权、上下文隔离与结果整合；Skill 误调用则要讨论触发条件、适用范围、权限不变和执行后验证。若面试官问“为什么不多开几个 Agent”，用共享文件冲突、通信成本和无法并行的依赖说明取舍。
