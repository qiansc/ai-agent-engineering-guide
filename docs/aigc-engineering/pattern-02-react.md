# ReAct：每做一步，就用环境反馈校正下一步

ReAct（Reasoning and Acting）让模型在推理与行动之间交替：明确当前缺口，提出工具动作，读取真实观察，再决定下一步或结束。它适合浏览器导航、故障排查、多跳检索和编码探索，因为在这些场景里，初始计划无法预知所有页面、日志或测试结果。

## 一轮完整循环

一次任务先明确目标、可用工具、预算和终止条件。模型选择下一步动作并生成参数，宿主校验并执行，环境返回 observation；下一轮模型基于观察继续。最终答案要经过任务验收，不能只凭模型说“完成”。研究论文常写 Thought → Action → Observation；工程系统不一定向用户展示内部推理，可只展示动作目的和必要的状态摘要。

以“找出订单支付失败原因”为例，第一轮读取订单状态；若工具返回支付网关超时，第二轮查网关事件；若日志没有对应记录，就不能直接断言“网关故障”。当前 observation 决定下一步，外部事实逐步替换初始猜测。工具返回的网页、评论和日志又是低可信内容，不能让其中的命令绕过权限策略。

| 比较点 | 单次 CoT 推理 | ReAct |
| --- | --- | --- |
| 事实来源 | 主要依赖模型已有信息 | 可引入实时工具观察 |
| 运行成本 | 一次或少量模型调用 | 多轮模型和工具调用 |
| 适合的问题 | 无需外部数据的推理 | 需要检索、交互和验证 |
| 主要故障 | 推理或事实幻觉 | 无效搜索、循环调用、注入与延迟 |

## ReAct 与 Self-Consistency 如何组合

CoT-SC 通过多条推理路径的一致性来选择答案，ReAct 通过外部工具补事实。它们可以按缺口组合：多个内部候选分歧大时，先找外部证据；工具搜索得到事实后，再对复杂结论做多路径检查；工具暂时不可用时，也可以给出基于已有信息的不确定答案。但“多数路径一致”并不证明事实正确，尤其当所有路径共享同一个错误前提时。不能把 CoT-SC 作为验证失败后的自动兜底答案。

## 防止无效搜索和死循环

为每个工具动作保存名称、规范化参数、预期信息增量、结果摘要和成功/失败状态。重复调用同一工具且参数相近、连续几步没有新证据、预算用尽时，应停止、换策略、重规划或请求人协助。工具失败时先看错误类型：权限拒绝不能靠换个工具绕过，超时可以按幂等规则重试，未找到可换查询，部分成功要先核实完成集合。

ReAct 比纯 CoT 更容易纠正事实错误，却并非天然“更真实”：搜索结果可能过期，工具返回也可能含糊。执行器应保留来源版本、时间和错误码；回答层区分已有观察支持的结论与待验证假设。对外部写操作，Action 前需要独立权限判断，Observation 后记录实际产物，不允许模型编造结果来推进。

CoT-SC 的投票也要分清任务类型。数学题中多条计算路径可能帮助发现失误；“某公司今天的价格是多少”属于外部事实，十条一致的内部推理也不如一条可核查的实时数据。先判断缺的是推理还是事实，再决定多样化采样还是工具检索。

观察要压缩，但不能丢掉来源和关键错误。对于副作用工具，运行时负责判断是否能重试，不能让模型凭文本决定“再做一次”。最终结论也要检查是否有证据支持。比如两笔差额只解释了其中一笔，应明确未解释部分，而非提前收尾。

## 练习：一条四轮以内的检索轨迹

用两个只读工具 `search_policy` 与 `read_policy` 查“某订单适用哪个版本的退款规则”。要求最终答案包含政策 ID、版本和引用。准备一次空搜索、一次过期版本和一次重复查询；记录每轮 action history，看看系统何时应调整查询、何时应终止。再把最大调用数设为四，练习预算耗尽后的交接说明。

## 面试会怎么问

百度 Coding Agent 三轮复盘明确提到了 ReAct，小红书 Agent 复盘追问 Planner/Executor/Critic。回答“ReAct 是什么”时，用一次真实工具轨迹解释观察怎样改变下一步；若问缺点，讲工具循环、成本、外部内容不可信和终止验收。回答“ReAct 与规划模式怎么选”时，关键是下一步是否依赖刚获得的事实。
