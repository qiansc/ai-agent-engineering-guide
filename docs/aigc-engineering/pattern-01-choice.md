# Agent 设计模式：先看任务，再决定给模型多少自由

一个模型接上工具之后，就会遇到规划、失败恢复、成本、状态和权限问题。设计模式是这些反复出现的问题的解决结构：Prompt Pattern 组织单次推理，Agent Pattern 组织多轮感知与行动，Workflow Pattern 用代码约束节点与转移。它们可以叠用，例如代码修复任务先生成计划，探索阶段用 Agent Loop，提交 PR 前进入固定的人审流程。

## 三类模式各管哪一层

| 模式 | 主要控制对象 | 常见做法 | 应警惕 |
| --- | --- | --- | --- |
| Prompt | 单次模型输出的推理或格式 | CoT、Plan-and-Solve、Self-Consistency | 模型未必遵循，不能替代验证 |
| Agent | 多轮观察、工具和记忆 | ReAct、Reflection、Tool Use | 调用成本、副作用、任务漂移 |
| Workflow | 程序层的路径和状态 | Router、DAG、状态机、人审 | 流程过细会损失探索能力 |

从需求确定性判断自由度：步骤和分支已知时，固定 Workflow 容易测试和审计；下一步依赖新证据时，用 Agent 动态选择；节点固定但节点内要理解自然语言时，在该节点使用模型即可。报销审批、身份认证和付款转账应让确定性流程拥有最终控制权；代码排障或研究调研可以允许模型在受限工具与预算内探索。

几种常见名字可先对应到它们处理的问题：ReAct 处理“下一步看观察再决定”；Plan-and-Solve 与 Plan-and-Execute 处理“长任务先分步”；ReWOO 处理“工具依赖可预先编排”；Reflection/Reflexion 处理“有反馈后的纠错”；Tree/Graph of Thoughts 与 LATS 处理“探索多条候选”；Supervisor/Router 处理“如何分工”。名字相近不表示互斥，选型仍应落到状态、反馈、成本和权限。

## “过度自主”会怎样失败

给系统一个巨大目标、所有工具和很少约束，容易出现计划无法收敛、工具调用过多、错误中间结果层层传递、上下文被日志挤满、权限副作用难审计等问题。解决办法是把大目标拆成可验收的小段：每段有输入、产物和失败出口；高风险动作经过策略或人审；限制步数、时间和费用；关键阶段运行测试或评估器。

例如“自动处理所有退款投诉”包含身份核验、政策查询、金额判断和退款执行。模型可以理解投诉并查缺失信息，但身份校验、金额上限和打款动作应由明确业务规则控制。系统不必让模型在整个流程中自由决定下一步。

## 选择模式时可问五件事

1. 任务步骤能否提前列举？能则优先显式流程。
2. 新观察是否会改变下一步工具？会则在该段保留 Agent Loop。
3. 错误能否由测试、规则或人工验证？没有反馈时少用自反思。
4. 工具会否产生不可逆副作用？会则增加审批、幂等和补偿。
5. 需要的延迟与成本是多少？复杂搜索和多 Agent 不适合每个请求都开。

设计的目标是把开放式判断放在确实不确定的地方，同时让其他部分可预测、可恢复。比较方案时，除了完成率，也看路径错误、人工接管、平均调用数和事故后能否解释。

## 把混合模式落成可执行流程

设想一个“根据用户投诉处理订单异常”的系统。入口 Workflow 先确认用户、订单归属与投诉类别；这个阶段的规则明确，不能交给模型自由推断权限。接着进入调查节点，Agent 可以在已授权的订单查询、政策检索和物流状态工具中选择，直到找齐原因或耗尽查询预算。调查结束后，程序把已验证事实、缺失信息与建议动作写成结构化产物。涉及退款金额、发券或对外承诺时，回到固定规则和审批节点；审批通过才执行写操作。这样既保留开放式调查，又记录每个副作用的授权来源。

若投诉只是“如何修改收货地址”且回答可由知识库直接找到，调查 Agent Loop 就没有价值。若政策与订单状态不断变化，只有固定 FAQ 又不够。选择模式时先看实际数据与错误类型，不必强迫所有请求经过同一种复杂编排。

## 面试会怎么问

小红书 Agent 开发复盘问“为什么用 Agent”，美团 Agent 复盘问长流程保障。回答时先界定任务中哪些步骤未知，再说明采用 Agent、Workflow 或混合模式的原因；接着给出停止条件与失败出口。若只回答“Agent 更智能”，无法解释多出来的成本与风险。
