# 规划、执行与反思：怎样让长任务可检查

任务有多步依赖时，先规划可以减少漏步；但“请先想一想”的提示语与可恢复的工程计划不是一回事。Plan-and-Solve 是提示方法，通常由模型在一次推理中先列步骤再求解；Plan-and-Execute 把规划、执行、状态、验证和重规划拆成系统组件，能调用工具，也能从中断处继续。

## 从计划文字到可执行状态

一个工程计划至少要写步骤 ID、目的、前置依赖、负责人、可用工具、验收条件和失败出口。例如修复登录错误可以是：复现失败 → 定位请求与状态变更 → 修改 → 跑相关测试 → 审 diff。若“跑测试”失败，状态应保留日志和影响范围，不能直接进入交付。Replanner 只调整未执行步骤；已完成的写操作和通过的身份核验不能因计划更新而无记录地重来。

| 模式 | 计划在哪里 | 执行在哪里 | 主要代价 |
| --- | --- | --- | --- |
| Plan-and-Solve | 单轮提示中的文字步骤 | 同次推理 | 轻量，但难以恢复和审计 |
| Plan-and-Execute | 独立计划状态 | 工具/子 Agent/工作流执行器 | 需维护状态、验证与重规划 |
| ReWOO | 带变量依赖的预先计划 | 根据依赖执行工具，再求解 | 初始计划错时后续易偏离 |

ReWOO 把推理规划与工具观察解耦。比如先声明 `E1=搜索甲公司财报`、`E2=搜索乙公司财报`、`E3=比较 E1/E2`。前两项无依赖，可以并行；执行器无需每步都重新调用大模型，降低串行延迟。任务若高度依赖每一步的环境反馈，预先列完整计划就可能不如 ReAct 灵活，因此需要在重大新事实或工具失败时允许局部重规划。

一个持久化步骤可以长这样。`success_check` 指向可核查产物，`on_failure` 说明失败出口；这两个字段比“先查资料”更能帮助恢复。

```json
{
  "step_id": "read_current_policy",
  "depends_on": ["verify_order_owner"],
  "tool": "read_policy",
  "status": "pending",
  "success_check": "返回与订单日期匹配的政策 ID 和版本",
  "on_failure": "停止自动答复并请求人工核对"
}
```

执行器接受计划时应检查依赖是否存在、是否成环、工具是否获准，以及不可逆动作是否被安排在审批之前。执行中发现新事实，只更新未执行节点和计划版本，并说明修改原因。

## Reflection 与 Reflexion 的有效反馈

Reflection 是对当前输出或行动做检查；Reflexion 进一步将失败经验作为后续尝试可见的记忆。关键不是多一轮“仔细想想”，而是先有外部反馈。例如测试报告提示缺少 `user_id` fixture，反思应定位该失败、检查 fixture，再决定是否改测试数据或业务逻辑；“我应该更小心”没有给下一轮任何可执行信息。

可把反思记录写成四项：失败的步骤、证据、下一轮策略、不得重复的动作。写入长期记忆前还要过滤，因为错误反思会污染后续任务。任务简单、没有可靠 evaluator、反思成本高或多轮反思已经偏离需求时，应停止反思。对同一失败设置轮数上限，并以测试、规则或用户反馈检查修复是否真的有效。

例如浏览器 Agent 填表失败，截图只显示按钮没变色，不能马上反思为“按钮选择器错了”。还可能是必填字段校验、网络未返回、权限不足。好的 Reflector 会列出候选与可检验观察，下一轮优先读取表单错误或网络状态；若重复点击可能重复提交，先查外部系统是否已经创建记录。

## 一次完整的失败恢复

假设计划让 Agent 修改配置并运行测试。测试失败后，不直接重新生成全部计划，而是把该步骤标为 failed，保存退出码与日志，分析是否因配置字段、测试数据或环境问题。若发现是依赖服务不可用，标为 blocked 或选择可验证的替代测试；若是代码错误，只改相关未完成步骤。用户可从计划与 trace 中看到已完成、待办和需要确认的部分。

## 面试会怎么问

小红书 Agent 复盘问 Planner、Executor、Critic 如何协作，端侧推理优化复盘提到工具依赖与重规划。回答时画一条带依赖和验收的任务链，讲清 Critic 检查什么证据、失败后修改哪一步、如何避免已执行动作重复。若问反思何时无益，指出没有外部反馈时模型可能只是生成更长、同样错误的解释。
