# Tree of Thoughts、Graph of Thoughts 与 LATS：何时值得搜索多条路径

有些难题的第一条推理链很容易走进死胡同。搜索式方法让模型生成多个候选中间状态，比较价值、剪枝或回溯，再选择下一步。它们提升的是复杂问题的探索上限，同时增加模型调用、工具调用、状态管理和延迟。

## 从一条链到树和图

普通 Chain-of-Thought（CoT）沿一条思路推进。Tree of Thoughts（ToT）在一个状态生成多个候选 thought，用评估器评分，再用 BFS、DFS 或 Beam Search 继续扩展；低价值分支可剪掉，失败路径可以回溯。24 点、数独或复杂规划这类可定义中间状态与成功条件的任务较适合。

Graph of Thoughts（GoT）进一步允许两个分支的信息聚合、同一结论迭代修正、多个证据指向同一节点。它可以表示 branching、aggregation、refinement、scoring 和 pruning。多文档研究或方案比较中，一份证据可能同时影响多个结论，这时图比严格的父子树自然；代价是图状态、依赖和终止条件更难维护。

| 模式 | 状态形状 | 能做的关键事 | 常见代价 |
| --- | --- | --- | --- |
| CoT | 单链 | 顺序推理 | 一步走错难回头 |
| ToT | 树 | 生成、评估、回溯分支 | 搜索宽度带来成本 |
| GoT | 图 | 合并、修正、复用中间结论 | 状态与依赖复杂 |
| LATS | 行动搜索树 | 在环境反馈中比较行动轨迹 | 工具副作用和评估难 |

## LATS 把行动也放进搜索

LATS（Language Agent Tree Search）结合模型生成候选动作、环境反馈、价值评估和搜索树。可以按选择（Selection）、扩展（Expansion）、执行或模拟（Simulation）、评估（Evaluation）、价值回传（Backpropagation）理解一次迭代。重点是比较不同轨迹，而不是只让模型“多想一步”。Web 交互、游戏或可模拟的复杂工具链适合试验；真实生产环境里的发消息、付款、删数据不能随意在多个分支上试错。

价值函数必须与任务目标对齐。若评估只看回答流畅度，搜索可能选出更漂亮但不真实的路径。对代码修复，可用测试、静态检查和 diff 风险作为部分反馈；对研究任务，可看引用覆盖与矛盾处理。没有可靠评分信号时，增加搜索宽度未必提升质量。

举个简化的方案评估：用户要给两个服务设计故障切换。第一条候选路径采用双写，第二条采用主从切换，第三条先保持单点但增加恢复工具。树搜索可以分别追问写冲突、恢复时间和维护成本，再剪掉不能满足约束的分支。如果一条路径用了“数据库可强一致复制”这个未经验证的假设，评分器应把它标为待验证，而不是因为方案描述完整就加分。图结构则可让“延迟预算”这一证据同时约束双写和主从两条分支。

LATS 更进一步，把路径中的某些节点变成真实行动。若是在模拟环境里部署与压测，可比较多条配置轨迹；若是生产环境的实际切流，就不能让搜索器每个分支都执行一次。先区分虚拟试探、只读观察和真实副作用，再允许行动扩展。

## 生产使用的限制

分支数扩大时成本可能迅速增加，工具执行又会增加等待时间；搜索树/图需要持久化，方便中断与审计。适合把搜索用于高价值、低频、难题求优的环节，常规高并发请求优先简单 Workflow 或 ReAct。可限制宽度、深度与预算，用较轻的评估筛去明显无效分支，再在关键节点调用强模型。外部工具尽量只读或在模拟环境执行，缓存可复用的检索结果。

## 练习：比较两条路线而不是只比较答案

给同一道多步骤资料题，分别运行单链 CoT 与宽度为二的 ToT。记录调用数、耗时、每个分支的证据和最终错误。若结果相同但 ToT 多花五倍成本，就需解释这种任务是否真的值得搜索；若只有搜索找出一条被单链遗漏的证据，也要确认评估器为何选择它。
