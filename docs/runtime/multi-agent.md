# 多 Agent：任务所有权、消息与汇合

多 Agent 让若干独立执行者处理同一目标的不同部分。收益来自可并行的工作、上下文隔离或清晰的专业边界；代价是更多模型调用、权限传播、状态同步和冲突处理。先让单 Agent 使用清楚的工具完成基线，再记录瓶颈。若主要问题是工具名字相似，应先改善工具描述和参数；若固定步骤总被重排，应考虑 Workflow；只有分工确实改善结果或时延时才扩展团队。

## 两种编排与三类执行者

Manager 模式由中心 Agent 分派并汇总，便于控制总预算；handoff 模式把控制权交给专家，适合会话确实需由专家接管。一次性 subagent 接收窄任务，有独立消息上下文，返回结果后结束。持久 teammate 则可在 `WORK → result → IDLE` 间循环，接收后续消息与任务。二者都可能共享文件系统；“消息隔离”并不等于“写入隔离”。

| 对象 | 生命周期 | 适合工作 | 关键风险 |
| --- | --- | --- | --- |
| 一次性 subagent | 单次委派后结束 | 独立调查、验证某个假设 | 共享目录的副作用 |
| 持久 teammate | 持续接任务 | 多阶段开发、长期协调 | 任务所有权、旧消息、空闲轮询 |
| 固定 Workflow 中的 agent 调用 | 由脚本阶段控制 | 已知步骤的审查或处理 | 阶段缓存与部分失败 |

## 从依赖图开始，而非先启动队友

把目标拆成含输入、输出、验收标准和 owner 的 Task。`blockedBy` 指向前置任务；创建任务节点后再加依赖边，可检查不存在的节点、自依赖和环。`pending` 任务只有前置任务全部完成才 ready。运行时扫描 ready 列表只是发现候选；真正 claim 必须在进程锁和持久化锁内原子更新 owner 与状态，否则两个队友会同时开工。claim 失败应重读任务板，不可沿用旧快照继续写。

```text
on_idle(teammate):
    deliver_inbox_first(teammate)
    if no_direct_message:
        candidates = scan_ready_tasks()
        task = atomic_claim_one(candidates, teammate.name)
        if task: run_with_bound_workspace(task)
    else:
        handle_message_or_control_request()
```

消息放在 MessageBus，而非所有 Agent 共享一个 `messages[]`。Lead 发任务说明，teammate 回结果；“结果已发出”和“队友回到 IDLE”是两个事件。运行时消费收件箱并唤醒 Lead，避免让模型反复调用检查消息工具。关机、计划审批等控制消息要有类型和 `request_id`；普通文本“好的”不足以证明哪个审批被同意。

## 并行写入与计划闸门

两个队友可同时阅读同一仓库，但并行修改应先按模块或文件分工。任务可绑定独立 worktree；认领时解析绑定的目录，若目录被删除或绑定失效，应拒绝执行而不是退回主仓库。Worktree 只隔离 working copy，命令仍需沙箱与权限策略。合并时检查类型契约、测试和行为冲突，不能只看 Git 是否无冲突。

高风险修改可要求队友先提交计划。计划未获批时允许只读调查和提交方案，阻止 Shell、写文件与编辑文件。审批要绑定 task ID 和 work version；若队友认领了新任务，旧审批自动失效。启动更多 Agent 会增加成本和写入范围，应由 Lead 说明分工、预算与权限，再按用户授权启动。后台队友遇到需要交互确认的操作时，返回权限错误给 Lead，由前台与用户处理。

## 汇合、失败与评测

每个子任务的产物应有 schema：结论、证据、改动文件、验证、未解决事项。Lead 汇合时去重事实、标注冲突和置信度，并独立检查最终验收。某分支失败时，重试预算、是否换 Agent、是否取消其他分支都要明确；不能让失败的子结果被一段流畅总结掩盖。Trace 至少串起父子任务 ID、委派原因、输入摘要、版本、工具调用、结果、重试、交接次数、成本和关键路径时延。

动手实验可让三个角色共同完成代码审查：安全、兼容性和测试覆盖并行调查，Lead 汇总并验证。先用单 Agent 跑同一 diff 建立基线，再比较多 Agent 的准确率、误报率、总成本和耗时。第二轮故意制造两人认领同一任务、worktree 消失、计划审批过期和结论矛盾，检查运行时是否阻止竞态并保留证据。若收益不足以抵消协调成本，保留单 Agent 或改成固定 Workflow 即可。

## 成本与上下文传播

委派时只传任务所需的目标、约束和证据引用，不把父会话完整历史复制给每个队友。独立上下文减少相互污染，也使子任务更容易评测；但关键用户限制必须显式传入，例如“只读”“不得联网”“不可修改生成文件”。队友的结论返回 Lead 时应包含可核查证据，Lead 不应把“队友说测试通过”当作自己已看到测试结果。长期任务中，消息需标记任务版本；过时的结果到达后应归档而不覆盖新计划。

并行收益不能只看墙钟时间。总体 token、工具配额、合并冲突和人工审查也要计入。如果三个 Agent 同时读取同一大仓库，总成本可能大幅上升，而关键路径只缩短一点。给团队设置总预算、每任务预算和并行度上限；其中一个分支耗尽预算时，Lead 应能降级为单 Agent、缩小范围或向用户报告部分结果。汇合阶段尤其要防“多数意见即正确”：三个 Agent 基于同一错误证据得出相同结论，并不能代替独立验证。

任务板也需要处理失败所有权。队友崩溃后，任务不能永远停在 `in_progress`；宿主可根据租约、心跳或明确的错误事件释放它，再检查该队友的工作区和已发生副作用。释放后重新认领的执行者必须先读前任留下的产物和状态，不能从头重复写。任务完成与 worktree 清理分开：先验证产物、合并或保留分支，再由宿主检查未提交文件并决定是否移除目录。

## 团队协议的最小字段

消息可用自由文本解释思路，但任务和控制事件需要结构化字段：`task_id`、`sender`、`recipient`、`message_type`、`request_id`、`work_version`、`created_at`。接收方按 `request_id` 去重，按 `work_version` 判断是否过期。计划批准与任务完成使用不同事件，不能因为队友提交了结果就自动把任务标为完成；应先检查产物和验收条件。队友回到空闲状态后，也不能自动领取尚未通过依赖检查的任务。所有权变更应写入持久事件，便于重启后恢复，也便于追查并发冲突。

## 贯穿案例：并行修改两个相邻模块

用户要求同时调整认证模块和登录页，但保持现有接口，并让 Agent 在修改前展示计划。Lead 先调查依赖：认证接口改动会影响登录页，因此可并行的不是“任意两处修改”，而是认证 Agent 负责接口与测试，页面 Agent 先做只读梳理和 UI 方案，待接口契约确定后再写。Lead 创建 `auth-contract`、`auth-implementation`、`login-ui`、`integration-test` 四个任务，给后面三项设置 `blockedBy`；其中页面实现与认证实现可以在契约完成后并行，集成测试需等两者完成。

Lead 向用户说明分工、两个工作区、预算和预计汇合点，得到同意后启动队友。认证任务绑定独立 worktree；页面任务可绑定另一个 worktree。两个队友先提交计划，计划闸门允许读取文件但阻止修改和 Shell。Lead 审查计划时把批准绑定到各自 `task_id` 与 work version。某队友随后换任务，旧批准不再有效。队友执行完发出结果事件，附 diff、测试命令和未解决风险；运行时将事件投递给 Lead，并在队友进入 IDLE 时另发通知。Lead 合并分支、运行集成测试；若登录页调用了旧接口，即使两个分支分别通过测试，整体仍未完成。

```text
Lead: create nodes -> validate DAG -> ask user to approve team
Runtime: bind worktrees -> atomically claim ready tasks -> start teammates
Teammate: read -> submit plan -> wait for approval -> edit/test
MessageBus: deliver result, error and idle as separate events
Lead: verify artifacts -> merge -> run integration test -> complete goal
```

这条时间线说明 Task DAG、消息和工作区各管一件事。DAG 决定什么可以开始，MessageBus 传递进展，worktree 隔离修改，权限闸门控制动作；任何一层都不能替代其他层。

## 认领和释放的细节

队友空闲时先读收件箱，再扫描任务板。扫描只获得候选快照，claim 必须在锁内重新检查状态、依赖、owner 和 worktree 绑定。成功后把 owner 与 `in_progress` 原子写入持久存储，再允许文件工具运行。若绑定路径损坏或 Git 注册信息不一致，认领失败并留下明确错误；自动退回主仓库会让两个队友写进同一个目录。任务完成时先记录产物与状态，当前模型轮剩余工具调用仍使用原 assignment；下一轮回到 IDLE 才释放工作目录，防止一轮内路径突然改变。

队友崩溃后的任务不能无限占有。宿主检查心跳、线程状态与持久租约，确认原执行者不再运行，再释放认领并记录原因。新队友接手时先核对工作区 diff、后台命令和外部副作用，避免重复提交。完成任务不意味着可以删 worktree：分支上可能有干净提交、未跟踪文件或需要人工审查的改动。移除应由宿主在检查 Git 状态、任务租约和用户确认后处理。

## 选择协作形式的实验

同一个代码审查任务分别使用单 Agent、三个一次性 subagent、持久团队和固定 Workflow。单 Agent 作为基线；subagent 适合三个互不依赖的调查，但共享工作区时全部保持只读；持久团队适合有后续追问与任务认领的开发；Workflow 适合审查阶段与汇合顺序固定。评测时保持输入和工具权限相同，记录发现真实缺陷数、误报、总耗时、token、冲突和人工协调时间。若持久团队只在长任务上有优势，短问题就不应默认启动团队。

让实验再经历四种失败：两个队友同时扫描同一 ready task、一个 worktree 被外部删除、计划批准后任务被重新分配、一个队友返回与测试日志相矛盾的“已通过”。预期行为分别是原子 claim 只让一人获得所有权、工作区 fail-closed、旧批准失效、Lead 以测试证据为准。把这些变成自动化测试，才能说协作运行时可靠。

## 汇合冲突怎样裁决

假设安全队友认为一个接口存在越权，测试队友却报告用例全部通过。Lead 不应在总结里把两种结论平均成“可能有风险”，而应检查权限用例是否覆盖攻击路径、测试使用什么身份和数据、两队友基于同一代码版本吗。能写确定性复现时，优先运行复现；不能复现时保留两份证据与不确定性，交给有权限的人判断。对每个结论记录来源任务 ID 与代码版本，防止后到的旧消息覆盖新事实。

协作权限也应最小化。只读调查队友不需写权限；负责页面的队友不需生产数据库凭据；验证队友可运行测试但不应推送分支。Lead 不能通过给队友下命令绕开用户原本的授权范围。若新的分工会增加成本、并发写入或外部访问，应先告知用户并取得对应授权。团队规模变化后重新计算总预算，尤其关注多个队友在相同错误上同步重试造成的成本放大。

## 管理者自身也要有完成条件

Lead 的任务不是收齐队友消息就结束。它需检查所有必需 Task 已完成、产物版本一致、共享契约通过集成验证、用户最初的限制仍被满足。队友结果若只是一段自然语言，应要求补充文件或测试证据；队友无法补齐时标记部分完成。后台队友尚在运行，Lead 可给用户进度，但不能给最终成功结论。用户修改目标后，Lead 更新任务图与版本，并使不再适用的计划批准和结果失效。

团队退出也要可控。请求关闭队友使用带 `request_id` 的控制消息，队友完成当前安全收尾后回执；超时后由宿主按任务租约处理。直接杀线程可能留下后台命令、未持久化结果和被占用的 Task。清理顺序是停止新认领、处理进行中的动作、保存结果或错误、释放所有权、再检查 worktree。这个顺序可在故障注入实验中验证。

在教学练习中可用文件收件箱实现 MessageBus，但生产系统还要考虑跨进程并发、消息保留期和权限。消息正文可能包含敏感仓库片段，不能因为它位于“团队内部”就免除访问控制与脱敏。

## 面试会怎么问

小红书 Agent 一面问到多 Agent 并发；美团 Agent 开发复盘问状态汇总与路由。面试回答应先证明拆分的必要性，再讲并行的共享边界。

**问：怎样判断一个任务值得拆成多个 Agent？** 答：先做单 Agent 基线。如果两个子任务可以独立读取、结果容易合并，且并行节省的时间大于协调成本，可以拆分；如果它们持续修改同一状态或都需要完整上下文，多 Agent 可能只增加消息和冲突。给每个子任务定义输入、可用工具、输出格式、预算与验收标准，最终由一个确定的汇合点处理冲突。

**问：两个 Agent 同时改同一文件，怎么处理？** 答：尽量按文件或模块划分所有权；必须共享时用版本或工作区隔离，合并前检查 diff 和测试。发生语义冲突不能简单以后提交者覆盖前者，应保留两个提案、指出冲突区域，由协调者根据任务目标裁决并重新验证。多 Agent 轨迹需记录谁做了哪个动作、用的哪版输入，避免最终只剩一条模糊摘要。
