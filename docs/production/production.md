# 生产运行：状态、恢复、容量与成本

生产 Agent 的一轮请求可能调用多次模型、检索和外部工具，持续数分钟甚至跨用户会话。服务需在用户离开、进程重启、模型限流、工具部分成功和人工审批迟到时仍能给出可信状态。核心做法是把任务状态、事件和副作用明确持久化，让每次继续执行都知道此前做到了哪一步。

## 任务状态与恢复点

任务至少区分 `queued`、`running`、`waiting_for_input`、`waiting_for_approval`、`succeeded`、`failed`、`cancelled`。每次状态变化写入原因、版本、时间、当前 owner、已完成步骤、输入输出引用和检查点。状态更新使用版本比较，防止两个 worker 同时把旧状态覆盖成新状态。取消应先阻止新动作，再尝试停止正在运行的命令或模型调用；已生效的外部动作要单独记录，不能靠改状态字段撤销。

| 故障 | 恢复前先查 | 安全处理 |
| --- | --- | --- |
| 模型 429/529 | 重试次数、剩余预算、服务状态 | 退避、切换已评测模型或排队 |
| 上下文过长 | 可恢复的旧输出、当前目标 | 先裁大结果和旧结果，再摘要 |
| 工具超时 | 上次调用是否已生效、幂等键 | 查询状态后重试或交给人 |
| 部分成功 | 已完成对象集合 | 只补剩余对象，保留补偿路径 |
| 进程重启 | 快照、journal、工作区差异 | 重新取得任务所有权后续跑 |
| 审批迟到 | 动作参数和策略版本是否变化 | 旧审批失效，重新展示精确动作 |

幂等键应由同一业务意图稳定生成，重试沿用原键。写工具返回 `PARTIAL_SUCCESS` 时列出已写对象和未完成部分；运行时不可把它归一化成普通失败后盲目重放。长任务可用快照加追加式 journal，恢复时检验日志完整性、取得运行锁并跳过已确认完成的阶段。Workflow 的稳定语义 key 适合复用纯计算或模型阶段；外部副作用仍要以业务系统状态为准。

## 后台、队列和定时任务

显式后台调用先返回任务 ID 与占位结果，worker 完成后把 `task_notification` 注入会话。主模型想结束时，若关键后台任务仍在运行，应保持目标待定，不能根据旧消息宣称完成。队列需要重试、死信、取消和 backpressure；任务所有权要有租约或原子 claim，避免 worker 故障后产生双重执行。

定时任务的定义和触发记录应持久化。若采用至少一次投递，重复通知是正常情况，消费方需去重；调度进程停机期间是否补跑也要明确约定。只有前台用户轮次可以弹交互确认，定时或后台轮次遇到高风险动作应停在审批状态。若定时器仅存在于 Agent 进程内，进程完全退出时它不会自行醒来，持续运行需要外部调度器或常驻宿主。

## 容量、路由与降级

Agent 请求消耗的资源具有放大效应：一次用户请求可产生几十次模型与工具调用。预算应分层设置：每个 run 的时间、token、费用和最大步骤；每个模型的并发、超时和重试；每个工具的 QPS、队列与熔断；每个租户的配额和优先级。使用队列与 backpressure 限制突发量，而不是让所有请求同时触发下游限流。

模型选择先用能力较强的模型建立评测基线，再将分类、参数提取等简单阶段换成便宜模型，比较质量、P95 时延和成本。缓存只用于输入、权限和版本语义允许复用的结果；用户私有、实时变化或有副作用的结果不能简单按相似文本复用。降级可依次减少非关键反思、候选检索或并行分支，再切换已评测模型；必要时退到固定 Workflow、只读模式或人工队列。用户应看到降级和未完成范围。

## 操作演练

搭建一个“读取资料、生成草稿、等待批准后发送”的长任务。运行到草稿阶段强制杀掉 worker，恢复后核对快照与 journal，不重新生成已确认的副作用。让发送工具在写入成功后超时，验证同一幂等键下不会重复发送。再让审批在策略版本变化后到达，检查运行时拒绝旧批准并重新展示动作。最后并发发起多项任务，观察队列长度、租户配额、P95 时延、成本与死信数量。

这套演练完成后，应能回答“任务现在处于什么状态、哪一步已生效、为什么停下、谁能让它继续、继续会不会重复执行”。若这些问题只能由模型猜测，系统仍停留在 Demo 阶段。

## 状态的一致性与数据生命周期

状态持久化不应只存一段自然语言摘要。任务记录应能回答：当前 owner 是谁、最后确认完成的动作是什么、下一次安全重试从哪一步开始。对跨系统写入，可采用“先记录意图和幂等键，再执行工具，再记录结果”的事件顺序；若在执行后、写结果前崩溃，恢复程序能用幂等键查询外部系统。若选择事件溯源架构，追加事件是变更过程的权威记录，快照只是加速恢复的派生结果；二者不一致时需暂停并报警，不能默默选择看起来更新的一份。若采用普通 checkpoint 架构，版本化的 checkpoint 本身可以是权威状态，仍须记录关键副作用和状态迁移，保证恢复与审计可核验。

运行数据也有生命周期。完整工具输出和截图可能占空间、含个人信息，应设置保留期限、访问控制和删除策略；任务摘要、审计事件与可恢复文件的保留期可不同。删除用户数据时，要同步处理主库、索引、缓存、长期记忆和可访问的产物引用。长期记忆只保留稳定、获准跨会话使用的信息，并允许更正或删除。若删除后旧任务无法恢复，应向用户明确报告，而不是从过期副本悄悄重建。

## 生产值班要看什么

仪表盘至少显示队列长度、运行中与等待审批数量、成功率、P95 时延、模型与工具错误率、每任务成本、重试和死信。告警按可行动的条件触发：持续 429 且队列增长、部分成功无法补偿、同一幂等键出现不同结果，或安全拒绝率异常升高。值班人员应能从任务 ID 打开 trace、状态、版本和工作区引用，并有暂停新任务、关闭高风险工具、切只读模式和回滚发布的入口。没有明确操作手册的告警，只会制造噪声。

## 贯穿案例：长任务在发送后崩溃

一个 Agent 读取工单、生成回复草稿，经用户批准后发送邮件。任务状态从 `queued` 到 `running`，生成草稿后进入 `waiting_for_approval`。用户批准时，宿主保存精确动作摘要和幂等键，再把任务投递给发送 worker。Worker 调用邮件服务后进程崩溃，来不及记录成功结果。恢复程序不能把 journal 末尾的“准备发送”当作未发送，也不能从头再发；先使用幂等键查询邮件服务。如果服务确认已发送，补写 `tool_succeeded` 事件并继续；如果明确未发送，才重试；若结果无法确认，停在人工接管状态。

这个例子需要一条清楚的事件序列：`draft_created → approval_requested → approval_granted → send_intent_persisted → external_send → send_result_persisted → task_succeeded`。用户撤销批准只在外部发送前有效；发送后要走业务撤回或解释，不能简单把任务标为 `cancelled`。若审批到达前订单或工单内容变化，旧动作摘要失效，重新生成草稿或确认。把状态和事件分开，可以回答“现在是什么状态”和“过去实际发生过什么”。

## 幂等、补偿与重试预算

幂等键应关联同一业务意图，而不是每次工具调用都生成新随机值。比如一次邮件发送的键由任务、收件人和草稿版本确定；重试沿用它。对不支持幂等的外部服务，先查询业务对象或保存发送回执，仍无法确认时交给人。补偿不是数据库回滚的替代品：已发邮件可能无法真正撤回，只能发送更正；已创建草稿则可删除或标记作废。任务设计时就列出每个副作用的可逆性和补偿方式。

模型、工具和任务三个层级的重试预算不能叠加失控。模型 429 可退避，工具 503 可在限定次数内重试，整个任务失败后由队列重投；若三个层级都各重试五次，实际调用可能远超预期。应让最外层协调器记录总尝试次数与费用，并把错误分为可重试、需改输入、需审批和不可恢复。连续无进展时熔断，将任务与现场交给人。

## 容量设计的一个计算框架

估算峰值时，不只看每秒用户请求数，还要看每次请求平均和尾部模型调用、工具调用与后台持续时间。例如一个研究任务常见是三轮模型、五次检索，少量复杂任务可能十倍于此；只按平均值配置并发，会在尾部任务聚集时压满模型配额。队列入口可按租户和优先级限制，worker 对模型和工具分别设并发上限；超量任务返回排队状态与取消入口。耗时长的审批任务不占用模型 worker，但继续执行时仍要重新竞争容量。

缓存和路由应与评测绑定。先用强模型确定质量基线，再把简单的分类或摘要降到小模型；对检索答案缓存必须包含用户权限、文档版本和有效期。成本分解到任务类型、模型调用、检索和工具，有助于识别大输出、重复搜索或失败重试。降级为只读或人工队列时，状态中明确记录降级原因和未完成动作，用户可选择稍后继续或取消。

## 消息投递与任务所有权

队列通常只能保证消息可能重复到达，不能保证外部动作恰好执行一次。Worker 领取任务时使用原子 claim 或租约，记录 owner 与版本；执行前再次检查任务是否已取消、权限是否仍有效。处理完毕后持久化结果，再确认消息消费。若确认消息前崩溃，同一任务会被重新投递；新 Worker 读取事件和幂等键，跳过已生效动作。若租约到期而旧 Worker 仍在执行，需要防止两个 Worker 并发写同一对象，例如使用 fencing token 或业务版本比较。

定时任务要区分“计划到点”和“用户目标仍有效”。到点触发的提醒可重复投递，消费端按触发 ID 去重；进程离线期间是否补发由产品语义决定。每分钟运行的巡检任务若停机两小时，补跑一百二十次可能毫无意义，应显式选择跳过或合并。定时触发不代表授予新的权限，尤其不能让无人值守轮次自动批准发信、删除或发布。用户取消计划后，队列里已投递但尚未执行的事件也要检查取消版本。

## 从故障到值班动作

若队列突然增长，先区分入口流量上升、模型限流、工具 P95 变慢和 Worker 故障。限流时降低并发可能比加 Worker 更有效；工具部分成功激增时应暂停有副作用的重试，避免数据重复。若成本异常，沿 trace 检查循环、重复检索和大结果压缩，再决定调整模型路由或预算。值班手册至少提供暂停新任务、切只读、禁用某工具、查看 run 状态、恢复或取消单任务的步骤。所有操作写审计事件，便于事后还原。

演练可在测试环境连续注入：模型 429、工具超时、Worker 崩溃、通知重复、审批过期和用户取消。逐个核对最终状态、外部副作用次数、队列残留与 trace。通过标准是系统既不丢任务，也不把不确定状态假装成成功；无法自动判断时把明确证据交给人。

容量评估也要考虑失败模式：上游模型慢时，排队任务仍占内存与存储；下游工具恢复后，大量重试会形成第二次流量峰值。重试加入抖动、按租户限速，并给用户可见的排队状态，比让所有 Worker 同时冲击服务更稳妥。

## 面试会怎么问

字节 Agent 秋招复盘问到文档自动更新时怎样防并发覆盖、RocketMQ 放在哪；美团 AI Agent 一面复盘问到长流程稳定性。两题都考“后台任务被重复运行时会发生什么”。

**问：为什么文档更新不直接放在定时任务里做完？** 答：定时器可以负责发现待更新文档，队列或持久任务负责后续处理，让解析、索引和验证拥有独立重试与容量控制。每份文档使用稳定任务键和版本条件写入，避免两个 worker 用旧结果互相覆盖；删除与权限变化也要传播到索引。队列保证可投递，不天然保证业务只执行一次，因此消费者仍需要幂等与状态核对。

**问：任务发出外部消息后进程崩溃，怎么保证不重复发送？** 答：先承认状态可能不确定。发送前持久化操作 ID，尽量使用下游幂等键；恢复时查询外部系统或发送回执，确认成功便补写本地状态，确认失败才复用原键重试。若下游不支持查询或幂等，需要设计人工核对或补偿，不能承诺绝对“只发送一次”。

题目来自候选人个人复盘，回答按生产运行的通用故障语义展开。
