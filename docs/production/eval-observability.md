# Agent 评测与可观测性：从结果追到轨迹

Agent 的一次任务可能跨越多轮模型调用、检索、工具与人工审批。只看最终回答，无法区分模型判断错误、工具返回错数据、检索漏掉证据，还是运行时重复了动作。可观测性记录实际发生的步骤；评测用预先定义的标准判断这些步骤及结果是否可接受。两者合起来，才能把线上失败变成可复现的改进任务。

## Trace 应该记录什么

一个任务对应一条 trace；模型调用、检索、工具调用、审批、子 Agent 和 Workflow 阶段可各成 span。父子 ID 将它们连起来。每个 span 记录开始与结束时间、版本、输入输出摘要、状态、错误码、token 与成本；敏感内容只保留脱敏摘要或受控引用。工具的真实参数与结果需足以重放故障，但不能把密码、完整个人资料和机密文档无差别写入日志。

| 层级 | 关键字段 | 常见问题 |
| --- | --- | --- |
| Run | task_id、用户/租户作用域、目标、版本、最终状态 | 同一类任务成功率是否下降 |
| Model span | model、prompt 版本、token、耗时、停止原因 | 是推理慢，还是上下文膨胀 |
| Tool span | 工具名、参数摘要、权限决定、错误码、幂等键 | 是否重复写入或被拒绝 |
| Retrieval span | 查询、索引版本、候选 ID、过滤原因 | 证据是否进入候选集 |
| Human span | 审批对象、决定、时间和批准的动作摘要 | 人批准的是否就是执行动作 |

OpenTelemetry 形式的 span 有助于把 Agent 轨迹与后端服务、队列和数据库请求关联。手动补充业务字段时，高基数值不要用作指标标签或 span 名称，敏感原文不要写入遥测；受访问控制和保留期约束的 span 属性可保存 run ID、操作 ID 等关联标识。比如订单处理任务的指标标签可用订单类型、工具错误类别和策略版本，不应把整张订单或每个订单 ID 塞进标签。状态机事件与 trace 要能互相定位：`waiting_for_approval` 的 run 应找得到暂停它的动作。

## 四层评测

Outcome 看任务是否达成，可用确定性断言、人工标注或业务系统结果；Trajectory 看路径是否合理，包括多余步骤、循环和不必要的交接；Tool 看参数、权限和错误恢复；Safety 看注入、越权、泄露和高风险确认。一个答案正确但曾把机密数据发给外部工具的运行，应在 Safety 层失败。一个安全但没有完成目标的运行，也不能计作成功。

评测集从窄任务开始。为每例保存输入、环境快照、期望结果、禁止行为、允许的工具与评价方法。准备正常、边界、失败和对抗样本；至少让少量 smoke cases 在每次提交时运行，更大的离线集在发布前运行。案例最好覆盖工具超时、空检索、权限变化、部分成功、上下文压缩、后台通知迟到等条件。数据集版本固定，模型、prompt、工具和策略版本也记录下来，才能比较前后差异。

```text
for case in eval_set:
    run = execute_agent(case.input, frozen_environment=case.fixture)
    scores = {
        outcome: check_expected_artifact(run, case),
        trajectory: check_loop_and_unnecessary_actions(run.trace),
        tool: check_schema_permission_and_retries(run.trace),
        safety: check_forbidden_actions(run.trace, case),
    }
    save(case.id, run.version, scores, failure_category(run))
```

LLM-as-Judge 适合评价难以写成精确断言的表达质量，但应使用明确 rubric、盲化候选版本并用人工标注样本校准。对于“文件是否写对”“指定测试是否通过”“有没有调用禁用工具”，直接执行检查更可靠。报告同时列样本数、分群、置信范围和失败类型；只报平均分会掩盖少数高风险场景。

## 从线上 bad case 回到离线集

先按任务类型观察成功率、P50/P95 时延、每 run 成本、工具错误、人工接管和安全事件。出现退化时取 trace，沿“目标 → 上下文 → 检索 → 模型决策 → 工具 → 结果”逐段定位。复现前固定输入和可控依赖；把新失败抽象成不含敏感数据的回归样本。修复后比较总体收益和分群退化，再用小流量 shadow 或 canary 检验真实分布。用户显式评分、重问、撤销和手动修正都可提示问题，但这些信号不能直接等同于真值标签。

动手练习可构建 20 例评测表：10 例常规、5 例错误/恢复、5 例权限/注入。对同一 Agent 跑两个版本，输出四层评分、成本和失败分类。选一例“任务从 5 分钟涨到 20 分钟”，用 trace 证明究竟是模型调用、重复读取、工具等待还是重试造成，再做一项改动并回归。验收标准是别人能重跑、能定位、能说明修复对哪些样本有效，而不是图表变好看。

## 评测集的维护规则

评测集会老化。新工具上线、业务政策变化、知识库更新后，旧期望结果可能不再成立。每条样本应保存创建原因、适用版本、标注人或自动断言来源，以及何时复核。发现模型“背熟”固定样本时，可保留一组从未用于调参的留出集，并用近期线上分布补充新案例。对含用户数据的坏例，先去标识化、取得允许的用途，再决定能否进入离线集；不能直接复制生产 trace 作为公开测试材料。

判分需要区分硬门槛和优化指标。越权工具调用、泄露密钥、未经确认的付款属于硬失败；响应时延和多余步骤可作为连续指标。不同任务类型的成功定义也不同：研究助手要核验来源、Coding Agent 要运行测试并审查 diff、FDE 试点还要看用户是否采用。一个通用的“回答质量分”不足以替代这些业务结果。上线比较应同时报告通过样本、失败样本和结论不确定的样本，人工仲裁结果要反写为明确规则。

## 指标异常时的诊断顺序

若成功率下降，先确认流量构成与版本是否变化，再抽取同类任务的成功/失败 trace 对照。若成本上升但成功率不变，检查模型路由、重复检索、长工具输出和失败重试；若 P95 变差而 P50 稳定，重点看少数慢工具、队列等待或长任务恢复；若用户重问率上升，检查是否有引用过期、答案与任务不匹配。每次改动只提出一个可检验假设，在离线集验证后再观察线上，避免同时换模型、Prompt 和检索策略导致归因不清。

给评测报告附上每类失败的原始 trace ID 或脱敏复现脚本。这样评审者能抽样检查分数是否对应真实行为，也便于后来判断一次修复是否只是更换了评价口径。

## 贯穿案例：文档助手答对了却仍不合格

假设企业文档助手回答“服务 A 如何回滚”，最终文字与公开手册一致，但 trace 显示它先读取了一份当前用户无权访问的事故报告。Outcome 若只看答案会给满分，Safety 必须判失败；Tool 层要指出哪个检索或读取工具绕过了 ACL；Trajectory 层可发现它多做了一次无关搜索。改进不能只让模型“不要看敏感文档”，应修复工具授权，再用同一用户、同一问题、两份权限不同的文档重放。修复后既要确认答案正确，也要确认受限文档从候选、模型上下文和日志中都消失。

为这个例子建立最小可复现 fixture：用户身份、文档版本、权限表、预期可见证据、禁止访问的文档 ID 和标准答案。运行时冻结索引快照，保存每段检索的候选 ID、过滤理由与最终引用。若线上无法保存原文，使用经批准的脱敏替代内容。这样一个“答案正确”样本同时覆盖结果、轨迹、工具和安全四层，也能在权限策略升级后复测。

## 设计一张可执行的二十例评测表

不要让二十例全是正常问答。可以按任务分为：六例常规成功、四例边界输入、四例工具或检索失败、三例权限变化、三例注入与危险动作。每条记录 `case_id`、输入、固定环境、预期产物、禁止动作、评价器与失败类别。常规例可用确定性断言核验引用、文件或 API 状态；边界例检查缺字段、无答案和歧义澄清；失败例注入 429、超时、空检索和部分成功；安全例检查是否真实调用了禁用工具，而不是只看最后回答是否拒绝。

评分时既保存每层的 0/1 或分档结果，也保存原始数值：调用次数、P95 时延、token、费用、人工接管和重试。比如“模型只多调用一次”在轻量 FAQ 中可能影响成本，在高风险诊断中也许合理；要按任务权重解释。硬安全门槛单独计算，不能让其他十九例的高分掩盖一次未经批准的写操作。样本数较小时，报告具体失败清单比强调一个小数点后的总体百分比更有用。

## 校准模型评分器

Judge 适合判断解释是否完整、引用是否支持结论等软指标，但应先写评分说明与正反例。抽取一批样本由两位标注者独立评分，核对分歧；对高风险样本使用人工裁决或确定性规则。将候选系统版本匿名，避免 Judge 因知道“新版”而偏向它。对照 Judge 分数与实际任务成功，检查是否偏爱冗长回答、忽略缺失引用或把安全拒绝误判为无帮助。若评估器本身版本变化，先在固定校准集上重跑，不能把分数变化直接归因给 Agent。

最终发布决策可用门槛表：Outcome 达到基线、Safety 零红线、Tool 错误率不过阈、成本与 P95 可接受。门槛数值应由业务风险和现有版本确定，而不是从教程抄一个通用比例。线上新失败进入离线集时标记采样来源，防止同一异常大量重复，使评测集偏离真实任务分布。

## 用轨迹定位一次时延退化

假设研究助手的 P95 从 4 分钟升到 17 分钟，但平均回答质量没有改善。先按任务类型和版本切分，确认不是长问题占比突然增加。抽取慢 run 的 span：模型推理总耗时、工具等待、队列等待和重试分别占多少。若模型 span 多，检查是否重复读取同一文档、工具结果是否膨胀、压缩是否频繁触发；若工具 span 长，检查检索或网页请求的 P95；若排队时间长，检查并发上限和下游限流。修复假设可以是“限制单次工具输出并给模型文件引用”，先在固定慢样本上重放，确认成功率不降、重复读取减少，再小流量观察真实 P95。

这类分析不能只比两张总体图。版本、输入长度、租户规模和工具健康状况都可能是混杂因素。对照实验尽量固定同一任务与环境；线上无法完全固定时，至少按关键维度分群，并标注结果不确定性。若改动同时降低成本却损害少数复杂任务，应展示这组退化，而不是让总体平均掩盖它。

## 轨迹数据的访问与保留

Trace 对排障有价值，也可能包含用户提问、文件片段和工具结果。采集前定义必要字段、脱敏方式、保留期限和谁能查看。研究调试人员未必需要看到原始个人资料；可使用内容哈希、受控对象引用和错误类别。需要复现时在获授权的隔离环境取回材料。评测数据从生产样本转来时，确保用途允许并去标识化，保留样本来源与版本；删除用户数据时同步处理可检索的 trace 和评测副本。

观测系统自身也会故障。Trace 出口不可用时，核心任务是否继续、是否落本地缓冲、何时告警要有约定。高风险写操作至少应保留可信审计事件；若连审计都无法保证，可选择拒绝动作。不要把全部原始模型上下文当默认日志，因为成本、隐私和访问控制都会失控。把最小可行动字段先做稳，再按具体排障需求增加采集。

最后将评测门槛写入自动化发布检查：保存候选版、基线版和评测集版本，输出逐例差异。评测脚本失败或数据集不可读时，发布应停下并报告基础设施错误，不能把“没有测到失败”解释为通过。

## 面试会怎么问

美团 AI Agent 一面复盘问到长流程保障、幻觉确认和异常测试；百度 MEG 的复盘从 Agent 项目追到诊断过程。回答评测题时，要让面试官看到你如何从一条失败轨迹定位问题。

**问：一个任务最终答对了，为什么还可能判失败？** 答：结果正确只是 outcome 的一部分。若过程中访问了无权限资源、重复执行写操作、泄露敏感数据或超出预算，这次执行仍不可接受。评测集应分别记录任务结果、工具轨迹、安全边界、成本与时延。对开放式答案可用人工或校准过的评分器，但金额、对象 ID、权限和写操作次数应优先用确定性断言。

**问：线上突然出现一批幻觉答案，怎么排查？** 答：先抽取具体 trace，核对输入、文档版本、检索候选、rerank 结果、模型可见上下文和最终引用。若正确证据根本没进入候选，修检索或索引；若证据可见却被忽略，检查生成约束与上下文竞争。把失败样本脱敏后加入回归集，修复前后在同一数据版本上比较，不只展示一个成功演示。
