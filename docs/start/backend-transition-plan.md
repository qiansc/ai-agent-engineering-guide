# 后端转 AI 应用开发：八周做出能交付的作品

如果你已经做过 API、数据库、缓存、消息队列或云原生服务，不必把过去的经验清零。AI 应用开发仍然需要这些能力，只是多了一条“不完全确定”的模型链路：相同输入可能产生不同输出，检索与工具调用会相互影响，HTTP 200 不能证明答案可靠。本路线面向有后端基础、想转向 LLM 应用、RAG、Agent 或模型服务的工程师。建议用六到八周完成一个可评测、可追踪、可降级、可部署的项目，而不只做聊天页面。

## 起点：哪些能力可以迁移，哪些需要新学

后端能力直接迁移到身份与权限、接口契约、并发、缓存、幂等、超时重试、状态机、观测和发布。新增的五个问题是：模型输出有概率性；Prompt、检索结果、工具返回和对话历史共同构成运行时上下文；质量不能只靠传统单测；同一个“答错”可能出在数据、召回、排序、生成或编排；自然语言与外部文档可能诱导系统越权。

学习时不要把两类能力割裂。例如调用模型 API 时仍需超时与限流，但还要验证结构化输出和内容依据；做 RAG 时仍需数据版本和权限控制，但还要评测检索命中与引用正确。下面每一阶段都有交付物和通过标准；完成标准比“看完某门课”更重要。

## 第 1 周：建立够用的模型运行认知

先弄明白 Token、上下文窗口、生成参数、幻觉和推理成本。后端应用工程师不必先掌握大模型训练，但必须知道 Token 为什么影响截断、费用与延迟；`temperature` 等参数会改变生成分布，不能拿一个漂亮样本当稳定性证据。还要区分传输错误、供应商限流、模型没有按 Schema 输出、回答虽成句却无事实依据等不同失败。

本周交付一个统一模型客户端。它接收系统指令和消息历史，支持超时、有限重试、流式输出、结构化输出、模型切换，并记录 Token、费用、延迟和错误类型。重试应只用于可重试的请求，并考虑重复扣费或重复外部动作；结构化输出必须由程序解析校验，不应只靠提示词要求“请输出 JSON”。用固定样本比较两个模型或两组参数，记录格式通过率和成本，而不只挑最顺眼的回答。

通过标准：当一次请求返回 HTTP 200，你仍能说明答案可能在哪里失败；当供应商超时、限流或返回非法格式时，客户端的行为可预期且可测试。

## 第 2 周：把 Prompt 变成可测试的接口

系统指令、开发者约束、用户内容和检索到的文档有不同可信级别。把 Prompt 当成版本化的程序接口：输入字段、任务边界、允许与禁止的输出、澄清条件、Schema 和错误处理都写清楚。对抽取任务，先定义什么字段“没有证据就留空”，再定义日期、金额和实体的格式。对内容审核，明确冲突规则和人工复核条件。

本周给一个信息抽取或审核任务建立测试集：至少 30 个正常样本、10 个边界样本和 5 个攻击样本。记录准确率、格式通过率、拒答率、单次成本，并保留失败样本。改 Prompt 时只变一个主要因素，固定模型版本和评测集，比较差异；否则你无法判断提升来自提示词、模型升级还是样本变化。攻击样本应包含把“忽略之前要求”藏在待处理文本里的输入，验证宿主不会把用户数据提升为系统指令。

通过标准：一次 Prompt 修改能走回归测试；效果下降时能定位变量，而不是继续凭感觉润色文案。

## 第 3–4 周：做出 RAG 的数据与检索闭环

RAG 是数据系统，不是“接向量库”。离线链路包括文档采集、解析、清洗、切分、元数据与权限、embedding、索引发布；在线链路包括问题处理、关键词或向量召回、过滤、重排、上下文组织、生成与引用。保留文档标题、章节、版本、生效时间、来源和 ACL，才能回答“为什么引用了这段、它现在是否仍有效、这个用户有没有权看到”。

切分时不要先背一个固定 chunk size。根据文档结构做几组实验：按标题与段落切、按固定 Token 切、带不同重叠率的切法。较小块利于精确匹配，但可能丢失上下文；较大块保留语境却可能增加噪声。关键词检索对精确名词、编号和错误码有优势，向量检索适合语义改写；混合检索需对分数与去重作设计。重排能改善前 K 个候选的顺序，但不能凭空找回初筛根本没召回的文档。

本阶段交付一个领域知识库和至少 50 条人工标注问题。每条问题至少标出应命中的证据、参考答案或“无答案”。分别测召回命中率、重排增益、答案事实性、引用正确率、无答案拒答率、延迟和成本。每个 bad case 分类为数据缺失、解析/切分、召回、排序、上下文组装或生成问题。知识更新后还要测新版本可见时间与旧版本失效时间。

通过标准：遇到错误回答，你能沿 trace 找到发生错误的层，而不是只让模型“再认真想一遍”。

## 第 5 周：先做工作流，再引入受限 Agent

若路径可提前穷举，使用确定性 Workflow；只有当下一步需根据环境状态选择工具、任务路径无法完全预设时，引入 Agent。可以从上周的 RAG 项目扩展两个工具，例如检索、数据库只读查询与工单草稿。模型负责在许可范围内选择何时查询或澄清，宿主程序负责身份、权限、参数校验、预算、状态和审批。

工具接口要写清输入类型、允许范围、副作用、超时和错误码。读操作可按策略重试；工单创建等写操作需要稳定幂等键，超时后先查是否成功。敏感动作默认草稿或人工确认，并记录审批人和执行结果。工具返回的网页或文档是数据，不是新的系统指令。若接 MCP，理解它是工具与上下文接入协议，不等于模型会安全调用工具；宿主仍要 enforce 权限。

本周交付一条可演示的工具闭环和完整 trace，包括模型为何选工具、实际参数、宿主校验、工具结果与终止原因。通过标准：你能明确指出哪几步由代码控制，哪几步交给模型判断；任何写操作都有审批、幂等、审计与必要的补偿设计。

## 第 6 周：补状态、记忆与长任务恢复

聊天历史、当前任务状态、用户偏好、领域知识和工具状态不该塞进同一个消息数组。聊天历史用于当前对话；任务状态存目标、步骤与进度；长期记忆只保存经过筛选且允许跨会话使用的信息；领域知识由版本化知识库管理。Memory 与 RAG 都可检索，但更新频率、权限和删除要求不同。不是所有用户一句话都应自动写入长期记忆。

给项目加入会话与任务状态分离、记忆写入规则、摘要压缩和中断恢复。模拟一次长任务运行到一半进程退出：新 worker 应从 checkpoint 读取步骤状态，确认已执行的副作用，再继续剩余步骤，不能盲目重放所有工具。再制造一次错误记忆写入，验证用户或维护者能查看、纠正、删除，后续回答不会继续引用污染信息。

通过标准：你能解释压缩摘要如何保留目标、约束、已完成动作和未完成项；恢复后系统不会重复发消息、重复下单或重复创建工单。

## 第 7–8 周：把 Demo 做成生产型作品

最后两周不以“再接一个框架”为目标，而是补交付能力。API 需要流式响应、取消、超时、限流和降级；数据需要版本、权限与清理；模型与工具需要路由、Schema 校验与故障分类；质量需要固定测试集、组件指标和回归门禁；可观测性要能查看每一步 trace、Token、费用、延迟和用户反馈。安全边界包括最小权限、敏感信息处理、提示注入测试和高风险动作人工批准。

上线从只读或建议模式开始，经过离线评测、shadow 运行、小流量灰度，再考虑低风险写入。模型、Prompt、工具 Schema、索引与策略都应有版本；错误增加时能回滚到上一个已验证组合。准备一份 Docker 化或同等可复现部署方式、配置说明、架构图、示例数据、演示与复盘。项目的 README 要写已知限制，不要只放一张成功截图。

最低交付检查可以按下表走；这里的“完成”意味着有运行证据或测试，而不是文档里写了这个词。

| 层级 | 最低可验证交付 |
| --- | --- |
| API 与运行时 | 流式响应、超时、重试边界、取消、幂等、限流 |
| 数据与状态 | 文档版本、会话和任务状态分离、权限隔离 |
| 模型与工具 | 模型路由、结构化输出校验、工具参数校验、降级 |
| 评测 | 固定样本、检索与生成分层指标、回归门禁 |
| 观测 | Trace、Token、成本、延迟、错误类型、用户反馈 |
| 安全 | 最小权限、数据脱敏、注入测试、人工审批 |
| 交付 | 可复现启动、配置隔离、架构图、演示和失败复盘 |

## 面试会怎么问

常见开场是“你做后端，为什么转 AI 应用开发？”不要回答“AI 热”。更好的叙述是：我把接口、状态、权限、可靠性和观测能力带进概率性系统；模型调用只是其中一环，我能定位检索、生成、工具和编排链路上的质量问题，并用测试集与反馈持续改进。

项目深挖通常沿三条线走。第一条问 RAG：一次答错怎样归因、如何比较 chunk 与重排；第二条问 Agent：为什么不用固定 Workflow、写操作如何保证安全和幂等；第三条问生产：任务断线是否丢失、模型升级后怎样回归、限流或供应商故障时如何降级。为每条线准备一组真实实验、失败样本和取舍，而不是背一段统一“标准答案”。如果项目只有个人实验规模，诚实说明边界，再讲若放量会先验证什么。
