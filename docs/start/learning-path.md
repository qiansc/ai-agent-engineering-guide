# 从最小闭环到生产系统：Agent 学习路线

学习 Agent 最有效的单位是一个可运行、可失败、可解释的产物。单独记住一个框架的类名，难以回答“工具执行了一半时怎样恢复”“检索结果越权怎么办”。相反，沿同一个项目逐步增加能力，可以看见每层机制解决什么问题，也能看见它带来的新风险。

这条路线以“支持工单助手”为贯穿案例。用户询问账单异常；系统读取政策与订单信息，生成带证据的解释；涉及退款时只创建草稿，等待人确认。案例可以换成代码审查或内部研究，但始终保留真实的输入、工具、失败和验收标准。

开始前需要具备最基本的编程能力：能调用一个 HTTP API、读写 JSON、运行测试、理解异常和异步任务。尚不熟悉模型 API 的读者，先用十几行代码完成普通聊天和结构化输出；不必先学复杂框架。已经有后端经验的人，可以直接从工具调用和状态开始；熟悉 RAG 的人应把重点转到权限、失败恢复与评测。路线按能力缺口推进，不要求所有人花相同时间。

贯穿项目应固定一份可复现的数据：若干账单、政策版本、用户权限和预期解释。初期可以用本地 JSON 模拟，避免外部系统抖动掩盖设计问题。等循环和测试稳定，再换成真实只读接口。每加入一个能力，都保留上一阶段的基线与失败样例。这样能回答“这次新增的模块究竟改善了什么”，也能发现增加复杂度后反而退化的情况。

## 第一阶段：做出最小工具闭环

先用一个模型、两个只读工具完成一件窄事。例如 `search_policy(query)` 查找候选政策，`read_policy(id)` 读取选中文档。模型收到用户问题后，可以返回最终答案，也可以发出结构化工具调用；宿主检查工具名和参数，执行后把结果回传模型。设置最大步数、单次超时和总费用上限。模型没有权限自己调用任意函数或决定扩大预算。

第一阶段的验收不是“演示能答对一个问题”，而是保存至少五个样例：正常命中、空结果、工具超时、错误参数、模型重复调用。每个样例应显示最终状态与原因。若检索为空，助手应说明缺少证据，而非补一个貌似合理的答案。此时不要引入多 Agent，也不需要持久记忆；复杂度会掩盖最小循环中的错误。

第一天可先画数据流：用户输入进入模型，模型返回动作或答案，宿主校验并执行动作，工具结果再送回。第二天实现结构化工具调用，并保存一条完整轨迹。第三天加入步数和时间预算，第四天处理格式错误与空结果，第五天写测试。代码规模并非硬指标；控制在自己能逐行解释的范围即可。若框架让工具调用像一个函数那样“自动发生”，仍应追踪究竟谁做了参数校验、错误回传和终止决定。

一个可核对的最小样例是输入“订单 `ord_a1` 适用什么退款政策”。预期轨迹为搜索政策、读取匹配版本、检查订单时间、返回带政策 ID 的解释。若订单时间缺失，系统应询问或标注无法判定；若模型直接从训练知识回答，测试应失败。把工具响应固定成模拟数据后，测试既能重复运行，也能避免今天与明天的外部搜索结果不同。

## 第二阶段：建立工具和知识边界

把查询工具接入真实或仿真的文档集合，给每份文档保留来源、版本和访问范围。建立一小组标注问题，先测搜索能否找回证据，再测生成是否忠于证据。随后加入一个写操作，例如 `create_refund_draft`，但执行前校验订单身份、金额范围和理由格式；“发送退款”仍不开放。工具失败需返回稳定错误码和可重试标记，让 Agent 知道是换查询、等待、停止还是请求人工帮助。

这一阶段的产物应包括工具 schema、权限测试、十到二十个检索样例，以及至少一次“正确证据在候选集中但回答仍错”的诊断记录。区分检索失败与生成失败，能防止反复修改提示词却放任索引质量问题。

建立评测样例时，给每道题保存问题、用户身份、预期证据、允许的动作、不可接受的动作和结果判断。不要只写一段标准答案，因为同一事实可以有不同表达。对于金额和订单 ID，用确定性断言；对于解释质量，可用人工检查或经过校准的评价规则。将“无法回答”与“拒绝越权”也列为正确结果，避免系统为了提高表面答题率而编造。若检索返回证据但回答不引用，单独记录引用失败，不要把它混进检索失败。

第二阶段结束时应能说明一次具体错误的定位过程：原始文档是否解析正确，正确片段是否进入候选，模型是否看见它，引用是否支持最终句子。若四步中任何一步没有日志，就补观测再优化。此时可以尝试简单 BM25 与向量检索对比，但不要急着接入多个框架或大量外部工具；先让一个窄场景的证据链成立。

## 第三阶段：让长任务可恢复

给工单任务显式状态：`queued`、`running`、`waiting_for_approval`、`succeeded`、`failed`、`cancelled`。持久化已读取文档、生成的草稿、等待的审批以及下一步。模拟进程在草稿创建后退出：重启后应复用原任务和幂等键，不再创建第二份草稿。再加入取消、超时、预算耗尽与人工接管。检查点应保存结构化状态和资源引用，不能只保存一段聊天摘要。

只有当单 Agent 的上下文或权限边界确实成为瓶颈，才考虑工作流图或子 Agent。可以让“证据收集”和“政策核对”并行，但两者都只读；合并时按证据 ID 去重，遇到冲突标记给人处理。这样学到的是任务依赖与合并机制，而非让多个角色互相对话。

第三阶段还应做一次“相同任务由三种方式完成”的比较：固定 Workflow、单 Agent、两个子 Agent。记录哪种方案最容易定位错误，哪种需要最少模型调用，哪种在政策版本冲突时更稳。若多 Agent 仅让步骤变多、答案不变，就把它从最终实现撤下。学习目标是建立判断复杂度的能力，而非每学一个概念就永久加入架构。

检查点测试应覆盖一个真实的中断时刻：草稿工具已经成功，模型还没收到响应。重启后从数据库或工具查询结果，找回草稿 ID，然后进入等待审批；不得再次创建草稿。再让用户取消任务，观察“取消 Agent 运行”和“撤销已创建草稿”是否被明确区分。若已提交退款，则需要另外的业务补偿过程，不能通过删除对话记录假装动作没发生。

## 第四阶段：评测、观测与发布

为每次运行记录 task ID、模型与提示版本、工具调用、错误、耗时、token、成本和最终结果。离线集按正常、空结果、权限、失败恢复、高风险动作分层。每次改提示、模型、检索或工具合同，都跑同一套回归测试；上线前设置必须通过的安全与正确性门槛。小流量 shadow 或 canary 观察真实问题分布，并将失败案例去敏后加入离线集。

一个可交付项目还要有运行说明、密钥配置方式、权限范围、已知限制、回滚办法和人工处理路径。产品指标不能只看“模型回答很好”：还应看正确工单解决率、人工接管率、平均处理时间、误操作率以及用户是否采纳结果。

上线门槛可分两层。第一层是确定性安全门：越权查询、审批缺失、重复退款草稿、敏感信息泄露等样例必须全部通过。第二层是质量门：在固定题集上比较新旧版本的完成率、引用准确率和成本，允许的退化范围要事先决定。灰度期间不能只看平均值；高金额订单、新用户、旧政策和多租户等分组更可能暴露问题。回滚后保留失败轨迹，去敏并加入回归集，下一次发布才不会重犯。

对结果的解释也要诚实：一次离线评测通过只能证明当前题集中的表现，不能保证未知任务完全可靠。试点阶段应显示哪些任务仍转人工，并让用户能反馈错误。将反馈绑定到 run ID，才有机会定位当时的模型、提示、工具和索引版本；没有版本和轨迹，投诉只会变成一句“AI 答错了”。

## 每一层都做一次限时口述验收

写出能运行的代码之后，还要能向一个没读过仓库的人解释它。可以把四周成果做成四个限时关卡。第一关给自己三分钟，不看稿画出“模型提出动作—宿主校验—工具执行—观察回填—停止”的循环，并在图上标出用户输入和不可信工具输出。第二关给五分钟，拿出一个工具 Schema，说明参数错误、超时、重复请求、权限和副作用分别由谁处理。

例如 `create_refund_draft` 至少要想清这些字段和契约，而不只是两个字符串参数：

| 问题 | 设计中要写清什么 |
| --- | --- |
| 输入 | 订单 ID、原因、金额与币种；哪些由用户给、哪些从订单服务读 |
| 权限 | 谁可读订单，谁可建草稿；模型能否看到账户敏感字段 |
| 幂等 | 客户端或任务重试时使用哪个稳定 idempotency key |
| 超时 | 请求超时后先查询草稿状态，还是可以安全重试 |
| 副作用 | 创建草稿与真正提交退款是否是两个分开的能力 |
| 错误 | 参数错误、权限不足、订单不存在、服务暂不可用如何区分 |

第三关给十分钟，展示一次失败 Trace：原始任务、模型版本、选中的工具和参数、宿主判定、工具结果、状态变化、最终答案与根因。需要区分 Outcome（结果是否达成）、Trajectory（过程是否合理）和 State（外部状态是否正确）；仅靠一段漂亮的最终回答无法覆盖后两者。第四关给三十分钟做系统设计：先问用户、动作和风险边界，画组件与数据流；再选单次调用、Workflow 或 Agent；最后用一个坏例子走完恢复、评测和上线。超时后能清楚说出尚未验证的假设，比图画得满更重要。

这些时间不是企业通用考纲，而是自我训练的约束。哪一关说不清，就回到相应阶段补测试和轨迹；不必再收集十篇同义面经。

## 四周练习节奏

| 周次 | 主要产物 | 必须演示的失败 |
| --- | --- | --- |
| 第 1 周 | 最小 loop、两个只读工具、五个测试输入 | 空结果、重复调用、超时 |
| 第 2 周 | 带引用的知识检索、受控草稿工具 | 越权文档、错误引用、非法参数 |
| 第 3 周 | 持久任务状态、审批、取消和续跑 | 中途崩溃、重复执行、预算耗尽 |
| 第 4 周 | 离线评测集、trace、灰度与回滚说明 | 分群退化、安全拦截失败 |

时间只是组织方法；真正的完成标准是能展示输入、轨迹、产物和失败证据。如果第一周的循环尚不能稳定处理空结果，继续学框架编排只会叠加故障。已经熟悉 LLM 应用的读者可从第二周开始，但仍要手写一个最小 loop，以确认自己理解模型决策与宿主执行的分工。

## 读材料的顺序

先读官方的工作流与 Agent 边界、工具调用，再学习一种框架的状态与工作流抽象；不要同时跟三套框架 API。做检索时先用简单关键词或 BM25 建基线，再看向量检索与 rerank。做多 Agent 前先用单 Agent、显式 Workflow 解决同一任务，比较成功率、成本和故障定位难度。读一个开源 Harness 时，重点找 loop、工具注册、权限门、session store、上下文压缩和 trace，而非只运行首页 Demo。

每学完一部分，写下三个问题：它新增了什么能力；引入了什么风险；用哪一个测试证明风险受控。这三问能把知识变成可讲述的项目证据，也能直接用于面试中的系统设计与失败复盘。

建议把练习材料放在一个可重跑仓库中：固定输入、模拟工具响应、任务状态样本、评测题、运行命令和预期结果各有独立文件。实际模型输出可能有波动，因此既要测试确定性合同，也要在多次运行中统计任务成功与失败类型。记录配置版本后，下一次试验才能与上一次比较。每次升级模型或框架之前先跑旧样例，能避免“新版本演示更好，但旧任务悄悄退化”。

仓库说明可以按读者第一次接手的顺序写：要解决的窄任务、样例数据的含义、启动与测试命令、工具权限、一次正常轨迹、一次失败轨迹、已知限制。这样他人不依赖作者口头解释就能复现。学习者也可以每周录一段五分钟演示：先说明系统当前能做什么，再现场触发一个失败，展示日志如何解释失败，最后展示测试如何保护修复。能清楚讲出这条链，比做一张复杂架构图更能证明掌握。

如果准备求职，可在四周结束时把材料整理成一页项目说明：任务边界、系统图、最小可运行命令、关键设计选择、两条失败案例、评测表和下一步风险。应用岗位重点展示检索与任务成功，平台岗位强调工具合同与恢复，FDE 岗位补需求收敛与实际使用反馈；事实不变，只调整重点。回答面试追问时，先指出你亲自实现和验证的部分，再讨论如果上生产还需要补什么。这样可避免把教学 Demo 说成真实大规模部署。

路线也不要求做完所有主题才算可以交付。若任务只需一次只读检索，完成第二阶段并有合格评测就可能已经足够；若面向多人使用且有副作用，第三、四阶段的状态、权限和发布机制不能省。学习深度由目标任务的风险决定，而不是由框架功能列表决定。

每完成一阶段都请另一位读者只看仓库说明和测试运行一次。若他无法复现，先修文档、样例数据或启动过程。可复现性本身就是学习成果：它迫使你把隐藏在自己脑中的权限假设、配置和成功条件写成明确合同。

## 面试会怎么问

近期面经很少要求背一张统一学习路线，却经常顺着简历问“为什么做这个项目”“下一步会补什么”。学习路线的价值在于让每一阶段都能交出可检查的产物。

**问：如果只给你四周准备 Agent 工程岗，你先做什么？** 答：第一周做一个带终止条件的最小工具循环，第二周补检索与有标注的评测集，第三周加入权限、幂等、恢复和 trace，第四周做灰度演练与项目深挖。每一步都沿同一个任务扩展，并保存 baseline、失败样例和改进结果。若目标是 Coding Agent 或 FDE，再把最后两周的练习换成相应工具链或客户试点；不要把框架名当学习成果。

这是一道模拟追问，训练目标来自下方一手面经中的项目深挖方式，并非原帖逐字题目。
