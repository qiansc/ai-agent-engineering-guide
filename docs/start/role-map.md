# AI 岗位地图：应用工程、基础设施、FDE 与模型方向

“AI Engineer”不是单一岗位。面对同一个 Agent 项目，有人负责把用户问题做成产品功能，有人负责运行时与工具平台，有人深入客户现场交付，还有人优化模型训练和推理。看清交付物，才能决定应该展示什么能力、准备哪类面试题。

| 方向 | 主要交付物 | 面试常问的证据 |
| --- | --- | --- |
| AI 应用 / Agent Engineer | 面向用户的任务流程、检索与工具集成、质量指标 | 任务成功率如何定义，错误怎样回流，哪些动作需审批 |
| Agent Infra / Platform | 模型网关、运行时、沙箱、状态、观测和开发工具 | 并发、隔离、恢复、幂等、成本与 API 合同 |
| FDE / Applied AI | 在真实业务环境交付并推动使用的方案 | 怎样澄清需求、处理数据边界、缩小范围、衡量采用 |
| 模型 / 算法 | 训练、后训练、推理优化与研究成果 | 数据、实验设计、指标、误差分析和性能权衡 |

这些方向会重叠。小团队的应用工程师可能同时写工具网关和评测脚本；平台工程师也必须了解应用的失败模式。但简历应突出你实际承担的责任，而不是把同一项目包装成四种不同的经历。

岗位名称还会随公司规模变化。“Applied AI”在一个团队可能主要做客户应用，在另一个团队可能研究模型能力；“Agent Engineer”也可能偏产品集成或偏平台。判断方向时，优先看职责中的动词和交付物：是设计用户流程、维护共享服务、在客户环境部署，还是训练模型与优化推理。招聘要求里的技术栈只是线索；同一个 Python 或 TypeScript 技能可以服务于完全不同的目标。

求职准备可从一个真实项目建立证据库：你负责的范围、使用者、输入数据、关键接口、上线方式、故障样例、指标与结果。以后读一份 JD，只选择相关证据并调整叙述顺序。这样既不会给每个岗位编造一套经历，也能避免在应用岗面试只谈分布式缓存，或在平台岗面试只展示生成文案的截图。

## AI 应用工程：对端到端任务负责

应用岗位首先要把模糊需求缩成可验收的任务。例如“做一个企业知识助手”过宽；“帮助客服回答指定产品的退款规则，并给出当前有效政策链接”才可以设计输入、权限、检索、拒答与评测。工程师需要判断何时采用固定 Workflow，何时允许 Agent 选择工具；需要把模型输出与数据库、搜索、文档、业务 API 连接，并处理空结果、错误引用和工具超时。

面试中的系统设计题通常不会止于“用哪个模型”。更完整的回答会说明：数据怎样进入索引；文档更新与删除怎样传播；查询时怎样按用户身份过滤；工具参数怎样校验；高风险动作如何先生成草稿再确认；用哪些离线题和线上指标判断系统是否改善。应用工程的优势来自把这些环节连起来，而不只是能调用 API。

准备一个项目时，最好能给出一张数据流图、一组失败案例和至少两次版本对比。例如初版只用向量检索，遇到产品编号召回不稳；加入关键词检索与重排后，标注集中的证据召回改善。没有真实量化数据时，不要补造百分比；展示评测方法和原始样例同样有价值。

应用岗经常需要同时考虑算法质量与产品体验。用户问“订单能退吗”，系统若证据不足，合理体验可能是展示已找到的政策、指出还缺购买时间，并提供补充信息入口，而非简单返回“无法回答”。若工具正在超时，界面需要区分处理中、失败和需要人工接管。工程师应能解释这些状态如何从后端任务状态产生，以及用户是否能取消、重试或纠正输入。产品质量不是最终一句话好不好听，而是用户能否在不确定情况下继续完成任务。

可以准备一个端到端设计题自测：给定十万份文档、分租户权限、每天更新，设计客服知识助手。先描述数据接入与版本，再说明查询时授权、混合检索与引用，最后给出离线集、线上反馈与回滚。若只说“向量库加大模型”，还没回答文档删除、旧政策、错误引用和多租户越权。这类题的价值在于把所有组件落实到同一条请求路径。

## Agent Infra：提供可复用的安全运行环境

基础设施岗位关心“多个应用如何稳定地运行”，而非单个 Prompt 是否漂亮。运行时要区分模型建议调用工具与工具已经实际执行；为任务保存状态、检查点、取消信号和恢复信息。工具网关要实施鉴权、限流、幂等、脱敏和审计。代码执行或浏览器工具还需要文件、网络、进程和凭据隔离。

一个常见平台题是：上游模型超时重试，支付草稿工具已经成功，怎样避免重复创建？回答应从请求 ID、工具幂等键、持久化状态和查询已执行结果展开，而不是“再试一次”。另一个问题是多租户并发：要给租户配额，限制单任务 token 和工具调用，避免一个长任务挤占所有资源。平台工程师还要定义稳定、窄小的公共接口，因为一旦许多应用依赖，改变参数和错误语义的代价很高。

准备这类岗位时，可用一个小 Harness 展示模型适配、工具注册、权限门、session store、trace 和回放。代码不必庞大，但应能演示取消、超时、部分成功、恢复以及新工具如何接入。测试要覆盖合同边界，不能只放正常路径截图。

Infra 的设计权衡通常来自多个业务方同时接入。一个团队想加任意代码执行，另一个只需要只读检索；平台不能把最危险能力默认开放给所有租户。工具注册时应声明风险和所需权限，执行网关从身份上下文核对，模型版本与工具版本分别管理。队列积压时可限制低优先级长任务、保留审批任务状态并告知用户等待，而不是让请求无限占用连接。面对“为什么不让每个团队自己写 Agent Loop”，可以从一致的权限、可恢复状态、观测和公共测试合同回答，同时承认过度统一会阻碍业务迭代，因此平台接口要窄。

准备项目证据时，可展示一次真实或模拟的故障演练：工具执行成功但响应丢失，任务重新入队；运行时如何通过幂等键识别已完成动作，补写状态并继续。再展示两个租户同时运行时的配额与隔离测试。平台岗位面试看重你能否把失败语义说清，尤其是“模型提出了动作”与“动作确实发生”之间的边界。

## FDE：把现场问题推进到实际采用

Forward Deployed Engineer 通常在客户或业务团队的真实约束下工作：问题表述不完整、数据分散、系统历史复杂、权限和部署方式受限制。第一步常常不是写 Agent，而是弄清谁会使用、当前流程哪里耗时、错误代价是多少，以及什么样的结果足以先试运行。一个可交付的窄流程，比一个功能齐全却没人使用的演示更有价值。

例如客户希望“自动处理所有采购邮件”。更可靠的第一版可能只识别指定供应商邮件，提取订单号并起草回复；未匹配、缺附件或金额异常时转人工。FDE 需要与客户确定审批责任、数据保留方式和成功指标，再把现场定制的部分沉淀成可复用的连接器或配置。面试会追问你怎样推动试点、处理阻力、发现真实需求与初始说法不一致，以及上线后谁负责维护。

讲述这类经历时，应分开技术结果与采用结果。技术上可能提高了某类工单的正确处理率；业务上仍要看使用频率、人工节省时间、误操作和反馈。若试点最终没有推广，也可诚实复盘：是质量、权限、流程所有权，还是用户习惯阻碍了采用。

一段 FDE 交付可分成发现、试点、部署、采用和沉淀。发现阶段与实际操作者一起走完旧流程，量出耗时和高风险步骤；试点阶段选有明确输入和验收条件的窄任务；部署阶段处理身份、数据位置、日志和客户现有系统；采用阶段观察谁真正使用、何时退回人工；沉淀阶段把重复的连接器、工具或操作说明变成可复用组件。每一阶段都有技术和沟通工作，不能把“做了一个 Demo”直接等同于客户已经采用。

客户可能提出与安全边界冲突的需求，例如希望 Agent 自动发送所有邮件。FDE 应能提出可操作的缩小方案：限定供应商、只读附件、生成草稿、展示差异并由负责人确认；记录试点中自动化覆盖率和误判样例。若客户对数据出域有约束，部署方案还要说明哪些数据进入模型、哪些保留在客户系统、如何做脱敏和删除。好的现场判断往往体现为主动收窄权限，而非承诺 Agent 什么都能做。

这类岗位也需要把一次性交付反馈给产品或平台团队。若三个客户都要同一种工单连接器，应提炼共同的认证、分页、错误和审计合同；客户独有的政策差异留在配置或本地 Workflow。面试中可用一个例子说明哪些部分被复用、哪些没有，以及为何没有强行抽象。这样既证明交付速度，也证明长期维护判断。

## 模型与算法：实验能力是主轴

模型岗位也会研究 Agent，但核心工作可能落在数据构造、监督微调、强化学习、工具使用能力训练、推理加速或评测基准。准备这类岗位，不能只背 Agent 架构图。要能说明训练目标、数据过滤、基线、消融实验、误差分布以及计算资源约束。若岗位强调 kernel、并行推理或后训练，应用层项目只能证明场景理解，不能替代算法与系统基础。

把一个应用项目转成模型方向的证据时，可以展示工具选择错误的标注数据、不同提示或模型的对照实验、失败类别，以及是否值得微调。注意把“模型错了”拆成检索不足、工具描述含糊、状态缺失和模型决策错误，避免把所有问题都交给训练。

若确实讨论模型改进，可以从一个可验证假设出发：“模型在相似工具之间误选”，先固定工具描述、任务集和评价规则，再比较提示、模型选择与训练方案。训练数据应覆盖正确调用、应拒绝调用、参数缺失和工具失败后的行为；评测集与训练集分离。若更改工具描述已经解决多数错误，微调可能不值得成本。若岗位偏推理优化，则准备吞吐、延迟、显存或并行策略的实验；同一 Agent Demo 并不能代替这类系统指标。

## 用 JD 和项目事实决定准备顺序

读岗位描述时，先圈出重复出现的交付名词。`runtime`、`sandbox`、`gateway`、`observability` 指向 Infra；`retrieval`、`workflow`、`evaluation` 指向应用工程；`customer`、`deployment`、`adoption` 指向 FDE；`training`、`post-training`、`inference kernel` 指向模型方向。再看任职要求里的实际工作方式：个人负责一个功能、建设平台供团队使用，还是在客户现场快速集成。

同一个“工单助手”项目可以按事实换叙述重心：应用岗讲任务定义、RAG 和质量闭环；Infra 讲工具合同、幂等、状态和 trace；FDE 讲需求收敛、试点范围与采用；模型岗讲工具选择评测与实验。不要改写自己没有做过的部分。最后准备一段失败复盘：发生了什么、如何定位、采取何种修复、用什么证据判断有效，以及还有哪些限制。

## 用同一项目练习四种追问

面向应用岗，回答“为什么用户看到的解释可信”：说清权威数据源、政策版本、引用和拒答。面向 Infra，回答“模型超时重试会不会重复写入”：说清任务状态、幂等键和副作用查询。面向 FDE，回答“客户为什么愿意把流程交给你”：说清旧流程痛点、试点范围、审批责任和采用指标。面向模型岗，回答“错误来自模型还是系统”：展示分层标注、对照实验和消融结果。这四个问题都围绕同一事实，不要求为迎合岗位改变项目内容。

练习时准备两分钟和十分钟两种版本。两分钟先讲用户问题、自己负责的部分、可核对的结果和一个限制；十分钟展开架构、关键权衡、失败复盘与指标。不要把所有工具名一口气列出，面试官通常更想知道你为什么选这个边界，以及替代方案有什么代价。遇到没做过的部分，直接说明假设和下一步验证方式，比假装拥有生产经验可靠。

使用 AI 准备面试也应遵守目标公司的说明。有的公司鼓励用 AI 研究岗位、练习表达，却要求笔试或现场面试独立完成，除非题目明确允许。可用工具帮自己发现项目叙述中的缺口，但简历经历、指标与技术决策应由本人核对。准备时让 AI 追问“哪条数据支持这个改进”，比让它代写一个看似完美却无法深挖的故事更有帮助。

## 面试会怎么问

同样叫“Agent 岗”，FDE、应用工程和平台工程对项目的追问不同。百度 Coding Agent 的复盘同时涉及 Agent 架构与 OS、并发；用户提供的 FDE 文章则强调客户试点与交付。准备时应先讲自己承担的责任，不要用一个通用模板回答所有岗位。

**问：你的项目更像应用 Agent、平台能力还是 FDE 交付？** 答：先说最终交付物和使用者。若主要负责一条业务任务的正确完成，重点讲输入输出、工具与质量指标；若负责多团队复用的运行时，重点讲隔离、权限、预算与恢复合同；若在客户现场把模糊需求落成试点，重点讲需求澄清、集成限制、验收与采用。再用一次失败说明你个人做了什么、怎样验证修复，而不是靠岗位名称推断能力。

面试复盘和 FDE 文章用于理解可能的追问，不代表任何公司的固定面试流程。
