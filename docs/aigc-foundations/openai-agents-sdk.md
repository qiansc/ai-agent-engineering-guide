# OpenAI Agents SDK：用少量原语搭起受控的 Agent

如果你已经会调用模型并解析一次 Function Calling，下一步常遇到的问题是：模型还要再调用一次工具怎么办？一个客服请求该交给账单专员还是退款专员？用户第二轮提问时，上一轮状态从哪里来？出了问题如何知道是哪次工具或交接造成的？OpenAI Agents SDK 主要替应用管理这些**运行时**细节，而不是让模型本身变得永不出错。

以一个账单支持助手为例。入口 Agent 理解用户诉求，可以使用只读账单工具；遇到退款意图时，转交给有独立指令的退款 Agent；高风险动作仍需服务器授权和人工批准。用这个例子认识 SDK 的几个原语，比背功能列表更容易看清它们的边界。

## Agent 与 Runner：配置和执行不要混为一谈

`Agent` 描述一个工作单元：名称、指令、模型、工具、可交接的其他 Agent、输入/输出检查以及可选的结构化最终输出。它更像一份可复用配置，不是一次运行后的全部状态。`Runner` 执行这份配置，负责多轮模型调用、分派工具、处理 handoff，直到得到最终结果或触及运行限制。

一次典型运行是这样的：用户问题进入入口 Agent；模型选择回答、调用工具或交接；SDK 校验模型给出的工具参数并执行相应工具；工具结果再成为模型下一轮可见的输入；若模型选择 handoff，控制权转给目标 Agent；最后返回输出及运行轨迹。SDK 托管这个循环，不等于它替你定义了业务“成功”：账单数字仍需从权威系统取得，退款资格仍需业务服务确认。

如果任务仅是短促的一次模型回复，且你希望完全自己控制循环和工具分派，直接使用底层 Responses API 可能更简单。需要多轮工具、交接、会话和内置 tracing 时，SDK 的价值才明显。选 SDK 并不意味着要把所有业务流程都塞进一个 Agent；确定性的审批、状态变更和通知仍可由普通代码组织。

## Tools：模型能提议，宿主才真正执行

函数工具可把应用中的 Python 函数包装为模型可调用的工具，SDK 根据定义生成参数 schema 并做类型校验。还有平台托管工具、在本地或沙箱执行的工具、远程 MCP 工具，以及把另一个 Agent 作为工具调用的方式。它们共同点是：工具调用由模型**选择**，实际执行环境和权限由宿主决定。

把 `lookup_bill(bill_id)` 设计为只读接口，要比给 Agent 一个可执行任意 SQL 的工具好得多。schema 应写清参数含义、格式和何时使用；执行函数内部按当前用户身份检查账单归属；输出只返回需要的金额与版本，而不是整个客户档案。即便 SDK 已帮你解析参数，也无法自动知道“这张账单是否属于这位用户”。权限检查必须落在工具或服务端边界。

工具失败同样要设计成可处理的结果。账单查询超时、账单不存在、没有权限，含义完全不同。可重试的超时应有限次退避；不存在可提示用户核对编号；无权限应停止，不应换一个工具绕过。模型可以用错误反馈重新规划，但安全策略不应交给模型决定是否继续。

## Handoff 与“Agent 作为工具”有什么区别

当入口 Agent 把请求 handoff 给退款 Agent，目标 Agent 接管后续处理，适合不同专员拥有不同指令和会话视角的场景。若入口 Agent 只想请一个专员计算或检索，再由自己统一回答，可以把专员 Agent 暴露为工具。前者是控制权转移；后者是主 Agent 调用一个子能力并收回结果。

例如用户问“这张账单为什么涨了，我能退款吗？”入口 Agent 可先查账单原因，再把退款资格部分 handoff 给退款专员。要明确交接时转移哪些上下文：只给工单号、账单事实与用户诉求，不要把其他用户的记录或完整工具日志一股脑传过去。另一种设计是入口 Agent 调用一个“核对退款政策”的子 Agent 作为工具，得到结构化建议后继续组织最终答复。选哪一种取决于最终回答和控制权应由谁拥有。

不要把 handoff 当权限提升机制。目标 Agent 即使配置了退款工具，执行时仍要检查用户、对象、金额与审批。多 Agent 只是职责划分，不是绕过授权的快捷通道。

## Guardrails 的运行边界

SDK 提供输入、输出与函数工具的 guardrails。输入检查可拦下明显不在服务范围内的请求；输出检查可发现最终答复包含敏感信息或不合规承诺；函数工具的输入/输出检查可围绕实际调用过滤参数与结果。它们可以使用规则、分类器或模型，但不能等同于企业的完整安全体系。

这里有一个容易误解的细节：Agent 级输入 guardrail 只在链条的**第一个 Agent**处理输入时运行，输出 guardrail 只在**最终产出回答的 Agent**上运行。你不能默认“每次 handoff 都会重复做相同检查”。函数工具 guardrail 也只覆盖适用的函数工具调用路径；handoff 和某些托管工具有各自的执行路径。应在真正能产生副作用的服务端再设硬性权限检查。

输入检查还有时机选择。并行检查通常降低等待时间，但在检查完成前 Agent 可能已经消耗 token，甚至开始执行工具；若要保证危险请求在任何工具运行之前被拦截，应使用阻塞式检查或在执行端独立拦截。输出检查发生在最终结果阶段，不能挽回前面已经发生的外部写入。把“检查在哪里、何时执行、失败后是否可能已有副作用”写进设计，guardrail 才不是一个听起来安心的装饰。

## Session、结构化输出与 trace 怎样配合

Session 帮助多轮请求保持工作上下文；它不自动成为业务数据库。用户说“上次那笔已经退款”，真正退款状态仍需从支付系统核实。会话历史、长期偏好、任务进度和外部交易应分开保存：历史用于理解对话，任务状态用于恢复，外部交易用权威业务系统判真。跨会话恢复时，还要考虑哪条信息过期、何时删除以及用户权限变化。

结构化输出适合让最终结果符合预定义格式，例如 `bill_id`、`difference`、`evidence`、`draft_text`、`needs_approval`。格式约束能减少解析失败，却不保证字段事实正确。应用还要校验金额来自哪次查询、引用是否可访问、`needs_approval` 是否与业务规则一致。格式校验与事实校验是两道不同关口。

内置 tracing 可以记录模型调用、工具调用、交接、guardrail 和自定义事件，帮助定位“为什么答错”是模型选择、工具故障、上下文遗漏还是交接丢信息。生产环境要考虑 trace 里可能有用户输入、工具参数和敏感结果；按数据策略选择脱敏、留存与导出方式。观察到一条成功轨迹也不代表系统稳定，仍要收集失败样例做回归。

## 做一个最小但完整的练习

先用两个只读工具做账单解释：查账单、查政策。给 Agent 一个明确任务合同：只解释有证据支持的差额，不承诺退款，找不到依据时说明缺口。要求最终输出结构化的事实、证据和待核实项。运行三类样例：正常活动到期、工具超时、请求读取别人的账单。

观察每次轨迹，而不是只看最后一句话。工具超时后有没有无限循环？没有权限时模型是否换工具重试？如果把“查询退款资格”加入第二个 Agent，交接时携带了哪些字段？最后再加草稿创建与人工审批，确认无论模型说什么，真正发送都必须经过业务授权。这样你学到的是 SDK 的运行边界，而不只是会写一个能回答“你好”的示例。

## 面试会怎么问

公开的一手面经中，面试官更多是问 Harness、工具选择、权限和恢复，而不是要求背诵某个 SDK 的类名。若被问“用 OpenAI Agents SDK 如何实现你的 Agent”，可以用实际任务说明 Agent 配置、Runner 循环、工具授权、handoff、session 和 trace 的位置；再主动指出 SDK 不替代业务身份校验、幂等和效果评测。这里是教学回答路径，不是对任何候选人现场表述的复原。
