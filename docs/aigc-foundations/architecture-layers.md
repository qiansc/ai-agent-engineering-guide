# 一次 Agent 请求穿过哪些层：从九层技术栈到可运行系统

刚接触 Agent 时，很容易把架构图画成“用户 → 大模型 → 工具”。这个图能解释一次函数调用，却解释不了三个更重要的问题：模型为什么看到了这段资料、谁允许它执行动作、服务中断后从哪里继续。把系统拆层的目的，是让每个决定都有主人，而不是为了凑齐九个名词。

不妨从一个具体任务出发：用户请内部助手“查清一笔账单为什么增加，并起草解释邮件”。它需要读取账单、订单与促销政策；若证据矛盾，不能自行承诺退款；生成的草稿还要由客服确认。下面九层不是九个必须独立部署的微服务，而是九种必须有人负责的能力。同一程序可以实现多层，但不能因为部署在一起就把责任混掉。

## 九层分别解决什么

| 层 | 这次账单任务中做什么 | 不该替其他层做什么 |
| --- | --- | --- |
| 模型层 | 理解诉求、比较证据、决定下一步要查什么 | 不保存账单真值，不直接授予自己退款权限 |
| 指令层 | 告知任务目标、完成标准、可用工具和禁止承诺的事项 | 不把自然语言警告当强制授权检查 |
| 工具层 | 提供查账单、查订单、查政策、创建邮件草稿等接口 | 不把整库读写权限包装成一个万能工具 |
| 规划层 | 安排先查账单差额，再找可能原因；证据不足时改计划 | 不保证计划永远正确，也不代替实际验收 |
| 记忆层 | 保存本次已查账单、已核实事实与任务进度；按需读取用户偏好 | 不把所有对话原样永久保留 |
| 上下文工程层 | 从历史、工具结果和政策中挑选这一次模型真正需要看的内容 | 不把检索到的文字升级为系统指令 |
| 权限与安全层 | 按用户身份限制账单对象，拦截敏感字段与高风险动作 | 不只靠模型自觉遵守提示词 |
| 执行与编排层 | 管循环、队列、超时、重试、审批等待、取消与恢复 | 不用“再调用一次模型”代替状态一致性 |
| 评估与观测层 | 记录轨迹、测解释准确率、越权率、时延与成本 | 不把一次漂亮演示当上线证据 |

这九层不是按请求严格串行通过。一次工具结果返回后，上下文工程会重新挑选证据，规划可能调整，权限层还会再次检查下一次动作。把它们理解成相互协作的职责，比把它们理解为九个顺序节点更准确。

## 跟着一次请求走

入口先拿到用户身份、目标、账单编号和可操作范围。执行层建立 `task_id`，记下开始时间、步数预算与取消信号。指令层提供“解释差额、列出证据、只起草邮件”的任务合同。上下文层只取当前任务相关的会话信息，不把客户过去所有工单塞进提示词。

模型可能先请求 `get_bill(bill_id)`。工具层把调用表示为有明确参数的结构化请求；宿主在执行前验证参数、用户是否有权读这张账单、调用额度是否足够。工具返回“上月 100，本月 120”，模型再决定查订单、费率或活动。此时规划层体现的是**反馈改变下一步**：若活动确实到期，查政策；若工具超时，重试或改走人工；若拿到另一客户的数据，立即隔离并上报，而不是让模型继续推理。

证据完整后，模型生成一份草稿。输出校验检查金额是否与工具事实一致、是否附上政策版本、是否出现未获授权的退款承诺。创建草稿与真正发邮件是两个不同动作：前者可在有限授权下执行，后者要等客服确认。观测层把模型版本、指令版本、工具调用、审批及最终结果串在同一条 trace 中，以便之后复盘。

这条路径里最容易被忽略的是**状态的真实性**。模型曾说“我已发邮件”，并不代表邮件系统接受了请求；工具超时也不代表它一定没执行。涉及副作用时，执行层要保存稳定的操作 ID 和幂等键，查询外部系统确认状态，避免恢复任务时重复发送。

## 哪些层由模型做，哪些必须由代码做

模型擅长理解模糊意图、比较非结构化证据、在有限选项中选择下一步。代码擅长判定身份、校验账单归属、计算精确金额、执行事务、限制步数和保存状态。人负责高代价、不可逆或带业务承诺的最终决策。这个划分不是“模型不可信，所以什么都不让它做”；恰恰相反，只有确定性边界扎实，模型才能在边界内灵活探索。

例如“促销是否可能导致差额”可以由模型提出假设，再用工具查政策和订单核实；“此用户可否读取该账单”必须由服务端按身份和对象判断；“是否真的退款”由业务规则与审批流程决定。把后两项写进 system prompt，不能替代真正的检查。

## 为什么从 Demo 走向工程系统

模型的结构化输出与工具调用更稳定，MCP 等协议降低了连接工具的成本，框架提供循环、状态与追踪，编码 Agent 又给了可运行测试和 diff 的验证环境。这些进步使多步任务更容易演示和开发。但“能跑”与“可交付”之间仍隔着权限、成本、恢复、评测和责任边界。

标准化还包括面向远程 Agent 协作的 A2A；工具连接与 Agent 服务委托是不同接口，不能因为有了协议就认为权限问题已解决。公开基准也开始按任务环境区分能力：SWE-bench 看仓库修复，WebArena 看网页操作，OSWorld 看桌面操作，GAIA 与 τ-bench 分别覆盖通用工具任务和带政策约束的交互。它们比展示单个成功案例更可比较，但不替代企业的私有评测。企业推动落地的任务也越来越具体：客服核查、数据分析、研发提效、运营执行和知识工作流都需要跨系统读写，因而更需要清晰授权与过程记录。

一次 Demo 可以在开发者本机读取文件、调用一个 API，看到预期文字就结束。面向真实用户的系统要处理并发、撤销、登录过期、工具部分成功、提示注入、模型版本变化和客服交接。若模型选错工具，能否定位是描述歧义还是权限配置？若服务在发送前崩溃，恢复后会不会重复发？若新版本更快却使拒绝率上升，能否回滚？这些问题才是工程化的门槛。公开 Benchmark 能帮助比较某类能力，最终仍要用自己的业务任务集验证。

因此初版不要一上来叠多 Agent、长期记忆和所有可用工具。先固定一个窄任务，给模型最小只读工具，明确成功条件和失败出口；跑通后再加草稿写入与审批，再验证异常和恢复。复杂度随需求增长，而不是随框架功能表增长。

## 把架构图变成验收清单

试着拿自己的项目回答这些问题：模型决策的范围在哪里？每个工具的输入、输出和授权对象是什么？请求失败时哪些状态已真实写入？哪些资料会进入当前上下文，哪些资料只作为可检索引用？用户如何取消，谁来审批，谁接手无法解决的任务？最后，哪批样本能证明它比固定 Workflow 或人工辅助更好？

如果答不出来，不必先补一张更大的九层图。挑一条实际任务轨迹，把模型调用、工具执行、身份校验、状态写入和最终验收逐步标出来。缺失的职责自然会浮现：有人只记录了文本却没有记录动作状态，有人做了检索却没有版本与权限过滤，有人能重试却没有幂等。这比背熟层名更有用。

## 面试会怎么问

百度 MEG 2026 年 8 月复盘中，面试围绕 Prompt、Context、Harness 的边界展开；小红书 8 月 Agent 开发复盘则追问为什么用 Agent 以及具体编排。它们不是直接考“九层名单”，而是在检查你能否把系统职责拆清。

**问：你项目的 Agent 架构是什么？** 先说任务和可验证目标，再用一次真实请求交代指令与上下文怎样构造、模型如何选择工具、宿主怎样授权、状态如何持久化、怎样评估。不要只报模型、向量库和框架名称。

**问：Prompt、Context、Harness 各管什么？** Prompt/指令定义目标与行为约束；Context Engineering 决定本次调用能看到哪些资料；Harness 在模型外执行循环、工具、权限、预算、状态和恢复。举“模型要求读取别人的账单，但宿主拒绝”说明三者边界。这里是教学回答思路，不是候选人的现场原话。
