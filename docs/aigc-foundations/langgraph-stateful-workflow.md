# LangGraph 怎么管理长任务：状态、检查点与人工接手

普通的“模型调用 → 工具调用 → 模型再回答”足以处理不少短任务。问题出现在任务跨越几分钟甚至几天、会遇到多次审批、可能中途失败、还要知道每一步到底完成到哪里时。LangGraph 把这类过程写成有状态的图：节点执行工作，边决定下一步，状态保存事实，检查点支持暂停和继续。

用一个报销审核任务来看。系统先读取单据，识别费用类别；金额较低且政策明确时自动生成建议；超过阈值或证据冲突时暂停，让审核人修改或批准；批准后才调用支付或入账接口。这个任务中，模型只承担分类、解释和补证据等不确定判断，金额规则和审批节点可以是确定性代码。LangGraph 的价值不是“所有节点都要用 LLM”，而是把两种步骤放在一个可追踪的控制流里。

## 图里有哪些东西

`State` 是这次任务的共享工作状态，例如 `claim_id`、已读单据、识别出的金额、政策引用、审核意见、审批结果、错误次数。节点接收状态并返回更新；不要把一切塞进一段对话文本，否则恢复时无法区分“模型猜测”和“系统已确认”。

节点可以是模型调用、普通 Python 函数、工具调用或子图。边可以固定，也可以根据状态条件选择路线。例如“金额 ≤ 阈值且票据完整”走自动建议，“金额超阈值”走人工审批，“票据缺失”走补件。这样每个分支有可阅读的转移理由，不会藏在一个巨大的提示词里。

一个简化状态表可以这样设计：

| 字段 | 谁写入 | 恢复时必须知道什么 |
| --- | --- | --- |
| `claim_id`、`requester_id` | 入口服务 | 始终与当前身份绑定，不让模型改写 |
| `documents`、`policy_version` | 读取工具 | 证据是哪个版本，是否仍有权限 |
| `proposed_category`、`reason` | 模型节点 | 只是建议，尚未生效 |
| `approval_status` | 审批服务 | 待审批、拒绝、批准，不能从对话推测 |
| `payment_operation_id` | 支付服务 | 是否已执行，恢复时避免重复支付 |
| `attempts`、`last_error` | 运行时 | 哪类失败可重试，何时升级 |

这张表也说明图式编排和业务数据库不是一回事。Graph State 便于节点之间传递与恢复，支付是否发生仍以支付服务为准。尤其在有外部副作用时，仅恢复图状态不保证外部世界与图状态恰好一致。

## Checkpointer 与 Store 不要混用

LangGraph 的 checkpointer 保存某个 thread 的图状态快照。它让同一任务能在中断、故障或下一次用户输入后继续；人工审批暂停尤其依赖它。你通常需要给运行指定稳定的 `thread_id`，否则系统不知道要恢复哪条任务。生产环境必须选能跨进程保留数据的持久化后端；内存保存器适合实验，进程重启后不会保住检查点。

Store 则保存应用定义的跨 thread 数据，例如一个用户长期偏好或团队共享知识。它不是把某个报销任务的全部状态随便复制到“长期记忆”。检查点回答“这条任务执行到哪一步”；Store 回答“多条任务都需要读取什么持久信息”。用户偏好可以跨任务，审批结果却属于特定任务与业务系统。

图中的持久化也有治理成本：检查点可能包含敏感单据和工具结果，需要按租户隔离、加密、保留期限与删除策略。长任务的快照会持续增长，不能无限保存。并且代码、状态 schema 或政策版本升级后，旧任务怎样恢复要经过迁移或兼容测试；“有 checkpointer”不等于“永远自动可恢复”。

## 人工审批不是一条聊天消息

在高金额报销节点调用 interrupt，可以暂停图，让审核人查看当前状态。审核人可能批准、拒绝或修改类别；恢复时把这个决定作为结构化输入交还给图。别用“模型读到一句‘同意’就执行支付”代替身份验证。审批入口要确认审核人角色、所属组织、单据权限和批准时看到的内容版本。

暂停前尤其要想清外部副作用的位置。假如某节点先发送付款请求，再触发 interrupt；任务恢复或节点重放时，可能又发送一次。稳妥做法是把“提议付款”“审批”“实际付款”“核对结果”拆开，并让付款工具接受稳定的幂等键。对于可能部分成功的网络请求，先查询外部系统确认状态，再决定是否重试。Graph 能帮助你编排恢复，不能替支付接口凭空实现恰好一次。

若审核人修改状态，也要验证修改后的值。例如不允许把金额改成负数，不能把另一租户的账户号塞进当前任务。Human-in-the-loop 的意思是让人接手高风险判断，不是绕开原有业务校验。

## 失败、循环与并行怎么设计

图可以有循环，但每条回边都要有退出条件。票据缺失时可以请求补件，政策检索失败时可以换搜索策略；若同一错误出现三次，应结束或转人工。预算、超时和可取消性属于运行时设计，不会因为用图表示就自动完善。

并行节点适合互不依赖的调查，例如同时查询差旅政策与票据真伪服务；合并时要定义谁写哪个状态字段、冲突如何处理、某一分支失败是否允许整体继续。对同一笔报销同时做两次有副作用的状态更新则不应为了加速而并行。把“并行检索证据”和“并行改变业务状态”区别开。

调试时，一条完整轨迹至少能回答：经过哪些节点、每次状态更新来自哪里、哪条条件边被选中、是否发生重试和审批、外部副作用是否实际落地。输出错误只是表象，可能根因是检索到旧政策、条件边写错、检查点取错 thread，或恢复时缺少权限上下文。

## 什么时候用它，什么时候不用

你需要明确的状态迁移、长时间执行、故障恢复、复杂分支与人工审批时，LangGraph 的低层控制力有价值。只有一次检索加一次回答、或几个稳定的固定步骤时，直接写普通函数或使用更高层的 Agent 抽象通常更省维护。LangGraph 不强制你使用 LangChain 的模型和工具组件，也不替你设计 prompt、业务 schema 与授权策略。

选型时可以先画状态表和失败路径，而不是先画一张很复杂的图。若状态只有 `input` 和 `output`，也没有暂停/恢复需求，多半不需要图式运行时。若每次故障都要知道“已写入账本但尚未通知用户”这类中间事实，状态图与持久化才真正帮助你。

## 动手推演一个恢复场景

假设系统处理单据到“待审批”，服务重启。重新启动后，先用 `thread_id` 取回任务状态，显示给有权审核的人；审核通过后，验证审批针对的仍是同一版本单据；生成稳定操作 ID 请求入账；若调用超时，向入账服务查询该 ID 的结果；确认成功后更新任务状态。现在故意让它在“入账成功、图状态尚未更新”之间宕机，再运行恢复流程。如果出现重复入账，说明幂等和外部状态核对还没做好，而不是简单把检查点频率调高就能解决。

## 面试会怎么问

美团 2026 年 9 月的一手复盘将 LangChain、疑似 LangGraph 的“LongGraph”和手写 Agent 放在一起比较；原帖用的是 `LongGraph` 一词，现场应先向面试官确认所指。回答时可用一条需要暂停审批、恢复和回滚的任务说明状态图价值，同时承认简单短流程用普通代码更清晰。

**问：LangGraph 与普通链式调用差在哪里？** 答：不只是“能画分支”。它让状态、控制流、检查点和人机介入成为显式对象；但外部写入的幂等、用户授权与状态迁移仍需自己设计。若说自己在项目中用过，要明确是实际生产方案、原型，还是只熟悉概念。这里给出的是教学回答思路，不是候选人原话。
