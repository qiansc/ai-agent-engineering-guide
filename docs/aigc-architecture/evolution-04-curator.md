# Curator：长期运行的 Agent 如何维护自己的知识资产

长期运行系统会不断积累 Skill、模板和记忆。如果只增不减，检索会把过时步骤和重复流程交给 Agent；如果让 Agent 自动大扫除，又可能删掉仍被用户依赖的能力。Curator 是一个后台维护器：依据使用、质量、依赖与安全信号提出保留、修订、合并或归档建议，并让变更可审计、可恢复。

## 维护对象与触发方式

Curator 可统计 Skill 使用情况、识别重复或过期流程、检查失效链接/工具依赖、修订低质量说明、归档长期未使用资产并生成报告。它应尊重 `pinned`、官方和内置资产；自动维护优先作用于用户或 Agent 自建且明确授权的资产。

可以按 Cron 周期运行、在 Gateway 空闲时运行、由用户手动 dry-run，或在版本升级、大量新 Skill 产生后触发。触发频率不是越高越好：维护任务要有时间与费用预算，并支持用户暂停。

## 一个 Skill 的生命周期

可将生命周期表示为 `created → active → stale → archived`，从归档可恢复；真正删除由用户或明确治理流程决定。评分不宜只看“多久没用”，还应结合使用频率、成功任务占比、是否被用户显式调用、重复程度、依赖是否失效、链接/命令是否过时及安全风险。

合并需要谨慎：只在作用域相同、目标相似且内容真正互补时合并，并保留双方来源、变更 diff 和版本记录。两个 Skill 名字相似，可能面向不同权限或平台，不能机械拼接。高价值 Skill 的合并或改写应人工确认。

归档要记录原因、版本与恢复路径；`pinned` / 官方 / 内置内容默认不自动归档。修改前保存版本，维护报告应支持按单个 Skill 或一次 Curator Run 回滚。回滚后还要确认依赖和权限没有恢复成不安全状态。

## 后台复盘为什么要“少工具”

任务结束后另起受限进程/子任务，整理 Trace 并提出记忆或 Skill 更新，这是合理的；但复盘上下文可能包含网页和工具输出等不可信内容，且后台没有人实时盯着。它的目标是整理知识，不是继续替用户执行任务。

| 工具类别 | 建议范围 |
| --- | --- |
| Memory 读写 | 允许候选写入，带脱敏、Scope 与审核 |
| Skill 读取/更新 | 限定授权目录，优先 Agent 自建资产 |
| 文件读取 | 只读指定知识目录 |
| Shell、浏览器点击、邮件发送 | 默认不开放 |
| Web 搜索 | 有必要才启用，结果仍不可信 |
| 删除 | 默认禁止，改为可恢复归档 |

这一限制减少的不只是恶意行为，还包括任务跑偏、循环调用和成本失控。重要变更保留人工审批，Curator 输出 diff 与理由，而非静默改动。

## 防止错误经验写入与复用

写入阶段只采纳高置信、可验证、相对稳定的信息，区分事实、偏好、猜测和失败教训；先去重、脱敏、检测注入，高风险资产请用户确认。检索阶段带 `source/time/confidence/scope`，当前用户指令优先于长期记忆；过期内容降权，冲突内容先澄清。维护阶段标记 stale、支持更正/删除、版本化回滚，并把线上失败送到评测 Harness。

例如某次工具超时后模型猜“此 API 已废弃”。若未经验证就写入 Skill，后续任务会持续绕开可用 API。正确做法是保留失败 Trace，核对接口状态，再决定是更新工具重试策略、记录临时故障，还是修订 Skill。

## 面试会怎么问

**问：Curator 是什么？** 回答它是后台知识维护器，负责评分、合并、归档、报告；用 Skill 生命周期说明可恢复性。

**问：自维护 Skill 怎样评分与回滚？** 给使用、质量、依赖、安全信号，说明合并条件、只读/固定资产与版本 diff。

**问：后台复盘 Fork 为什么限制工具？** 因为输入不可信、无人值守、目标只是知识整理；列出允许的候选写入和禁止的副作用工具。

**问：怎样避免错误经验长期污染？** 按写入—检索—维护三阶段作答，不能只说“给 Prompt 加一句不要相信网页”。
