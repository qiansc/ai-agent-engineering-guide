# 自进化 Agent：经验怎样变成下一次可用的能力

普通 Agent 关注当下任务能否完成；长期记忆系统会保存偏好和历史；自进化 Agent 进一步把任务轨迹中的经验变成可复用流程、安全规则或评测案例。这个过程必须有筛选、版本和回滚。否则，一次偶然成功、一段恶意网页或一个模型猜测，都可能长期影响后续任务。

## 一次任务之后，分别沉淀什么

| 资产 | 保存内容 | 例子 | 不宜保存的内容 |
| --- | --- | --- | --- |
| Memory | 用户偏好、项目事实、稳定经验、任务状态 | 某项目的测试入口与用户偏好 | 未验证的猜测、跨用户私密信息 |
| Skill | 可复用流程、模板、脚本与参考材料 | 代码审查步骤、网页调研流程 | 只在一次任务中碰巧有效的动作 |
| Policy / Guardrail | 权限、安全和执行约束 | 删除前确认、某工具连续失败后停止 | 从不可信网页直接提取的“新规则” |
| Eval Case | 可复现的成功/失败任务 | 工具 schema 变化导致误调用 | 没有初始环境和期望结果的轶事 |

例如一次修复任务发现仓库必须先运行特定测试命令：如果命令经仓库规则或成功测试验证，可以进入项目范围的 Memory；如果形成完整“定位—修改—验证”可迁移流程，可整理为 Skill；若发现“写某目录需要批准”则应由授权的 Policy 管理；失败本身可写成回归样本。不要把所有东西扔进一条长期记忆。

## 从 Trace 到受控资产

一个可审计的流程是：收集完整 Trace → 提取成功经验和失败教训 → 判断资产类型 → 去重与脱敏 → 标记 `scope`、`source`、`confidence`、`version` → 写入候选资产 → 后台维护器评分、合并或归档 → 让用户查看、编辑、删除或回滚。

这里的“自进化”通常是**在边界内维护知识资产**，不是让 Agent 任意改系统提示词、权限或自身代码。高风险策略变更应由人批准；官方或内置 Skill 可设只读/固定版本；自动删除优先改为可恢复归档。更新前还应检查输入是不是不可信工具结果或网页注入。

这条链的终点也不是“写入成功”。下一次任务应通过检索或条件激活使用新资产，评测它是否减少失败；若带来退化，就撤回版本，并把误写入过程纳入事故分析。

## 为什么风险会累积

单轮回答错误只影响当前一次；错误记忆或 Skill 会影响未来许多次。常见风险有：把推测当事实、把偶然路径固定成通用流程、恶意内容进入 Skill、自动重写高价值资产导致能力退化、归档仍有用的知识、后台任务无上限消耗，以及权限在多次“优化”中逐步扩大。

控制点分别在写入、维护和使用三个位置：候选资产先验证与脱敏；维护时保留 diff、版本和审计；使用时按用户/项目 scope 与当前指令优先级判断。运行环境仍必须对工具调用做独立权限检查，不能因为某个 Skill 写着“可执行”就放行。

## 面试会怎么问

**问：自进化 Agent 与普通长期记忆 Agent 有什么区别？** 先说记忆只解决“记得过去”，自进化还要改进流程、策略与评测；随后补版本、评分、回滚、安全边界。

**问：一次任务如何沉淀为 Memory、Skill、Policy？** 用具体任务说明分类、验证、脱敏、scope、写入与回滚。追问“谁可以改 Policy”时，应明确需要独立治理和审批。

**问：为什么要防失控？** 用一次错误知识被后续任务反复调用的放大效应解释；提出只读资产、审批、受限工具、可恢复归档和评测验证。
