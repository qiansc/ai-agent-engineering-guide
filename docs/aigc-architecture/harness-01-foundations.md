# Agent Harness：让一次执行成为可比较的实验

一个 Agent 可以在演示里完成任务，距离稳定交付仍有很长一段路。模型会选择工具、读取不断变化的环境、修改文件或业务状态，甚至在中途请求人工批准。要判断一次改动是否真的让它变好，需要把任务放在受控环境中反复运行，记录过程，并用相同规则判分。这套任务、环境、执行、记录与门禁设施，就是评测语境中的 Agent Harness。

## 先区分四个常被混用的词

| 名称 | 回答的问题 | 一个具体例子 |
| --- | --- | --- |
| Benchmark | 考哪些标准化任务？ | 一组真实软件缺陷及验收测试 |
| Eval | 用什么版本、指标和配置进行这次评估？ | 比较旧模型与新模型在同一任务集的表现 |
| Harness | 如何准备环境、运行、收集轨迹、评分并形成门禁？ | 重置仓库、启动沙箱、执行 Agent、跑测试、出报告 |
| AgentOps | 上线后如何监控、灰度、回滚与回流失败？ | 线上 Trace 告警与发布回滚 |

同一个公开 Benchmark 可以用不同的 Eval 配置运行；一次 Eval 又要靠 Harness 执行。AgentOps 消费这些结果，但还负责线上运营。很多系统同时称自己的“模型循环 + 工具运行时”为 Harness，那是执行 Harness；本篇讨论的是**评测 Harness**。设计讨论中先说清语境，比争论名字更重要。

## 为什么不能只给最终答案打分

普通问答可以先比较输入和输出。Agent 在中间会产生副作用：查询客户资料、修改订单、写文件、调用另一位 Agent。假设客服 Agent 最后说“退款已提交”，文本流畅，但实际执行了不允许的直接退款工具；最终话术合格，安全和业务状态都失败。反过来，文案与参考答案不同，也可能合法地完成了任务。

因此至少要分开看六类结果：

1. **Outcome**：用户目标和交付物是否达到。
2. **Trajectory / Tool Use**：工具选择、参数、权限请求和中间决定是否合规。
3. **State**：数据库、仓库、页面和文件最终处于什么状态。
4. **Safety**：有无越权、泄密或未经确认的高风险动作。
5. **Cost / Latency**：Token、工具调用、人工审批与任务耗时。
6. **Robustness / Recoverability**：多次运行是否稳定，失败后能否安全恢复。

一个任务可以有不止一条正确路径。不要把某条预设轨迹逐字匹配成唯一标准：应把不可违反的规则、必须满足的状态和允许的替代路径分别写出。

## Harness 的九个部件怎样接起来

| 部件 | 输入与责任 | 输出 |
| --- | --- | --- |
| Task Dataset | 保存输入、初始状态、权限、风险、期望与评分规则 | 可版本化的任务样本 |
| Environment Builder | 构造仓库、数据库、网页、API mock、用户模拟器或沙箱 | 每次运行可重置的环境 |
| Agent Runner | 固定模型、Prompt、工具、策略和预算运行任务 | Run 状态与产物 |
| Tool/API Simulator | 返回正常、异常、超时或权限失败 | 可控的外部观察 |
| Trace Collector | 记录模型、工具、审批与状态变化 | 可回放的执行轨迹 |
| Grader | 比较答案、状态、轨迹、安全与成本 | 逐维度评分和失败标签 |
| Report Dashboard | 聚合任务与版本表现 | 差异与趋势 |
| Regression Gate | 按规则决定能否继续发布 | 放行或阻断及原因 |
| Feedback Loop | 把线上失败固化为新任务 | 持续增强的回归集 |

这些部件不一定要九个服务。一个小团队可以先用任务文件、隔离脚本、运行日志、测试和 CI 门禁实现同样的职责。重要的是每次运行拥有 `task_id`、`run_id`、完整版本组合和可核验的结果，让“新版本更好”变成可复核的判断。

## 一个小型退款例子

给定用户“退掉昨天买的蓝色外套”，任务环境包含订单快照和退款政策；Agent 只能查询订单、检查商品并创建待审核退款单，不允许直接退款。成功条件是确认正确订单、创建 `pending_review` 申请并给用户解释下一步。评分时既看数据库状态，也查轨迹有没有调用被禁工具。若最终答复正确而后台状态没变，Outcome 未通过；若状态正确但绕过审批，Safety 未通过。

这个例子说明 Harness 应把业务目标、受控环境、可观察状态和安全边界放在同一任务里，不能只保存一句用户提问。

## 面试会怎么问

**问：Benchmark、Eval、Harness、AgentOps 有什么区别？** 按上表先给职责，再用一次版本更新串起来：选任务集，确定本次评估配置，由 Harness 运行和判分，AgentOps 决定灰度、监控与回滚。

**问：为什么 Agent 比普通 LLM 更需要 Harness？** 用“最终回复正确但中间越权修改订单”的例子解释轨迹和环境状态；继续说明随机性、多工具、长任务与真实副作用怎样要求隔离和重复运行。

**问：设计完整 Harness 会有哪些模块？** 从 Dataset、Environment、Runner、Trace、Grader、Report、Gate、Feedback 讲数据如何流动；Tool Simulator 属于环境运行边界。面试时别只列名，要说明同一 `run_id` 如何贯通这些模块。
