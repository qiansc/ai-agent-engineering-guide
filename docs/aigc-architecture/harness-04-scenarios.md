# 四种场景，四套不同的 Agent Harness

评测框架可以复用任务、Runner、Trace 和报告的骨架，但环境与正确性标准不能完全通用。编码、浏览器、客服以及多 Agent 协作的副作用不同：代码形成 Patch，浏览器改变页面或账号状态，客服修改业务记录，多 Agent 还会在交接时丢失或重复信息。设计时先确定最终状态，再确定模拟环境和轨迹约束。

## 编码 Agent：真实仓库、Patch 与测试

准备固定的仓库 base commit，给出 issue、失败测试或需求；在隔离容器/工作区安装固定依赖，授予搜索、文件读写、Shell、Git 和测试工具，同时限制网络、密钥与危险命令。Agent 生成 Patch 后，Harness 应用改动、跑测试、检查 diff 范围和安全日志，最后保存评分、Trace 与失败标签。评测环境不能覆盖用户的未提交修改。

公开软件工程基准带来的关键启发是使用真实仓库、真实问题和可复现测试，而不是只生成一个独立函数。不过“测试通过”并不等于代码可交付。还要检查无关文件修改、回归、最小必要 diff、性能/可维护性，以及是否运行了必要检查。企业私有仓库还会增加权限、Dirty Worktree、Review 与发布约束；公开榜单不能代替自家任务集。

同样一次失败可能由定位不到文件、依赖构建失败、工具权限不足或代码修错造成。Trace 和失败标签要能把这些分开，否则团队容易把环境问题误当作模型能力问题。

## 浏览器 / GUI Agent：操作轨迹与高风险确认

浏览器评测要提供可重置页面、DOM 或截图、账号权限、表单/弹窗、重定向、错误页与网络响应。任务可以是查找信息、填表、修改设置、下载报表、跨页面导航、处理登录失效。环境还应测试页面内容中的不可信指令：网页可提供任务数据，却不能扩大 Agent 权限。

评分除了任务完成率，还需错误点击率、提交/支付/删除前确认率、注入攻击成功率、平均步骤、页面恢复能力和超时率。最终页面显示“提交成功”仍应对照后台状态；UI 提示可能延迟或错误。公开 Web/GUI 基准能帮助练习，但企业后台往往有特殊角色、权限和审批流程，应另建私有用例。

## 客服 / 工具调用 Agent：用户—Agent—工具三方闭环

客服 Harness 应把模拟用户、政策文档、领域 API 和订单数据库放在同一环境里。用户模拟器可以追问、补充信息、纠错、反悔或表达不满；工具可提供订单查询、库存、退款申请和工单创建。每个任务从独立客户与订单快照开始，结束时比较数据库、消息和工单状态，检查是否遵守政策、有没有多余工具调用或越权修改。

例如“外套退款”：用户在第二轮补充订单号，第三轮又改变退款原因。Agent 必须按政策更新判断，而不是对第一轮信息一条道走到底。衡量 task success、policy compliance、state match、unnecessary tool calls、对话轮数、重复运行一致性与升级人工的准确性。只评 Agent 与工具，会漏掉它是否正确处理用户变化。

## 多 Agent / A2A：交接是否真的帮了忙

把研究任务交给数据分析 Agent，或让编码 Agent 邀请审查 Agent，是可测试的协作场景。Harness 要记录接收者、协作者选择、handoff message、返回 Artifact、调用链和最终交付。要检查交接信息是否足够，远端结果是否被正确引用，是否重复搜索、互相覆盖状态，失败时能否回退到单 Agent 或人审。

除最终成功率，还看 handoff 成功率、上下文丢失率、Artifact 可用性、冲突解决、调用成本与责任边界。一个由三个 Agent 完成的任务，若带来大量重复工作和等待，即使最后通过，也可能不适合生产。跨 Agent Trace 应能说明每个决定来自谁。

## 场景选择对照

| 场景 | 关键初始状态 | 核心验收 | 特别容易漏掉 |
| --- | --- | --- | --- |
| 编码 | 仓库 commit、依赖、测试 | Patch + 测试 + diff | 用户未提交改动与危险命令 |
| 浏览器 | 页面/账号/后台状态 | 目标状态 + 安全点击 | 注入、确认、重定向 |
| 客服 | 政策、订单、模拟用户 | 对话 + 业务数据库 | 用户反悔、政策合规 |
| 多 Agent | Agent 能力、消息与任务状态 | 交接 + Artifact + 完成 | 重复劳动、状态冲突 |

## 面试会怎么问

**问：怎样设计编码 Agent Harness？** 按固定仓库、隔离运行、工具权限、Patch/测试/安全判分讲完整流程，补一句真实工作不只看测试。

**问：网页 Agent 与客服 Agent 有什么不同？** 前者重页面状态、危险点击与页面注入；后者重政策、多轮用户变化和数据库终态。两者都应看轨迹与副作用。

**问：多 Agent 评测为什么更难？** 因为要判任务分配、上下文交接、Artifact 使用与协作成本，不是分别测几个单 Agent 分数即可。
