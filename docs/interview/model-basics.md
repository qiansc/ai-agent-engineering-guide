# 模型基础：不同 AI 岗位需要学到多深

Agent 工程师不一定训练大模型，但必须理解模型特性怎样改变系统设计：上下文窗口有限，输出有随机性，Embedding 与生成模型解决的问题不同，推理有显存与吞吐约束。模型/算法岗则需要能解释训练方法、实验设计和指标。按岗位分层准备，既能避免应用岗被训练细节淹没，也能避免算法岗只会讲框架接入。

## 应用岗最低基线

Tokenizer 把输入转成 token；token 数决定上下文占用、费用和一部分时延。不同语言、代码和特殊格式的 token 比例不同，因此字符数不能直接当 token 预算。长文档不是简单塞进窗口：检索、摘要和结构化状态各承担不同任务。把工具说明、历史消息、检索证据和当前指令放在同一窗口时，还要考虑信息被大量无关内容稀释。

Embedding 把文本或其他内容映射到向量空间，用于相似性检索或聚类；生成模型根据上下文产生后续 token。向量相近不等于事实正确，且不同 Embedding 模型的向量通常不能混在同一索引里直接比较。检索系统需要记录模型版本、索引版本与重建计划。面试问“为什么换了 Embedding 模型后命中下降”，应检查向量维度、归一化、重建是否完整、查询与文档是否使用同一模型，以及评测集分布。

Attention 允许 token 利用上下文信息，自回归解码每次生成新 token。KV Cache 缓存已处理前缀的 Key/Value，避免每一步从头计算全部前缀，但会占用显存；长上下文与多并发会加大缓存压力。应用岗不必推导全部公式，也要能解释为什么长 Prompt 增加成本、为什么首 token 和后续生成的瓶颈不同，以及为何“窗口足够大”仍不能替代信息筛选。

| 概念 | 应用岗至少会说 | 常见系统设计影响 |
| --- | --- | --- |
| Token 与窗口 | 输入、输出、工具结果共用预算 | 裁剪、检索、压缩、成本上限 |
| Embedding | 表示相似性，不直接证明事实 | 索引版本、召回评测、混合检索 |
| 结构化输出 | schema 可约束格式，不能替代业务校验 | 参数检查、错误恢复、审计 |
| 采样参数 | 影响输出分布，不保证事实正确 | 一致性与多样性权衡 |
| KV Cache | 降低重复前缀计算但耗资源 | 并发、长上下文与显存 |

## 平台与推理岗往下一层

Prefill 处理输入上下文，decode 逐 token 生成。首 token 延迟受排队、输入长度和 prefill 影响；输出长时 decode 成本更明显。平台岗要能讨论吞吐与单请求时延的取舍：批处理可提高资源利用率，却可能增加等待；continuous batching 动态加入请求，仍要管理 KV Cache、优先级和租户公平性。Prefix cache 对重复前缀有用，但涉及缓存命中、隔离和失效。

量化可降低权重或激活的存储与计算需求，但效果取决于模型、硬件、精度和任务；不能笼统说“压到 4 bit 就不掉点”。模型网关还需要限流、超时、fallback、路由、审计与每租户配额。面试题“P95 突然变慢”应先分清网关排队、模型 prefill/decode、检索与工具等待。若 fallback 到另一个模型，还要验证结构化输出、工具能力和安全策略是否兼容。

## 算法岗需要解释训练与实验

Transformer 题至少应能画出 Q、K、V 的来源与 Attention 输出，解释多头为何能学习不同关系、位置编码为什么必要，以及训练和自回归推理的差异。SFT 使用高质量示范数据优化模型跟随任务指令；LoRA 通过低秩可训练矩阵适配部分权重，QLoRA 进一步把量化基座与低秩适配结合。它们降低训练资源需求，却不能代替数据质量和评测。

DPO 等偏好优化方法使用偏好对调整模型行为；GRPO 等策略优化方法在特定训练方案中使用群体相对反馈。面试不应只背缩写，应说清数据是什么、目标函数想改善什么、baseline 怎样设置、离线指标是否与线上任务一致、是否有奖励投机或分布外退化。若岗位以模型训练为主，还要准备数据清洗、去重、污染检查、消融实验、显存估算和推理部署。

## 端侧与多模态的额外问题

端侧推理受设备内存、算力、电量、包体和算子支持限制。选择端云分工时要同时考虑隐私、网络可用性和时延；本地小模型可以做意图识别或低风险规划，复杂检索和生成可能需要云端，但敏感数据能否上传由业务与合规决定。量化、蒸馏、缓存和批处理应在实际设备上评测，而不是只报告服务器指标。

语音 Agent 的错误可能起于 ASR，后续 RAG 和生成即使正确也会建立在错误转写上。评测要分开看字词错误率、关键实体识别、任务完成率与隐私处理。PDF/视觉文档则需检查版面、表格、图片和 OCR 的结构化质量。端到端分数下降时先定位是哪一个模态环节，不要直接更换主模型。

## 三组模拟追问

“上下文窗口变大，还需要 RAG 吗？”回答应比较资料总量、更新频率、权限、成本和证据定位。大窗口有价值，但不能自动解决最新资料、用户级 ACL 与来源可追溯。

“Embedding 换成新模型，为什么召回变差？”先核对索引与查询版本，再用固定标注集分辨解析、切分、召回、排序各段，最后才调参数。

“LoRA 微调后线下分数升了，为什么线上效果没变？”检查离线集是否代表真实请求、基线是否公平、任务是否真正需要参数更新、线上路由是否命中新模型，以及改进是否被检索或工具错误掩盖。

## 复习时做两张对照卡

第一张是“问题该用哪类改动”：知识缺失或频繁更新，先查数据与检索；输出格式不稳，先加 schema、验证与错误恢复；固定风格或特定任务行为长期不稳，才评估微调；时延与成本问题先拆 prefill、decode、排队和工具时间。每项都要给出实验集和回滚方式。这样可避免一遇到错答就提议训练模型。

第二张是“指标落在哪一层”：ASR 用转写和关键实体指标，检索用 Recall/MRR，生成用正确性与依据性，Agent 用任务成功与轨迹，推理服务用首 token、吞吐、P95 和资源占用。分层指标能告诉你先优化哪一环；端到端业务指标则检验局部改进是否真正产生价值。两张卡配一个自己的项目例子，通常比背更多缩写更有用。

## 从 Attention 到实际预算

在自注意力中，每个位置生成 Query、Key、Value 表示；当前位置的 Query 与可见位置的 Key 计算关联权重，再对 Value 聚合。多头注意力让模型在不同表示子空间学习关系。应用场景无需从矩阵推导开始答，但要理解输入越长，prefill 的计算与中间状态越重；自回归生成时每步依赖已有前缀，KV Cache 用显存换掉大量重复计算。并发会让多个请求同时持有缓存，因此长输入和长输出可能把服务从算力瓶颈推向显存或排队瓶颈。

面试官问“把上下文窗口从较短配置扩大后为什么 P95 恶化”，先检查真实输入长度分布，而不是只看最大窗口参数。可能是检索返回过多片段、工具输出变长、更多任务不触发压缩，导致 prefill 与缓存压力增加。做实验时固定任务集，比较首 token、总时延、显存、完成率和遗漏关键事实。若剪掉信息后速度提高却错答增多，就应使用更有选择性的检索或结构化状态，而非继续粗暴截断。

## RAG、提示和微调如何选择

这三种方法解决不同问题。知识频繁变化、要求引用和权限过滤时，先考虑检索；任务目标和输出格式不清时，先改输入说明、schema 与验证；模型在大量同类样本上稳定表现出某种行为缺陷，且有足够高质量数据时，再考虑微调。它们可以组合，但必须分别测量收益。微调后的模型不会自动知道昨天新增的企业文档，RAG 也不会自动保证工具参数合法。

以客服意图路由为例：先用清晰标签定义和少量示例构建基线，检查错误是否来自类别重叠、缺少上下文或样本不平衡。如果仍有大量可复现错分，且类别定义稳定，再收集标注数据评估微调。上线后还要比较不同渠道与新类型工单，防止离线数据只覆盖旧分布。这个选择过程比简单回答“数据多就微调、数据少就 Prompt”更稳妥。

## 微调实验怎样讲清楚

SFT 数据要覆盖目标任务、拒答边界和异常格式，并去重与隔离验证集。LoRA/QLoRA 降低需要更新或存储的参数与资源，但适配层选择、秩、量化精度和硬件仍影响结果。回答“LoRA 为什么省资源”时，应指出冻结大部分基座参数、训练低秩增量；回答“代价是什么”时，说明并非所有能力都能用小适配层补足，推理合并/加载和多租户适配器管理也有工程成本。

偏好优化需要先定义“偏好”从哪里来。若标注者只偏爱长答案，模型可能学会冗长而非准确；若奖励只看结果而不看工具越权，Agent 可能走危险捷径。因此训练指标需与任务级安全评测分开，保留独立测试集和负面样本。算法岗还应能解释基线模型、数据规模、消融设置以及何时停止训练，不仅报最终分数。

## 端侧方案的推演题

题目假设是手机端助手需要理解离线文档并在网络恢复后同步。先列约束：设备内存、可接受响应时间、电量、文档敏感性和离线可用范围。可考虑本地索引与小模型处理简单问答，复杂任务经授权后交给云端；同步时记录索引与文档版本，避免本地旧资料覆盖云端更新。测试应覆盖低端设备、长文档、网络抖动、权限撤销和设备丢失。端侧优化不能只在开发机上展示平均速度，还要报告最慢设备和隐私风险。

## 从一道题看模型与系统的分工

假设企业问答 Agent 经常把“可以申请”说成“已经批准”。这可能是知识库原文含糊、检索拿错版本、模型生成越过证据，也可能是工具状态与文档描述冲突。先固定失败任务并看最终依据：若证据里根本没有批准状态，生成层需限制结论和表达；若业务状态工具返回 pending，宿主应把它作为结构化事实，禁止生成 approved；若文档版本过旧，先修数据。微调也许能改善措辞，却不能替代真实审批状态查询。

这道题体现应用岗应懂的模型边界：模型可以解释文本、选择查询和组织答复，但关键业务状态应来自权威系统。模型输出应有类型与校验，尤其在金额、权限、法律和医疗等高风险场景。评价也要跨层：检索证据是否正确、状态工具是否正确、最终句子是否与事实一致，以及用户是否被误导。

## 推理性能题的答题步骤

面试官说“模型 QPS 上不去，先优化什么”。第一步量当前负载：输入/输出长度分布、并发、首 token、总时延、GPU 利用率、显存和缓存命中。第二步判断瓶颈：prefill 重则检查长输入、缓存与批处理；decode 重则看输出长度、批次与带宽；队列重则看配额与优先级；工具重则与模型服务无关。第三步给可验证实验，逐项比较吞吐、P95、任务质量和成本。量化或更小模型可能改善资源，却可能损害某些任务，因此需分群评测。

若候选人是应用岗，不必给精确 GPU 内核优化方案，但应能与推理团队沟通需求并控制上游输入。若是平台岗，需进一步解释 batching、缓存、路由与租户隔离；若是算法岗，还要讨论量化校准集、模型精度与任务退化。不同岗位的回答深度不同，基本诊断顺序相通。

模型基础的自测不只问“定义是什么”，还应问“这个机制改变了哪一项系统取舍”。例如 KV Cache 与并发显存有关，Embedding 版本与索引重建有关，量化与端侧质量和电量有关，SFT 数据与任务分布有关。若无法把机制连到输入、指标和失败案例，说明还停在名词层。每学一个术语，找一个能够证伪自己理解的小实验，比继续背更多术语有效。

## 面试会怎么问

小红书端侧推理优化实习复盘同时问到 HyDE、BGE rerank、HIT/MRR/Recall、LoRA 与 MNN；这要求候选人把检索、模型训练和设备约束分层回答。

**问：端侧 RAG 召回差，先做 LoRA 吗？** 答：先检查文档解析和标注集，测基础检索的 Recall@K，再比较查询改写、混合检索和 rerank。LoRA 调整的是模型参数，不会自动让缺失的证据进入候选集。只有当证据已正确送入模型而生成或特定领域行为仍不稳定，且有足够训练数据与离线/端侧评测时，才考虑微调。端侧还要报告模型体积、峰值内存、首 token 时延、耗电和离线能力。

**问：HIT、MRR、Recall 各说明什么？** 答：HIT 关注每道题是否至少有一个相关结果进入候选，Recall 衡量相关结果覆盖了多少，MRR 对首个相关结果的位置敏感。它们都不能单独证明答案正确；最终还要检查引用是否支持结论、模型是否在证据不足时停下，以及端侧时延是否可接受。

题目来自个人面试复盘，技术答案仍需结合具体数据集与实现核验。
