# 字节 Agent 秋招一面：记忆、幂等、Harness 与 AI-native 开发

这场面试先深挖企业助手与文档更新项目，再谈 Agent Harness、Computer Use 和 AI Coding，接着转到数据库与两道算法。原帖作者记录当天下午已约二面，但没有公开每道题的现场回答或项目实现细节。下面按原帖“项目—八股—算法—反问”的顺序展开可学习的答法；涉及个人项目的数字只能由实际做过的人填写。

## 项目 1–2：滑动窗口与摘要压缩的会话记忆

滑动窗口保留最近若干轮原文，适合短期连续追问，因为细节仍完整；摘要把较早对话压成较短的事实与状态，适合长任务和长期会话，但可能丢掉否定条件、用户新约束或工具状态。两者通常组合：近期消息原样保留，较早消息以受控摘要承接，当前任务的硬约束与待办状态另外保存。

窗口大小不该只答“设置十轮”。先测模型上下文预算：系统/工具说明、检索证据、当前用户消息、工具返回和预留输出分别占多少 Token；再看对话的平均长度、失败样本里丢失了哪些信息，以此选轮数或 Token 上限。窗口滑动后要检查被移出的内容：项目规则、已批准动作、未完成任务、用户否定约束进入结构化状态或摘要。摘要需记录版本、来源和更新时机，避免“摘要的摘要”逐轮漂移。

## 项目 3：文档自动更新如何防并发覆盖

文档更新链路可能有定时任务、人工触发和消息重投。若两个 Worker 同时读到旧版本并写回，后提交者会覆盖前者。可以为文档设置版本号/ETag，写入时采用条件更新；为同一事件定义幂等键，重复消费返回已有结果；需要串行化时按文档 ID 分区或使用受控锁。写入前后保留内容版本和更新来源，冲突时重读并合并或进入人工处理，不能简单重试旧 Patch。

RocketMQ 可放在“发现变更/任务创建 → 消费者更新索引或文档”的异步边界，承担削峰、解耦与失败重投。它本身不保证业务写入只执行一次：消费者仍须幂等，消息确认时机与数据库提交关系要设计清楚。相比定时任务直接处理，队列便于并发控制、重试与观测；若任务少且没有异步要求，直接处理也可能更简单。回答时按自己项目的链路讲，不能把 MQ 描述成无条件必需。

## 项目 4–5：不同 Harness 怎样比较、是否该替换

先澄清这里的 Harness 指模型工具调用宿主，还是评测运行环境。介绍某个实现（原帖点名 DeepSeek Harness 与 Pi Agent）时，不要只背名字：讲它如何组装上下文、声明工具、执行权限、持久化状态、处理工具错误、观测与验收。与当前方案比较时，列出真实痛点和固定任务基线，例如恢复成功率、越权阻断、每任务成本和维护难度。若新实现解决了关键缺口，再做小范围接入；若只是相似包装，替换会带来状态迁移与回滚风险。

谈其他厂商产品与 Claude Code 压缩机制时，应分清公开可观察行为与内部未公开实现。一个实用解释是：当上下文接近预算，宿主可将较早工具输出与对话总结为摘要，保留当前目标、约束、关键文件、测试结果和未完成状态；恢复后仍需重新核验仓库实际状态。不要把“模型记住了”说成文件版本和副作用已被可靠保存。

## 项目 6：Computer Use 本地与云端

Computer Use 的典型循环是观察屏幕或可访问 UI 状态、选择点击/输入/滚动动作、由宿主执行、再观察结果。关键不是截图识别演示，而是坐标与元素稳定性、权限、页面注入、高风险操作确认、超时后状态核验，以及完整动作 Trace。本地电脑方案更接近用户现有应用和文件，但可能碰到私人资料与不可恢复副作用；云端隔离环境更易重置和审计，却要处理登录态、数据同步、性能和费用。无论哪种，模型请求动作与宿主授权执行必须分开。

## 项目 7–8：AI Coding 出过什么问题，完整工作流是什么

可信回答用一个自己遇到的错误讲：AI 生成了什么、为何一眼看不出错、哪项测试/Review 发现、最后怎样修复。完整工作流可按“澄清需求与验收 → 阅读项目规则和现有代码 → 给出小范围计划 → AI 辅助实现 → 审查 diff → 跑测试/静态检查 → 修正 → 交付说明”展开。不同任务的自主度不同：危险迁移、权限与支付代码需要更强人审。不能把“让 Agent 一次性写完并提交”当作 AI-native。

## 八股：数据库类型和 B+ 树

关系型数据库适合事务与结构化查询；文档、键值、列族、图等系统各有数据模型与访问模式。选型先看一致性、查询、索引和运维要求，不能用“SQL 过时”概括。MySQL InnoDB 的索引常用 B+ 树：内部节点组织查找路径，叶子节点承载有序记录/索引项，适合范围扫描与磁盘页访问。回答“为什么不选其他树”时讲页扇出、树高与范围查询，不要声称所有 MySQL 索引都只有 B+ 树，也不要忽略 Hash/全文索引等特殊场景。

## 算法 1：判断 B 是否是 A 的子结构

遍历 A 中每个可能根节点；当节点值与 B 根相同，从两个根同步比较：B 的节点匹配完表示找到了子结构，A 对应位置为空或值不同则此起点失败。需要先与面试官确认空 B 的定义、重复值、节点值类型。朴素最坏复杂度可到 `O(|A|×|B|)`；可用递归或显式栈实现，注意不要把“子结构”误答成要求两棵子树连空孩子都完全相同。

## 算法 2：两个有序 List 的交集及无限序列

两个已排序有限 List 用双指针线性前进，值相同则输出并同时移动，较小的一侧前进，时间 `O(m+n)`、额外空间取决于输出。先问交集是否保留重复元素：若集合语义，要在输出时跳过重复值；若多重集语义，则按两边出现次数取最小次数。

原帖继续追问“无法整体排序的无限序列、Bitmap 值域过大、能否局部分批处理”。无限流无法声称已经求得完整交集，必须定义时间窗口、停止条件、数据到达次序和可用内存。局部分批可在有限窗口内排序归并或用哈希/外存分桶；Bitmap 只有值域可控时才划算，稀疏且巨大值域会浪费空间，可用分段 Bitmap、压缩位图或哈希/外存索引。若数据永不结束，只能持续输出截至当前已确认的交集或窗口结果。

## 反问：从“我用 AI”到“AI-native 怎么做”

原帖反问团队业务与 AI Coding 氛围，面试官又反问是否有更 AI-native 的工作方式。可从任务单位回答：把可验收工单交给 Agent，给它读/改/测工具与受控工作区；把需求、测试、权限和完成标准写成契约，开发者在关键设计、Review 与风险审批处介入。之后用固定任务比较交付时间、缺陷率、返工和审查成本，而不是只看生成代码行数。

## 面试会怎么问

准备一条真实长任务轨迹，分别标出压缩后必须保留的信息、MQ 重投后的幂等键、工具动作的审批点和中断后的状态核验。被问新框架是否替换时，用基线与迁移风险作答；被问 AI-native 时，把工程责任与验收讲清。算法题先澄清“子结构”“重复元素”“无限序列”的定义，往往比直接背模板更重要。
