# FDE 面试：证明从客户问题到生产采用的交付能力

Forward Deployed Engineer（FDE）与 Applied AI 工程岗位通常要求候选人既能写生产级软件，也能进入客户实际流程，识别值得解决的问题并推动系统被使用。面试准备不能只围绕 Agent 框架：需求发现、集成、权限、安全、评测、上线、沟通和产品反馈会连成一条交付链。具体面试轮次由招聘团队决定，不宜背某篇二手指南中的固定轮数。

## 从模糊诉求收窄试点

假设客户说“希望 AI 自动处理所有法务合同”。第一轮会谈不应立即承诺全自动 Agent。先问实际使用者是谁，当前合同如何流转，哪些环节耗时，错判的代价是什么，哪些数据可访问，谁批准上线。把目标改成可验证的窄任务，例如“对一种标准合同提取指定字段、标出与模板不同的条款，并由法务确认”。这时可比较规则、检索、模型抽取与 Agent 的必要性，而不是先选技术栈。

| 发现问题 | 需要拿到的答案 | 对试点的影响 |
| --- | --- | --- |
| 谁作决定、谁每天使用？ | 预算方、业务负责人、终端用户 | 采访对象与采用指标不同 |
| 哪类样本最常见？ | 模板、语言、格式、例外比例 | 限定第一版范围和评测分层 |
| 错误代价是什么？ | 误报、漏报、泄露、审批延误 | 决定人工确认与失败终止 |
| 现有系统如何接入？ | API、身份、网络、数据驻留 | 决定部署和集成成本 |
| 成功由谁签字？ | 质量、时延、节省工时、采用率 | 决定试点验收方式 |

一个好的回答会给出一周或两周可落地的最小闭环、明确暂不支持的合同类型，以及停止条件。若客户无法提供可标注样本或合规审批，先做数据和流程盘点可能比做 Demo 更有效。客户发现不是让客户说出“想要 Agent”，而是找出能被可靠改善的工作单元。

## 现场交付要兼顾速度与约束

FDE 常需在现有身份、审计、网络和部署限制下交付，而不只是从零搭样板。现场方案应有数据流：客户系统怎样发起请求，敏感内容在哪里处理，模型可见什么，工具凭据由谁保管，结果怎样返回和留痕。若做 MCP server 或 Agent skill，仍需定义工具 schema、业务校验、最小权限和失败语义。协议提供接入方式，不会自动完成授权与合规。

交付时可将系统分三层：确定性入口负责身份、配额和策略；受限 Agent 负责开放式判断与工具选择；执行与评测层负责校验、幂等、审批、trace 和回归。这样客户能知道哪些行为由模型建议，哪些必须由程序和人批准。高风险操作展示对象、影响和不可逆性，不能只弹一个“继续吗”。

## 衡量采用，不只衡量模型分数

离线抽取准确率只能回答“在这批样本上是否做对”。交付成功还要看真实用户是否愿意在工作流中使用、节省的人工时间是否被返工抵消、异常样本是否有明确去处。试点指标可包括合格任务比例、人工修改量、平均完成时间、用户留存、误放/误拦截、审计完整性和每任务成本。统计时区分“被邀请用户”和“实际使用用户”，避免把演示访问量当采用率。

上线通常从建议模式开始，让客户在原流程里审阅；积累错误类型后，再挑选低风险、可撤销的动作自动化。若数据分布变化或安全事件超阈值，应能退回建议模式或人工处理。一次性为客户写的特殊规则若在多个客户反复出现，可以反馈到产品；只有单个客户需要的例外则应隔离配置，避免污染通用产品。

## 四类故事提前准备

**客户发现：**讲你如何把“做一个 AI 助手”变成明确任务。说明访谈对象、反例、最小试点和被舍弃的需求。

**工程交付：**讲一个 API、工具或工作流如何接入客户系统。覆盖认证、重试、幂等、日志、测试、回滚，以及你亲自实现的部分。

**失败或冲突：**讲客户希望扩大自动执行范围，而你如何用错误样本、风险等级或法规约束解释为什么先加人工审批。重点不是“说服客户”，而是提出可验证的替代路径。

**产品反馈：**讲现场出现的共性摩擦，如何整理成可复用工具、文档或产品需求；附上多客户证据，而不是把一个定制需求泛化。

可以用一个练习检验准备是否充分：客户要求 Agent 读取内部文档并向外部邮箱发送总结。你应先确认授权范围、数据分类与接收对象，再设计只读检索、草稿生成、内容检查和发送确认。若不能满足数据出境或邮件审批要求，停止自动发送并给出替代流程。面试官在这里看的是交付判断，而不是你能否现场拼出邮件工具。

## 面试中的 AI 使用规则

准备材料时可以使用 AI 辅助练习，但现场和 take-home 是否允许，应看招聘方当次说明。不同公司的规则可能相反；有的明确安排 AI-assisted coding，有的默认不允许，除非题目另有授权。开始前确认允许范围、是否需共享提示记录，并准备在无 AI 的情况下解释架构和代码。

## 一道完整案例题

客户是一家多地区企业，想让员工通过聊天窗口申请软件权限，并要求两周内上线。先确定“申请”是生成工单还是直接授权，厘清审批人、地区政策与现有身份系统。第一阶段只让 Agent 解释申请条件、补齐缺失字段和生成待审批工单；权限变更由现有审批系统执行。对外部知识库按员工身份检索，工具只返回当前用户有权查看的条目。工单创建使用幂等键，网络超时后先查询工单状态，避免重复申请。

验收样本要覆盖标准申请、字段缺失、无权限申请、跨地区政策冲突、审批人不存在和恶意文档注入。除正确率，还要测用户完成申请的时间、人工补改率、审批拒绝原因、越权事件与工单重复率。试点范围可限于一个地区、一类软件和一组自愿用户；若身份集成或政策无法核实，就不启动自动授权。面试中讲清这些限制和升级路径，比承诺“全员两周上线”更有交付意识。

## 从试点到可复用产品

现场交付常会遇到客户特有字段、审批链和网络环境。实现时要分清哪些是稳定产品能力，哪些只是某个客户的配置。身份、任务状态、工具权限、trace 和评测等机制通常应形成通用底座；特殊字段映射、术语和流程分支可以由配置或适配器承载。若每个客户都复制一份 Agent 代码，升级模型、修安全漏洞和比较质量将很困难。反过来，过早把所有客户例外抽象成平台能力，也会拖慢第一个试点。

可用“重复出现且机制相同”判断是否产品化：先记录现场问题、影响与临时处理；在第二个客户验证是否仍出现；再和产品团队讨论统一抽象与迁移成本。反馈时不要只报客户说“需要一个按钮”，而应交代任务、当前绕路、失败频率、受影响角色和可复用的最小能力。FDE 的价值之一，是把部署中的重复模式送回产品，而不是永远留在定制项目里。

## 数据与安全冲突怎么处理

设客户要求把包含个人信息的历史工单送到外部模型做快速评测。先确认数据分类、处理地区、授权范围与合同约束；若不能确认，就用脱敏样本、合成数据或在批准环境中跑最小实验。不能因为“只是评测”就绕开生产数据规则。若要求 Agent 自动给员工开通权限，先检查现有审批系统是否有明确 API、谁能批准、如何撤销和审计。缺少可验证的授权链时，方案应停在建议或草稿层。

面试官可能追问“客户不接受人工审批，威胁改用竞品怎么办”。较好的回答是先解释具体风险与证据，提供可测的低风险替代范围，例如只自动处理可撤销、低权限、标准化申请；对高风险动作保持审批。若客户仍要求越过安全边界，应明确升级给安全和业务负责人，而不是工程师个人私下让步。这里考的是在交付压力下保持可信任的判断。

## 案例题的评价标准

回答“客户要一个 Agent”时，可以按五项给自己检查：是否识别决策人和日常用户；是否把任务缩到可验收范围；是否给出数据与权限集成图；是否设计失败、回滚和人工接管；是否定义采用而非只定义模型质量。每项都应有具体问题或动作。若答案只介绍 MCP、RAG 和模型选型，却无法说明客户何时会真正使用，说明还停留在技术展示。

准备两个相反的真实故事，一个是你如何克服系统约束交付试点，一个是你如何拒绝或收窄不合适的自动化。两个故事都要分清个人决定、团队共识和客户决定。若没有 FDE 工作经历，可用内部平台落地、跨团队集成或开源用户反馈的经历练习，但不要把内部用户伪装成外部客户。

## 客户发现的五分钟角色扮演

面试官扮演客户说：“我们的客服每天很忙，想要一个能回答所有问题并自动退款的 Agent。”候选人先问最常见的请求类型、工单量、现有知识与退款规则、异常比例、错误退款的成本和谁有审批权。客户若回答“我们还没有整理好历史数据”，下一步是选择少数高频类别做人工标注与只读建议，而不是立即承诺全自动。客户若坚持先做退款，可把范围限制到金额低、规则明确、可撤销的情形，并让现有交易系统做权限与幂等校验。

较差的回答会迅速画出多 Agent、RAG 和工具列表，却不问谁使用、如何验收或谁承担退款风险。较好的回答会总结刚听到的事实，请客户确认最小目标，并给出一张一页纸的试点契约：输入、输出、样本范围、验收指标、数据授权、部署环境、人工接管、停止条件和责任人。若客户无法确认这些前提，下一阶段应是发现与数据盘点，而不是假装进入开发。

角色扮演结束后再补一个交付追问：“试点准确率达标但一线人员不用，怎么办？”应去观察实际流程：入口是否额外增加操作、答案是否缺少可信依据、处理时延是否拖慢工作、错误是否集中在最重要的类别。与使用者共同调整工作流，比较人工修改量和完成时间；若收益仍不足，收窄或停止试点。采用率不是销售口号，而是需要设计和测量的结果。

## 技术实现的最低交付清单

一个现场演示可以很快，但进入客户试点至少应有明确身份与授权、版本化配置、基本测试、失败日志、人工接管和回滚办法。集成 API 要处理限流、超时、重复消息和字段变化；模型输出要经过结构化校验，不能直接写入客户系统。若需要安装 MCP server，确认它运行在哪个环境、使用什么凭据、谁能发现和调用它、如何撤销权限。每个能力都对应一个负责人和可观察的成功信号。

当客户环境限制网络出口或数据驻留时，不应只说“可以私有化”。先列模型服务、日志、索引、工具、监控和支持人员访问分别部署在哪里；离线或受限网络下哪些功能无法使用；升级和补丁如何交付。面试时间有限时可给出待核实清单，但不能跳过这些条件直接保证上线。

与客户汇报时，区分“已经在测试环境演示”“已在小范围试点”“已进入生产且持续使用”。每个阶段给出实际使用人数、任务范围、故障与下一步门槛；不能因为演示顺利就宣称完成交付。若客户现场发现严重缺陷，先止损和说明影响，再安排复现与修复，不用含糊的“模型偶发问题”代替责任清晰的技术报告。

## 面试会怎么问

把客户发现、现场实现与安全责任放在同一条交付链上练习。具体面试轮次与出题方式仍要以当次招聘方告知为准。

**问：客户说“请给全公司做一个什么都能查的 Agent”，你怎样收敛？** 答：先找一个业务负责人和一条高频、可验收的任务，例如只回答最新差旅政策。确认用户群、资料权限、更新频率、不可接受的错误和人工接管方式；拿小样本建立 baseline，再做两周试点。第一版只读且带来源，不自动执行报销或审批。试点指标同时看正确完成、引用可信度、实际使用率和人工节省时间；若没有采用，继续访谈阻力，而不是只调模型分数。

**追问：客户要求绕过权限让演示更顺畅怎么办？** 答：拒绝在真实数据上绕过权限，解释这会让试点结论失真且可能泄露信息。可以用获授权的测试数据演示流程，随后与客户安全负责人明确身份、审计和审批条件，再决定真实上线范围。这个回答需要展示推进交付的替代路径，而不是一句空泛的“安全第一”。

以上问题是训练用的场景题，不代表某家公司的固定面试题；回答应换成自己经历中真实做过的决策与结果。
