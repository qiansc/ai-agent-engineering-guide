# 美团 AI Agent 一面：长流程可靠性一路追到交易与异常测试

这场个人复盘有 30 个连续问题，前半段围绕 Agent 项目的背景、长流程、幻觉、上下文与知识库，后半段转到交易系统、线上稳定性，以及 AI 辅助开发缓存一致性验证项目。作者说之后约了二面；原帖没有给出项目的架构图、实际指标、现场回答或二面内容。下面按题目原顺序组织成可学习的答法，个人经历题只能给表达方法，不能替候选人编经历。

## 1–3：自我介绍、项目成果与长流程保障

自我介绍用“业务问题—自己的责任—主要设计—验收结果”四步。项目背景应说明谁使用、过去流程哪里慢或不稳、为何需要 Agent 而非固定 Workflow；落地方案讲入口、状态、模型决策、工具执行、权限与观测；成果讲真实数据口径或可复核样例，不要用没有基线的“效率提升明显”。

长流程最重要的是**任务状态不能只活在聊天历史里**。给每个步骤明确输入、输出、失败/超时出口与完成条件，执行后持久化检查点；每个有副作用动作带操作 ID 或幂等键；恢复前先查外部状态。模型循环设轮数、时间与成本预算，关键写操作审批，异常时允许重试、补偿或转人工。可用一条“创建退款申请 → 等审批 → 更新订单 → 通知用户”的任务说明：审批等待不能被当成完成，通知失败也不能让订单修改无记录。

这条教学任务可拆成如下状态；它说明回答时应该说出什么，并非原帖项目的实现：

| 状态 | 持久化信息 | 恢复时检查 |
| --- | --- | --- |
| 已接单 | 用户目标、身份、任务版本 | 是否同一请求重复投递 |
| 待资料 | 已确认订单、政策版本 | 用户是否补全资料或修改目标 |
| 待审批 | 审批对象、金额、过期时间 | 审批是否仍有效，金额是否变化 |
| 执行中 | 操作 ID、工具请求与最近状态 | 写操作是否已成功，避免重放 |
| 待通知 | 业务已生效的事实、消息 ID | 通知失败可重试，业务动作不能重做 |
| 完成/失败 | 最终状态、原因、人工接管记录 | 能否向用户准确说明结果 |

追问“每一步按预期推进”时，可给出状态转移的客观条件：例如审批通过且订单版本仍匹配才进入写入；工具超时后先查询操作 ID 对应状态。这样比说“加了重试和日志”更能证明长流程可靠性。

## 4–7：幻觉、置信度与上下文膨胀

项目里是否真的遇过幻觉，应给一次具体坏例及 Trace：模型引用不存在的政策、误读工具结果，还是在没有订单证据时声称退款成功。不同根因对应不同修法：缺证据先修检索/工具，证据错误先修数据，模型无视证据则用引用约束、核验器和回归题集；高风险动作必须在执行层审批，不能只靠提示词“不要幻觉”。

置信度也不能等同于模型自己给出的 0.9。可结合检索分数校准、证据版本/一致性、工具校验结果、业务规则与风险等级。证据缺失、多个候选订单、金额或收款对象不确定、不可逆动作，都应澄清或二次确认用户。阈值从标注坏例与误放行/误拦截成本确定，不能照搬某个数。

多 Agent 往往把中间消息、工具结果与重复讨论塞满窗口。可按任务分隔上下文、只传必要的结构化 Artifact 与引用，对较早对话做摘要；保留当前目标、硬约束、待审批动作和未完成状态。摘要后检查是否丢失否定条件与来源。并行 Agent 的结果要有归属、版本和冲突处理，不能把“压缩了”当作状态一致性方案。

## 8–11：框架选择、原生实现与知识库保鲜

原帖写的是“LangChain、LongGraph、原生手写 Agent”；若其中 `LongGraph` 是指 `LangGraph`，可按链式组件、状态图编排与自研 Runtime 比较，但现场先向面试官确认名称。框架有现成抽象与生态，代价是默认行为和版本兼容需要理解；原生实现能精准控制状态、权限、工具与观测，代价是大量边界要自己补。选择由任务复杂度、持久化/恢复需求、团队维护能力决定，不是“框架不行所以自研”。被问亲自写过没有，要明确原型、线上系统和个人负责范围。

知识库建设要说明原文来源、解析/切分、元数据、权限、索引与查询路径。产品更新后“知识保鲜”需要源文档版本、增量摄取、删除/失效旧片段、索引原子切换或版本过滤、缓存失效和过期监控。设计一批“旧政策与新政策冲突”的回归问题，检查检索和最终引用是否指向正确版本。模型再强也无法自行修复一个只含旧资料的索引。

一个完整更新事件应能从“源文档变更 ID”追到“解析结果—Chunk 版本—向量/关键词索引版本—缓存失效—查询使用的版本”。如果新索引构建一半就切换查询，用户可能同时检索到新旧条款；可以先写入候选索引，校验片段数与回归题，成功后切别名/版本指针，再异步清理旧版。若不能原子切换，至少在查询中过滤同一文档的最新有效版本。答案处保留文档与版本引用，便于发现过期回答。

## 12–16：AI 如何融入日常交付与本地工作流

日常提效不要只答“用 AI 写代码”。按具体任务讲：需求澄清与设计草稿、代码定位、实现建议、测试生成、Code Review、文档同步；分别说人工负责哪项决定、哪些输出被测试或 Review 证实。若你写需求交付代码，就给出一条从 Issue 到 PR 的真实路径；如果团队有统一平台，讲自己实际使用的部分，本地工作流与平台服务的权限、模型版本和审计差异。

本地 Agent 遇到异常时，至少处理工具超时、无权限、文件已变化、测试失败、循环调用与错误外部状态。失败返回结构化错误，按幂等性决定是否重试；达到预算或安全边界时停止并交给人。被问模型原理和传统架构，可从 Token/注意力、工具循环，到数据库、队列、缓存和事务的职责分层回答；不必把 Agent 技术当作后端基础的替代品。

## 17–21：交易系统与线上稳定性

交易关注正确性和资金安全：订单状态、库存与金额一致性、支付回调、幂等、防重复扣款、超时与对账、权限和审计。若系统经统一支付团队封装，应准确说明自己的边界：你可能只调用支付网关并处理结果，而不直接对接三方。不能把未参与的资金链路写进自己的项目。

线上稳定性可沿“入口限流 → 服务降级/熔断 → 幂等与事务/补偿 → 队列和重试 → 观测告警 → 灰度回滚 → 演练”展开。每层举具体故障：消息重复投递如何避免两次退款，外部支付超时如何先查询状态而非直接重试，库存扣减与订单创建部分成功怎样补偿。监控告警要对应业务指标、错误率、延迟、队列积压和任务停滞，并让 Trace/日志能把一笔交易从入口追到工具动作。若简历写了自动化运维，需说明告警规则、执行权限、误报和回滚机制。

交易场景中“重试”需要按动作分类。只读查询在限流条件下通常可以重试；创建订单或支付请求应使用业务幂等键，并在超时后查询实际结果；取消订单、退款等还要检查状态机允许的转移。数据库事务只覆盖本地数据，不能让外部支付也自动回滚。回答架构题时，画出订单、库存、支付和消息的责任边界，以及哪一步需要人工或补偿流程。

## 22–24：基础架构团队何时信任 AI

问团队 AI 使用程度时，只报告自己知道的范围。基础架构或交易业务要扩大 AI 使用，先从只读分析、测试/文档等低风险场景建立基线；引入隔离、权限、评测、审批和审计后，逐步放开有限动作。信任是某一任务在给定风险下达到可验证标准，不是“模型整体很聪明”。谈 AI 影响时区分已验证的日常提效与未来业务形态推测，避免把个人预测当成公司规划。

## 25–28：缓存一致性验证项目与 AI 生成测试

完整开发过程可按“问题定义 → 缓存/数据库读写时序 → 不一致场景 → AI 辅助生成方案/代码 → 人审 → 故障注入与测试 → 结果”讲。缓存一致性常见坏例是数据库更新成功但缓存删除失败、并发读把旧值重新写入、消息重复消费或乱序。验证项目应明确要覆盖哪些时序、是否使用版本号、重试/补偿、监控和最终一致性窗口。项目最终结果要用实测通过的用例、发现的真实故障或剩余限制回答，不编造百分比。

AI 生成测试可以帮助扩充边界，但人应先给业务不变量和危险路径：重复请求不得重复扣款，旧版本不得覆盖新版本，故障恢复后数据能对账。再让 AI 提候选异常：网络超时、进程崩溃、缓存丢失、消息乱序、并发写入。逐条审查可执行性和断言，跑故障注入并检查是否真能使错误实现失败。若场景完全由 AI 自己想到，也要承认覆盖未知；不能把“生成了很多用例”当作测试充分性的证据。

| 注入故障 | 应检查的不变量 | 仅看“接口返回成功”会漏掉什么 |
| --- | --- | --- |
| DB 更新成功、缓存删除失败 | 后续读不能长期返回旧版本 | 旧缓存仍在服务用户 |
| 两次并发更新同一键 | 最新有效版本不能被旧写覆盖 | 最后写入者不是最新业务事件 |
| 消息重复投递 | 一次业务变更只生效一次 | 重复扣减、重复通知 |
| Worker 在写入后崩溃 | 恢复能辨认已生效操作 | 盲重试造成重复副作用 |
| 缓存失效风暴 | DB 不被瞬时请求压垮 | 单条用例通过、整体服务失稳 |

测试结果要记录初态、并发时序、注入点、最终 DB/缓存值和 Trace。这样面试官问“异常场景是 AI 想到的，还是你告诉它的”时，可以回答自己如何定义验收不变量、审查 AI 候选并验证其杀伤力。

## 29–30：职业选择问题

原帖最后两问涉及此前面试与实习转正选择。这类问题没有通用标准答案：按真实时间线、所承担的项目、希望进入的业务方向和岗位匹配度说清楚，避免贬低前团队，也不要编造 Offer 或转正条件。技术复盘中可准备一两句简洁回答，把更多时间留给可验证的项目经历。

## 面试会怎么问

这场的追问链是：长流程能否推进 → 幻觉怎样被发现 → 什么条件下需要确认 → 上下文如何不丢状态 → 知识更新是否可信 → 交易副作用能否安全恢复。准备时选自己项目中的一条长任务，画出步骤、检查点、工具权限、异常路径和结果指标，再给出至少一条真实失败与修复。缓存一致性项目要准备“AI 建议了什么、我审查并验证了什么”，否则很容易被追问到只有工具使用经历、没有工程判断。
