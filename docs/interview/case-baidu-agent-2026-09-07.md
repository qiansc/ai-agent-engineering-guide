# 百度 Agent 开发实习一面：从项目细节追到中断恢复

这场面试从自我介绍、RAG 项目一路追到 Coding Agent 的工具执行、长期记忆、MCP 传输、断点恢复和 Trace，最后是二叉树序列化算法。原帖记录了 15 个项目问题；候选人说自己没有做可观测，也没有完成 LC297。下面沿真实提问顺序讲准备方法和技术解法，具体项目数据与候选人当场回答并未公开，不能代填。

## 1–3：自我介绍、混合检索与切片粒度

自我介绍不要堆框架名。用“业务问题—我负责的链路—可验证结果”组织 60–90 秒，之后准备一条能从原始文档走到最终答案的具体请求。面试官紧接着问“混合检索用什么做”，重点是两路检索如何互补：关键词/BM25 适合精确术语、编号和低频实体；向量召回适合语义相近但措辞不同的问法。可以并行召回、去重并做 RRF 或带标定的加权融合，随后重排。回答时要说实际用的索引、版本、过滤和指标，没做过的不要说做过。

切片大小没有通用的 512 或 1024 标准。先按标题、段落、表格/代码边界保证语义完整，再按模型窗口与检索任务选候选粒度；用同一批标注问题比较 Recall@k、命中片段质量、答案引用和时延。过小切片容易丢条件和上下文，过大切片会让召回向量失焦、挤占生成窗口。对于需要精准定位的子片段，可检索小块、返回其父段，但要核验父段的版本和权限。

## 4–8：Coding Agent 是否基于开源、差异和工具层“兜底”

被问“基于什么开源项目”时，明确哪些是复用、哪些亲自实现：模型循环、工具 schema、权限层、工作区管理、上下文压缩、测试/评测分别怎么做。对比开源实现时不要泛称“更轻量”或“更适合业务”；给出一项可测差异，例如某工具失败后的错误分类、重试上限、工作区隔离或恢复路径，再讲对照任务结果。若没有对比实验，诚实说是设计取舍。

“工具兜底”最好分四种：参数无效在执行前用 schema 拦截，并返回可修正错误；暂时性超时可按幂等性、预算与退避规则重试；权限拒绝必须停止或请求批准，不能换工具绕过；有副作用工具返回不确定状态时先对账，不能盲目重放。执行器通常还负责输入校验、身份与权限、沙箱、超时/取消、结构化结果、日志脱敏及结果大小限制。模型只能提出工具调用，宿主决定能否执行。

问“最难点”时挑一个真实失败：输入、预期、实际 Trace、根因、修复、前后验证和剩余风险。比如长任务中工具超时，系统一度不知道是否已写入；修复不仅是增加重试，还要用操作 ID 查询副作用状态。没有亲自做过的复杂机制，不必硬讲成自己产出。

## 9：长期记忆怎么做

先区分会话内任务状态与跨会话记忆。前者包括当前目标、计划、已执行工具、待审批动作和外部副作用，必须为恢复可靠保存；后者才是稳定的用户偏好、项目规则与经过验证的经验。写入长期记忆需要 scope、来源、时间、置信度、去重与删除/更正能力；读取时按用户和工作区过滤，不能让一个人的私密事实进入另一个会话。摘要压缩可以减少窗口占用，但不能替代任务状态存储。

## 10–11：MCP 的 stdio 与 Streamable HTTP

`stdio` 通常连接本机子进程：宿主启动 Server，通过标准输入/输出交换协议消息；生命周期、进程权限、日志输出和重启由宿主管理。Streamable HTTP 面向通过 HTTP 可访问的 Server：要处理认证、会话、超时、重连以及可能的流式响应。这里的“streamable”描述协议交互方式，不等于它天然适合传输音视频流；工具的输入输出仍应按协议内容类型与资源能力设计，大型媒体数据往往需要对象存储或专门流媒体通道。答题时先说本地/远端部署与信任边界，再说传输机制，不把“流式”理解成视频协议。

## 12–14：中断恢复和黑盒可观测

任务到一半中断，需要持久化 `run_id`、当前步骤、计划与工具结果引用、待审批项、模型/工具/策略版本和外部副作用标识。恢复时核验文件与远端业务状态：若写操作实际上已成功，就推进到下一步；若未发生才在幂等保护下重试。只把历史聊天重新喂给模型，可能重复执行付款或文件写入。

一次请求可形成父 Run 与多个模型/工具 Span。每个 Span 记录输入摘要、版本、耗时、错误码、权限决定、状态变化及脱敏后的参数，不记录密钥明文。排障时沿 Trace 找最后一个成功步骤，分辨模型迟迟不出工具调用、工具超时、权限等待、上下文截断或循环调用。日志是事件文本，Trace 提供跨步骤因果关系；两者配合才能定位“卡在哪里”。原帖候选人明确说这块自己没做，因此学习时应把它当作补课项，而非其项目已有能力。

## 15：多 Agent 怎样展开

先说明为何单 Agent 不够：不同工具权限、独立长上下文或可并行子任务。再说主 Agent 怎样拆任务、给子 Agent 传目标/输入/预算/禁止动作，子 Agent 返回什么 Artifact，谁验收与合并，失败时如何取消或改由人处理。若共享仓库，明确文件所有权和冲突检测；若共享 Memory，按用户与任务 scope 过滤。不能仅以“角色多”证明效果提升，应比较相同任务的成功率、成本与延迟。

## 手撕：二叉树序列化与反序列化（LC297）

一个稳定方案是先序遍历：节点值后依次写左、右子树；空节点写明确哨兵，如 `#`，用分隔符避免 `12` 与 `1,2` 混淆。反序列化按同一顺序消费 Token，遇 `#` 返回空节点，否则建立节点并递归建立左右子树。这样保留结构，时间与空间均为 `O(n)`。层序方案也可行，但必须对空孩子编码，否则不同树可能得到相同序列。

下面是核心逻辑伪代码，省略平台规定的输入输出包装：

```text
encode(node):
  if node is null: append "#"; return
  append node.value
  encode(node.left)
  encode(node.right)

decode(tokens, cursor_ref):
  token = tokens[cursor_ref.index]; cursor_ref.index += 1
  if token == "#": return null
  node = new TreeNode(parse(token))
  node.left = decode(tokens, cursor_ref)
  node.right = decode(tokens, cursor_ref)
  return node
```

`cursor` 在两次递归之间必须共享并推进，不能让左右子树各自从原位置读取。序列化时也不能只保留非空节点：例如一个只有左孩子的树与一个只有右孩子的树，若没有空位标记，可能得到同样的值序列。

ACM 模式要先澄清输入输出格式、空树表示、负数与大值、尾部空节点如何处理；测试单节点、单边链、完全树和空树。原帖仅给出题名，没有面试平台的具体格式，不应猜一个固定 I/O 合同。

## 面试会怎么问

这场追问的主线是“项目到底由你做了哪些可运行、可恢复、可观测的部分”。准备时为自己的项目画一张请求路径，逐步标注真实组件、工具错误、状态保存和验收方式；再用一条失败 Trace 练从症状到修复。若被问到没做过的 Trace，不必装作线上已有，可回答你现在会怎样补：Run/Span 结构、需要的事件、脱敏、定位步骤与回归测试。

算法题在项目问答之后出现，日常实习也可能考不熟悉的树题。练习时把编码思路、边界输入和 ACM 读写分开准备，避免“知道递归”却卡在数据输入。
