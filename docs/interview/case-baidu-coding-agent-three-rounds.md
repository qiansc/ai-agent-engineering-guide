# 一份 Coding Agent 三轮面试：从 Agent 设计走到操作系统

这份记录的三轮面试分别发生在 2026 年 8 月 18 日、21 日和 24 日。第一轮从候选人的 Agent 项目问到 ReAct、工具、上下文，再切到 Java、数据库和算法；第二轮围绕 Skill 的选择、误调用、权限与隔离持续深挖；第三轮几乎完全转为操作系统、并发和算法。它特别适合拿来练习“同一个项目怎样经受三层追问”。下面的解法是教学推演，不是候选人当时的回答；具体项目事实仍要换成你自己的。

## 第一轮：先讲清项目，再证明 Agent 值得存在

一开始的自我介绍和实习经历，最好不要按简历逐字念。用两分钟说出问题、约束、自己负责的模块、可以核对的结果和一个失败案例。接着面试官问项目整体架构时，可以画一条完整路径：输入进入任务状态，模型看到经过筛选的上下文，按受限工具契约发起动作，宿主执行和校验，结果回到模型，最后形成答案或交给人。不要把“用了 OpenManus / 某个框架”当作架构说明；框架名称回答不了状态在哪里、谁持有密钥、失败如何恢复。

原帖在架构题之前还问了 Python 与 Java 写项目的主要区别。这不是简单比“哪门语言更快”：Python 常便于快速试验模型、数据与工具链，但运行时动态类型、CPU 密集计算和依赖环境需要额外治理；Java 的静态类型、JVM 与成熟服务端生态适合明确合同和长期维护，也要考虑启动、线程与部署成本。回答应基于自己实际写过的两种项目，说清类型校验、并发模型、库生态和可观测性给开发带来的差异，不能拿语言刻板印象代替工程经验。

“为什么做这个项目”和“Agent 流程一定比单次 LLM 调用更优吗”是一对重要问题。先给出单次调用基线：例如对固定模板的纪要摘要，输入足够、步骤稳定，单次调用通常成本更低、错误面更小。只有当任务需要动态取证、执行外部动作、根据中间结果改计划，且这些能力能带来可测收益时，才引入循环。比较时至少看任务成功率、人工接管率、延迟、Token 与工具成本；不能用“过程更智能”代替结果。

如果项目处理视频关键帧，讲法应从业务目标开始：要检测什么事件？视频是离线文件还是实时流？帧采样间隔、镜头切换检测、语音转写与时间戳如何对齐？例如只按固定间隔抽帧会漏短事件，逐帧调用视觉模型又过贵。可以先用廉价特征与镜头切换候选区间缩小范围，再让视觉模型处理候选帧；对一组人工标注片段测漏检率和成本。不要声称“关键帧检测准确率很高”而拿不出标注定义。

## ReAct 与工具调用：模型提议，宿主执行

设计 ReAct 流程时，可将一次迭代解释为“观察当前状态 → 选择下一动作 → 工具返回新观察 → 判断是否完成”。模型输出的工具名和参数只是提议，真正的执行由宿主完成。宿主需要验证工具是否在白名单中、参数是否符合 Schema、调用方是否有权限，并设置超时、次数与预算。工具结果要标记为外部数据，不能让网页或仓库里的文字升级成系统指令。循环必须有停止条件：目标已满足、达到预算、连续无进展，或进入人工审批。

举一个失败例子比画完美流程有价值：模型连续两次搜到同一页面却没有足够证据。此时不应无上限重试；应记录查询与结果，判断是检索问题、页面权限问题还是问题本身缺少答案，然后改变查询、请求用户澄清或明确拒答。面试官若问“工作流板块出了问题怎么办”，按任务 ID 找到模型决策、工具入参、工具输出和状态转移，先区分模型选择错误、工具故障与状态持久化错误，再用同一输入回放。不要一上来修改 Prompt。

上下文设计也要落到内容预算：固定系统规则、当前用户请求、必要的项目资料、最近的工具结果分别放在哪里？长任务不能无限追加原文日志；可保留当前目标和未完成约束的结构化状态，对旧观察做可追溯摘要。压缩之后要验证关键信息仍在，比如用户确认过的限制、失败工具的错误码、文件路径和下一步。Prompt 调优要有题集与回归：先找失败类型，再改一个变量，观察成功率与副作用；只看几条“看起来更好”的回答很容易过拟合。

## 检索、断点续传与后端基础是同一条工程链

向量检索的简要解释是：把文本或图片映射到向量空间，用相似度找候选，再结合关键词、元数据和重排得到最终证据。近似最近邻索引可以降低大规模查询成本，但牺牲一定召回；还要说明切分、权限过滤、版本更新与引用。若候选人把“向量数据库能找到答案”说成模型原理，就会漏掉解析与检索评测。

项目里的分片断点续传，可用上传会话 ID、分片序号、校验值和提交状态来解释。客户端重试同一分片不应重复写坏数据；服务端记录已确认的分片，最终合并前验证完整性和总体哈希。尤其要回答并发上传、会话过期、最终提交重复触发时如何保证幂等。这与 Agent 工具重试很像：不能因为请求超时就断定动作未执行。

数据库 MVCC 可以从“读操作不必总阻塞写操作”讲起：事务按可见性规则读取某个版本的记录，具体实现依数据库与隔离级别而异。AOP 则是将日志、事务、鉴权等横切逻辑织入调用链，需警惕代理边界与内部自调用。JVM 垃圾回收要能解释可达性、代际假设和暂停代价，不必把收集器名字全背一遍。线程池回答“为什么”时，应说控制线程创建与并发资源、复用工作线程、提供队列和拒绝策略；无界队列不是安全默认值。`volatile` 解决可见性和部分有序性，不把复合读改写自动变成原子操作。

第一轮算法题是访问日志窗口：每条记录含用户与时间，要求在最近 `T` 秒内给每个用户的最近访问时间，并按最近到最远输出。先问日志是否按时间到达、是否允许迟到、查询是一次性还是持续滚动。一次性输入可扫描窗口，哈希表更新每人的最大时间，再按时间排序，复杂度约为 `O(n + u log u)`，`u` 是窗口内用户数。若是实时滚动，则还要处理过期事件：可维护时间有序事件队列和按用户的活动记录；只存每人最新时间但不保留次新访问，最新访问过期时就无法正确回退。

## 第二轮：把 Skill 当成受控能力，而不是一段提示词

第二轮最密集的追问是：两个相似 Skill 选错怎么办？只有一个 Skill 却执行错怎么办？Skill 如何设计、怎样从选择走到执行、动态入参怎样适配？可以先画出四层错误位置：

| 位置 | 典型故障 | 检查与改进 |
| --- | --- | --- |
| 选择 | 两个描述相似，选错能力 | 调整能力边界与描述，加入反例，用混淆矩阵评测 |
| 参数 | 工具选对了，字段或实体错误 | Schema 校验、缺参澄清、引用来源与语义核对 |
| 执行 | 权限、超时、页面变化导致失败 | 最小权限、明确错误类型、有限重试与版本化适配 |
| 解释 | 工具成功，模型误读结果 | 结构化返回、保留来源、关键动作前后校验 |

相似 Skill 不要只靠改名字。先看它们是否本该合并成一个带明确参数的能力；如果必须分开，写出正反触发条件，建立真实任务集，统计选择混淆。只有一个 Skill 被错误执行时，说明问题不在路由数量，可能是模型误判何时调用、入参映射错误、宿主缺少前置条件，或工具本身副作用不安全。应该能从 Trace 精确判断，而不是把所有错都归咎于“模型不稳定”。

一个完整 Skill 调用可口述为：登记能力与 JSON Schema → 根据当前目标决定是否可用 → 模型提出调用 → 宿主做参数与权限检查 → 必要时人审 → 在沙箱或受控服务执行 → 记录结果与副作用 → 将可信度受限的观察交回模型 → 验证目标是否达成。动态参数不是把任意字符串拼进命令；要区分枚举参数、来自用户的实体、来自上一步工具的 ID，并在每一层校验。页面结构变化导致浏览器 Skill 失效时，可以先检测预期元素与页面版本、限制盲点重试、截图或 DOM 定位失败现场；修复优先稳定语义定位和状态断言，而非无限增加选择器候选。

多任务上下文隔离要说明任务 ID 与状态存储的关联。A 任务的用户资料、工具观察和摘要不能因为共享进程或缓存 key 设计不当进入 B 任务。执行并发数的限制也不仅为了节约模型费用：浏览器、文件系统、外部 API 和数据库都有资源上限；并行任务还可能写同一文件或争夺同一会话。使用队列、配额、锁或版本检查，并明确取消和超时处理。

## 密钥和敏感中间结果：别交给模型“自觉保密”

面试官连续问了执行时如何不暴露密钥，以及一个 Skill 取得敏感信息、下一个 Skill 还要用，但用户不能看到的情形。正确边界是：密钥留在宿主的凭据服务或执行环境中；模型只拿到能力标识与受限结果，不能读取原始密钥。若中间敏感数据需要传给下一工具，可让宿主保存结果并给模型一个短期、绑定任务和权限的句柄。下一工具由宿主凭句柄取值，向模型返回脱敏摘要或成功状态。要防日志、Trace、错误信息和前端流式事件泄漏；只在最终回答遮盖是太晚了。

“从零设计 Coding Agent”可围绕这条边界展开：仓库读取、搜索与编辑工具；先定位影响范围，制定可核对计划；在隔离工作树或沙箱中修改；执行目标测试与静态检查；展示 diff 给人审；保留可回滚点。自动提交、推送或访问生产密钥属于更高风险操作，应另设批准。面试官若问“AI Coding 流程的提示词怎么写”，先说提示词承载任务目标、约束与交付格式，但测试、权限与审计不能靠提示词保证。给出一个含验收条件的简短任务，比朗诵超长系统 Prompt 更能体现工程判断。

第二轮还转向 HTTPS 建连和输入 URL 后的链路。这提醒我们不要把 Coding Agent 当纯模型岗位。答 HTTPS 时按 DNS、TCP 或 QUIC、TLS 握手、证书链与域名校验、会话密钥、HTTP 请求与响应组织；具体取决于 HTTP 版本。输入 URL 后还涉及缓存、代理/CDN、服务端路由、资源下载与浏览器解析执行。能讲清自己项目使用的协议和故障点即可，不要把所有网络术语混成固定步骤。

接下来原帖还记录了 React 熟悉度、是否付费使用 Codex/Claude Code、最喜欢的模型、一次亲自开发 Skill 的流程，以及“能否看到代码面板”的现场确认。这些题不应被写成候选人实际用过某付费工具或有某前端经验；按真实范围回答即可。若常用编码 Agent，可挑一次实际任务说它怎样读仓库、建议改动、运行测试，自己怎样审查；比较模型时先说代码理解、工具调用、成本和上下文要求，不给脱离任务的绝对排名。Skill 开发流程应从业务触发条件、输入输出、权限与失败路径开始，写实现和最小测试，再拿误触发/漏触发样本验证。代码面板一问属于现场交互确认，先确认可见、可编辑及运行方式，不需要硬造一道算法题。

## 第三轮：操作系统、并发和算法不能临时补

第三轮一开始就是算法。多线程交替输出 `A1B2C3…`，附加条件是任一线程退出后其余线程不能永久阻塞。普通“你打印完我打印”的条件变量方案若只通知固定下一线程，一方退出就可能死等。需要共享终止状态，在锁内更新并 `notify_all`，等待谓词同时检查“轮到我或已终止”；其他线程看到终止状态后按约定退出或继续处理剩余工作。答案应先澄清线程数、输出上限和线程退出语义，再给能证明不会丢通知的条件循环。最长有效括号可用索引栈并放一个哨兵 `-1`，遇到右括号弹栈，栈空时更新边界，否则用当前位置与栈顶之差更新最长长度；时间 `O(n)`、空间 `O(n)`。也可以用动态规划，但要说清转移条件。

随后是进程、线程、协程；线程切换保存什么；用户态与内核态；键盘输入到程序；`malloc` 是否立即拿到物理内存；缺页中断、抖动、工作集，以及 FIFO/LRU/Clock 页面置换。可以把它们串成一条路径，而不是背八个独立定义：进程拥有地址空间和资源边界，线程是内核调度的执行流，协程通常在用户态由运行时安排；线程切换需保存足以恢复执行的寄存器、程序计数器、栈指针和相关调度上下文，具体开销取决于架构与是否跨进程。系统调用进入内核态，硬件中断与缺页异常则由不同事件触发，但都可能引起调度。

“键盘输入一个字符到应用拿到它”可以沿硬件到软件讲：输入设备上报扫描码，驱动或输入子系统处理按键事件，操作系统把事件送到当前焦点窗口或终端，应用的事件循环/输入读取接口再取得字符。按键布局、输入法组合与终端行缓冲会改变“按下一次键”和“应用收到一个字符”的对应关系。面试时先说明操作系统与应用场景，不要把桌面 GUI、终端和浏览器输入说成完全相同的固定链路。

`malloc` 返回的是进程虚拟地址空间中的分配结果，不等于立刻为每个字节分配物理页；实际是否触碰到页、何时分配受分配器和操作系统策略影响。访问尚未映射的虚拟页会触发缺页异常，由内核建立映射或从磁盘载入；并非所有缺页都意味着磁盘 I/O。工作集若大于可用物理内存，就可能反复换页形成抖动。FIFO 实现简单但可能出现 Belady 异常；LRU 贴近近期使用但维护成本高；Clock 用访问位近似 LRU。面试里最好能解释具体访问序列下三者为何表现不同。

末尾的部门选择与转正问题是经历一致性检查。实事求是讲当前状态、岗位匹配和个人选择，不需要揣测面试官意图。候选人自述第三轮未通过，但不能据此推断是哪道题决定了结果。对学习者更有价值的结论是：项目和 Agent 术语可以让你进入深挖，基础工程能力决定你能否持续把设计落地。

## 怎么用这份记录做三次模拟

第一次只练第一轮：用自己的项目讲架构，准备一个“为什么不做 Agent”的反证、一个可回放的失败案例，以及一条后端链路。第二次让同伴连续追 Skill 误调用、单 Skill 错误、上下文隔离和密钥传递；每问都定位到模型、宿主或工具层。第三次限时手写一道并发题和一道算法题，再口述虚拟内存的完整因果链。每次复盘只记录自己没说清的机制与下一步验证，不抄原作者的经历或现场答案。

## 面试会怎么问

**问：为什么你的 Agent 比一次模型调用更合适？** 给出单次调用基线与场景差异，说明必须动态取证或行动的环节，再用成功率、成本和延迟对比；如果基线更好，就应保留基线。

**问：两个相似 Skill 总被选错，怎么办？** 先从 Trace 确认错误在选择还是参数/执行；检视边界是否可合并，补正反描述与混淆样本，修改后跑回归。关键动作由宿主权限校验，不能仅靠提示词。

**问：第三轮转到操作系统，你怎样保持回答深度？** 从自己的 Agent 服务资源问题切入：并发限制、线程池、虚拟内存、上下文切换和缺页如何影响延迟；给出机制与可测指标，而不是只背定义。
