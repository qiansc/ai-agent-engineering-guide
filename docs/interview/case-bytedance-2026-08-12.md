# 字节 Agent 开发一面：AI 能力与后端基本功一起考

这场 2026 年 8 月 12 日的 Agent 开发一面约一小时。候选人记录了项目介绍、RAG、AI Coding 质量、SSE 与 WebSocket、数据库索引、实时热点榜单的高并发设计，以及“两栈实现队列”与线程安全追问。原帖题号从第 6 题直接跳到第 9 题，没有公开第 7、8 题；本文只沿已记录的问题展开。它提醒我们：Agent 岗不是只会调用模型 API 就够了；结果要通过后端系统稳定交付。下面的方案是教学推演，不是候选人的现场回答。

## 项目介绍：让面试官知道自己真正做了什么

面试官让候选人在三个项目里任选一个展开。这是一个机会，也是压力测试：选与岗位最相关、自己能讲透失败和改进的项目，不要只挑技术名词最多的。两分钟开场可按“用户问题 → 输入与输出 → 自己负责的模块 → 一项可验证结果 → 最大的一次问题”展开。随后准备三张看不见的“图”：请求链路、数据链路和故障恢复链路。面试官无论从 RAG、并发还是存储切入，都能指回具体组件。

比如知识助手项目，不能只说“LangChain + 向量数据库 + GPT”。要说明文档如何解析与更新，权限如何进入检索，何时调用模型，引用如何定位，用户发现错误后怎样反馈。若没有真实线上指标，诚实说明是课程或个人项目，并展示实验集、基线和失败样例；不要把 demo 包装成生产系统。

## RAG 经验：从一个错误答案反推整条链路

“有没有 RAG 经验”往往是邀请你自己选择切入点。先说知识源的类型与更新频率，再说解析、切分、元数据、embedding、召回、重排、上下文组装、生成和引用。每一步给一个决策及原因。例如文档标题与章节路径需要随 Chunk 保存，因为单独的正文片段可能丢失适用范围；权限过滤应在检索阶段执行，而非等答案生成后才遮挡。

真正能区分深度的是 bad case。假设用户问“最新版报销上限”，系统却引用旧制度。先定位：旧页是否仍在索引？文档更新时间与生效时间是否分开保存？召回时有没有版本过滤？重排是否把旧页排到前面？模型是否忽略了新页引用？修复要对应原因：删除或降权过期版本、索引发布采用版本切换、结果携带生效时间、回答时显示引用。不能把所有问题都归结为“换更好的 embedding 模型”。

评测时至少分开看检索与回答：对标注查询测 Recall@K / MRR，观察正确证据是否进到上下文；再看回答的事实正确、引用支持和拒答边界。新增知识要测“新文档可见时间”，废弃知识要测“旧答案消失时间”。对权限敏感的知识库，还要做跨租户、跨角色的负例测试。

## AI Coding：把“写得更快”改成“交付得可验证”

面试官问“AI Coding 如何确保 AI 生产更高质量的代码”。不要回答“提示词写清楚、多 review 一下”就结束。可以给出一个小闭环：先列验收条件与不允许改变的行为；让 AI 阅读相关代码与测试；要求提出最小实现计划；逐步修改，每一步运行目标测试；人工审查公共 API、并发、异常路径和安全；最后跑全量验证并记录还未验证的风险。

关键是区分模型的自述与执行证据。“模型说测试通过”不算通过；要有实际命令、退出码和日志。对生成的测试也不能盲信：测试可能只是复述实现，遗漏业务边界。可以先写一个人类确定的失败用例，或用历史 bug 复现，再让 AI 修代码。如果是 Agent 自动改仓库，工具必须限制工作目录和网络、避免读取密钥，并由人控制提交与合并。能讲出一次具体的 AI 建议错误、如何发现和修复，比宣称“效率提升十倍”更可信。

## SSE 与 WebSocket：先确定通信形态

SSE 是基于 HTTP 的服务端向客户端单向事件流，适合模型逐段输出、任务进度通知等“服务器持续推送，客户端偶尔另发请求”的场景。WebSocket 建立持久双向通道，适合需要频繁双向消息的协作或实时交互。选型不能只比较“谁实时”：还要考虑代理与负载均衡、重连、消息序号、鉴权续期、心跳、限流、断线恢复和客户端兼容。

以 Agent 生成回答为例，用户提交任务可用普通 POST，响应内容用 SSE 逐段推；每个事件带任务 ID、序号和类型，客户端重连时可按最后事件 ID 请求缺失片段。若后端不保存输出片段，重连也无法神奇续上。若是双向语音会话、需要客户端频繁传音频帧并接收中间结果，可以考虑 WebSocket；大规模音视频还需根据协议与媒体服务专门设计，不能因为“实时”就把所有负载塞进一个 WebSocket 连接。

面试官可能追问：连接断了，任务是否取消？答案应由业务决定。模型任务状态不应只活在一个 HTTP 连接里。服务端记录任务 ID 和状态，客户端连接只是观察通道；取消需显式 API 和权限校验。这样才支持用户刷新页面后恢复进度。

## 数据库索引：不背名词，解释查询如何变快

“了解哪些数据库索引”先界定数据库：关系型数据库中常见 B+ 树索引，也可能有哈希、全文、空间等索引，不同引擎支持与约束不同。结合自己的表和查询解释。假设任务表按 `tenant_id`、`status` 过滤，再按 `created_at` 倒序查最近任务，复合索引顺序应从查询模式、选择性、排序和范围条件考虑，并用执行计划验证，而不是机械背“最左前缀”。

索引不是越多越好。每次写入要维护索引，索引占空间；低选择性字段单独建索引未必有效。覆盖索引可能减少回表，但会加大索引体积。若问向量索引，别与数据库 B+ 树混为一谈：ANN 索引用近似搜索换取速度和内存/召回之间的折中，仍需测过滤后召回、更新成本与延迟。回答时可以举一条慢查询，说明如何看 `EXPLAIN`、行数估计与实际扫描，最后验证改动没有让写入或其他查询明显退化。

## 实时热点榜单：先问“实时”与“热点”是什么意思

场景题要求高并发实时更新、数据结构和数据库选型。先向面试官确认：排行榜按点击、观看、评论还是加权分？按全站、城市还是类别分？一分钟更新算实时吗？是否容许最终一致？要前 100 名还是任意排名？峰值写入与读取量是多少？这些条件直接影响设计。

若仅需分钟级热点 Top-N，可将事件流写入消息系统，在流处理或聚合服务中按时间窗计数，增量更新 Redis Sorted Set 或专门的排序结构；读路径从缓存获取 Top-N，并附计算时间与版本。原始事件和聚合快照落持久化存储，用于重算与审计。每个榜单维度都要有明确 key 和过期策略，避免“每个用户一张榜”引起键爆炸。若“热点”是小时内热度而不是历史总量，应解释滑动窗或时间桶衰减，不能只做永久累加。

高并发下要讨论三个细节。第一，事件重复投递会使计数虚高，需用事件 ID 去重或让聚合有幂等语义；第二，热点 key 可能写入极不均匀，要考虑局部分片聚合、批量合并和限流；第三，榜单更新与缓存发布要有版本，避免用户读到一半新一半旧。若强一致排名是硬要求，系统成本会显著上升，应明确取舍。数据库用于持久记录与回溯，不一定承担每次排名查询；Redis 是快路径，不应是唯一真相来源。

## 两栈实现队列，以及“线程安全”追问

标准做法是输入栈接收 `enqueue`，输出栈服务 `dequeue`。当输出栈为空时，把输入栈所有元素逐个搬过去，顺序恰好反转；输出栈非空时不能提前搬，否则会破坏 FIFO。每个元素最多入栈、搬运、出栈各一次，所以单次出队的最坏时间可能是 O(n)，但摊还时间是 O(1)。两个栈总空间 O(n)。先把空队列行为说清：抛异常、返回可选值，或阻塞等待，取决于接口契约。

线程安全不是“给两个栈各加一把锁”就自动成立。`dequeue` 的判空、整批搬运与弹出要作为一个原子逻辑区间，否则一个线程刚判断输出栈为空，另一个线程就可能同时搬运或弹出。最容易证明正确的是用同一把互斥锁保护队列的公开操作；若要支持阻塞出队，再用条件变量等待并在入队后通知。性能压力明确存在时才考虑分离锁或无锁设计，并必须证明元素不会丢失、重复或乱序。面试里先给简单正确的方案，再讨论吞吐取舍，比直接喊“CAS”更稳。

## 面试会怎么问

这场面试最适合用一条“项目—系统—代码”模拟：先两分钟介绍项目，再让同伴从 RAG 追一个失败案例；接着口头比较 SSE 与 WebSocket，画出热点榜单的写入与读取路径；最后手写两栈队列并让同伴制造并发交错。每一题都要说出假设和验证办法。若自己是偏 AI 的候选人，数据库与并发不能跳过；若自己是后端转 AI 的候选人，则要补足检索评测与生成质量的实际实验。
