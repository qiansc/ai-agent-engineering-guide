# 小红书端侧推理一面：工具调用、RAG 评测与训练实验怎么讲

这场面经不是只问一个 Agent 框架。面试官沿候选人的三个项目追问端侧函数调用、医疗问答 RAG、楔形文字翻译，再问 SFT/LoRA 与岗位匹配。原帖有五组问题，但没有公开完整项目实现、真实用户数据或指标明细。文章按原顺序给一套能用来准备的技术讲法；其中 `1024/256`、8 秒、5076 条样本、30 到 32 分等都是题目提到的项目数字，不能当成行业推荐值。

## 第一组：端侧 RAG、函数 Token 与工具执行

**System Prompt、工具数量与参数填充。** 回答“Prompt 多长”要给实际 Token 口径、场景分类、可见工具数，以及每轮如何筛选工具；只报字数很难比较上下文开销。参数填充错误可拆成三类：schema 类型/枚举不匹配，用户话语到参数的上下文推导错误，数字/单位/时间等值提取错误。每类都应有标注样本和错误率，区分模型生成、参数校验、工具内部兼容各阶段。若没有真实用户数据，应明确评测只是离线或设备模拟；不能用线程数模拟不同手机就宣称真实端侧体验。

**8 秒响应怎样优化。** 先拆耗时：输入预处理、模型加载/首 Token、生成、工具等待、检索、网络与 UI。端侧可考虑模型量化、缓存、限制输出、工具预筛选、异步/流式反馈、降低不必要的模型轮数，并在目标机型上看 P50/P95、内存、能耗、热降频与成功率。优化必须带效果对照，不能用“上了量化”代替体验证据。

一个能说清“8 秒从哪来”的实验是为每轮记录 `prompt_tokens`、首 Token 时间、生成 Token 数、检索/工具耗时和总耗时，并按设备档位、冷/热启动、是否命中缓存分组。若主要时间在模型冷启动，压缩 Prompt 并不会解决核心问题；若工具串行等待占大头，优先检查依赖图是否允许并行。所有优化都要同时看错误率，不能靠过度缩短输出牺牲参数正确性。

**Schema 与宽松约束。** 工具合同至少说明名称、用途、参数类型、必填项、枚举、边界和示例。过宽约束让模型输出更多模糊值，过窄约束会拒绝用户自然表达。可以在入参层做别名和单位归一化，但业务关键字段应在执行前严格校验。内部兼容只能处理等价表示，不能把未知枚举猜成某个会产生副作用的动作；错误应结构化返回给规划器，而不是静默成功。

**规划与工具依赖。** 若请求需要“查日程→确认时间→预订”，先识别意图和必需前置数据，再形成带依赖的计划；独立的只读查询可并行，有副作用步骤等待前置验证和批准。工具失败后区分可重试超时、参数错误、权限拒绝和业务冲突：只对安全可重试部分重跑，影响后续步骤时重规划。ReAct 更适合短步探索，显式 Plan/Execute 适合稳定依赖，多数生产场景可混合。原帖问到“IG”但未说明其项目定义，答题时应先界定自己所用术语，不能替作者猜缩写。

**父子索引的 1024/256。** 小块用于定位问题，大块用于提供完整条件或上下文；检索子块、回传同版本父块可减少断章取义。但父块 1024、子块 256 只是项目中的设计值，须按 Token 而非不明字符单位、文档结构和标注题集验证。比较不同粒度的 Recall@k、MRR、引用正确性、窗口占用与延迟，尤其测试表格/列表跨块。若父块中混入无权限内容，回传时还要做权限过滤。

工具规划可画成一张依赖表来解释，而不是只说“模型会自动规划”：

| 步骤 | 前置条件 | 失败后的处理 |
| --- | --- | --- |
| 识别用户要完成的动作 | 用户原话 | 意图不明则澄清 |
| 查询可用对象或资料 | 已知身份和范围 | 空结果时改 Query 或返回无结果 |
| 填充并校验参数 | 工具 Schema、查询结果 | 类型/枚举错误要求修正，不执行副作用 |
| 执行写操作 | 参数通过、必要审批 | 超时先查外部状态，再决定重试 |
| 验收结果 | 工具返回及目标状态 | 未达到目标则局部重规划或转人工 |

这是教学示例，不是原帖候选人实际的生产流程；现场应把表格替换为自己项目真实的工具和错误码。

## 第二组：医疗问答 RAG 的检索与质量证明

口语化 Query 可先做规范化、实体/时间识别，再选择改写、扩写或拆成子问题。HyDE 让模型先生成一个假想答案/文档表示用于检索，但生成内容不是医学事实，最终答案必须回到可信文档核对。为防重复生成，对语义相近的改写去重并限制预算，记录每条改写实际带来多少新增有效召回。

选择 BGE 系列重排模型不能只说“排行榜高”。要在同一领域标注集比较原始召回与重排后的 MRR、nDCG 或答案正确率，注意医疗术语、否定句和长段落。重排只能重排已召回候选，无法弥补首轮漏召回。Top K 应在相关性、窗口预算和推理成本之间用曲线确定：低分文档可设阈值或拒答/补检，但分数需校准，不能跨不同模型直接比较。

上下文太长时，先限制来源数量、去重相似片段、保留问题相关句和原始引用，再按需要用压缩模型；压缩要测试是否删掉禁忌、时间、剂量或否定条件。面试官提到 encoder-decoder 与强理解能力，回答可以解释其适合条件化压缩的动机，但最终以事实保留率和答案安全性评测，不能凭架构名称推断更可靠。

报告 HIT@5、MRR@5、Recall@20 时分别说明命中、首个正确结果排名和正确资料覆盖的口径，给出绝对数、增量、置信区间或重复实验。5076 条自合成样本可能帮助扩大覆盖，也可能把生成模型偏好写进题集；应有真实/人工标注的独立测试集、去重、难例分层和泄漏检查。原帖没有给出提升数字，因此不能替候选人填写。

以一条查询的标注资料集合为例，HIT@5 看前五条是否至少出现一条相关资料；MRR@5 把第一条相关资料的排名取倒数，前五条没有则记零；Recall@20 看前二十条覆盖了多少标注相关资料。三者可以出现“命中率提升、覆盖率不变”的不同结论。比较改写、HyDE、混合召回和 BGE 重排时，应固定同一标注集和权限过滤，分别保存每个阶段的候选列表，才能说清改进来自哪里。医学问答还要单独检查答案是否忠实引用、是否遗漏警示或禁忌，检索指标不能代替答案安全性。

## 第三组：楔形文字翻译项目如何证明改进来自哪里

面试官从 Tokenization 问起：BPE 依赖训练语料中的子词统计，低资源、特殊符号或噪声文字可能切得不理想；字节级输入保留原始编码覆盖，不会遇到 OOV，但序列更长，计算与对齐难度增加。具体项目为何选择字节流，需展示样本分布和模型对照，不能一概说字节流优于 BPE。

高分伪标签先按质量模型、译文一致性和长度/异常字符过滤，并抽人工样本审查。原帖问到 `blur` 与 `chrF1` 几何平均，面试应先核实 `blur` 在该评测里的定义、取值方向和官方实现；几何平均会惩罚某一项特别低的方案，但不能在指标含义未明时硬讲。十模型、110 个答案的集成是题目引用的对照方案，不代表候选人也做了。若讨论集成或自蒸馏，要区分用什么数据选择、哪些数据训练、最终用独立集验证，防止挑选泄漏。

“分数从 30 到 32”必须用消融回答：固定训练/验证集与预算，逐一加入随机掩码、双向互译、随机编码，再测组合与多种随机种子。若多个改动一起上线，不能声称其中某一项带来了 2 分。随机编码可能提高对编码/噪声变化的鲁棒性，也可能引入破坏语义的噪声；通过错误类型与消融结果判断，而不是事后讲故事。

| 实验组 | 保持不变的条件 | 只变化的条件 | 需要回答的事 |
| --- | --- | --- | --- |
| 基线 | 数据划分、模型预算、评测实现 | 无 | 30 分能否稳定复现 |
| 随机掩码 | 同上 | 加掩码策略 | 哪类错误减少，是否只是正则化效果 |
| 双向互译 | 同上 | 加互译数据/目标 | 低资源方向是否真的改善 |
| 随机编码 | 同上 | 加编码扰动 | 特殊字符鲁棒性是否改善 |
| 组合 | 同上 | 组合有效改动 | 是否相加、冲突或引入新噪声 |

若原始评测指标或数据划分未公开，只能说明应这样设计实验，不能替候选人认定分数变化的因果来源。

## 第四组：SFT 数据、过拟合、全参微调与 LoRA

SFT 数据量没有按“风格对齐多少条、复杂任务多少条”一刀切的标准。先定义目标与基线、清理重复和错误标注，再画数据量—效果曲线；风格任务可能较早饱和，复杂推理/工具任务更依赖覆盖率和难例质量。所谓“质量比数量重要”要落到人工一致性、可执行验证、来源合法性、难例分层与测试集隔离。

过拟合要同时看训练/验证 Loss、目标任务指标与真实坏例：训练 Loss 持续降而验证或任务指标停滞/下降，是警讯；数据分布变化也可能造成同样现象，需核对样本。全参数微调更新整个模型，表达空间更大但显存、计算、存储与回归风险更高；LoRA 只训练低秩适配参数，资源更省、便于多任务适配，但可能在大幅知识/能力迁移上受限。选型用相同数据、评测和成本比较，不只按模型参数规模猜。

## 第五组：跨方向动机、购物场景和端侧框架

从地理信息或智慧城市转 AI，可以讲可迁移的建模、数据、端到端交付经验，再举做过的端侧或检索项目；不要虚构业务实习。其他 Offer 与个人经历按事实回答。购物场景的潜在价值包括更自然的多轮需求澄清、商品属性理解与推荐解释，但必须讨论真实库存、价格、广告标记与误导风险。

端侧模型可能带来本地隐私控制、较低网络依赖和交互延迟，也有设备算力、内存、电量、模型更新与能力限制。苹果 Foundation Models、MNN 等框架的比较应落在目标设备、可用算子、量化、工具调用、开发体验和离线评测；“60 多分”必须明确是哪套任务、哪个指标、何种设备，不能拿来做泛化性能结论。

## 面试会怎么问

这场一面反复追问“你用的参数和分数由什么实验支持”。为每个项目准备一张表：问题、基线、改动、固定评测集、指标、设备/模型版本、失败样本。遇到没测的真实用户体验或消融，明确说目前只有离线证据，并提出可执行的补测。端侧系统先讲耗时与资源，医疗 RAG 先讲事实安全，翻译实验先讲数据隔离；这样比堆模型名称更经得起追问。
