# Agent 故障诊断矩阵：从症状找到下一项实验

Agent 的失败常跨越模型、上下文、检索、工具和运行时。诊断时先固定输入、版本、权限和环境，再通过 trace 找到首次偏离预期的位置。一次只改变一个主要变量，比较修复前后同一批任务；否则即使最终答案变好，也无法知道是哪项调整起作用。

## 先收集最小证据

每次运行至少记录 run/task/step ID、时间、模型与 Prompt 版本、工具名称和参数摘要、工具结果引用、状态迁移、token、费用、时延、终止原因及人工操作。敏感内容可脱敏或保存受控引用。RAG 还需文档与索引版本、检索候选、排序分数和最终证据；副作用工具还需幂等键和外部执行结果。没有这些字段时，应先补观测，而不是自信地猜模型“思考太久”。

| 症状 | 首先检查 | 下一项可验证实验 | 常见误判 |
| --- | --- | --- | --- |
| 五分钟任务变二十分钟 | 排队、step 时延、token、重试、工具 P95 | 固定输入与模型，逐段回放 | 直接换更快模型 |
| 同一工具反复调用 | 动作指纹、错误码、完成状态 | 增加重复检测和稳定错误语义 | 只加最大步数 |
| 压缩后忘记约束 | 压缩前后事实集、未完成项 | 结构化保存约束并跑长任务集 | 无限制扩大窗口 |
| 答案无证据 | 标注证据是否召回、排序位置、引用 | 分开测 Recall 与 groundedness | 调低 temperature 就算修复 |
| 更新后仍答旧内容 | 文档、索引、缓存与权限版本 | 验证更新/删除传播和缓存失效 | 只重建向量索引 |
| 工具执行两次 | 请求 ID、超时点、服务端记录 | 稳定幂等键并在重试前查询 | 认为客户端超时代表未执行 |
| 多 Agent 结果冲突 | 输入版本、共享写入、汇合规则 | 单写者或乐观版本检查 | 让 Agent 再讨论一次 |
| 费用突然上升 | 调用次数、长输出、路由和重试 | 为每层设预算并比较质量 | 只压低输出 token |

## 症状一：任务变慢

先画耗时瀑布：入口等待、队列、模型 prefill/decode、检索、工具、人工审批和重试。看 P50 与 P95 是否同时变化，区分全局负载与少数任务的长尾。若 token 量增加，继续看是对话历史、工具输出、检索片段还是重复摘要；若排队增加，查并发限额与下游限流；若单个工具变慢，查服务端指标和超时设置。一个“从五分钟到二十分钟”的描述只能作为症状，不能直接推导是上下文问题。

实验可以固定同一个任务快照，分别回放旧版和新版，比较每步耗时与动作数；再暂时禁用非关键反思或缩小工具输出，确认是否影响质量。若优化速度却降低成功率，应报告两项变化并决定是否接受，不把速度单独当成功。

## 症状二：RAG 答错

拿一批有人工标注证据的失败任务，逐项问：原文是否成功解析；相关 chunk 是否在索引；权限过滤是否过早排除；候选检索是否召回；rerank 后是否排到可见窗口；模型是否引用了正确证据；生成内容是否超出证据。Recall@K 低时优先试切分、query、混合检索或索引；召回已有但排序差时看融合与 rerank；证据已给出仍答错时再审 Prompt、上下文冲突与输出校验。

“知识库更新后仍答旧内容”还要查版本链。文档删除事件是否被消费、索引切换是否原子、缓存键是否包含版本、历史对话是否保留旧事实。设计回归用例时同时覆盖新增、修改、删除和权限撤销，避免只测最容易通过的新增文档。

## 症状三：工具循环或重复副作用

模型可能因模糊错误反复调用相同工具，也可能因工具已经成功却客户端超时而重复提交。前者记录工具名、规范化参数、输入状态和结果形成动作指纹；多次相同指纹且状态不变时停止或转人工。后者必须用业务级幂等键和执行记录处理，超时后先查询外部状态，确认未成功再决定是否重试。最大步数只限制损失，不能替代根因修复。

多 Agent 场景还需看父子任务输入版本。两个子 Agent 同时修改一份文件或数据库记录，汇合时仅对比最终文本可能漏掉覆盖写。让每个子任务写独立产物，汇总者按版本合并；必要时对共享资源采用锁、乐观并发控制或单写者。并行只用于真正无依赖或可协调的步骤。

## 面试演练：说出证据与下一步

面试官说：“上线一周后，客服 Agent 的人工接管率上升。”先问是否同时更换模型、知识库、工具 schema 或权限；按工单类型、租户、时段分层；比较接管原因代码与 trace。若主要是检索无结果，检查知识库更新和 ACL；若主要是工具超时，查下游与排队；若是模型拒绝率变化，检查路由和提示版本。最后给出最小回放实验、灰度止损与回归集更新。回答不需要假装当场知道根因，关键是把下一项实验设计得能排除假设。

## 将诊断实验做成回归门槛

修复前先保存能稳定复现的任务输入、依赖版本和期望行为。对模型随机性，重复运行同一任务并记录分布；对工具故障，采用可控的超时、限流、空结果与部分成功注入。评测 Harness 应隔离环境、恢复初始状态、执行任务并按结果与轨迹分别判分。它与负责线上循环和权限的执行 Harness 不同，名称相似但责任不同。

回归门槛不能只看平均任务成功率。高风险用例可设零容忍；普通用例再比较完成率、P95、成本和人工接管率。修复可能让某类问题改善、另一类退化，因此按任务类型和权限级别分层。上线后把真实 bad case 去敏、标注并并入回归集，同时保留独立的 held-out 集，避免每次都对同一批题调到过拟合。

面试中若没有现场数据，也可以明确提出最小可执行实验。例如怀疑上下文压缩导致遗忘，就固定模型与工具版本，把同一长任务在“不开压缩、现有压缩、结构化约束压缩”三组条件下运行，比较目标达成、遗漏约束和成本。这样的实验能区分质量与资源开销，而不是仅靠观察一条成功轨迹。

## 完整推演：知识库更新后仍答旧内容

假设用户指出政策已经更新，但 Agent 仍引用旧政策。先保存本次 run、用户身份、问题、回答、引用文档 ID 和索引版本。第一步确认新政策文档是否成功上传、解析与发布；若解析失败，修索引没有用。第二步在相同身份下直接查索引，检查新旧文档是否同时可见、ACL 是否正确。第三步回放检索，确认候选中是否有新文档；如果候选有但旧文档排前，才进入融合或 rerank 调整。第四步看模型实际 Context：即使新文档已排第一，历史会话摘要可能仍写着旧政策。最后检查答案缓存是否按文档与索引版本失效。

修复取决于第一次偏离的位置。若更新事件丢失，补事件消费与重放；若旧文档未删除，修版本切换；若排序偏向旧内容，加入时效特征或明确过滤；若旧事实留在记忆，给记忆设置来源和有效期并在文档撤销时使其失效。回归集至少包含新增、修改、删除、权限撤销和不同租户同名文档。线上观察一段时间的旧版本引用率，才能判断修复是否有效，而不是只手测一条问题。

## 完整推演：外部工具超时后重复提交

设 Agent 调用创建订单工具，客户端 10 秒超时，随后自动重试，用户收到两张订单。先从 trace 找两次请求是否共享操作 ID、第一次服务端是否已经处理、超时是网络还是下游业务耗时。若操作 ID 每次由模型重新生成，即便“参数相同”也无法可靠去重；应由宿主从任务 ID 与业务步骤派生稳定键，工具服务在持久层建立唯一约束并保存结果。重试先查询旧键的状态，若处理中则等待或转人工，而不是发第二次写入。

若外部供应商不支持幂等键，就需要本地执行记录、查单接口和明确补偿流程；无法确认第一次是否成功时，停止自动重试并提示人工核查。回归测试包括第一次成功响应丢失、请求未到达、供应商处理一半、并发重试和取消发生在提交后。这里的关键是区分“请求失败”和“业务动作失败”，二者不能画等号。

## 完整推演：多 Agent 汇合结果互相矛盾

两个子 Agent 分别检索政策和订单状态，一个认为订单可退款，另一个依据旧政策认为不可退款。汇总者不应简单投票，应检查各结论的来源、版本、时间和权限，并在冲突未解决时暂停自动退款。若两者引用不同规则版本，先确认生效日期；若引用同一规则但解释不同，可增加确定性规则检查或人工复核。多 Agent 设计应让每个子任务返回结构化证据和不确定性，汇合阶段才有可比较的信息。

若冲突来自并行写入，比如两个子 Agent 都更新同一任务状态，则问题不在模型“意见不一”，而在并发控制。给状态写入加版本检查，失败者重新读取新状态并决定是否继续；或者规定只有父任务可以提交最终状态。评测要同时检查最终答案与中间副作用，不能只在最后看到“退款成功”就认为路径安全。

## 诊断答案的四级评分

低分答案直接猜根因，例如“模型幻觉，换模型”；稍好的答案能列几个可能原因，但没有先后顺序；合格答案能提出最小 trace、分层假设与区分性实验；高分答案还会定义止损动作、回归集和上线监控。被追问“你没有这些日志怎么办”时，先说明当前无法确认哪一层出错，再提出最少需要补的字段和临时保护措施。承认未知不等于放弃诊断，编造确定根因反而会让方案失真。

## 建立故障优先级

不是所有 bad case 都应按出现次数排序。优先处理越权、错误支付、泄露和不可逆写入，即使只发生一次；其次处理导致任务无法完成或大量人工返工的问题；最后再优化冗余步骤、成本与措辞。可以用“影响范围 × 错误代价 × 可复现程度”给团队排队，但高风险安全事件不应因样本少而被平均分掩盖。诊断期间可先将相关动作改为只读、审批或人工处理，避免边排查边继续扩大损失。

对每个故障建立时间线：用户触发、任务入队、模型决策、工具调用、外部状态变化、系统记录和用户看到的结果。多个服务的时间戳可能不完全同步，需用 run ID、操作 ID 和事件顺序关联。若只保存最终答复，看不到工具已执行却状态未更新的窗口，也无法判断是重复消息还是模型重复选择。

## 面试现场的三分钟诊断答法

第一分钟确认症状与范围：什么时候开始、哪些用户或任务受影响、最近发布了什么，是否需要立即止损。第二分钟给分层假设和最小证据，按“最可能且最容易排除”排序。第三分钟给一个能区分假设的实验、预期结果和回滚条件。若面试官追问细节，再展开某层机制。不要一口气列十种可能原因却没有下一步，也不要为了显得确定而提前指定根因。

例如“调用工具后答案变坏”，先比较工具原始结果与模型看到的裁剪版本，再看是否有恶意指令或格式变化；固定同一任务，分别用旧工具结果和新工具结果回放。若只有新结果出错，定位工具输出与解析；若两者都错，再查提示与状态。这个实验比“调低 temperature”更能解释问题。

诊断结论也要有结束条件。若实验能稳定复现并证明某一层导致失败，修复后在回归集与灰度流量中都达到预设门槛，才可关闭问题。若暂时无法复现，应保留 trace 采样、保护性限流和下次触发时的自动快照，而不是把“没再出现”当成已修复。

## 面试会怎么问

百度 MEG Agent 一面谈到长任务与故障定位；美团 AI Agent 一面关注长流程稳定性。可以用一个“平时五分钟，今天二十分钟”的模拟追问检验是否会分层诊断。

**问：Agent 任务突然慢了四倍，你第一步看哪里？** 答：先比较同一任务类型的 trace，拆出排队、模型调用、检索、工具执行、重试、人工等待各段耗时。若模型步数变多，检查上下文体积、工具选错或循环震荡；若单步模型变慢，看模型网关、限流与输入 token；若工具慢，看下游依赖与超时。先定位变慢的层，再做有控制的实验，例如固定检索结果重放、切换模型版本或隔离一个工具。不能在没有证据时直接“加缓存”或“换更快模型”。

**追问：修复后怎样防复发？** 答：将这次输入、依赖版本、工具观察和预期耗时范围保存为回归样本；设置按阶段的延迟指标及错误预算。对偶发外部故障，还要测试退避、熔断与预算耗尽时的用户可见结果。

这道题是基于近期项目深挖方式设计的练习，非某公司公开标准题。
