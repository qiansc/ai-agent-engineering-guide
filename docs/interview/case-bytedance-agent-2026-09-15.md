# 字节 Agent 开发一面：RAG 诊断之后，后端基础仍会追到底

这份 9 月 15 日的候选人复盘列出 19 个环节：自我介绍与实习，RAG、索引、Go/Java、Function Calling、线程池、DFS，以及 AI Coding。题单中有些问题只记了名称，例如 DFS 没有给出具体题面；下面按原顺序给准备路径，不把未披露的项目经历和代码题条件补造出来。

## 1–3：自我介绍、排名与实习

项目回答先交代业务目标、你负责的边界、关键设计、量化或可复核结果。排名问题直接给真实口径和阶段，别试图把与岗位无关的数字包装成技术能力。实习被追问时，把简历每个动词落实到一次具体改动：谁提出需求、你改了什么、怎么验证、上线后怎样看结果。做过 Go 开发但底层不熟，答题时把“生产使用经验”和“语言原理掌握”区分清楚。

## 4–6：RAG 流程、召回率与 Chunk

RAG 的主路径是文档解析与切分、索引、查询改写、召回、融合/重排、上下文构建、生成与引用。问“召回率低怎么办”，第一步不是立刻上 Reranker，而是取一组标注查询，确认正确文档是否入库、权限过滤是否误拦、正确片段是否进入 Top K。如果候选片段根本没召回，重排无法凭空找出它。

随后分层尝试：切分保留标题/表格等语义，调整父子块和重叠；改写 Query 处理简称、同义词和多意图；关键词/BM25 与向量检索互补；召回后用 Reranker 改善排序。每次只改一层，在相同标注集比较 Recall@k、MRR、答案正确率、延迟和成本。Chunk 的依据不是一个神奇数字，而是文档结构、问题跨度和窗口预算。过小丢条件，过大降低定位精度；表格、代码和长政策需单独策略。

## 7–8：回表查询与 MySQL 索引失效

二级索引记录通常包含索引键和主键；若查询列不全在二级索引中，执行器再按主键读取聚簇索引行，这就是常说的回表。覆盖索引可避免某些回表，但应以查询计划和实际数据分布判断收益。不要把“有回表”直接等同于“SQL 一定慢”。

索引失效或无法有效利用索引，常见于对索引列做函数/计算、隐式类型转换、前置通配符 `LIKE '%x'`、联合索引不满足可利用的前缀、低选择性导致优化器选择全表扫描，以及范围条件后续列使用受限。实际答题应展示 `EXPLAIN`、索引定义、谓词、行数和统计信息；“用了 OR 就一定失效”这类绝对说法不准确。

## 9–11：Java 与 Go、内存模型和并发

比较语言时先讲工程环境：Java 常见 JVM、成熟生态与线程池，Go 以 goroutine、channel 和 Runtime 调度提供轻量并发。选型还取决于团队、依赖、部署、观测与已有系统，不能用“Go 一定更快”收尾。

Go 内存模型回答的是并发读写之间何时有可见性保证。无同步的数据竞争不能靠“看起来执行顺序正确”证明；通过 channel 发送/接收、互斥锁和原子操作建立同步关系。`goroutine` 不是 Java 线程池中的 OS 线程一对一替代：Go Runtime 将大量 goroutine 调度到较少的执行线程，阻塞和调度行为也不同；Java 传统线程池复用平台线程，具体 Java 版本还可能有虚拟线程，比较时要先说所指模型。Java 线程池还有任务队列、核心/最大线程数和拒绝策略等资源边界，不能只讲线程创建。

## 12–14：Function Calling、RAG 与 Java 线程池

原帖把 Function Calling 拼成“Functional calling”，回答按通常的模型工具调用理解：模型根据工具 schema 产生调用建议，宿主校验参数与权限、执行工具、把结果回传模型。RAG 则从外部知识源取回与问题相关的材料，通常用于给生成提供事实。工具可查询或修改状态，RAG 通常检索资料；二者可以结合，例如 Agent 调用检索工具后再生成带引用的回答。

线程池接收任务后，典型执行顺序是先用未满的核心线程、再入队；队列满且线程数未达最大值时再扩容；仍无法接纳时触发拒绝策略。要明确所用队列是有界还是无界，以及如何监控活跃线程、队列长度、等待和拒绝数。把最大线程数设得很大、队列也设无界，并不能防止积压。

## 15：DFS 题的已知边界

原帖只说有一道 DFS 题，并提到被题目里的陷阱影响，没有题面，不能写成某道具体 LeetCode。练习 DFS 时重点在状态定义、访问标记、回溯恢复、终止条件与边界数据：树题要确认是否有重复节点/空树，图题要防环，网格题要确认能否重复访问。现场先用小样例复述题意，尤其问清“路径”“子树”“恰好一次”等限制，再写代码。

## 16–19：AI 时代、Code Review、AI Coding 和反问

“怎么看 AI 时代”可以从自己做过的一项任务回答：AI 把重复生成和检索提速，但需求理解、验证、安全与责任仍需要工程流程。Code Review Agent 的“正确”不能凭自我评价：先限定它负责发现哪类问题，如空指针、权限、回归或风格；用带标签的历史 PR 做精确率/召回率与误报统计，结合静态检查、测试和人工 Review。危险自动修改须审批，建议应附文件位置、证据和复现路径。

谈 AI Coding 坑时说真实案例，如生成代码引用不存在的 API、改错边界或遗漏测试；说明怎么发现、修复、更新工作流。若没有真实经历，可以说准备方法，但不要编造实习事故。反问可围绕团队当前 Agent 场景、效果指标、发布责任与新人的工作边界。

## 面试会怎么问

这场最值得演练的是“RAG 召回低”的诊断链：先证明正确答案在哪里丢失，再选择切分、Query、混合检索或重排，最后用固定标注集比较。另准备一张 Go/Java 并发对照卡和一条自己实际使用 AI Coding 后如何验证的案例。DFS 没有公开题面，练的是澄清能力与通用边界，不是背一个虚构题解。
