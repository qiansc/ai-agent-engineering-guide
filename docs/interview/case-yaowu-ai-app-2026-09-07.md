# 要务科技 AI 应用开发实习一面：Webhook、AI 编码与业务落地逐题讲解

这份复盘记录的是 2026 年 9 月 7 日、约 46 分钟的 AI 应用开发实习面试。与只列题目的面经不同，作者还写了自己的回答和面试官反馈。下文按 Q1～Q22 原顺序讲，凡“候选人当时怎么做”仅限原帖自述；“更稳的工程解法”是教学建议，不冒充现场回答。作者后来在评论中表示没有通过，转述的原因涉及 AI 应用设计与开发链路能力；不能据此推断公司统一评价标准。

## 消息托管与可靠投递：Q1～Q6

### Q1. 社交平台私信和评论如何托管

候选人说项目接入了名为 ZERNIO 的第三方账号托管平台。回答这题要画清数据路径：平台事件怎样进入第三方服务、Webhook 怎样到自己的系统、消息怎样去重和归档、回复怎样经第三方发回。接入前核对官方授权、用户同意、可操作范围、API 速率与平台政策；凭证在服务端保存，不能送进模型上下文。若第三方不可用，要能辨别“消息未收到”和“收到但未处理”。

### Q2. 广告和系统消息怎样过滤

作者使用模型做意图识别，将判为垃圾的信息拦截。更完整的设计是先用明确规则过滤系统通知、平台已标记广告和重复事件，再让模型处理难分类文本；将模型输出设为“类别、置信度、理由摘要”，按阈值决定自动忽略、人工查看或继续处理。误杀真实客户消息的代价通常比多审一条垃圾消息高，评测应分开看误拦截率与漏拦截率。

### Q3. 意图识别错了如何兜底

作者说所有消息会留档，操作者能看到拦截标记。这提供了复核入口，但还要能撤销错误标记、补发被漏掉的回复，并把纠错样本回流到规则或模型评测。不能只靠“有日志”：日志保留多久、谁能看、是否含个人信息、纠错后会否重复回复，都要定义。低置信度时直接转人工，比自动静默丢弃更安全。

### Q4. 已落库但第三方发送失败，怎样保证一致

原帖的做法是先落库、事务外调用 SDK，维护发送中/失败状态，最多重试三次并在前台显示失败。这能解释基本状态，但“三次重试”并不能保证最终一致：进程可能在落库后、调用前崩溃；调用超时也可能已发送成功。更稳的方案是在同一数据库事务写业务消息和待发送事件（Outbox），worker 异步发送；给第三方请求稳定幂等键或查询回执，按指数退避重试，超过限额转死信/人工处理。前台区分待发送、已确认、失败与状态未知。

### Q5. Webhook 突然堆积怎么办

作者坦诚客户规模还小，未实际处理过大堆积。这种诚实比假装有成熟方案好。教学设计可从入口验签和限流开始，快速持久化事件并返回确认，把重处理放到有界队列和 worker；按账号或会话键保证必要顺序，用分区扩展吞吐。监控队列深度、最老事件年龄、处理 p95、失败与重试率。处理不过来时触发背压、降级非关键任务，并以平台的回拉接口做对账。

### Q6. Webhook 的三层保障

原帖把保障分成签名校验、唯一键幂等和定时回拉兜底。面试回答时补上边界：签名应严格按平台文档使用原始请求体、时间戳、密钥及规定算法（常见为 HMAC），做常量时间比较与时间窗口校验，防重放；唯一键应取平台事件 ID 或明确的业务键，数据库冲突时确认与旧事件语义相同再按成功处理；回拉任务按游标或时间窗对账，不能只查“本地未完成”，否则完全漏收的事件在本地根本不存在。Webhook 可能重复、乱序、延迟到达，状态更新要按版本或事件时间处理。

## 大文件、多模态和交互时序：Q7～Q10

### Q7. 二十万行 Excel 怎么解析

作者说真实项目只有几千行，建议分块导入；“单表存不下就分表”是他的设想，不是二十万行的必然要求。教学解法是流式/只读解析，避免把整表载入内存；先校验表头、类型、行数与重复键，再按有界批次写入，记录行号、错误文件和导入进度。导入任务异步化，按业务键幂等，失败可从检查点续跑。是否分表取决于查询模式、数据库容量和索引维护，不应只凭行数判断。测试要包含空行、公式、日期格式、坏单元格和用户取消。

### Q8. PDF 转写从 31 分钟到 2.5 分钟

作者自述使用豆包 2.0 Pro 多模态模型，发现默认开启思考模式后，即便简单图片也会产生大量 token；关闭后，原项目的转写时间从约 31 分钟降到约 2.5 分钟，并称质量未下降。讲自己的优化时应补完整实验口径：同一批 PDF、页数和图片比例、并发、模型版本、质量标注、延迟分位数与费用。视觉转写不能只比速度，还要检查表格、数字、页序和图片文字是否漏失。对于纯文本 PDF，可优先解析文本层；扫描件再走 OCR/VLM，按页异步处理和重试。

### Q9. 为什么给 AI 回复设 30 秒窗口

候选人的目标是合并客户连续短句，避免每句都触发一次回复。工程上要定义窗口从第一条还是最后一条消息计时，期间新消息如何更新任务，是否允许用户发送“取消”“人工客服”等高优先级指令立即生效。窗口结束后用同一会话的消息快照生成一次回复，并以版本号防止旧任务发送过时答案。30 秒是该项目的选择，不能当成所有客服场景通用值；要用响应时延与重复回复率做权衡。

### Q10. Java 线程池核心参数

`corePoolSize`、`maximumPoolSize`、工作队列、拒绝策略、`keepAliveTime`、`TimeUnit` 和 `ThreadFactory` 都要讲到。任务提交时先补核心线程，再入队；队列满且未达最大线程数时继续建线程；再满则触发拒绝策略。无界队列会使最大线程数的作用变小，还可能吃光内存。结合 Webhook worker 说明：队列容量和拒绝后的业务行为要与上游重试协议匹配，不能只报参数名。

## 提示词、安全与 RAG：Q11～Q14

### Q11. 怎样让 AI 讲产品卖点

作者用产品名和描述占位符，允许配置客服语气，并在提示词里写安全限制。教学上应把产品事实放在可维护资料库，生成时检索当前版本、价格和适用条件，让答案可追溯；提示词定义风格、禁止杜撰和无法回答时的转人工行为。对外身份披露应遵循平台规则与用户预期，不能用“不要暴露 AI 身份”作为普遍设计目标。防注入主要靠工具最小权限、资料与指令隔离及输出检查，而不是再多写几条 system prompt。

### Q12. 多轮脏数据影响判断怎么办

作者提出把修改权限留给用户，模型只读指定数据库/SQL。这抓住了安全边界，但还要治理上下文：用户消息、工具返回、旧模型摘要按可信度分层；检索资料标版本与来源；长对话压缩时保留已验证事实，丢弃无关或可疑内容。只读 SQL 也可能读取超范围数据，因此需要参数化查询、行/列权限和配额。发生明显注入时，模型可以拒绝相关动作并说明原因，宿主策略负责最终阻断。

### Q13. PDF、Word、PPT 和图片型文件怎样入库

候选人说用多模态模型描述图片，再将文字与图片转写文字双轨入库。完整流程先解析原生文本、结构、页码和表格，再对扫描页或关键图像做 OCR/VLM；保存原文件、片段与图片的定位关系，给每个 chunk 加文档版本、页码、权限和来源。向量检索与关键词检索可并用，答案引用回原位置。图表中的轴、单位与数值若视觉模型不确定，要留不确定标记或人工复核，不能把生成的描述当原图事实。

### Q14. 多语言语境怎样处理

作者坦诚当时没考虑，随后推测相似语义的向量会接近。这不足以覆盖文化差异、专有名词、混合语种和不同语言的检索偏差。教学方案是按语言/地区保留元数据，评测每种语言的召回和回答质量；对短词、品牌名、法规词结合关键词检索与翻译/同义词扩展；必要时选多语言 embedding 与 reranker，但要用本领域样本验证。生成时保持用户语言，引用原文并说明翻译可能带来的歧义。

## AI Coding 与 Skill：Q15～Q18

### Q15. 平时使用哪些编码工具

作者列了 Cursor、Trae、Qoder，以及连接 DeepSeek 的 Claude Code 使用方式。面试回答别堆产品名，讲一条你实际工作链：如何把需求给工具、如何审计划和 diff、跑过哪些测试、哪些操作不授权自动执行。不同工具的能力和版本会变，面试时说自己使用的配置和限制。涉及企业代码或密钥时遵守所在环境的数据要求。

### Q16. 怎样让 AI 写业务代码

作者描述了需求澄清 → 生成 plan → 审核 → 实现 → 编译/单测 → Browser Use 或 Playwright 验证界面的流程。他举了 `Grill-me` 一类 Skill 逐项追问不确定需求，实际曾进行十几到二十轮对话。这个顺序值得保留，关键是每一步的成功条件：澄清要覆盖权限、异常和非目标；计划应标文件与风险；实现要小步提交；测试要核对真实退出码；浏览器验收要覆盖主要路径，不只点开首页。某些需求不必做十几轮澄清，轮数由不确定性决定。AI 生成的测试也要人工审查，防止测试只验证 AI 自己写的错误假设。

### Q17. AI 重复造轮子怎样避免

原帖只写了在 system prompt 里约束。教学上还要让 Agent 能发现已有代码：先搜仓库相似函数、依赖与设计文档，利用 LSP 看引用，写前检查当前 API 和模块边界；在计划中说明复用哪个现有能力，若新增实现则解释为什么。最终 review 可以检查重复工具、重复组件和新增依赖。提示词只能提醒，检索与审查才是可验证的约束。

### Q18. Skill 的渐进式加载

作者理解为先提供 Skill 名称与简述，需要时才读取完整内容，以节省上下文。进一步要说清触发条件、适用范围、依赖工具和失败处理。Skill 文档本身不增加工具权限；其中的脚本依旧受沙箱和审批。评测不只看任务成功，还要看误触发、漏触发、额外 token、执行时间与规则过期。团队自建 Skill 应针对真实重复任务，而不是把一份很长的 prompt 换个文件名。

## 产品赋能、实时通信与缓存：Q19～Q22

### Q19. 口语练习产品如何用 AI

作者用客服辅助场景作类比：实时转写、每隔几秒给模型一段转写、向操作者展示建议。口语练习可对应为音频流 → ASR/说话人分段 → 发音、流利度或表达评估 → 针对性反馈。先确认用户是学员还是教师、是否要实时纠错、可接受延迟与隐私要求；再选择流式建议或练习结束后总结。评价质量应按语言水平、口音和噪声分层，不能用一个总分声称“AI 能教口语”。

### Q20. 系统提示词与用户提示词怎样设计

作者强调实时场景的 token 和响应速度，建议各场景独立提示词，并转述面试官建议从数据库动态加载。实现时系统提示词规定角色、工具边界和稳定安全规则；用户提示词承载当次目标；检索资料或外部消息只作为数据。提示词存库要有版本、审批、灰度、回滚与访问控制，避免任意运营编辑立即影响所有请求。缓存稳定前缀能省成本，但更新提示词后要同步失效。

### Q21. WebSocket 与 SSE 的区别

SSE 是服务端向客户端的事件流，基于 HTTP，适合 Agent token/进度单向推送；客户端控制消息可另用普通 HTTP 请求。WebSocket 建连时使用 HTTP Upgrade，之后是双向帧通信，适合需要频繁双向交互的会话。选择时考虑代理支持、重连、心跳、事件补发和权限；不要简单说 WebSocket“与 HTTP 无关”，也不要说 SSE 完全不能接收用户输入，只是该连接本身单向。

### Q22. Redis 缓存承担什么业务

原帖描述了双 Token 方案：短期 Access Token 携带租户 ID，较长期 Refresh Token 用于续期，租户菜单权限在 Redis 查询。教学回答要区分认证与授权：JWT 有效不代表当前权限没有变化；敏感操作要用当前权限版本或服务端权限检查。Redis 缓存需要 TTL、失效与权限变更通知，防止旧权限长时间生效；Refresh Token 要安全存储、轮换和撤销。缓存击穿、雪崩和多租户键隔离也要考虑。原帖的具体 30 分钟、7 天是该项目说法，不能当通用安全标准。

## 面试会怎么问

这场面试特别适合练“我做过什么”和“如果重做会怎样”。作者坦诚未处理过大规模 Webhook、多语言语境等问题；你也可以先讲当时规模和真实实现，再补设计方案及验证方法。反问时可围绕 AI 赋能开发链路、专属 Skill 和业务验收标准展开。原帖的面试官反馈属于候选人转述，不代表公司官方题库或统一录用标准。
