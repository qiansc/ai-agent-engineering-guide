# 2026 年 8–9 月 AI Agent 面试信号

这份观察面向准备 Agent 应用、Coding Agent、AI 平台和 Applied AI 岗位的同学。它整理的是截至 2026 年 9 月 21 日公开的一手候选人复盘，而非任何公司的官方题库。阅读时应关注同一项目如何被连续追问，而不是把出现次数当成精确的出题概率。

## 面试正在检验什么

本批样本多次出现“怎样把非确定性模型放进可控软件系统”的追问。只说“接了模型、做了 RAG、用了多 Agent”很难走完追问。你需要说明输入与输出、工具执行后的状态变化、失败后如何恢复、什么证据说明它比固定程序更合适，以及上线后如何发现质量下降。传统后端、数据库、网络和算法题仍与 Agent 题同时出现，有的三轮面试从 Agent 设计转向操作系统、并发与编码。

| 观察到的主题 | 常见追问方式 | 准备时应拿出的证据 |
| --- | --- | --- |
| Harness 与运行时 | 循环在哪里停止？工具超时后谁决定重试？ | 状态图、终止条件、trace、恢复记录 |
| Context 与 Memory | 压缩后丢了约束怎么办？跨会话如何续跑？ | 压缩前后测试、结构化状态、记忆写入规则 |
| RAG | 召回差还是生成错？文档更新后为何仍答旧版本？ | 分层评测、索引版本、权限过滤、错误样本 |
| AI Coding | 如何审查计划、验证改动和解释代码？ | 测试、diff、失败定位、个人决策 |
| 软件工程基础 | 高并发、幂等、线程池、SSE、数据库索引 | 可运行设计、容量假设、边界与权衡 |

## 从项目追问到工程边界

面试通常从简历上的项目开始。例如“做了一个会议助手”会先被问 ASR 错误如何评估，再问转写文本如何切分、敏感内容如何处理、召回错误和生成错误怎样区分，最后可能转向存储与接口。一个 Coding Agent 项目则可能从 ReAct 循环进入 Skill 误调用、上下文隔离、密钥保护和并发修改文件。表面上题目分散，实际是在核验你是否真的掌握系统中每一段的责任。

准备项目时给每个阶段写四行：输入是什么；谁决定下一步；可观察的输出是什么；失败时系统如何结束或恢复。若模型建议调用工具，参数应先经过 schema 与业务约束校验。若工具有写入副作用，幂等键、权限和人工确认必须由执行层实施。若后台任务可能运行数分钟，应能解释 checkpoint、取消、重试和最终状态。这个小练习能把“懂概念”转成可回答的工程事实。

## 三组真实追问的练法

第一组是“为什么用 Agent → 如果固定 Workflow 能做呢 → 哪一步真的需要动态决策 → 如何防止模型偏离目标”。较好的回答先界定任务：若路径稳定、分支有限且失败代价高，固定流程通常更合适；如果必须根据未知网页、工具结果或用户反馈不断选择下一步，可以在确定性外壳里放一个受限 Agent。再给出最大步骤数、预算、动作白名单和失败终止条件。

第二组是“RAG 命中率低 → 你看哪个指标 → 改 chunk 是否一定有效 → rerank 后为什么仍答错”。先固定一个带标注证据文档的样本集，分别计算检索候选的 Recall@K、相关文档排序的 MRR/NDCG，以及答案的依据性和正确性。召回不到时查解析、切分、索引、过滤和 query 改写；召回到了但排不前时查融合与 rerank；证据已进入上下文却答错时再查生成约束。不要用同一个“准确率”覆盖全部阶段。

第三组是“任务原来五分钟，现在二十分钟 → 如何定位 → 是否直接换更快模型”。先按 run、step、模型、工具、队列拆开耗时，比较 token 数、重复调用、工具 P95 与等待审批时间。若是工具结果膨胀造成反复压缩，换模型未必有效；若是下游限流，增加 Agent 并发可能更糟。面试官期待的是证据驱动的定位路径，而非立即猜根因。

## 不同岗位的准备重心

Agent 应用岗优先准备工具可靠性、RAG 诊断、项目指标和上线边界。Coding Agent 岗要深入文件操作、代码检索、沙箱、权限、长任务压缩和 AI 辅助编码验证。平台岗要进一步理解任务队列、多租户隔离、模型网关、可观测与成本。FDE/Applied AI 除技术外，还要能把模糊客户诉求收敛成可验收试点。模型与端侧岗位则需要更强的 Embedding、训练/推理、量化、设备资源和实验指标基础。

建议按“一个可复盘项目 + 一个系统设计场景 + 一组后端基础题 + 一道编码题”组织每次模拟面试。录音或写下追问链，重点检查自己在哪一步开始只报框架名、没有数据或说不清个人贡献。真正的准备单位是一条证据链：目标、方案选择、个人实现、基线、失败、修复和回归结果。

## 把信号转成四周训练

第一周选一个主项目，补齐系统图和个人贡献，列出三个真实失败样本；若项目未上线，可用故障注入代替线上事故，但要明确标记。第二周围绕 RAG、Context、工具三条链做分段评测，每次改动都保留同一批测试任务，避免“感觉更好了”。第三周补后端基础：用自己的语言实现任务状态机、流式进度接口与幂等工具调用，再做树、图和滑动窗口练习。第四周做两次完整模拟，一次偏项目深挖，一次偏系统设计与编码，并在每次结束后只修最明显的证据缺口。

若目标是实习岗，优先保证基础实现、算法与一个小而完整的项目；若目标是资深平台岗，应把容量、多租户、权限、发布与故障恢复讲到可执行。所谓“高频”只是这批样本中多次出现的主题，不代表每家公司的岗位要求相同。面试前仍应按招聘描述、候选人自己的简历和招聘方说明调整权重。

整理错题时给每个问题标记“不会概念、没有项目事实、没有量化数据、不会定位”四种原因。概念缺口回到课程，事实缺口回到代码和 trace，数据缺口补评测，定位缺口做故障注入。同一道题因不同原因答不好，需要的训练完全不同。

## 把一道题答成完整工程过程

以“你们的 Agent 为什么偶尔调用错误的工具”为模拟题。第一层回答应先界定“错”：是选错工具、选对工具但参数错、权限不足、工具返回不符合预期，还是结果正确却被模型误读。这些情况不能用同一个“优化 Prompt”解决。第二层说明观察方法：给每次调用记录候选工具、最终选择、参数校验结果、执行错误码、返回摘要与后续动作；用人工标注的一组任务分别计算选择与参数错误率。第三层提出实验：减少工具描述的歧义、按任务类型路由候选工具、给 schema 增加枚举和范围、执行前加入确定性校验，并保持同一评测集比较。第四层说明安全边界：若错调的是发送、删除或授权工具，仅改善选择准确率不够，宿主必须拦截越权动作并要求确认。

面试官若继续问“工具越多，怎么保持选择准确”，可以回答先按权限和任务阶段做候选集筛选，再延迟加载细节，必要时通过显式工作流限定可用工具。把全部工具描述塞进 Context 会增加成本，也可能让相近工具互相干扰。若仍需动态发现，发现结果要包含清晰名称、输入/输出、风险级别和版本。评价时不只看一次调用是否成功，还看额外调用数、恢复率与误触发副作用的次数。

这道题的低分答案是“我会把工具描述写清楚，让模型再想一遍”；中等答案能列出 schema、重试和监控；高分答案能区分错误层级，给出一条实际 trace、修复前后同样本比较，并指出哪些操作不允许依靠模型自行纠错。用同样的四层法也能回答上下文压缩、RAG 召回和长任务恢复。

## 信号强弱与复习顺序

一手面经证明某位候选人当时遇到了什么，不证明题目对所有岗位“高频”。因此可按三个维度排序：其一，是否在多个独立的一手复盘中出现；其二，是否与目标岗位的真实职责相符；其三，是否属于一旦答不好就无法解释自己项目的基础能力。工具边界、项目证据、RAG 分层诊断和后端基础通常符合后两项，即使单个名词只出现一次也值得掌握。某个新框架或产品名称即使在一篇面经中被深入追问，也不意味着所有人都应优先背它的 API。

对每个主题设置“停止学习”的检验点。Agent 与 Workflow 的取舍，应能给两个反例并画出自主决策边界；Context 压缩，应能说出保留字段、丢失风险和回归测试；RAG，应能拿标注样本区分召回与生成；生产化，应能解释一次超时、重复和取消的具体状态变化。通过这些检验后再进入较新的协议或框架细节，比无限收集面经更有效。

## 45 分钟模拟面试脚本

前五分钟只讲一个项目：业务目标、范围、自己实现、基线和结果。接下来的十五分钟让同伴沿项目选择一条链追问，例如从“用了 MCP”一路问到 host/client/server、鉴权、工具参数、超时与副作用；回答时每出现一个名词，同伴就问“它在你的系统哪一层，失败后怎样观察”。再用十分钟做系统设计，要求先澄清输入、权限和不可接受失败，之后才允许画架构。后十分钟做一题编码或后端机制，检查是否仍具备独立实现能力。最后五分钟记录没有证据支撑的回答，不急着查标准答案。

复盘表只需四列：问题、自己的原话、缺失证据、下一次验证动作。“我不了解某协议”可通过官方规范和最小实验解决；“我不知道自己项目的成功率”必须回到数据；“我解释不了一次失败”需要 trace 或可重复的故障注入。这样每次模拟都会缩小实际缺口，而不是只增加焦虑。

## 用一条 RAG 追问检验准备深度

模拟问题是“团队知识库明明有答案，Agent 却答错”。先确认所谓“有答案”是原始文档里有、索引里有、检索候选里有，还是已经进入模型 Context。若原文有但索引没有，查解析、切分与更新事件；若候选没有，查 query、权限和召回；若候选有但排序靠后，查融合和 rerank；若证据已进入 Context 却仍答错，查冲突信息、提示、输出引用与模型行为。每层都给一个能复现的样本和指标，不要把全链路错误只归因于“RAG 不准”。

面试官再问“为什么不直接加大 Top-K”，应指出候选更多可能增加噪声、时延与 token 成本，还可能把未经授权的内容送入后续阶段。先看标注证据是否被权限过滤、相关文档的排名分布和不同问题类型，再决定调 K、切分或 rerank。若问题来自旧文档未失效，加大 K 甚至会加重冲突。最后给出回归测试：同一批问题比较证据召回、答案正确、依据性、P95 和成本，避免只优化一个数字。

这条追问练习同时检验概念、数据链、权限、性能和实验设计。若候选人能给出自己项目中一条错误样本、对应索引版本和修复前后评测，答案自然会比背“混合检索 + rerank”更有说服力。即使没有实际线上 RAG 项目，也可用公开文档做小型实验，但要明确区分练习与工作经历。

面试信号还提示要训练“快速承认边界”的能力。被问到没用过的框架，可以说明你熟悉的同类机制、准备如何验证差异，不要冒充实际使用经验。被问到没有监控数据的性能问题，可以先给诊断计划，而不是编 P95 数字。面试官往往沿这些不确定处继续追问；清楚区分已知、假设和下一步实验，本身就是生产工程能力。

复习时也要留意自己的简历会改变题目分布：写了“多 Agent 架构”，就应准备并行收益、状态汇合和冲突；写了“线上稳定运行”，就应准备故障、监控和发布记录。真实追问首先针对你主动宣称的能力。
