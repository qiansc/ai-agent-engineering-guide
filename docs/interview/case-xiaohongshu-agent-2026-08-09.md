# 小红书 Agent 开发一面（8 月 9 日）：项目深挖、多 Agent 与广告优化

这份一面复盘由候选人发布于 8 月 13 日，面试发生在 8 月 9 日。原帖依次记录了项目、Agent 架构、多 Agent、记忆、ReAct、后端基础和广告投放场景，共 17 个技术及项目问题，最后是反问。候选人自述未通过；原帖没有给出每题的现场答案。以下按原题顺序给教学解法，项目数值、贡献和系统实现都应替换成你自己的经历。

## 从经历讲到 Agent 方案：第 1～5 题

### 1. 自我介绍和 Agent 工作经历

用一分半到两分钟讲一条主线：你参与的业务、用户痛点、你亲手负责的模块、上线或离线验证结果。面试官后面会按你说的名词深挖，所以每个框架、指标和数字都要能展开。没有线上流量，就诚实给样本集、基线、测试条件与未覆盖情形；不要把“参与项目”讲成“主导整套架构”。

### 2. 实习看哪些业务指标

指标要贴业务动作。客服 Agent 可看自动解决率、转人工率、错误回复率、平均处理时长和用户反馈；内容分析系统可看任务完成率、人工修改率、引用准确性和成本。讲出指标定义、采样口径、怎样发现 bad case、依据它做了什么改动。例如“转人工率上升”可能是模型变差，也可能是策略变严；需结合错误类型分层看，不能只追一个总数。

### 3. 项目背景、上下游和个人责任

从请求入口到最终产物画一条链：谁提出任务、上游给什么数据、Agent 的工具和状态是什么、下游如何使用结果。随后指出自己负责的具体节点及边界。若上游数据质量不稳定，说明清洗或重试；若下游需要人工审核，说明为什么。原帖没有披露候选人的项目细节，因此任何具体架构图只能作为你的自述模板，不能冒充这位候选人的实现。

### 4. Agent 用在哪里，为什么不做固定流程

先指出开放式不确定性在哪里：任务拆解是否依赖新观察、工具选择是否动态、失败时是否需要改计划。若步骤固定，Workflow 更容易测试和审计；若仅需知识问答，RAG 可能足够。可以把关键高风险业务放进固定流程，只在调查或资料整合环节允许 Agent 自主选择工具。最后讲真实比较方式：同一组任务比较完成率、人工接管、延迟和费用，而不是说“Agent 更先进”。

### 5. 框架与代码架构

讲自己实际用过的框架和为什么选它，随后画入口/会话、状态与上下文、模型循环、工具层、权限与验证、观测与持久化。框架会替你处理部分状态流转和调用接口，却不会自动解决业务权限、幂等和验收。准备一条真实 trace：模型提出什么动作，工具返回什么，系统如何判定完成。若项目只用了 API + 自写循环，就如实说，不必强行套热门框架名。

## OpenManus、Harness 与并发：第 6～9 题

### 6. OpenManus 用什么框架，怎样理解设计

先澄清题目里的“框架”：OpenManus 本身是 Python 开源 Agent 项目，不应答成“它就是 LangGraph 写的”。其官方源码可见 `BaseAgent`、`ReActAgent`、`ToolCallAgent` 和 `Manus` 等分层，`ReActAgent` 的一步按 think→act 组织，工具层提供执行动作。准确回答应基于你看过的具体版本与代码；如果没读过源码，承认只知道它的使用层面，再用通用 Agent Loop 说明自己的理解。不要把开源项目某版设计当作你项目的现成实现。

### 7. Harness 为什么帮助复杂任务

Harness 负责让模型在环境中持续执行：准备上下文和工具、校验模型动作、保存状态、限制预算、处理超时、运行测试并核实终止。模型提供候选下一步，Harness 保证真实工具结果回填，失败能诊断与恢复。举代码修复例子：如果模型宣称补丁已完成，而测试没有通过，Harness 不该让任务结束。它与单个 prompt 的区别在于拥有运行时与验收责任。

### 8. 多 Agent 并行的瓶颈

除了 token 与模型服务限流，还会有共享文件争抢、数据库连接池耗尽、工具串行依赖、重复检索、结果合并等待和上级协调者瓶颈。先画依赖图：真正独立的只读探索可并行，创建草稿后才能提交是串行。分工时划清 workspace、可写文件与凭证，结果带来源和版本。评估并行是否有收益看关键路径时长，不只看“启动了几个 Agent”。

### 9. 怎样控制并发量

可以按用户、租户、模型、工具和下游系统分别设上限，入口用队列或信号量控制运行数；关键写操作按资源键串行；遇到限流读 `Retry-After` 或退避，不能无界重试。调度策略可按任务优先级、截止时间或公平性分配。监控排队时长、活动任务、模型 429、工具 p95 延迟与拒绝率。若瓶颈在数据库，单纯多开模型线程会恶化问题。

## 记忆、推理和上下文：第 10～14 题

### 10. 长短期记忆的底层区别

短期状态包含当前消息、计划和工具结果，通常与 session ID 绑定；长期记忆保存经过筛选、对未来任务稳定有用的事实或偏好，需作用域、更新时间和删除权。结构化任务状态可放关系库，历史与产物可放对象存储，语义片段可建检索索引。存储选型服从写入和读取需求，不等于“短期放 Redis、长期放向量库”。把模型未经核验的推断写成用户长期记忆，后面会产生连锁错误。

### 11. ReAct 流程

给出目标和可用工具，模型基于当前状态提出 Action，执行器校验并执行，Observation 回填，模型继续或给 Final。Thought 可用于内部决策摘要，但真实动作由宿主执行。最终答案需独立核查，例如报告是否真的生成、引用是否支持结论。ReAct 适合下一步依赖最新观察的任务；步骤已知且风险高时，用固定 Workflow 更合适。

### 12. Planner、Executor、Critic 怎么分工

Planner 把目标拆成带依赖和验收的步骤；Executor 调工具、保存真实结果；Critic 根据明确规则或外部证据检查结果，失败时指出要修改的步骤。Critic 不能只说“再想一遍”，要检查如数值是否对齐、引用是否可信、测试是否通过。计划变更只针对未执行部分，已产生的写操作要对账，防止重复。

### 13. 为什么需要 Critic，ReAct 不够吗

ReAct 的下一步取决于观察，但模型可能在没有充分证据时提前结束。Critic 可作为验收节点：根据测试或业务规则否决“已完成”。任务很简单且已有确定性校验时，额外模型 Critic 可能只增加成本；没有可靠反馈时也可能给出自信但错误的评价。回答要说明 Critic 的输入、判断标准和失败后的动作，而不是说“多一个 Agent 更可靠”。

### 14. 上下文过长如何拆分、压缩

先按相关性装配：当前目标、项目约束、近期状态、关键代码/资料优先。大工具输出保留摘要和原始产物引用；历史消息按阶段压缩，记录已执行动作、失败尝试和待办。子 Agent 只拿它需要的文件和权限。压缩后恢复时重新检查外部状态，尤其是 Git diff、待审批动作和长任务状态。衡量压缩质量看是否丢掉用户约束、重复副作用或导致任务偏航。

## 后端基础和广告场景：第 15～17 题

### 15. Redis 数据结构与用途

常用有 String、Hash、List、Set、Sorted Set、Stream；还可讨论 Bitmap、HyperLogLog、Geo 等特定需求。String 可做计数与缓存；Hash 组织对象字段；Set 做去重；Sorted Set 做排名/延迟队列；Stream 用于带消费组的消息流。回答“底层机制”不要把所有结构都叫哈希表：具体编码会随版本、元素规模改变，例如紧凑编码和哈希表、跳表等。再落到 Agent 场景：会话热状态、限流计数、任务队列或去重键，分别考虑 TTL、持久化和一致性。

### 16. Java 类加载机制

按加载→链接（验证、准备、解析）→初始化讲。加载取得字节码并形成类元数据；验证检查规范；准备给静态字段默认值；解析转换符号引用；初始化执行类初始化逻辑。双亲委派是常见加载器关系，有助于核心类一致性；但容器或插件也有自己的加载边界。举一个静态字段赋值例子区分“准备时默认值”和“初始化时显式值”。

### 17. 设计广告投放自我优化 Agent

先问清目标是转化率、ROI、获客成本还是预算利用率，并设预算、品牌、安全与合规约束。数据链路要拿投放曝光、点击、转化和归因窗口，处理延迟与选择偏差；候选策略生成后，离线评估或小流量实验，不直接让模型改全量预算。执行层用受控工具创建草稿，人审或规则批准后发布；观察效果时与基线和对照组比较，再决定继续、回滚或重新探索。停止条件包括预算上限、样本不足、指标变差和工具异常。若没有实时转化数据，系统不能声称已经找到“最优投放方式”。

## 面试会怎么问

这场面试的追问从“做过什么”连续走到“为什么这样选、底层怎么跑、失败怎么办”。准备时可以沿一条真实项目轨迹练习：业务指标 → Agent 适用段落 → Harness 与工具 → 并发与状态 → 验收与恢复。广告题先确认目标和边界，再讲实验与人工控制；不能把自我迭代理解为无限制自动投放。
