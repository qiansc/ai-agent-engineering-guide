# 一场文档评估 Agent 面试：规则、协作与最小 RAG

这份 2026 年 8 月的面试记录由平台编辑发布，作者匿名，细节少于逐题的一手日志。作者还提到现场面试之前有一道 Google Sheets 电话面试题，但没有披露题面，不能据此编写题解。可确认的现场技术环节有三类：设计按规则给文件评级并提出修改建议的 Agent，深挖一个时间紧张的项目，以及用 Notebook 搭一个最小 Embedding/RAG 流程，最后讨论召回与命中率。它适合练“文档判断怎样做得可解释”，不适合猜测具体评分规则或录用标准。以下方案是教学假设，不是候选人现场答案。

## 先把文件评级问题改写为可验证的任务

题目要求根据一套规则把文件分成“合格、可接受、不合格”，并对后两类给出修改建议。第一步应向面试官澄清：文件是什么格式、规则来自谁、是否有优先级或例外、需要引用哪一段证据、单份文件多长，以及错误判为合格与错误判为不合格哪个代价更高。法律、合规或其他高风险场景中，模型不能替代最终授权人；至少要规定人工复核阈值和申诉路径。

把输出拆为两层。第一层是逐条规则的结构化结果：规则 ID、适用性、找到的文件位置、判断、置信或不确定原因。第二层才是总评级和建议。总评级尽量由明确的决策表计算，而不是让模型自由写一个结论。例如一条“必须项”不满足直接进入不合格；只有非关键项缺失时可能是可接受；所有适用规则都有证据支持才合格。真实规则需由业务方确定，这里只是展示架构。

| 环节 | 产物 | 需要防的错 |
| --- | --- | --- |
| 解析 | 带页码/段落位置的文本、表格和附件 | OCR 漏字、表格列错位、附件丢失 |
| 规则匹配 | 每条规则的适用性与证据 | 错把相似条款当成同一条、忽略例外 |
| 决策 | 可复算的总评级 | 规则冲突、阈值不一致 |
| 建议 | 缺口、建议修改、依据 | 建议超出规则、暗示不存在的义务 |
| 复核 | 人工确认或退回记录 | 模型对不确定情形强行定论 |

建议最好具体到“第 3 页第 2 段缺少某项信息，请补充；依据为规则 R-07”，而不是泛泛说“进一步完善文档”。若文件无法解析、关键附件未收到、规则版本不明，应返回待补充或待人工确认，而非硬塞进三种评级之一。这是系统设计里很关键的第四种状态。

## 多 Agent 冲突：先问为什么需要多个

面试中讨论了多个 Agent 同时参与时的冲突。容易犯的错误是先画一个“解析 Agent—判断 Agent—修改 Agent—审核 Agent”的复杂团队，再想办法解决它们的争论。可先给单 Agent 或确定性工作流基线：解析服务提取文本，检索服务找规则与证据，一个评估模型逐条判断，确定性程序汇总评级，人工复核异常。只有当任务量、专业分工或隔离要求使单路流程明显不足，才引入多个独立 Agent。

若确实需要并行评估，可以按互不重叠的规则集分工，每个 Agent 只提交结构化证据与判断，统一的汇总器处理冲突。不能让多个 Agent 同时直接改同一份文件。修改建议与实际修改应分开：一个角色提出建议，人或指定执行器在版本锁保护下应用，另一个只读评审结果。冲突判断依预先制定的规则优先级和证据位置解决；仍无法解释的冲突交给人。分工必须带来可测收益，如处理时间下降或错误率降低，否则复杂性不值得。

这类题常追问“如何证明系统没遗漏规则”。准备一个包含正常、边界和故意冲突样本的评测集；逐规则统计适用性判断、证据定位和最终评级。特别关注错误放行的代价，不要只看总准确率。新增规则版本时用同一批文件回放，比较旧新结果差异，并让业务方审核变化。

## 现场搭最小 RAG：小而完整比堆框架重要

现场编码环节要求在 Notebook 里搭基础的 Embedding/RAG。先讲清最小闭环：给定少量文档，解析为可定位片段，生成向量，保存向量和片段元数据；对问题生成查询向量，计算相似度得到 Top-K 候选；把候选片段连同来源交给模型生成答案；答案若缺证据要承认不确定。数据量小时不必先部署数据库，内存列表加余弦相似度就足以展示原理，并更容易调试。

为了避免“能跑”但不能评估，留出几道带标准证据位置的问题。`Hit@K` 问的是正确证据是否至少有一个进入前 K 个结果；`Recall@K` 在一个问题有多个相关片段时，问被召回了多少。两者都只看检索，不代表最终答案正确。回答还要评事实准确、引用是否支持和无法回答时是否拒答。面试官若问如何提高召回，先展示失败样本属于哪类：解析缺失、切分把条款拆断、查询改写失败、Embedding 不匹配、元数据过滤过严，还是 Top-K 太小。不同错误对应不同改法，不应默认“换更大的向量模型”。

如果现场时间很短，可以用可解释的简化实现：固定几段文档、一个 embedding 接口、一个相似度函数、一条生成调用、三条测试查询。说明生产版本还需文档更新、权限过滤、版本切换、限流、缓存与观测，但不要在 30 分钟练习里把这些都写成不可验证的空架子。最终向面试官展示一次正例、一次无答案例和一次检索失败诊断，价值往往高于堆更多框架代码。

## 项目深挖：时间紧张时做了什么取舍

另一轮问某个项目为什么排期紧。回答重点不是抱怨压力，而是解释约束如何影响决策：截止日期由什么事件决定，哪些需求必须交付，哪些风险可以延后，哪些不能降级，团队如何分工，自己负责什么。若时间不允许完成完整评测，就至少保留几条关键安全和正确性用例，同时对未覆盖范围明确标注。要能讲一次具体取舍的后果以及后续补救，而不是只说“大家加班完成了”。

一个自然的回答结构是：背景与时间约束 → 风险排序 → 最小可交付范围 → 当时的质量闸门 → 结果和遗留问题。若项目实际上没有成功，也可以讲清问题暴露在哪里、如何修正计划。真实经历不可用题目设定来补造；面试官深挖时，细节一致比故事漂亮更重要。

## 面试会怎么问

**问：一个 Agent 能做文档评级，为什么还要有确定性规则引擎？** 模型擅长从非结构化文件里找候选证据并解释条款，规则引擎负责稳定、可复算的评级组合。两者用结构化中间结果连接；证据不足或规则冲突交人处理。

**问：三个 Agent 给同一文件不同判断，谁说了算？** 先质疑是否必须多 Agent；若必须并行，让各自输出规则 ID、证据位置与版本，统一汇总器按优先级合并，未能解释的冲突升级人工，不以“多数投票”掩盖规则矛盾。

**问：RAG 的 Hit@K 提高，答案就一定更好吗？** 不一定。正确片段进了候选集，仍可能被截断、被错误重排、被模型忽略或引用错。检索指标和答案指标必须分开测。
