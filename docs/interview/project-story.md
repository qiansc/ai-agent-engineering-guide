# 项目深挖：把 Agent 经历讲成可检验的证据链

面试官通常不会只问“项目做了什么”，还会沿你说出的每个设计决定追问。因此准备项目介绍的目标不是背一段流畅的故事，而是让目标、个人实现、取舍、指标和失败案例彼此能对上。一个项目准备充分，往往比三个只会讲框架名称的项目更有价值。

## 先写项目证据包

用下表为主项目填一页纸。数字必须来自自己的记录；没有基线或实验样本时直接说明，不要用“提升明显”代替。

| 字段 | 需要写出的具体内容 |
| --- | --- |
| 业务目标 | 谁在什么流程中遇到什么问题；原来由谁完成 |
| 任务边界 | 输入、输出、哪些动作只能生成草稿、哪些可执行 |
| Agent 必要性 | 哪些步骤需要根据反馈动态选择；固定 Workflow 的替代方案 |
| 个人责任 | 自己设计、实现、上线或评测的明确部分 |
| 关键链路 | 数据、状态、模型、检索、工具、权限和人工接管 |
| 基线与结果 | 指标定义、样本量、测试环境、改动前后、置信范围 |
| Bad case | 症状、trace、假设、根因、修复和回归集 |
| 尚未解决 | 明确的约束、风险与下一步实验 |

项目开场可按 90 秒组织：业务问题与规模，为什么采用 Agent，系统主链路，你负责的关键决定，一项可验证结果和一项失败修复。后续被打断是正常的；应能从架构图、指标表和事故卡任意一张继续展开。不要把团队整体成果说成个人工作，也不要把试点指标讲成正式生产收益。

## 用“为什么”检查技术选择

如果说用了 RAG，面试官会问为何不直接把文档塞进长上下文、文件怎样解析和切分、ACL 在哪里过滤、文档更新后索引怎样失效。如果说用了多 Agent，会问单 Agent 为什么不够、状态如何汇合、同时写文件怎样防冲突。如果说用了 MCP，会问协议给项目解决了哪一层接入问题、工具侧鉴权在哪里做、调用失败怎样处理。每个名词都应对应一个原始问题、一项替代方案和一条可观察结果。

例如回答“为什么用了 Agent”，可以说：原流程的前半段是稳定的身份校验和资料检索，后半段需要根据不同来源的缺失信息决定追加查询或询问用户；因此确定性流程控制权限和审批，模型只在受限集合内选下一项只读工具。再说明，如果任务只剩固定三步，将退回普通 Workflow。这样的回答展示边界，而不是夸大 Agent 的用途。

## 指标要有分母和比较条件

“准确率 90%”没有解释力。应交代样本怎么来，人工如何标注，是否与训练或调参集隔离，以及是结果正确率、证据召回率还是工具成功率。线上指标还需说清流量、版本和时间窗口。P50 改善而 P95 恶化时不能简单宣布更快；人工接管率下降但误操作率上升也不是成功。

一张可靠指标卡可以这样写：在同一批脱敏任务上，比较旧规则流程和新版本；记录任务完成率、平均步骤、P95 时延、每任务成本及安全违规数；按简单、困难、数据缺失和权限受限分层。若样本只有几十条，应说明它适合发现回归，不足以证明稳定的线上收益。数字不足时，展示评测设计与待验证假设，同样能体现工程判断。

## 把 Bad case 讲到可复现

“模型偶尔幻觉”无法定位。可用六段结构：现象与影响 → 触发条件 → trace 证据 → 排除过的假设 → 修复措施 → 回归验证。假设一个知识库助手答旧版本文档，先检查请求对应的用户和索引版本，确认检索结果确实来自旧索引；再查更新事件、缓存键与权限标签；最后修复失效传播并加入“更新后立即查询”和“旧版本不得出现”的回归用例。这里的场景是练习示例，不应冒充自己的事故。

长任务案例同理。面试官问“五分钟变二十分钟”时，可以先按 step 时延分桶，比较模型 token、队列等待、工具重试和重复动作。若发现同一工具被反复调用，继续查返回错误是否清楚、状态是否记录完成、终止条件是否生效。没有 trace 就不能断言根因；此时应说明会补哪些观测字段，而不是编一个漂亮结论。

## 三组模拟追问

**追问一：去掉 Agent 可以吗？** 先承认哪些确定性阶段本来就应由程序完成，再指出动态决策的那一小段。若去掉 Agent 后业务质量变化不大，你应能解释为何考虑简化方案。

**追问二：你个人究竟做了什么？** 把团队设计与个人贡献分开，具体到接口、状态模型、评测集、工具校验或故障修复。面试官继续问代码细节时，应能讲出关键字段和失败语义。

**追问三：如果今天重做？** 先说已验证的部分，再选一个投入产出比最高的改动，比如先补任务级 trace 和回归集，再扩大自动执行范围。避免随手罗列最新框架。

最后进行一次反向审查：简历上每个数字、技术名词和“负责”都要能被追问两层；项目图上的每条箭头都应有实际数据或状态变化。讲不清的内容宁可删掉，也不要靠大词填空。

## 项目还在试点时怎么讲

没有线上大规模结果并不等于没有可验证成果。区分三类证据：功能证据是关键路径与测试通过；质量证据是固定样本上的任务成功率、错误类型与人工评分；采用证据才是实际用户持续使用和业务结果。试点阶段可以诚实说尚未获得采用证据，同时解释为何当前样本足以支持下一轮试验、还有哪些风险不允许扩大自动执行范围。

还要准备“指标变好但用户不满意”的讨论。可能是离线集太干净、少数高风险错误被平均分掩盖、响应慢导致用户返回旧流程，或人工确认步骤过多。此时不要只重算总体准确率，应按用户群、任务类型和失败成本分层，和业务方重新核对验收口径。能说出何时暂停上线、何时退回简单规则方案，比一味维护自己的 Agent 更可信。

## 例子：如何讲一个企业知识库项目

以下是练习用的虚构项目，数字需由候选人换成自己的真实记录。假设团队希望减少内部支持人员重复回答政策问题。旧流程由员工提交问题、支持人员搜索文档后手工回复。第一版系统限定为“给出带文档引用的建议答复”，不自动更改账号或发送邮件。候选人负责文档解析与版本、带权限的混合检索、评测集和工具执行 trace；身份系统和审批平台由其他同事负责。这样的职责划分比“我主导了整个平台”更清楚。

系统先按员工身份确定可见资料，再检索候选、重排、生成带证据的答复。若没有足够证据，返回需要人工处理的原因。项目选择受限 Agent 而非纯问答，是因为部分问题需根据缺失字段追问或选择不同资料源；但权限过滤、索引更新和最终答复格式仍由确定性组件控制。若面试官问“为什么不是把所有文档塞给模型”，可以从权限隔离、资料更新、成本和引用可追溯性回答。

指标卡应写成可核对的格式：多少条历史问题、如何脱敏、如何划分开发与保留集、人工如何标注正确证据、对照基线是什么。检索看证据 Recall@K，答复看正确性和依据性，业务看支持人员修改量与采用率。若没有线上采用数据，就明说目前只有离线质量和小范围试点，不把“预计节省时间”写成“已经节省”。

一个可讲的失败是政策更新后旧文档仍被召回。排查中先看文档版本与索引事件，再查缓存键和用户权限；确定具体层后修复失效传播，加入修改、删除和权限撤销的回归样本。项目故事到这里才完整：业务需求引出方案，方案带来风险，风险由证据定位，修复后有回归验证。

## 十分钟项目深挖演练

找同伴按下面顺序追问，每题最多一分钟，答不出就记录证据缺口，不现场编造。第一问“你做的哪部分最难”；第二问“为什么不采用固定 Workflow”；第三问“工具成功但状态更新失败怎么办”；第四问“资料删除后旧索引如何处理”；第五问“压缩后丢了用户约束如何发现”；第六问“上线评测是否覆盖越权”；第七问“你报告的质量指标样本量多大”；第八问“若成本翻倍，先删哪一项”。这些问题横跨系统层，准备充分的候选人应能把答案都落回同一个项目，而不是每题换一个不存在的架构。

评分时看四项：事实是否属于自己的项目；是否指出决定由哪个组件执行；有没有能验证的指标或 trace；是否承认尚未确认的部分。每项 0–2 分。若四项都只能拿 1 分，说明表述流畅但证据不足。改进顺序应是回代码与数据补证据，再练表达。不要为了高分给每个问题编精确数字。

## 面对负面结果

项目没上线、试点停止或指标没有提升，也可以讲，只要解释为什么停止。例如一类工单中规则已经覆盖大部分需求，Agent 的额外成本和审批负担抵消了收益，最终改为固定流程加一个模型辅助摘要节点。这样的结果不是“项目失败所以不能讲”，而是展示你能用证据调整技术选择。要区分技术性失败、数据或权限阻塞、业务采用不足，不能都归因于模型不够强。

面试官问“如果重新做”，可按已知瓶颈排序：先补可复现的评测与 trace，再修高风险错误，最后扩大功能。若只回答换更强模型或上新框架，会显得没有从已有证据学习。项目故事的结尾应落在下一项可验证实验，而不是“未来持续优化”。

## 指标被追问时的答法

面试官问“你说成功率提升了，成功怎么定义”，应先给任务级判定规则：例如用户拿到了被授权资料支持的正确建议，或外部动作达到目标状态，且没有越权。再给样本来源、标注者、争议处理和对照版本。若分母是“Agent 接手的任务”，还要说明被规则过滤、转人工和超时的任务是否计入；不同分母会让同一个系统看起来差很多。若多人标注不一致，可以报告一致性或争议比例，而不是只保留有利样本。

若被问“这个提升与哪项改动有关”，说明是单一改动的对照实验，还是多个改动一起上线。后者不能强行归因于某一项，可通过消融或分阶段发布继续验证。若 P95 时延变差、成本上升或人工审核量增加，应和质量提升一起报告，让面试官看到取舍。少量样本可用于发现明显回归，但不宜给出过度精确的小数点收益。

最后问“用户真的用了没有”。试点使用次数、留存、人工修改量和业务完成时间比单次 Demo 更接近采用；但早期可能还没有足够数据。此时清楚说明“目前已验证功能与离线质量，采用待小流量验证”，并给出下一阶段门槛。保留未知比将推测写成成果更能经受追问。

准备简历时，为每个项目保留“可公开讲的边界”。内部数据、客户身份和未公开架构可以匿名化或用相对变化描述，但不能为了保密而把因果也说没了。你仍可说明任务类型、设计权衡、测量方法和自己负责的组件；若具体数值不能披露，就不要换成未经授权的近似值。面试官追问时坦诚说明限制，并转向可公开的机制与实验，通常比含混夸大更稳。

最终检查项目叙述时，找一个不了解你项目的人复述主链路。若他只能记住框架名，却说不出用户问题、你负责的部分和一次修复，说明开场还需要收窄。

## 面试会怎么问

百度 Coding Agent 三轮复盘里，项目架构、为什么做 Agent、流程是否优于单次 LLM 调用被连续追问。准备时不要先背“项目亮点”，先把可核对的对照实验讲出来。

**问：你怎么证明 Agent 比一次模型调用更好？** 答：选一批相同任务，记录单次模型调用的完成率、人工修正次数、时延与成本，再让 Agent 在相同数据和验收口径下运行。给出哪些任务因工具观察而改善，哪些任务因多步调用变慢或更易出错。若没有对照实验，就如实说目前只验证了 Agent 的可行性，还不能声称整体更优；接着说明补实验的方法。

**问：项目里最难的一次故障是什么？** 答：从用户可见现象讲起，展示 trace、工具返回、状态版本和验收失败点；说明你排除了哪些假设，改了什么、如何回归验证，最后交代尚未解决的边界。面试官可能继续问“为什么不改 Prompt”，此时要用定位结果回答：若正确文档未进检索候选，改 Prompt 无法补回证据。

这些问题来自候选人复盘，回答方式是站内教学整理。
