# 小红书 Agent 开发一面（8 月 12 日）：同一项目怎样经受连续追问

这份个人复盘记录的面试发生在 2026 年 8 月 12 日，发布于 9 月 2 日。作者说当晚约了二面。原帖保留了部分题号：第 3～12 题只概括为“实习相关追问”，没有逐题文本；第 23、24 题缺号。下面按披露的顺序讲准备方法，对未披露题目不补造；所有答案示例都是教学推演，不代表候选人当场这样作答。

## 自我介绍和项目指标：第 1～13 题

### 1. 自我介绍

选一个与 Agent 开发最相关的项目做主线，用“业务目标—我的模块—可验证结果”讲清。自我介绍里说到的每个数字都要能解释分母、时间范围与数据来源；说到框架就准备讲状态流、工具和代码组织。若实习任务里并没有自主 Agent，不要把固定工作流包装成复杂多 Agent。

### 2. 实习关注什么指标

先区分业务指标与系统指标。业务上看自动解决率、转人工、用户满意度或任务耗时；系统上看任务成功、工具失败、调用成本、响应时延和安全拦截。说明你负责哪个指标、改动前基线、实验方法和风险。例如“自动解决率提高”可能是拒答减少，也可能是错误回答增多，因此必须同时看错误率和人工复核。

### 3～12. 连续的实习追问怎样准备

原帖只说这十题围绕数字指标、业务上下游和代码框架，没有给出逐题内容。准备时可自己画一张链路图：用户请求 → 上游输入与质量检查 → Agent/Workflow 决策 → 工具执行 → 产物验收 → 下游使用；在每个节点标出你写过的代码、状态存储、日志及失败方式。再准备一张指标卡：指标定义、取样范围、基线、改动、结果、反例与局限。面试官追问某个数字时，先讲口径，不要用笼统“效果很好”搪塞。这里提供的是备考方法，不声称原帖逐题问过这些细节。

### 13. Agent 在项目中的位置

说明它究竟负责动态选择工具、规划多步任务、生成回复，还是只做分类与提取。若高风险动作交给固定流程或人工审批，也要说出来。回答“为什么不用普通程序”时指出真正依赖新观察或自然语言理解的环节；若全是确定性业务分支，Workflow 通常更合适。把选择依据与前面的业务指标接起来，比单纯介绍组件更可信。

## 框架、Harness 与多 Agent：第 14～17 题

### 14. OpenManus 的实现

OpenManus 是 Python 开源 Agent 项目。官方源码可见 BaseAgent、ReActAgent、ToolCallAgent、Manus 等分层，ReActAgent 的一步由 think 和 act 组成。问“用什么框架”时，要区分项目本身、它依赖的 Python 组件，以及你自己项目是否基于它改造。若没有看过对应版本源码，就说自己熟悉的范围；不要武断地答“它是 LangGraph 写的”。可以用一次工具调用轨迹说明你理解的模型循环。

### 15. Harness 的职责

Harness 是模型外的执行环境：给模型装配必要上下文、提供工具 schema、校验与审批动作、保存会话和任务状态、控制预算、回填真实观察、做最终验收。模型生成“要查什么”，Harness 确定“能不能查、怎样查、结果如何记录”。例如工具超时后，Harness 应记录执行状态并决定是否安全重试，而不是让模型凭文本假设查询已成功。

### 16. 并行 Agent 的性能问题

同时开多个 Agent 会增加模型并发、token、工具连接与状态合并成本。瓶颈可能在模型服务 QPS、数据库连接池、共享文件写冲突，也可能是任务根本无法并行。先画依赖图，把无依赖的只读搜索并行，把写同一资源的步骤串行；每个子 Agent 返回结构化产物、来源和失败状态。最终汇总由一个责任方验收，不把两个相互矛盾的结果直接拼在一起。

### 17. 如何控制并发

按租户、用户、模型和外部工具分别设配额，用信号量或工作队列限制活动任务；关键写操作按资源键串行。遇到 429 按服务端提示退避，限时、限次；队列过长时拒绝或降级，而不是无界堆积。调度要考虑优先级与公平性，避免一个大客户占满所有运行槽。观察排队时长、p95 延迟、失败率和下游饱和度后再调整上限。

## 记忆、推理与上下文：第 18～22 题

### 18. 长短期记忆怎样落地

短期状态记录当前任务的对话、计划和工具观察，绑定 session；长期记忆保留跨任务仍有价值、经过确认的偏好或项目事实。两者都要有权限范围、新鲜度和删除机制。可用关系库存任务状态、对象存储放大产物、检索索引找相关片段；Redis 可做热缓存，但不能把“短期=Redis、长期=向量库”当普遍定义。防止把一次模型猜测写成永久事实。

### 19. ReAct 的完整闭环

模型基于当前状态提出下一步 Action，宿主校验并执行，真实 Observation 返回，再决定下一步或 Final。用户可以看到可解释的动作摘要，但不必暴露模型全部内部推理。循环要有步数、费用与时间预算；最终检查产物和证据，防止模型“说完成”但工具没有成功。工具返回若包含恶意指令，仍只是低可信数据。

### 20. Planner、Executor、Critic 怎样协作

Planner 生成可执行步骤和依赖；Executor 调用工具并记录状态；Critic 根据测试、引用、数值或业务规则评价产物。失败后 Replanner 只调整未完成步骤。若一步发出了消息、创建了任务，恢复时先核对外部副作用，不能因为计划改变就重发。准备一个真实例子，指出每个角色的输入与输出，而不是只列三个英文名。

### 21. 为什么要 Critic，不能只用 ReAct 吗

ReAct 可以依据观察继续行动，但未必有足够严格的最终验收。Critic 的价值在于检查具体错误，如引用不支持结论、测试没跑或指标没有达标；已有确定性测试时，不一定要再调用一个模型 Critic。没有可靠评估信号的“请再思考”也可能放大错误。是否需要 Critic，要用同一任务集比较质量、延迟和成本。

### 22. 长上下文如何拆分

先决定本轮真正需要的资料，分阶段装配；大工具输出保留摘要与原始产物引用；历史对话压缩成目标、约束、已执行动作、失败尝试和待办。恢复后检查文件、工具和权限状态。若系统有多 Agent，不要给每个子 Agent 整段历史，只给必要任务上下文。测试压缩时要看是否忘了用户约束、重复写操作或把假设压成事实。

## 后端知识与场景设计：原帖第 25～28 题

原帖在第 22 题之后直接写第 25 题，没有第 23、24 题内容。不要根据相邻主题推断它们是什么。

### 25～26. Redis 数据结构及底层机制

String 适合计数和缓存；Hash 管对象字段；List 是有序序列；Set 去重；Sorted Set 按分数排序；Stream 支持消息流与消费组。具体内部编码依 Redis 版本、元素数量和数据形态而变，不能把每一种结构都笼统说成“哈希表”。例如 Sorted Set 常与跳表等结构关联，回答时可解释排序与范围查询为何有效。再联系 Agent 场景：会话热状态、限流计数、去重键和任务队列分别要求不同 TTL、持久化与一致性语义。

### 27. Java 类加载

加载获得类字节码；链接包含验证、准备、解析；初始化执行类初始化逻辑。准备阶段给静态字段分配默认值，显式赋值通常在初始化发生。类加载器的双亲委派帮助保持核心类的一致性，自定义加载器仍可在受控场景工作。别把“找到 Class 文件”直接说成“对象已创建”。

### 28. 设计广告投放自动迭代 Agent

先问目标是转化、ROI、获客成本还是品牌曝光，再确认预算、出价上限与合规红线。数据层处理曝光、点击、转化、归因延迟和样本偏差；策略层提出候选方案；实验层小流量 A/B 或离线回放；执行层把预算修改作为需审批的写操作；监控层看效果和异常，指标恶化时回滚。大模型可分析报告并生成候选，不应凭一次观察就自行宣布“最优策略”。没有足够样本时，说明不确定性和继续采样条件。

## 面试会怎么问

这份记录显示项目追问可能占面试很大比例。最有效的练习是让同伴沿你项目链路追问十轮，要求每个数字有口径、每个 Agent 模块有责任、每个失败有恢复路径。关于第 3～12 和第 23～24 题，原帖没有完整题面，本文没有补造；其余按原帖顺序提供学习解法。
