# 一场从 Context 追到 Harness 的 Agent 面试

这场 2026 年 8 月 18 日的大模型研发一面约 80 分钟，问题从“你平时怎样用 AI 提效”开始，沿 Prompt、Context、Harness、压缩、团队 RAG 走到数据库、前端和树遍历。它不像一张背概念的题单，更像一次从个人实践到系统设计的连续检查。下面把每个问题转成可练的思路；候选人没有公开的实现细节和回答，不应自行补成其项目经历。

## AI 提效：先讲任务与验证，再谈工具

“平时怎样使用 AI 提效”不是让你列产品名。选一件你实际做过、有前后对比的工作：比如给现有服务补一个接口、定位一条线上错误，或读陌生代码库。说出任务原本的耗时点、你给模型的材料、允许它执行的动作、自己如何验证，以及它在哪一步帮不上忙。若没有严格计时，就不要声称效率提升百分之多少；可以说“减少了初次定位所需的人工搜索，但测试和最终责任仍由我承担”。

面试官常继续问：AI 生成的代码如何审？模型引用了不存在的函数怎么办？它让你执行危险命令怎么办？有说服力的回答要带执行证据：代码搜索结果、diff、单测命令与退出码、回归范围。AI 的总结不是证据，真正跑过的检查才是。若任务涉及密钥、生产数据或用户隐私，应先在输入和工具权限上划边界，而不是事后删聊天记录。

## Prompt、Context、Harness：三层解决不同问题

可以用同一个“查内部知识并给用户答复”的场景解释演进：

| 层次 | 你设计的对象 | 常见故障 | 应如何验证 |
| --- | --- | --- | --- |
| Prompt | 本轮目标、规则、输出要求与示例 | 指令含糊、格式漂移 | 固定样本上的回答质量和格式通过率 |
| Context | 本轮真正送入模型的历史、证据与状态 | 旧版本知识覆盖新证据、长日志稀释约束 | 证据召回、版本正确、引用支持 |
| Harness | 模型外的工具、权限、循环、状态、观测与恢复 | 工具超时后重复提交、越权读取、无限循环 | 轨迹回放、故障注入、预算与安全测试 |

三者不是互相取代。一个清楚的 Prompt 仍然重要，但模型看不到需要的文档时，改写提示词无法创造证据；检索到了正确文档却把它与旧摘要混放，上下文组装也可能让答案出错；模型知道该调用写入工具，但宿主没有幂等与权限校验，系统照样不可靠。面试回答最好拿一个 bad case，说明究竟要改哪一层，并给相应指标。不要把 Harness 简化成“给模型加更多工具”，它还包含不让模型任意行动的执行边界。

## 上下文将满时，先决定哪些东西不能丢

接近 Context Window 上限，不等于把前一半消息直接删除。先把内容分成四类：当前任务与用户约束；必须保持精确的状态，如 ID、路径、审批结果；可重新取得的外部资料和工具输出；已经完成的过程叙述。最后一类通常最适合摘要，第三类适合保留可重新定位的引用或句柄。对于长任务，可以保存结构化任务状态：目标、已完成步骤、当前阻塞、下一动作、未解决风险、证据位置。压缩后重新构造输入，并验证关键约束没有丢失。

例如 Agent 已经筛查 30 份合同，用户要求“只读，不对外发送”。压缩不能只留下“已处理 30 份”；还要留下只读和不外发的约束、每份合同的可追溯结果位置、仍未处理的列表。若把工具返回的原始文本整篇摘要，可能把有效期、主体名称、否定条件写错。因此高风险事实尽量保留原始来源定位，摘要只做导航。压缩质量可以设计回归：压缩前后问同一组关键问题，检查事实与动作选择是否一致；再比较 Token 节省、任务成功率和遗漏率。

关于面经中提到的“Claude Code 三层压缩”，不要凭一个未经核对的民间名称背出内部实现。公开文档能确认 `/compact` 会总结对话以释放上下文，也能确认持久项目指令、按需加载的 Skills 与隔离的 Subagents 占用上下文的方式不同；但这不等于公开证实存在一套固定、通用的“三层压缩算法”。面试时可以先问对方指的三层是什么，再用自己能验证的“工具结果裁剪、旧历史摘要、外部持久状态”作为通用设计方案，并明确这是自己的架构划分，不是产品内部源码事实。

## 从零搭团队 RAG：先定义知识的所有权

团队内部问答的第一步不是选择向量数据库，而是确认知识源：文档站、工单、代码、聊天记录是否都能被索引？谁有访问权？文档多久更新？哪些内容涉及个人信息或商业机密？将这些约束写成数据契约，再设计摄取流程。每条内容保存来源、所属团队、版本、生效时间、权限标签和可定位的引用；解析 PDF、表格与网页时要验证结构是否丢失。

切分要考虑文档语义：标题、章节、表格行列关系和代码块不应被随意截断。不同文档可试不同策略，离线标注一批真实问题与“支持答案的证据块”。检索阶段先做权限过滤，再组合关键词与语义检索；重排负责从候选中选真正回答问题的片段。生成阶段要求基于证据回答，不足则澄清或拒答。引用要指回用户能访问的原始位置，不能只显示一串模型自造的文件名。

评测至少拆成三段：摄取是否完整，检索是否把正确证据放进 Top-K，回答是否被证据支持。错误答案若由过期文档导致，应修版本与索引发布；若正确证据根本没召回，才去调切分、查询、混合检索或 embedding。上线后要监测更新延迟、权限负例、无答案率、用户反馈、成本和延迟。RAG 的核心难点是持续保持正确与授权，不是完成第一次 Demo。

## 如果让你设计 Agent 教程，就用可运行作品检验它

面试官还问如何划分 Agent 教程、怎样组织来源、什么才算好的教程。可以按能力依赖排序：先理解何时需要 Agent，再手写最小工具调用循环；接着加入检索和上下文管理；然后学习 Harness 的权限、状态、Trace 与恢复；最后再做多 Agent、浏览器操作与生产评测。每章都给一个可运行任务、失败样例和验收标准。这样学习者学到的不只是框架 API，还知道为什么需要下一层机制。

研究 Coding Agent 应特别盯住代码库探索、文件编辑、测试、权限、长上下文、任务恢复和人的审核点。选资料时，官方协议和运行时文档适合核对会变的接口；开源实现适合追执行细节；面经适合观察问题怎样被追问，但不能用来证明底层机制。一个好教程应主动比较普通脚本、单次 LLM、工作流和 Agent 的成本，而非把所有任务都塞入 Agent。

## 数据库、前端与树题：别把后半场当附录

索引问题可从一条真实查询说起。假设按 `tenant_id`、`symbol` 与时间范围查询 K 线，并按时间排序，表至少需要标的、周期、时间戳、开高低收、成交量和数据版本；主键或唯一约束要明确同一标的、周期、时间点能否有多条修订记录。访问模式决定复合索引，例如 `(tenant_id, symbol, interval, ts)` 可支持按租户与标的取时间段，但具体效果要用执行计划与数据分布验证。若写入量高，还要考虑时间分区、批量写入、冷热数据和修订数据的幂等。不要只回答“建 B+ 树索引”。

前端经验问题应据实说明。若主要做后端，也要能解释自己做过的页面如何获取任务状态、怎样展示流式输出、断线重连后如何恢复，以及错误状态怎样呈现。不要假装熟悉没做过的框架；能讲清接口与用户体验边界，比报出多个框架名更可信。

前序遍历是“根、左、右”，可递归，也可用栈迭代；迭代时先压右子节点，再压左子节点。层序遍历用队列逐层取节点；若需要每层单独输出，在进入一层前记下当前队列长度，处理这一层的固定数量后再开始下一层。两题时间均是 `O(n)`；空间要看树的高度或最大层宽。写代码前问空树返回什么、节点值类型、输出是否按层分组，避免把题意猜错。

## 面试会怎么问

**问：Prompt、Context、Harness 哪一个最重要？** 不做绝对排序。先给一个具体失败：若证据未进入输入，修 Context；若工具超时导致重复写入，修 Harness；若输出要求含糊，修 Prompt。最后说明三层各自的验证指标。

**问：上下文压缩怎样保证不会丢掉用户的限制？** 把当前目标、权限和未完成状态列为不可省略项；旧工具日志可摘要或外置，但保留可追溯位置。做压缩前后的关键事实问答和行为回归，不以节约 Token 作为唯一指标。

**问：一个新知识库上线后回答仍引用旧政策，从哪查？** 查来源版本与生效时间、摄取和索引发布、权限过滤、召回/重排、最后的生成引用；每一层用日志与评测样本验证，不先假设是模型幻觉。
