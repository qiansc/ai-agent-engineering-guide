# Agent 岗仍会考的后端、网络与算法

Agent 应用也是一个软件系统：模型调用慢且可能失败，工具会访问数据库或外部服务，长任务需要排队和持久化，流式结果会经过网络，敏感动作必须审计。因此传统工程题并没有消失。准备时把基础知识挂到具体 Agent 故障上，比背孤立的术语更有效。

## 并发与运行时：任务为什么会排队

一个请求可能触发多次模型和工具调用。若每个请求都无限并行，外部模型限流、数据库连接池和工具线程池会先耗尽。面试题“高峰时任务从五分钟变成二十分钟”应先看队列等待、活跃 worker、下游 P95、重试次数和每任务 token，不要直接归因于模型变慢。并发上限、超时、取消传播、背压和隔离池应与任务优先级配套设计。

Java 方向应能解释线程池队列、锁与可见性、GC 暂停、JVM 堆外资源；Go 方向应能解释 goroutine、channel、context 取消、竞态和内存分配。无论语言，模型生成的计划不能代替程序的并发控制。多个 Agent 同时写同一文件时，可以采用单写者、版本检查或按文件分区；“让模型协商”不能保证原子性。

## 数据库：状态和记忆不是一回事

任务状态应记录 run ID、版本、阶段、完成步骤和结果引用，支持恢复与审计。长期记忆则是经过选择后保留、可被未来任务检索的事实，两者生命周期不同。任务表常见查询是按租户、状态和创建时间分页；索引设计需看实际过滤条件与排序，不能只给每一列建索引。大量 checkpoint 写入还会影响事务日志、存储与清理策略。

需要复习事务隔离、MVCC、索引选择、覆盖索引、分页、WAL/binlog 的用途，以及“先写业务数据还是先发消息”的一致性问题。比如工具调用成功但状态更新失败：恢复时必须通过稳定幂等键或外部查询判断是否已执行，避免重复提交。若消息先发而数据库事务回滚，消费者可能看到不存在的任务；Outbox 或其他可验证的一致性方案应在设计中说明。

## 缓存、消息与重复执行

知识库更新后仍答旧内容，可能发生在文档解析、索引发布、权限过滤，也可能是缓存键没有纳入索引版本。不能一句“删缓存”结束；应说明更新事件、索引版本切换、旧缓存失效和读写窗口内的策略。Redis 可用于短期状态、限流或缓存，但不应把它当永久审计存储。

长任务通常用队列解耦入口和执行者。消息投递与消费可能重复，因此消费端按任务 ID 与操作 ID 幂等。对外发邮件、下单、改权限等副作用工具，需要稳定的幂等键、执行记录和超时后查询；重试次数、退避、死信与补偿都应有上限。面试官问“消息保证 exactly once 吗”时，应把消息投递语义与业务效果语义分开。

## 网络：流式响应和 Webhook

SSE 适合服务端向客户端单向持续推送文本或任务进度，基于 HTTP，客户端重连与事件 ID 需要设计；WebSocket 适合双向低延迟交互，但连接状态和扩缩容更复杂。选择依据是交互模式，不是“哪个更新”。断线续传要区分实时 token 流和持久任务事件：token 可丢一些时与审批/完成事件不可丢的要求不同。服务端不能把连接断开等同于任务取消。

Webhook 入口应校验签名、时间戳和重放窗口，再按事件 ID 去重并快速确认接收；耗时处理交给后台。还需处理乱序、重投和部分失败。外部工具调用应设置连接与总超时，限制重定向和响应大小，避免 SSRF 与资源耗尽。

## 数据结构与算法：将题目映射到系统

| 算法主题 | 典型 Agent 场景 | 练习要点 |
| --- | --- | --- |
| DFS/BFS、树 | 依赖树、目录或任务展开 | 访问标记、深度与复杂度 |
| 拓扑排序 | 带依赖的工具计划 | 检测环、可并行节点 |
| 堆与 Top-K | 检索候选、优先任务 | 复杂度与稳定排序 |
| 滑动窗口 | 最近消息保留、速率限制 | 边界条件与增量维护 |
| 哈希表与去重 | 幂等键、重复动作检测 | 冲突、过期和空间成本 |

校招与实习岗位常会在 Agent 题后直接给编码题。练习时先说输入范围与复杂度，再写可运行代码和测试边界。不要把“实际工作会用 AI 写”作为不掌握基础实现的理由。

## 五道串联演练

设计一个可取消、可重连的流式任务 API：区分任务 ID、事件 ID、当前状态和最终结果。设计百万任务表的状态查询：先给查询模式，再给索引与归档策略。解释 MQ 重投时如何避免重复发送邮件：校验、幂等记录、外部结果查询、补偿。定位线程池耗尽：看活跃线程、队列、下游耗时与重试风暴。最后用拓扑排序执行带依赖的工具计划，说明写冲突节点为何不能简单并行。

复习深度随岗位变化。应用岗要能从真实故障讲到机制；平台岗还需容量规划、租户隔离和分布式状态；模型服务岗位增加推理调度与资源管理。但所有方向都应能解释一次请求从网络入口到持久结果的路径。

## 结合一条请求回答基础题

设用户提交一个需要检索资料、调用外部系统并流式返回进度的任务。入口服务先鉴权和创建任务记录，队列负责削峰，worker 读取任务并调用检索与模型，工具执行层做权限与幂等检查，状态服务保存阶段结果，SSE 只负责把已产生的事件送给浏览器。若浏览器断开，后台任务仍可继续；若 worker 崩溃，新 worker 从 checkpoint 恢复；若外部工具超时，先查幂等操作结果。沿这条链，面试官可以问线程池、事务、MQ、网络重连、索引和取消语义。把每个基础概念放到实际位置，回答会比逐项背定义更稳。

复习时对每个组件再问一个“最坏情况”：队列满时是否拒绝新任务，数据库慢查询是否阻塞所有租户，客户端重连是否重放已执行动作，取消请求到达时外部工具是否仍在运行。能给出明确状态和处理结果，才算真正把基础机制用在 Agent 系统里。

## 演练：长任务状态与消息一致性

设计一个“提交研究任务，后台执行，完成后通知用户”的服务。入口收到请求后创建任务 ID 和 queued 状态，再把任务放入队列。这里会出现一个经典一致性问题：数据库记录已创建，但发消息失败；或消息已发，数据库事务回滚。可以用事务性 Outbox 将待发送事件与任务记录一起提交，由独立发送者投递，再按任务 ID 去重。消费者收到重复消息时，先通过版本与状态判断是否已领取或完成，不能仅依赖队列承诺不重复。

worker 领取任务后改为 running，记录租约或心跳；若 worker 崩溃，租约超时后其他 worker 可接手。恢复前检查 checkpoint 和已执行副作用。若任务已经向外部系统创建工单，但本地未收到成功响应，按稳定操作 ID 查询对方；查不到且调用可幂等时再重试。任务完成后写 succeeded 和结果引用，再发送完成事件。通知失败不应把已经成功的研究任务重新执行一遍；通知可单独重试。

面试官进一步问“用户点取消怎么办”：入口标记 cancel_requested，worker 在可中断点检查并停止后续调用，最终进入 cancelled；已发生的外部动作可能需要业务补偿。取消不是简单杀掉进程，因为要保留状态与审计。若 worker 正在阻塞的工具调用中，需有超时或取消机制；若外部服务不支持取消，就报告已执行部分与后续处理办法。

## 演练：数据库查询为什么慢

假设任务列表按租户、状态和创建时间查询，数据量增长后第一页也变慢。先拿实际查询与执行计划，看过滤选择性、排序是否用到索引、是否出现大量回表或深分页；再考虑以 `(tenant_id, status, created_at, id)` 一类组合索引支持常见查询，并按稳定排序键做游标分页。索引顺序需根据真实谓词与数据分布验证，不能把示例直接照搬。长期保留的 trace 和 checkpoint 可能比任务主表大得多，应分存储和保留策略。

若面试官追问事务与并发，说明同一任务的状态迁移用版本号进行条件更新，例如只允许 `running` 且版本匹配的 worker 写入完成结果。这样可避免过期 worker 在租约失效后覆盖新 worker 的结果。任务状态与副作用记录是否需要同一事务，取决于它们是否在同一数据库；跨服务则需要幂等、事件和补偿，而不是寄希望于一个本地事务。

## 演练：SSE 断线续传

服务端给每个重要任务事件分配递增事件 ID，浏览器重连时带上最后收到的 ID。服务端根据持久事件日志补发缺失的状态变化，然后继续推送实时进度。生成中的每个 token 若不持久化，断线后可能无法逐字补齐；系统可以选择补发当前完整文本快照，但必须明确事件语义。完成、失败、待审批等状态不应只存在于连接内，否则页面刷新后用户无法知道任务实际结果。

SSE 与 WebSocket 选型要看单向/双向需求、代理兼容性和连接规模。无论选哪种，连接层与任务执行层都应解耦：网络断开不自动取消任务，也不自动重试副作用工具。这个场景能串联 HTTP、状态存储、事件顺序和幂等，比单独背协议定义更能体现理解。

## 一道算法题怎样联系工程语义

题目：给定多个任务和依赖关系，输出可执行顺序；如果存在环，报告无法执行。先用入度表和邻接表做拓扑排序：将入度为零的任务入队，取出一个后把其后继入度减一，新变为零的任务继续入队；最终输出数少于任务总数时说明有环。时间复杂度与任务数加依赖数线性相关。若要求最大并行度，可每轮取出当前所有入度为零的节点作为一批，但仍要检查共享资源写冲突，图上无依赖不等于业务上可同时执行。

将算法放进 Agent 计划执行时，还需考虑模型生成的依赖是否可信。运行时验证任务 ID、工具权限和依赖环，并给每步设置输入输出契约。某节点失败后，只阻止依赖它的后继，独立分支可按策略继续；恢复时不能把已完成的写工具再执行一次。这样回答既展示算法基本功，也说明算法结果进入真实系统后仍有状态和副作用问题。

## 基础题的复习判据

每个知识点至少回答“机制、在 Agent 场景的位置、一个失败例子、一个验证方法”。例如 MVCC：讲读写版本与隔离，再说明任务状态查询为何可能看到旧值、如何通过事务和版本号防覆盖，最后用并发测试验证。SSE：讲单向事件流，再说明浏览器断线与后台任务解耦、如何用事件 ID 续传，并测试重连后的状态一致。Kafka/MQ：讲重复投递可能性，再用同一事件两次消费验证业务幂等。

若某题只能背定义，回到自己的项目找它具体出现在哪；若项目没有用到，不要谎称有生产经验，可以用练习服务做最小实验。传统基础不是 Agent 岗的“附加题”，它决定模型建议能否被安全可靠地执行。

## 语言题不要与业务题脱节

Java 被问线程池时，不只报核心线程数等参数，还要说当模型调用阻塞、工具慢且队列堆积时如何设拒绝策略、超时与隔离，如何避免重试把压力放大。Go 被问 goroutine 时，不只说“轻量”，还要说明每个任务的 context 如何向下游传播取消、channel 是否可能无人接收、共享 map 是否有竞态。两种语言的语法不同，系统目标相同：资源有上限，任务有明确终态，副作用可追踪。

用一个故障注入来验证：让工具服务慢十倍，看并发数、队列等待、内存和任务取消是否仍受控。若只在无故障时压测，很多线程、连接和重试问题不会暴露。

## 面试会怎么问

百度 Coding Agent 三面从 Agent 项目转向操作系统、并发和算法；字节 Agent 开发一面也问数据库索引、线程池与 DFS。传统工程题仍需要独立讲清，不能用“我做的是 AI”跳过。

**问：为什么 Agent 服务里的线程池可能越加越慢？** 答：先区分 CPU 密集的解析/重排与等待外部模型、检索、工具的 I/O。若 worker 长时间阻塞在网络调用，盲目增加线程会提高上下文切换、内存和下游并发压力。应测队列等待、活跃线程、下游限流、超时与任务分布，再分别设置并发上限和隔离池。必要时把长任务转为异步状态机；但异步不消除外部容量约束。

**问：两个有序列表求交集，数据变成无限流怎么办？** 答：有限有序列表可双指针线性扫描；无限流无法等全部数据排序或一次性放入内存，需要先明确时间窗口、去重语义与允许延迟。按分区或窗口维护状态，配合水位线和过期规则。Bitmap 只在值域可控时划算；值域巨大时稀疏结构或分桶更合适。回答前先把输入边界问清楚，比立刻给一个看似通用的算法重要。
