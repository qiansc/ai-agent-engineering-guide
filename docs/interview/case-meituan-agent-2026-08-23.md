# 美团 Agent 开发一面（8 月 23 日）：RAG、协作状态与异步工程

这份个人复盘记录了一场 2026 年 8 月 23 日的一面，作者在 8 月 25 日发布并表示未通过。原帖按顺序列出 16 道问题与反问，集中在 RAG、多 Agent、上下文、异步编程和 Vibe Coding。下面依题号讲回答思路；原帖没有逐题现场答案，示例均是教学推演。

## 项目与 RAG：第 1～4 题

### 1. 自我介绍

用最相关的 Agent 项目开场，讲清业务用户、自己负责的部分和可验证结果。把“会用 RAG、框架、模型”换成“我解决了什么问题、为什么选这条路线、效果怎样测”。面试官可能随即进入项目深挖，所以任何数字要能说清分母和评测集，任何工具要能解释失败行为。

### 2. 一个 Agent 项目的整体架构

从请求到产物画出入口、路由/规划、上下文与检索、模型循环、工具执行、权限、状态存储与验收。每层说明实际负责的事，例如“状态库存每一步任务状态，工具服务执行只读查询，最终答复必须带引用”。若项目其实是固定工作流，就如实说在某一节点使用模型，不必为了名称硬把它称作自主 Agent。最后挑一条真实 trace 展示你亲手处理的异常或优化。

### 3. RAG 端到端链路

先区分离线建库与在线查询。离线处理文档解析、清洗、切分、元数据与版本、向量/倒排索引；在线做查询理解、权限过滤、召回、去重、rerank、上下文组装、生成和引用校验。答案错要分层归因：正确文档没入库、召回不到、排序错、生成时误读，修法不同。评测可看 Recall@K、MRR、引用准确率、拒答率和最终任务正确率；不要只用“回答看着不错”。

### 4. 文本切分怎样选

固定长度切分实现简单，但容易把标题和关键条件分开；按章节/段落切分保留语义，却可能长短极不均；句子切分适合细粒度召回，返回给模型时可能缺上下文。可用“子块检索、父块返回”或重叠窗口兼顾命中与解释。合同、FAQ、代码仓库的结构不同，应保留文档标题、版本、章节、权限等元数据。用同一批带答案位置的问题比较不同 chunk 大小、重叠和召回数，观察命中、上下文长度、延迟及错误率，别凭一个通用 token 数下结论。

## 多 Agent、上下文与路由：第 5～10 题

### 5. 多 Agent 如何分任务、合结果

先看任务能否拆成独立子问题。Router 适合按意图分派；Supervisor 适合拆解并整合；固定 Pipeline 适合步骤稳定的工作。给每个子任务定义输入、可用工具、期望产物与成功条件，结果要带来源和版本。合并时检查矛盾与缺口，例如两个 Agent 对同一指标给出不同日期的数字，不能简单拼接成报告。共享文件写入要指定单一责任人。

### 6. 并行任务状态如何管理

每个子任务至少有 `task_id`、父任务 ID、依赖、状态、重试次数、产物位置与错误。常见状态包括 queued、running、waiting、succeeded、failed、cancelled。父任务按依赖和完成策略聚合：是否必须全成功？某个可选资料失败能否降级？等待超时怎么办？并行工具若一个失败，其他成功结果要保留，不能整批重跑导致副作用重复。状态持久化后才能断线恢复和追踪成本。

### 7. Agent 上下文如何管理

每轮只给当前目标、明确约束、已验证事实、关键工具结果和待办步骤。历史对话按阶段摘要，检索片段按相关性与新鲜度选择；大文件和日志留原始引用。区分用户输入、可信策略、外部文档和工具输出，防止把外部内容当高优先级命令。恢复会话时核对外部副作用与资源版本。

### 8. Agent 比传统应用多了什么

Agent 能在目标给定、路径未完全固定时，依据观察选择下一步工具、更新计划并尝试完成任务。传统应用也能调用 API、做规则分支，所以区别不在“会不会调用工具”，而在决策自由度与反馈循环。自由度带来灵活性，也增加不确定性、成本和权限风险。一个好回答会同时说适合与不适合的任务：开放式排障可用 Agent，明确支付审批必须保持确定性流程。

### 9. 请求怎样路由给正确 Agent

先做身份、租户、权限与任务类型检查，再按规则、分类器或模型选择能力。路由结果要有置信度或可解释依据；低置信度时澄清或交给通用 Agent，不能随机派发。Agent Registry 可记录能力、输入输出、成本和健康状态。多通道时还要按用户、群和工作区隔离 session，避免“路由正确但上下文串线”。

### 10. Context Compression 为什么必要

长流程累计工具结果和历史，窗口会满、费用升高、注意力分散。压缩应保留目标、约束、已执行动作、产物 ID、失败尝试、未完成步骤与证据来源；丢弃重复日志和低价值对话。原始数据保留在外部可再取，摘要不能把假设写成事实。用暂停—恢复测试检查压缩后会否重复发请求或忘记关键权限。仅增大模型窗口不解决噪声和状态真实性。

## 语言、并发和工程化：第 11～14 题

### 11. Java 与 Python 怎么选

Python 的模型生态、实验和数据处理库丰富，适合快速验证与部分推理编排；Java 在已有企业服务、类型约束、线程池、服务治理和团队经验上可能更顺。性能不能只凭语言名判断：外部模型延迟、数据库与工具调用往往占主要时长。可以将高吞吐业务入口留在既有 Java 服务，Python 服务承担模型编排，也可以用 Java SDK 完成全链路；关键是部署、团队熟练度、监控与接口边界。先说你更熟悉哪种及做过什么。

### 12. 并发与异步的区别

并发表示多个任务的执行时间段重叠；异步表示发起操作后不必阻塞等待，结果稍后通过 Future、回调、事件或消息获取。异步 I/O 可以在少量线程上同时等待多个模型或网络请求，但 CPU 密集计算仍需合适的执行资源。并行是同一时刻真正使用多核执行，概念又不同。面试时用“同时处理多个工具请求”说明并发，用“请求发出后继续做别的事”说明异步，再讲状态和取消如何管理。

### 13. 异步任务可怎样实现

单进程内可用 async/await、线程池或 Future；跨进程长任务可用消息队列、任务表与 worker。选型看任务时长、可靠性、需否重试和用户是否离线。创建任务时记录 ID 与状态，worker 取任务要有租约或可见性超时，写操作带幂等键；失败重试区分可恢复和永久错误；完成后通过轮询、SSE 或 WebSocket 通知客户端。不能只说“放进 MQ”，还要解释消息重复、顺序、死信和结果存储。

### 14. Agent 工程化问题

把任务调度、工具调用、状态管理分别落到可测试机制：调度要有队列、配额与优先级；工具有 schema、权限、超时、错误类型和 trace；状态有 session、步骤、检查点和副作用对账。再加成本预算、上下文装配、评测样本、安全隔离和灰度发布。一次工具超时的演练能串起这些模块：谁发现、谁决定重试、状态如何更新、用户看到什么、是否已经产生外部动作。

## AI 编码与系统设计：第 15～16 题

### 15. 怎样看 Vibe Coding

Vibe Coding 通常指更依赖自然语言与 AI 快速生成、迭代代码的方式。它适合原型、脚手架和探索方案，能降低起步成本；但需求遗漏、幻觉 API、隐蔽安全问题与缺少测试都可能随速度一起放大。实战中先给任务边界与验收条件，让 AI 查已有实现、生成小 diff，再跑测试和审查。高风险生产代码要有明确规格、代码所有者和回归验证，不能把“感觉能跑”当交付标准。

### 16. 从零规划一个 Agent 应用

先问用户、任务、成功条件和风险，再决定是固定 Workflow、单 Agent 还是多 Agent。定义输入输出与数据权限，列出工具合同和副作用，设计状态与上下文生命周期，给出预算、超时和人审节点。用小型真实任务集测完成率、路径错误、成本和恢复；上线从只读或草稿建议逐步扩大权限。现场设计时可以用“一个完整请求 + 一个失败请求”走一遍架构，面试官能看到每层为什么存在。

## 面试会怎么问

这场的题目在 RAG 与系统工程之间反复切换。复习时选一条自己的 RAG bad case，沿解析、切分、召回、rerank、生成逐层定位；再选一条长任务，说明并行状态、压缩和失败恢复。反问环节可问真实任务类型、质量指标和团队当前最难的瓶颈。原帖没有给出作者具体反问内容，不应把这些建议写成现场事实。
